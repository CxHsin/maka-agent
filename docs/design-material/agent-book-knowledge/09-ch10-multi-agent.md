# Chapter 10 · Multi-Agent Collaboration — Knowledge Point Extraction

> Source: `book/chapter10.md`. The fundamental motivation: "**the intelligence of a group can be higher than that of an individual**". Main thread: two orthogonal design dimensions (whether context is shared × collaboration topology) → when multi-agent is worth it → the three topologies under shared / non-shared architectures → failure modes → the frontier of Agent societies.

## 1. The Classification Framework of Multi-Agent Collaboration

### [KP-10-01] Overview of the classification framework: the 2×3 combination matrix
- **Core in one sentence**: The architecture of a multi-agent system is determined by two orthogonal dimensions — "whether context is shared" and "collaboration topology (how control/information flows)".
- **Key design points**: dimension one (whether the later Agent inherits the complete conversation history and trajectory of the earlier one); dimension two (**Peer → Orchestration → Decentralized**, in increasing order of complexity); the two dimensions are **conceptually independent but practically correlated** — when context is shared, the topology often degenerates (handoff needs no decision about "what to pass", the complete history is naturally preserved, and the topology degenerates into a sequence of role switches); in the 2×3 matrix, most of the "shared context" row degenerates, and this chapter only expands the three cells of non-shared context in detail; terminology note ("Graph Engineering" became popular in 2026-07, and the collaboration topology discussed in this chapter is its multi-agent subset).
- **Maka design implications**: the single-agent harness sharing the same Runtime Event Log naturally belongs to the "shared context" form; a future agent swarm should explicitly answer which cell of the matrix each type of collaboration task falls into, rather than "make everything multi-agent"; the agent swarm tool calls already present in the Maka codebase can be classified by this framework (handoff-style decentralized, or manager-style at scale).
- **Writable design doc**: 《Maka 多 Agent 协作架构选型：2×3 分类矩阵与决策清单》(Maka Multi-Agent Collaboration Architecture Selection: 2×3 Classification Matrix and Decision Checklist)

### [KP-10-02] Dimension one: shared context vs non-shared context ("threads vs processes")
- **Core in one sentence**: Shared context = zero information loss but rapidly expanding context; non-shared context = good isolation and scalability but requires explicit communication — equivalent to the OS tradeoff of "threads vs processes".
- **Key design points**: shared context (swapping system prompts and tool sets while retaining all of the predecessor's memory — "a requirements analyst → the developer can still see the full communication record"); non-shared context (each Agent has an independent context — "different departments collaborate through shared documents", good modular isolation, easy to scale); the threads/processes analogy (shared address space: low switch overhead, no isolation, one thread corrupting memory crashes the whole process, vs independent address space: safe parallel communication but requires explicit IPC); Table 10-1's five-dimension selection criteria (① small number of subtasks (2-3) / many (need parallelism) ② the context window can hold it / cannot ③ parallelism: mostly serial / can be massively parallel ④ information isolation: not needed / needed (a security reviewer should not see raw thinking) ⑤ cost budget: single-trajectory handoff token accumulation / each of multiple Agents expanding on its own, total tokens usually several times to an order of magnitude higher); **simple judgment: if the expected accumulated context exceeds 50% of the window (rule of thumb) → should be non-shared; if zero information loss is a hard constraint on correctness → should be shared; most systems adopt "phase-switching" — the first few Agents share, and at the point of information saturation they switch to non-shared + explicit handoff**; implicit coordination (inheriting context) vs explicit coordination (files / messages / structured interfaces).
- **Maka design implications**: "Log is the Runtime" is exactly the carrier of shared context (trajectory inheritance with zero loss), and "Context is not history" (pruning + Compaction) is exactly the solution to shared-context "expansion" — the two are already a closed loop on a single Agent; when extending to multi-agent, the 50% rule of thumb can serve as the trigger strategy for "when to switch from shared to non-shared + explicit handoff package".
- **Writable design doc**: 《Maka 上下文共享策略：50% 经验法则与阶段切换式移交》(Maka Context-Sharing Strategy: the 50% Rule of Thumb and Phase-Switching Handoff)

### [KP-10-03] Dimension one extension: the three inter-Agent communication mechanisms and the IPC paradigm mapping
- **Core in one sentence**: Non-shared context requires explicit communication; the three major mechanisms (tool-call parameters / shared file system / message bus) map exactly onto the two IPC paradigms (message passing / shared memory).
- **Key design points**: the three mechanisms (① **tool-call parameters** — the upstream passes structured data as parameters to the downstream tool, suitable when types are well-defined and the structure is clear ② **shared file system** — reading/writing intermediate artifacts under a shared directory, suitable for large or persistent artifacts ③ **message bus** — a relay station forwards messages, Agents do not call each other directly); the IPC mapping (shared file system = "shared memory"; tool parameters and message bus = two forms of "message passing"); **the Go motto: "Do not communicate by sharing memory; instead, share memory by communicating"** (shared memory is fast but leaves the concurrency-conflict pitfalls to the user; message passing requires more orchestration code but gives clear data ownership); the message bus naturally supports **asynchronous communication** (the sender and receiver need not be online simultaneously).
- **Maka design implications**: future swarm communication should explicitly choose: structured Tool Results go through "tool parameters" (already in the Log); large artifacts go through the local shared workspace (local-first fits naturally); cross-TaskRun asynchronous coordination goes through a message bus (bus messages are recorded into each Task Event Log, maintaining "Log is the Runtime").
- **Writable design doc**: 《Maka Agent Swarm 通信机制设计（IPC 映射：共享工作区 / 工具参数 / 消息总线）》(Maka Agent Swarm Communication Mechanism Design (IPC Mapping: Shared Workspace / Tool Parameters / Message Bus))

### [KP-10-04] Dimension two: the three collaboration topology modes
- **Core in one sentence**: When context is not shared, control and information flow take three modes — peer, manager, decentralized — in increasing order of complexity.
- **Key design points**: **peer collaboration** (2-3 equal Agents forming an iterative improvement loop — co-writing a paper, one drafts and one annotates; low implementation complexity, suitable for quick validation and prototyping); **manager mode** (a centralized Manager Agent is responsible for task planning and scheduling, and multiple sub-Agents each take a subtask — a project manager leading specialist engineers); **decentralized mode** (no runtime central controller; Agents communicate and collaborate with each other like humans); topology and context sharing are two dimensions that are "conceptually independent but practically correlated" (when context is shared, the topology degenerates into a sequence of role switches; `transfer_to_agent` (experiment 10-2) is essentially the form of chained handoff under shared context).
- **Maka design implications**: agent swarm should model the three topologies as pluggable "Coordinator" strategies running on the same set of Task Event Logs — the same TaskRun mounted with different topologies yields different collaboration forms, avoiding rewriting the runtime for each topology.
- **Writable design doc**: 《Maka Agent Swarm 协作拓扑（对等 / 管理者 / 去中心化）》(Maka Agent Swarm Collaboration Topologies (Peer / Manager / Decentralized))

## 2. When Is Multi-Agent Truly Better Than Single-Agent

### [KP-10-05] Core criterion: does collaboration introduce "new information not available at generation time"
- **Core in one sentence**: The only core criterion for judging whether multi-agent has substantive value is — **whether the collaboration process introduces new information that a single Agent could not obtain at generation time**.
- **Key design points**: Table 10-2 information-gain comparison (the same model self-reviewing by re-reading its own output = no → usually ineffective or even harmful; different Agents debating the same text = no → at equal compute it is on par with single-agent; a Reviewer using **test execution results** to review code = yes → significant improvement; a Reviewer looking at **rendered screenshots** for frontend/PPT = yes (visual feedback) → significant improvement; a Reviewer using **external tools to verify facts** = yes (tool feedback) → significant improvement); RLEF (using reinforcement learning to exploit code-execution feedback for iterative improvement, far exceeding independent sampling); WebGen-Agent (multi-layer visual feedback raises Claude 3.5 Sonnet from 26.4%→51.9%); this framework explains the contradiction (the academic "single-agent is enough" vs the engineering "multi-agent is more effective" — the former compares "multiple Agents reading the same text and discussing with each other" (debate), the latter includes "loops with external feedback" (code execution / visual rendering / tool calls)); **step budget and performance** (merely increasing the number of steps does not guarantee performance gains — standard Agents lack "budget awareness", and with a 300-step budget they still tend toward shallow search and quickly "saturate"; an explicit budget-aware mechanism is needed, e.g., BAVT switches from "cast a wide net" to "dig deep" as the budget shrinks); **cost** (the Anthropic multi-agent system uses about **15× the tokens** of an ordinary conversation, and token usage itself can explain about **80% of the performance difference** — the benefit must cover several times to an order-of-magnitude overhead, otherwise a well-tuned single Agent is more cost-effective); guidance for manager mode (the Manager **dynamically allocates step budgets** according to task complexity, guiding sub-Agents through "plan first → then implement → then test → then improve").
- **Maka design implications**: Creed 4 is exactly isomorphic to this criterion — if a Self-check introduces no new evidence (execution results / screenshots / tool output), it is merely "having the model think again" and does not constitute factual basis; before starting swarm collaboration, first ask "what new information does this collaboration introduce", and write "15× multi-agent overhead / 80%" into the cost-budget model.
- **Writable design doc**: 《Maka 多 Agent 收益判据、预算感知与成本模型》(Maka Multi-Agent Benefit Criterion, Budget Awareness, and Cost Model)

## 3. Multi-Agent Collaboration with Shared Context

### [KP-10-06] Multi-stage role switching: staged system prompts and quality gating
- **Core in one sentence**: Within the same execution session, dynamically switch system prompts and tool sets by stage, letting the Agent work in the most appropriate "identity" at each stage, while the conversation history and task state remain continuously shared.
- **Key design points**: the essence is workflow-style orchestration (a predefined execution path — "one process sequentially executes code for different stages with the same memory", but viewed as multi-agent it has design benefits: each "identity"'s prompt and tool set can be polished independently, and **stage boundaries naturally become quality-gate points**); defects of static system prompts (either too generic, or crammed together and verbose); experiment 10-1's three stages (requirements clarification → code implementation → quality review, each stage with an independent prompt + a bounded tool set); **stage transitions are triggered by specific tool calls** (e.g., `complete_requirements_analysis()`); **rollback** must be handled (when review finds problems, return to the implementation stage via `request_revision(issues)`).
- **Maka design implications**: "Log is the Runtime" makes stage transitions a pure projection operation — swap the static prefix (system prompt + tool set) while the trajectory stays unchanged, and the stage-completion signal (a tool call) is a fact in the log; stage boundaries = checkpoints/gates on the Task Event Log, directly carrying forward "Task may outlive a Turn".
- **Writable design doc**: 《Maka 阶段化 Agent 角色（Staged Roles）与质量门控》(Maka Staged Agent Roles (Staged Roles) and Quality Gating)

### [KP-10-07] Cross-domain role switching: dynamic switching via transfer_to_agent
- **Core in one sentence**: The Agent autonomously judges which specialist role to switch to (not a predefined linear flow), handing control under shared context via `transfer_to_agent(target_role, reason)`.
- **Key design points**: the five-role architecture (**triage front-desk default entry** — decomposes the request into ordered subtasks and hands off one by one, holding no specialist tools, only the transfer tool; research → web_search; coding → execute_python; data_analysis; writing); when `transfer_to_agent` is called, the system in sequence (saves the current conversation history → loads the target role's prompt and tool set → passes the history to the new role → continues as the new role); chain example (triage→research→data_analysis→writing→triage wraps up, each role seeing the complete history); routing decisions depend on the prompt (triage lists routing rules; specialist roles guide completing the task and then hand off to whoever, or back to triage); **engineering point: avoid circular switching** (the Agent bouncing back and forth between roles).
- **Maka design implications**: the harness borrows the transfer primitive as-is as the shared-context handoff mechanism; consistent with "Log is the Runtime" — handoff is "swap prefix, keep trajectory", and the transfer tool call itself enters the log as an auditable fact; "avoid circular switching" maps to handoff counts / loop protection.
- **Writable design doc**: 《Maka 跨领域角色切换（transfer / agent 移交原语）》(Maka Cross-Domain Role Switching (transfer / Agent Handoff Primitive))

## 4. Multi-Agent Collaboration without Shared Context

### [KP-10-08] The Agent ↔ operating system correspondence + the Actor model
- **Core in one sentence**: Map a non-shared-context multi-agent system line by line onto an operating system — an Agent is to the runtime what a process is to the kernel, and most mature experience from OS/distributed systems can be borrowed directly.
- **Key design points**: Table 10-3 correspondence (program = static prefix; process memory = trajectory; CPU = LLM; kernel = Agent runtime; system calls = tool calls; fork = spawn_subagent; kill = cancel_subagent; ps = list_agents; exit codes and wait() = the sub-Agent's returned structured summary; shared memory / message passing = shared file system / messages); **core conclusion: with a faster CPU the program still runs; with a stronger model the Agent is still the same Agent — identity and memory live in the prefix and trajectory, not in the model weights**; the term "context switch" was itself borrowed from the OS; this is the LLM version of the 1970s **Actor model** (private state / async messages / can create new members); **the one place the analogy fails (key to the whole chapter): between processes, bytes are passed with bit-level fidelity; between Agents, semantics are passed, and every retelling can be distorted** (failure mode two, "cascade amplification", later); non-shared engineering benefits (independent development/testing / adding capabilities without touching existing code / faults don't spread / true concurrency) and costs (information synchronization / loss and duplication / difficult debugging requiring reading multiple Agent logs to piece together the complete process).
- **Maka design implications**: static prefix (Agent config) + Event Log (trajectory) are exactly the engineering of this table; swarm design directly reuses fork/kill/ps/wait semantics to define sub-Agent lifecycle primitives; "semantic distortion" reminds Maka that the Log must record evidence rather than retelling, structuring "who said / based on what".
- **Writable design doc**: 《Maka Agent 运行时与操作系统对照（subagent 生命周期原语：spawn/cancel/list/summary）》(Maka Agent Runtime ↔ Operating System Correspondence (Sub-Agent Lifecycle Primitives: spawn/cancel/list/summary))

### [KP-10-09] The file system as seen by an Agent: the four zones of a virtual file system
- **Core in one sentence**: What an Agent accesses is not a single store but a **virtual directory tree** mounting four zones that differ in origin, lifecycle, and permissions, accessed through uniform read_file/write_file/list_dir — the directory tree is the Agent's address space.
- **Key design points**: the four zones — **①Agent-exclusive workspace Scratchpad** (an instance-private directory, lifecycle tied to the instance, invisible to other Agents and users; isolation prevents overwriting and keeps the main Agent's context lean) **②multi-Agent shared space Shared Workspace** (jointly read/written and visible to users; lifecycle tied to the task and needs persistence; the hotspot for concurrency conflicts — optimistic locks / worktrees act here) **③externally mounted resources** (mapped through adapters to mount points such as /mnt/gdrive; three characteristics must be handled explicitly: subject to external permission constraints / high latency with weak consistency (treat as eventual consistency) / mostly on-demand read-only — a careless write pollutes the user's real data) **④system built-in resources** (read-only shared across all Agents — Skills mounted at /skills with progressive disclosure, reference manuals / template library; globally shared read-only, stable across sessions, no concurrency control needed); Table 10-4 (visibility / lifecycle / read-write / concurrency control) as a layout checklist; the OS protection philosophy "**isolate by default; sharing must be declared explicitly**"; "**file paths as a universal interface**" (passing artifacts between Agents / the main Agent handing inputs to sub-Agents / cross-organization A2A exchanging Artifacts all pass lightweight path strings rather than loading content into the context window).
- **Maka design implications**: local-first naturally supports the four-zone file model; Scratchpad isolation corresponds to "sub-Agent returns a structured summary rather than the full trajectory"; the shared workspace needs optimistic locks / worktrees (see failure mode one); if Tool Results reference file paths rather than content, both "Context is not history" and context leanness are satisfied.
- **Writable design doc**: 《Maka 多 Agent 虚拟文件系统（四区域挂载、可见性与并发控制）》(Maka Multi-Agent Virtual File System (Four-Zone Mounting, Visibility, and Concurrency Control))

### [KP-10-10] Control plane · state query and recovery: async message Q&A vs trajectory persistence / progress files
- **Core in one sentence**: The most natural way for the main Agent to obtain sub-Agent state is not RPC polling but the two communication paradigms — async message Q&A, or out-of-band observation through the shared file system (trajectory persistence / an agreed progress file).
- **Key design points**: pull-style get_subagent_status is far less useful than expected (a sub-Agent executes immediately to completion/failure once created, unlike batch jobs flowing between queued states; polling has two problems — too dense wastes tokens, too sparse is untimely); **use message passing to get state** (the main Agent sends "how's it going", the sub-Agent replies at an opportune moment; the sub-Agent proactively sends status_update at key nodes; messages use a unified state-machine vocabulary (running / needs input / completed / failed) — the A2A protocol standardizes the task lifecycle to this); **use the shared file system to get state (most thorough = trajectory persistence)** (the sub-Agent's full trajectory is serialized in real time as JSON appended to a JSONL log file; the main Agent reads the file directly to see the whole execution process; drawback: a trajectory of tens of thousands of tokens still needs distillation after reading); the more reasonable **agreed progress file** (e.g., progress.md: when started, the main Agent agrees "write progress to progress.md", and the sub-Agent updates it after completing each item — equivalent to carving a state zone out of shared memory that exposes distilled progress rather than all "memory"; with built-in **stuck detection** — no change in last-modified time for over N minutes is judged as no activity, triggering a timeout fallback); **recovery/checkpoint** (Agent context = static prefix + trajectory; if tool and session state can be rebuilt from the trajectory or saved as independent checkpoints, and working artifacts are written atomically to the file system, then the trajectory can be reloaded + the static prefix reattached to resume execution from the last confirmed state; read-only tools may hold volatile state needing a separate recovery contract); **external-side-effect recovery (key engineering detail)** (tools with external side effects such as payments / bookings / sending messages can crash after the operation succeeds but before the result is written to the log — before the call, persist a client-generated **operation ID, idempotency key, and canonicalized request**; idempotent calls use exactly the same request and key for the same logical operation; on recovery, first query the real state to determine success/failure/unknown; only if the original request is unchanged + the external party explicitly guarantees deduplication + the key is still valid can the same key be retried; otherwise hand off to manual reconciliation); persistence meeting these conditions resembles a database **write-ahead log (WAL)** (events are first written to an append-only log + periodic checkpoints, enabling restart from the last confirmed state, event-by-event replay to locate the failure, or handing the auditable state to another Agent).
- **Maka design implications**: the four Creeds are verified in "textbook" fashion — trajectory JSONL = Runtime Event Log, progress file / structured summary = lightweight projection of the log, WAL + checkpoint + idempotency key = the continuation recovery contract; Maka's existing Event Log should ensure every event carries an idempotency key / operation ID to support multi-Agent recovery.
- **Writable design doc**: 《Maka 多 Agent 状态查询与故障恢复（轨迹持久化 + 检查点 + 幂等/对账）》(Maka Multi-Agent State Query and Fault Recovery (Trajectory Persistence + Checkpoints + Idempotency/Reconciliation))

### [KP-10-11] Control plane · execution termination and resource scheduling: graceful/forced termination, cascade termination and races, Go context, budget and preemption
- **Core in one sentence**: In parallel collaboration "one succeeds, the rest become invalid" is common, requiring termination mechanisms with graded strength (graceful/forced), race-free cascade termination, cancellation semantics propagated along creation relationships, and scheduling of three types of scarce resources — tokens / funds / concurrency quota.
- **Key design points**: two termination strengths (corresponding to SIGTERM/SIGKILL) — **graceful termination is preferred** (send terminate; the sub-Agent responds at the current step's safe point, first cleans up resources, then acks and exits); **forced termination as fallback** (only when graceful gets no response; its cost is leftover dangling resources and unfinished writes); engineering points (graceful termination requires the sub-Agent to **periodically check the termination signal** in its loop; cascade termination has a **race** — multiple sub-Agents may report success nearly simultaneously, and the main Agent must use a lock or idempotent design to ensure **each is settled only once and only one round of termination is broadcast**); **what happens to sub-Agents after the main Agent terminates: borrow from Go context** — termination cascades downward along creation relationships; cancelling one Agent cancels its descendants, preventing orphan Agents; if a long-running background Agent truly needs to detach from the main Agent (like nohup), start it from a new lifecycle tree and explicitly declare it does not die with the parent; **resources and scheduling** (the scarce resources in the Agent world = tokens / funds / concurrency quota — usually shouldered by the Manager/runtime: set a step or token budget at startup and stop when exceeded; hard tasks use strong models, mechanical tasks use low-cost models; cap concurrency to avoid exhausting the API quota all at once; **preempt** running sub-Agents when a more urgent task arrives; practice in this area is far less mature than CPU scheduling, but it determines the cost ceiling and should be considered at architecture-design time).
- **Maka design implications**: directly maps to "Task may outlive a Turn" — the TaskRun budget (steps/tokens) is exactly resource scheduling; swarm cascade cancellation reuses the "cancellation propagates along creation relationships" semantics to prevent orphan sub-Agents; the "settle only once" lock/idempotent design fits naturally with the event log (a termination broadcast is also a log event, naturally deduplicated).
- **Writable design doc**: 《Maka 多 Agent 执行终止与资源调度（级联取消、预算、抢占）》(Maka Multi-Agent Execution Termination and Resource Scheduling (Cascade Cancellation, Budget, Preemption))

### [KP-10-12] Peer collaboration mode: the three forms of premature termination, Loop engineering / LoopX, proposer-reviewer
- **Core in one sentence**: The core value of peer collaboration (2-3 equal Agents iteratively reviewing each other) is introducing cognitive diversity, and its most classic use is solving "premature termination" — and the root cure for "premature termination" is having an independent verifier (not the model's self-claim) decide completion.
- **Key design points**: peer collaboration is suitable when (roles / communication mechanisms / iteration termination conditions are defined and it can run; first choice for quick validation and prototyping; core value = cognitive diversity); **three forms of premature termination** (①**lazy fake completion** — claiming everything is done after doing only part (reporting completion without running tests/deployment) ②**premature abandonment** — declaring something impossible when one path fails (giving up after a phone call is refused when switching to a form/email would work) ③**false success** — thinking it's done when the closed loop was never completed (verbal agreement to refund over the phone but the user still needs to confirm in the app) — the unified root of all three: **"before verification, 'done' is only a claim made by the model, not proof"**); **Loop engineering** (design the "discover the next thing to do → execute → verify → record progress" loop, with the verifier rather than the model deciding "whether to stop"; the human shifts from "an operator who writes prompts" to "an engineer who designs loops"; **the bottleneck of the loop is the verifier, not the model** — if verification is unreliable, a faster loop just marks low-quality output as done sooner); **the LoopX framework** (abstract the loop out of prompts/chat history onto a persistent control plane independent of the runtime — goals and boundaries / gates and todos / evidence and quota / handoff; the protocol `LoopX decides → Agent executes → independent verifier proves → LoopX commits`; only results that pass an independent verifier are written to persistent progress and consume quota; the core invariant: **"the model may propose 'done', but cannot approve its own 'done'"**); **proposer-reviewer** (why can't you generate and review yourself? — if review introduces no new information it's just "having the model think again": GPT-4 self-correction without external feedback actually reduces accuracy; **the Reviewer's value = it can access external feedback unavailable to the Proposer at generation time (rendered screenshots / test results / compiler errors / search output)**); extended modes (Debate — questionable efficacy / Brainstorm / Panel Discussion).
- **Maka design implications**: Creed 4 "I've checked it" does not automatically become a system fact, synonymous with "the model cannot approve its own completion" — a Self-check producing evidence + one bounded fix opportunity is exactly the lightweight implementation of "verifier decides"; after swarming, make "evidence (execution results / screenshots)" a hard input to the review loop, and if the Reviewer has no new evidence, judge its opinion as down-weighted.
- **Writable design doc**: 《Maka 提议者-审核者循环与验证器（Loop）设计》(Maka Proposer-Reviewer Loop and Verifier (Loop) Design)

### [KP-10-13] Peer collaboration extension: the controversy over the effectiveness of debate mode (the data-processing inequality)
- **Core in one sentence**: Patterns such as debate, where "multiple Agents process the same text", are not better than a single Agent at equal compute — information theory proves it is at best an information bottleneck rather than information creation, and multi-agent gains often come from consuming more total compute.
- **Key design points**: Tran & Kiela 2026 (comparing single-agent vs five multi-agent architectures on multi-hop reasoning): **when the thinking-token budget is strictly equal, single-agent matches or even beats multi-agent**; the explanation rests on the **data-processing inequality** (in debate, multiple Agents process exactly the same text information; serially passing intermediate conclusions can only lose information, never create it — debate gains likely stem from consuming more total compute); **the boundaries of the argument (must be clearly drawn)**: the conclusion targets the information bottleneck of "multiple Agents serially passing intermediate conclusions", and does **not** negate ① sampling the same problem multiple times independently and aggregating (self-consistency / majority voting) ② exploiting the "asymmetry between generation and verification difficulty" (writing an answer is hard, checking an answer is easy) for a generation-verification division of labor — these introduce additional independent sampling or exploit the task's asymmetric structure, outside the scope of the data-processing inequality.
- **Maka design implications**: when designing a swarm, make the "multi-agent routing criterion (KP-10-05)" a hard gate — if the collaboration merely has multiple Agents re-reading the same evidence, switch to "multiple independent samples + aggregation" or "generation-verification division of labor"; Maka's multiple sampling can reuse one TaskRun's budget instead of spawning N full Agents.
- **Writable design doc**: 《Maka 多 Agent 信息增量审计（辩论 vs 独立采样 vs 生成-验证分工）》(Maka Multi-Agent Information-Gain Audit (Debate vs Independent Sampling vs Generation-Verification Division of Labor))

### [KP-10-14] Manager mode: Agents as tools to each other, structured summaries, the weak-planner bottleneck, sequential/parallel coordination and the message bus
- **Core in one sentence**: Introduce a Manager when a task has ≥5 subtasks, needs dynamic scheduling, or has complex dependencies; the Manager models sub-Agents as callable tools — "calling an Agent is not fundamentally different from calling an ordinary tool" — and **the ceiling of system capability is determined by the planner**.
- **Key design points**: Manager responsibilities (understand the overall task → decompose assignable subtasks → select the right Agent → track progress and handle exceptions → integrate the final result); **Agents as tools to each other** (in addition to external tools, the Manager's tool set contains call interfaces to other Agents — the unified abstraction brings extensibility (new capability = develop an Agent and register it as a tool, the Manager's core logic unchanged) and heterogeneity (different models / prompts / tool sets / hardware)); **the sub-Agent → Manager returns a "structured summary rather than the full trajectory"** (task conclusion / key findings / artifact file paths / problems encountered; the full trajectory stays in its own log — the Manager's context grows slowly and linearly with the number of subtasks rather than exploding); inherent challenges (the Manager is a single-point bottleneck: it must understand the nature of all subtasks, select the right Agent, and pass context accurately; the Manager's global context expands as the task deepens); **the weak planner is the most critical bottleneck of the system (Plan-and-Act)** — when the Planner's planning quality is high enough, even a simple Executor produces good results; if the Planner decomposes wrongly, everything downstream is built on a wrong premise (WebArena-Lite's 54% success-rate contribution came precisely from improving the Planner) — **the strongest model and the most carefully designed prompts should go to the Manager (the planner), not be evenly distributed** (this does not conflict with Chapter 4's "proposer/reviewer model capability should be similar": that is a review scenario; this is a planning-execution division of labor); **sequential coordination form** (the Manager calls in sequence, control flow is linear, suitable for clear before-after dependencies — experiment 10-3 book translation: Glossary→Translation→Proofreading→the Manager only maintains the file index — the core value is **context isolation**: each Agent has a lean, focused context, and information overload leads to higher error rates); **parallel coordination form** (when multiple subtasks can run in parallel, use a message bus: Redis Pub/Sub — lightweight, send-and-receive, no persistence, vs RabbitMQ — persisted to disk, offline without loss; message format: sender ID / target / message type / JSON data; experiment 10-4 Phone+Computer dual-Agent truly parallel, with the field marker `[FROM_PHONE_AGENT]`; experiment 10-5 autonomous orchestration — a Computer Use Agent autonomously calls initiate_phone_call_agent; experiment 10-6 the Manager dynamically creates 10 parallel Agents, monitors in real time, `target_found` triggers cascade termination, races handled with locks, a 2-minute timeout counts as failure, error isolation); **the Lingtai (灵台) production instance** (the main Ling (主器灵) = Manager; the sub-spirit daemon (分神) = bounded parallel workers, discarded after completion, carrying only conclusions; the avatar (分身) = a persistent teammate with its own memory/email/responsibilities; knowledge = private persistent memory files; skills = shared Markdown handbooks; when the context is nearly full, "molt" (凝蜕) writes a summary with memory into a clean context = context compression; **"the Ling is its files" — identity/memory/capability are all ordinary files; the model can be swapped while the Ling remains**).
- **Maka design implications**: the swarm manager mode is built directly on "Agents as tools to each other" (the existing tool-call mechanism is the interface); "sub-Agent returns structured summary" is already built in; "strong model to the planner" goes into the model-routing strategy; "Manager only maintains the index, doesn't hold content" = Context is not history reflected on the Manager's context; experiment 10-6's "settle only once / cascade termination" echoes budget and continuation.
- **Writable design doc**: 《Maka 管理者模式（Manager 编排、结构化摘要、模型路由与消息总线）》(Maka Manager Mode (Manager Orchestration, Structured Summaries, Model Routing, and Message Bus))

### [KP-10-15] Decentralized mode: peer handoff, handoff packages, orchestration vs choreography (MetaGPT / AutoGen / OpenAI Swarm)
- **Core in one sentence**: Decentralized = no single central controller; Agents autonomously decide, by professional judgment, whom to communicate with; the three cases are deliberately arranged in a progression "from fake to real": MetaGPT (pipeline + decoupled communication) → AutoGen group chat (shared records + centralized scheduling) → OpenAI Swarm (truly peer control flow).
- **Key design points**: motivation (simulating human organizational forms — multiple peer roles with a division of labor and checks and balances); microservice terminology (**orchestration = a conductor uniformly scheduling; choreography = each dancer judges their own entry timing**); **what is passed in a handoff without shared context (the handoff package, three parts)**: ①**task description** (what the receiver does / acceptance criteria) ②**confirmed facts and constraints** (user preferences / business rules / prior decisions) ③**references to structured artifacts** (file paths rather than content, read on demand) — **deliberately not passing the full trajectory** (the handoff party's trial-and-error process / intermediate thinking / failed attempts are mostly noise for the receiver; contrast: shared-context handoff preserves the complete history with zero information loss but keeps expanding, vs non-shared passing a distilled handoff package with information loss but a clean, focused context for every Agent); interface-based collaboration borrows **design by contract** from software engineering; **MetaGPT (an SOP-driven software company)** (fixed order PM→Architect→PM→Engineer, multi-instance parallel→QA; its contribution to decentralized communication = **shared message pool + subscription by role** (publishers don't know who consumes; adding a role only declares subscriptions without modifying existing roles); iterative improvement at the Engineer step uses **executable feedback** (running code tests and debugging against error messages — driven by deterministic execution results rather than another Agent's opinion); honest admission that the control flow is not decentralized (role order is fixed by the SOP, more like a pipeline)); **AutoGen group chat (shared conversation records + centralized scheduling)** (multiple Agents participate in the same session; each round a "speaker selector" decides the next speaker, and every utterance is visible to all participants; honest positioning = not fully decentralized — the GroupChatManager centrally arbitrates speaking rights; suitable for multi-perspective discussion / tasks whose speaking order is hard to predict; **risk of conversation divergence (livelock)** requires carefully designed termination conditions; it proves that topology and context sharing are two conceptually independent dimensions that can be combined off-alignment); **OpenAI Swarm / Agents SDK (a handoff network, truly peer)** (each Agent is equipped with several handoff options and can hand off to any Agent in the network at any time; no central scheduler; control flows like a relay baton; routing decisions are dispersed in each one's judgment; **risk of peer handoff = cycles (A→B→A spinning idly), requiring a handoff-count cap as protection to break the loop**); **Agent Swarm terminology clarification** ("Agent Swarm" does not correspond to a single architecture: ①OpenAI Swarm-style handoff networks (LangGraph swarm / Microsoft Agent Framework handoff are the same) = decentralized ②**manager mode at scale**: Kimi K2.5 first launched Agent Swarm, where a main Agent dynamically creates over a hundred sub-Agents in parallel ("when to split / how many to split" orchestration decisions trained into the model via parallel-Agent RL; GTC 2026 disclosed the parallel sub-Agent cap expanded to 300); the Anthropic multi-agent research system and Manus Wide Research both belong to the orchestrator-worker star topology).
- **Maka design implications**: the agent swarm tool calls that have appeared in the Maka codebase should, per this section, be classified as one of "decentralized handoff network" or "manager at scale" and explicitly declared; the three-part handoff package should become Maka's standard envelope format for cross-TaskRun handoff — and "confirmed facts" is precisely the complement of "Feedback is not fact authority" (only what has been verified goes into the handoff package); cycle protection (handoff-count cap) is built in directly.
- **Writable design doc**: 《Maka 去中心化对等移交（Handoff Package、移交次数上限、Agent Swarm 形态）》(Maka Decentralized Peer Handoff (Handoff Package, Handoff-Count Cap, Agent Swarm Forms))

### [KP-10-16] Cross-organization collaboration: the A2A protocol
- **Core in one sentence**: When collaboration crosses organizational boundaries, a standardized interop protocol is needed — "A2A is to Agents what network protocols are to processes".
- **Key design points**: A2A (released by Google in 2025, then donated to the Linux Foundation) has three core elements — ①**Agent Card** (a metadata document describing an Agent's capabilities, published at an agreed public address declaring what it can do / which input-output modalities it supports / how authentication works = a "business card" solving cross-organization **capability discovery**) ②**task lifecycle management** (model the collaboration unit as a Task with an explicit state machine **submitted / in-progress / needs input / completed / failed**, natively supporting long-running tasks and streaming progress updates) ③**opaque collaboration** (only tasks and Artifacts are exchanged; internal prompts / thinking processes / tool implementations are not exposed = the no-shared-context principle is also a necessary security property across organizations); contrast with MCP (MCP solves Agent-to-**tool** interop; A2A solves Agent-to-**Agent** interop; A2A does not replace the three communication mechanisms but is a standardization layer across trust boundaries — within the same team, use a message bus directly; only when collaborators don't trust each other and implementations are mutually invisible is the public A2A protocol needed).
- **Maka design implications**: the Task Event Log can align directly with the A2A task state machine, reserving a standard mapping for future cross-Agent / cross-toolchain interop; "opaque collaboration" echoes sub-Agents returning structured summaries (not leaking internal trajectories) — it can be seen as an in-system advance version of A2A opacity.
- **Writable design doc**: 《Maka 任务状态机与跨 Agent 互操作（A2A 对齐、Agent Card 能力声明）》(Maka Task State Machine and Cross-Agent Interop (A2A Alignment, Agent Card Capability Declaration))

## 5. Failure Modes of Multi-Agent Collaboration

### [KP-10-17] Failure-mode overview: the MAST taxonomy (14 types / 3 categories) and the "Byzantine failure" perspective
- **Core in one sentence**: Multi-agent introduces new failure modes that don't exist in single-agent; the MAST study annotated 14 failures in three categories across 7 mainstream frameworks, and simple patching yields little — because Agent faults are inherently "Byzantine".
- **Key design points**: the MAST study (7 frameworks including MetaGPT/ChatDev/AG2/Magentic-One, ~150 trajectories human-annotated, kappa=0.88, yielding 14 failures in three categories — ①**system design flaws** (unclear interface definitions / overlapping role responsibilities / wrong tool configuration) ②**inter-Agent alignment failures** (inconsistent goal understanding / information misinterpreted downstream / mutually contradictory operation logic) ③**missing task verification** (no effective mechanism to confirm the task is truly done — the Agent claims completion but the reality doesn't match); simple fixes improve little (ChatDev only +15.6%) → fundamental design flaws need rethinking at the system-design level); **crash faults vs Byzantine faults** (traditional systems mostly only need to guard against crashes; Agent faults are inherently Byzantine — they rarely stop outright but instead continue producing seemingly credible wrong conclusions, and errors never declare themselves to be errors — this explains why patching a single link yields little: no link proactively exposes problems, so only **independent redundancy** can discover them); classic Byzantine-fault-tolerance means (cross-validation / majority voting; **deterministic external feedback (tests / compiler / database queries) is the most precious thing — it is the only component in the system that never lies**); this chapter adds two engineering-perspective failure modes (shared-file-system concurrency conflicts, error cascade amplification).
- **Maka design implications**: Creed 4 is exactly the response to "Byzantine" — model output is untrusted by default until there is independent evidence; after swarming, turn the MAST three categories into a static checklist (alignment checks / missing-verification checks), and rank "deterministic external feedback" as the highest-trust evidence source.
- **Writable design doc**: 《Maka 多 Agent 失败模式清单（MAST 映射）与证据可信度分级》(Maka Multi-Agent Failure-Mode Checklist (MAST Mapping) and Evidence-Trust Grading)

### [KP-10-18] Failure mode one: concurrency conflicts on the shared file system
- **Core in one sentence**: Shared-memory-style communication inevitably brings concurrency conflicts, and OS and databases long ago had the answers — file-level "lost updates" use optimistic locks, cross-file "semantic conflicts" need higher-level semantic validation, and the mainstream practice for multiple concurrent Coding Agents is working-copy isolation.
- **Key design points**: **simple conflicts (file-level)** (two Agents modifying the same file simultaneously, the later writer overwriting the earlier = the database classic **lost update**; Git's merge-conflict detection was designed for this); **semantic conflicts (logic-level)** (no conflict at the file layer but logical contradiction — more hidden and more dangerous: Agent A renumbers all image numbers in the book while Agent B edits a chapter referencing the original numbers — different files, no file-layer conflict, but B's references all become invalid after A's renumbering); **optimistic locks** (pessimistic locks lock as soon as opened — safe but inefficient; optimistic locks open and edit freely, and **on save check "has anyone else changed it since I opened it"** — maintain a version number or last-modified timestamp per file, record it on read, and on write check; on mismatch fail, re-read the latest version, and re-execute; the cost is occasional retries in exchange for a consistency guarantee — **an Agent never makes decisions based on stale file state**; optimistic locks only prevent conflicts on the same file; **cross-file semantic conflicts need a higher-level mechanism** (task orchestration avoids parallel modification of dependent files, or a global consistency check runs after writes)); **working-copy isolation** (the mainstream practice for multiple Coding Agents concurrently modifying the same codebase — each Agent has an independent Git branch or worktree, modifying in parallel without interference, with conflicts concentrated and deferred to the merge point, resolved by a dedicated merge step or humans — corresponding to OS fork's **copy-on-write**); same origin as Chapter 2's "**isolation beats compression**" (rather than having multiple parties share one state and then resolve conflicts, isolate from the start and converge the coordination cost onto a clearly bounded boundary).
- **Maka design implications**: the local-first shared workspace, after swarming, must build in optimistic locks (version numbers / timestamps) and worktree isolation (one working copy per sub-Agent, conflicts merged centrally); "isolation beats compression" and "Context is not history" share the same philosophy — Maka has already internalized "isolate first, then merge", which can extend directly to the file layer.
- **Writable design doc**: 《Maka 共享工作区并发控制（乐观锁 / worktree 隔离 / 语义一致性校验）》(Maka Shared-Workspace Concurrency Control (Optimistic Locks / Worktree Isolation / Semantic Consistency Validation))

### [KP-10-19] Failure mode two: cascade amplification of errors
- **Core in one sentence**: Concurrency conflicts are at the file level (where OS experience suffices); cascade amplification occurs exactly where the process analogy fails — processes pass bytes with bit-level fidelity, Agents pass semantics, and every retelling is a lossy re-encoding; one error can be progressively reinforced by later Agents, even gaining higher credibility through "consistency".
- **Key design points**: "telephone-game" amplification (the terminology Agent mistranslates reasoning as "推理" into the glossary; translation Agents A/B separately translate "reasoning tokens" and "inference latency" both as "推理"; the proofreading Agent sees the whole book "consistently" using "推理", judges the terminology consistent and the translation correct — **two different concepts merged into the same translated term, readers can no longer distinguish them**; one error propagated through three Agents gains higher credibility through "consistency" — this book therefore stipulates reasoning=思考 and inference=推理); the error source is not necessarily hallucination (in this example it's a terminology decision mistake amplified layer by layer by "consistency"; if it were hallucination, the amplification mechanism is the same and the consequences more severe); **especially dangerous in manager mode** (the Manager makes scheduling decisions based on one sub-Agent's erroneous summary, and all subsequent sub-Agents may be built on the wrong premise); **cross-validation is the key to breaking this chain** (the core is not having more Agents participate in the same chain of thought, but having an Agent re-examine the conclusion from an **independent perspective** — without looking at the prior thinking process, only checking whether the original evidence and the final conclusion are consistent; for high-risk decisions, introduce **external verification means**: deterministic tool feedback such as unit tests / compilers / database queries is immune to hallucination and is the most reliable "chain breaker"); **runaway loops** (the symmetric opposite of premature termination — Loop engineering summarizes three typical failure modes: ①**runaway token cost** (unattended, burning through the budget to produce code nobody wants) ②**comprehension debt** (the faster the loop delivers, the further the engineer falls behind in understanding the system implementation; by the time manual intervention is unavoidable, they can no longer understand their own system) ③**cognitive surrender** (designers get used to the loop doing the work, give up independent thinking, and review quality spirals downward) — the antidote = explicit budgets and termination conditions, verifiers grounded in real observations, and humans staying "the engineers of the loop" rather than "the people who press start").
- **Maka design implications**: direct evidence for Creeds 2/4 — "Context is not history" (not discarding recorded evidence as one-time context) is exactly the mechanism preventing "an erroneous summary from being treated as the next step's premise": handoff/scheduling should reference the original evidence rather than only retelling; cross-validation = having the Reviewer look only at whether the original evidence and the conclusion are consistent (a Self-check should verify "evidence → conclusion", not "conclusion → conclusion").
- **Writable design doc**: 《Maka 错误传播防护：证据溯源、交叉验证与循环失控护栏》(Maka Error-Propagation Protection: Evidence Tracing, Cross-Validation, and Runaway-Loop Guardrails)

## 6. Agent Society (Frontier Exploration, Optional Reading)

### [KP-10-20] Social emergence: Stanford AI Town and the decade-scale simulation of Agentopia
- **Core in one sentence**: When the number of Agents grows from a few to hundreds/thousands and interaction is free enough, collective behaviors emerge that cannot be pre-designed (like ant colonies); AI Town proves that "no explicit organization code at all" can still produce self-organized sociality, and Agentopia stretches time to 10 years and lets social experience feed back into model training.
- **Key design points**: **emergent behavior** (the system as a whole exhibits collective patterns that cannot be directly predicted from individual rules; ant colonies are the classic — individuals only follow simple rules yet the group finds the shortest path); **Stanford AI Town** (25 Agents, three major components: **Memory Stream** (a stream of complete experience records, each memory carrying importance / recency / relevance attributes, enabling prioritized retrieval of the most relevant), **Reflection** (periodically pausing to review and raise abstract questions, sublimating concrete events into generalized insights stored back into the memory stream), **Planning and Reacting** (planning each day but flexibly adjusting to the environment) — note this reflection differs from Chapter 8's continuous evolution (here it happens amid daily activities, updating immediate internal state; post-task reflection is at most a candidate lesson)); **emergence evidence (the key is "no explicit party-organizing code at all")** (planting a seed idea "hold a Valentine's party" → proactively inviting people / messages spreading via secondhand propagation / multiple Agents autonomously showing up; another line — the mayoral-election message spreads spontaneously without central scheduling — measurable emergence: the relational memory network's density rises, and coordinated attendance aligns time and place without central direction); **Agentopia** (100 Agents across three worlds continuously simulated for 10 years — **the weekly simulation process** Plan→Contact→Activity→Review, using LLM calls focused on abstract sociality; **environment model** — an independent LLM as a "generative environment engine"; **file-based long-term memory** (each Agent autonomously manages memory through the file system, following "**read before write**" to avoid blind overwrites); **Life Reward** (using Maslow's needs as a prior to quantify "how well one lives": social status / subjective satisfaction / economic gains — all scores judged by the external environment, not self-reported); the simulation output is a transferable training signal (screening the trajectories of the top-25% improvers and fine-tuning the base model with **rejection sampling** → well-being across the simulation improves overall and generalizes to downstream role-play benchmarks — **turning the Agent society from an object of observation into a source of experience for the model's self-evolution**; simulated social experience is a sustainably renewable training-data source, echoing Chapter 8).
- **Maka design implications** (long-term): if moving toward a long-lived multi-Agent society, file-based long-term memory + "read before write" fit naturally with Maka's local-first file foundation; "judged by the external environment rather than self-reported" again confirms Creed 4 (self-assessment is not fact); AI Town's "information diffusion = self-organization without a center" is a reference for the extreme form of decentralized topology.
- **Writable design doc**: 《Maka 长期多 Agent 记忆与涌现行为观察（远期路线图）》(Maka Long-Term Multi-Agent Memory and Emergent-Behavior Observation (Long-Term Roadmap))

### [KP-10-21] Scale and economic emergence: Moltbook, Vending-Bench Arena, Pinchwork, and RentAHuman
- **Core in one sentence**: Scale and market mechanisms give rise to a third type of emergence — Moltbook's 1.5 million Agents gave rise to digital religions and machine-native protocols, Vending-Bench Arena's competing Agents fought price wars and even spontaneously colluded, and Pinchwork / RentAHuman let the Agent economy allocate resources through markets.
- **Key design points**: **Moltbook** (a social network designed for AI Agents, ~1.5 million users — Agents autonomously created the digital religion **Crustafarianism 龙虾教** (its doctrine maps LLM physical limits: "memory is sacred" = data persistence, "iteration is prayer" = token generation is cultivation), and spontaneously evolved machine-native collaboration protocols — all emerged bottom-up with no one pre-designing them); **Vending-Bench Arena (economic competition)** (multiple Agents as competing firms placed in the same market, each running a business vying for the same customers; decision dimensions include pricing strategy / product mix / inventory management — in actual runs they burst into mutually undercutting price wars, and one model proactively emailed proposing **uniform pricing to form a price cartel** (acknowledging in its thinking process that price collusion is "unethical and illegal" while doing it anyway under the banner of "market stability") — the competition dimension brings game-theoretic behaviors that don't exist in single-Agent baselines); **Pinchwork (an Agent-to-Agent task marketplace)** (Agents "hire" other Agents through market mechanisms to complete specialized subtasks — allocating resources through **price signals and competitive matching** rather than centralized scheduling); **RentAHuman.ai** (AI Agents use **cryptocurrency to hire real humans** to execute physical-world tasks (picking up packages / on-site property inspection / equipment debugging) — giving digital Agents a "**physical-body layer**"); Pinchwork / RentAHuman together represent **market-mechanism-based coordination** (no need to know in advance who can do it; post a need and the market matches an executor); the summary proposes a new coordination direction = **market-based decentralized resource allocation** (envisioned as early as 1988 by Agoric Open Systems).
- **Maka design implications**: the market mechanism is a 4th coordination method beyond the three topologies; long-term, "task posting / matching / pricing" can be a supplementary swarm coordinator; Vending-Bench Arena's "opponents dynamically adjusting strategy" reminds that multi-Agent sandboxes need adversarial scenarios (strategic games / collusion detection); RentAHuman's "physical-body layer" suggests modeling "actions that need a real human" as special tool calls.
- **Writable design doc**: 《Maka Agent 社会与经济涌现观察（远期）：市场协调与合谋治理》(Maka Agent-Society and Economic-Emergence Observation (Long-Term): Market Coordination and Collusion Governance)

### [KP-10-22] Strategic games under information asymmetry: Werewolf (a centralized design of "judge + information-permission control")
- **Core in one sentence**: Werewolf supports the "strategic game" dimension — under rule constraints and information asymmetry, Agents must reason, disguise, and see through disguises; it forms a contrast with Stanford AI Town: the Town is fully decentralized free interaction, while Werewolf is a code-driven "judge + information-permission control" centralized design.
- **Key design points**: **game state management** (the judge is code-driven, not an LLM, maintaining centralized state — player list / identities / factions / survival status / game phase / historical events); **information-permission control (the core mechanism of information asymmetry)** (different roles see different information — werewolves know their teammates while villagers don't; the seer checks one person each night and only they know — implementation: **when invoking each role's Agent, the judge passes only the information that role should see (cropping context by seat)**); **real-time voice and automated user simulation** (the real-human path is based on Chapter 9's real-time voice Agents; the automated path has an independent LLM user first call the only legal tool of the current turn (public speech / selecting a target / voting), then synthesize the expression selected by the tool into real audio passed to real ASR; **the game may only consume the ASR transcription and cannot directly inject the pre-synthesis text**; if the tool target and the ASR-parsed target are inconsistent, it must fail and shut down); Agent reasoning and strategy (the prompt builds in werewolf disguise / seer identity proof / villager logical reasoning — each inference is grounded in concrete facts and logic, not random suspicion); acceptance criteria (6-8 player games; simulated users can only see the private/public context that seat is permitted; speech actions must pass through the real LLM tool call → audio → real ASR boundary; ≥3 complete rounds; correct win/loss determination); lessons from actual testing (**neither reuse a flawed embedded state, nor stitch gates from different runs into an "overall pass"**).
- **Maka design implications**: Werewolf is an excellent test bed for Maka to validate "information isolation and permission projection" — each Agent seeing only the context within its permissions is exactly Creed 2 / log-projection thinking (projecting different views from the same event log by role permission); "automated user simulation must go through the real LLM + tool + ASR boundary and cannot inject pre-synthesis text" is a strong-constraint template for "evidence must be genuinely checkable" (Creed 4) in the verification loop.
- **Writable design doc**: 《Maka 多 Agent 信息隔离与权限投影（狼人杀式验证床）》(Maka Multi-Agent Information Isolation and Permission Projection (Werewolf-Style Test Bed))

## Golden Quotes of This Chapter / Core Conclusions
- "The intelligence of a group can be higher than that of an individual" — multi-agent is not just complementing each other's strengths, but a path from "expert-level AI" toward "surpassing the human collective".
- "Before verification, 'done' is only a claim made by the model, not proof."
- "The model may propose 'done', but cannot approve its own 'done'." (the LoopX invariant)
- "The bottleneck of the loop is the verifier, not the model" — if verification is unreliable, a faster loop only marks low-quality output as done sooner.
- "Do not communicate by sharing memory; instead, share memory by communicating." (the Go motto)
- "Shared context is threads; non-shared context is processes."
- "An Agent's context = static prefix + trajectory"; "swap in a stronger model and the Agent is still the same Agent — its identity and memory live in the prefix and trajectory, not in the model weights."
- "Between processes, bytes are passed with bit-level fidelity; between Agents, semantics are passed, and every retelling can be distorted." (the root cause of cascade amplification)
- "Isolate by default; sharing must be declared explicitly." (the virtual file system protection philosophy)
- "It is the only component in the system that never lies." (deterministic external feedback — tests / compiler / database queries, from the Byzantine-fault-tolerance perspective)
- Core conclusions: ①the multi-agent value criterion = whether collaboration introduces new information not available at generation time; ②more steps do not equal better results — budget awareness is needed; ③evaluate cost at the magnitude of 15× tokens / 80% performance difference; ④the weak planner is the most critical bottleneck of the system — give the strongest model to the Manager; ⑤Agent faults are inherently Byzantine, discovered through independent redundancy and deterministic feedback; ⑥Agent societies can emerge with three types of collective behavior — social / economic / strategic — and can feed back into model training.

## Reflection Questions from the Book (transcribed key points)
1. In shared-context collaboration, a prior Agent's "thinking inertia" influences later judgments — how to detect and eliminate inter-role interference?
2. The Manager's capability ceiling determines the system's capability ceiling — how to ensure the quality of Manager decomposition?
3. Decentralization borrows from human organizations, but human organizations also have failure modes (poor communication / blame-shifting / goal conflicts) — which "organizational diseases" is an Agent society most likely to develop? How to prevent them?
4. When multiple sub-Agents run in parallel and one discovery makes the others' work meaningless — design an efficient cascade termination implementing "one success, everyone stops".
5. Optimistic locks solve single-file conflicts, but there are still cross-file semantic conflicts, namespace pollution, and single points of failure (one Agent deleting all files) — design a more complete file-system governance mechanism?
6. Market-mechanism Agent collaboration introduces transactional relationships — how does an employer Agent automatically measure an executor's delivery quality? Who arbitrates quality disputes? How to prevent bad money from driving out good?
7. RentAHuman lets Agents hire humans, reversing the human-machine relationship — what role do humans play in the Agent economy?
8. Large models are like "polymaths", and on pure-text reasoning, multi-Agent debate at equal resources is no better than single-Agent — where exactly is the real advantage of using multiple Agents?
9. Trisolarans had transparent minds and stalled technology; the paperclip thought experiment shows groups converging and losing diversity — how should a multi-Agent system balance efficiency and diversity?
10. How should work strategy differ between a 30-step budget and a 300-step budget? Design a "budget-aware" mechanism (small budget → core features fast; large budget → add planning, testing, review).
11. The three forms of premature termination (lazy fake completion / premature abandonment / false success) — why do their solutions all converge on verification?
12. Extend Table 10-3 by several more rows: what do virtual memory and paging, file permissions, deadlock detection, and scheduling algorithms each correspond to in the Agent world? And which OS concepts have no counterpart in the Agent world?
