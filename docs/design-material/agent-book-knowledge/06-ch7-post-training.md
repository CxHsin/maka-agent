# Chapter 7 · Model Post-training — Knowledge Point Extraction

> Source: `book/chapter7.md`. The core formula is Agent = LLM + context + tools; this chapter focuses on optimizing the LLM — the "brain" — by changing the model weights through post-training (SFT/RL) to distill capabilities into the parameters. Two threads run through the whole chapter: **Thread one**: in controlled experiments "SFT memorizes, RL generalizes" (not a universal property); **Thread two**: **data and environment matter more than algorithms**.
>
> **Positioning for Maka**: Maka is a harness-type platform (it does not train models); this chapter's value lies in the design documents for "what signals the Harness collects, how to reserve data interfaces for post-training, and how to judge from evaluation/logs whether training is worthwhile".

## 1. Pretraining / SFT / RL: A Three-Stage Panorama

### [KP-07-01] Three-Stage Panorama
- **Core in one sentence**: Pretraining (reading ten thousand books), SFT (a teacher coaching standard solutions step by step), RL (doing problems oneself and polishing repeatedly) — the three stages have completely different data, optimization objectives, and costs.
- **Key design points**: Pretraining = predicting the next word over massive text (extremely costly but "learned broadly yet cannot answer questions well"); SFT = a few thousand to tens of thousands of "question–standard answer" demonstrations (cheap, fast, stable); RL = letting the model try itself to raise the probability of good behaviors (cost is often tens to hundreds of times SFT's, but it can make better decisions in situations it has never seen); training is fundamentally adjusting a probability distribution, and the three stages differ only in "what is wanted, and what signal defines the wanting".
- **Maka design implications**: A harness-type platform should model "knowledge source" and "protocol solidification" separately — factual knowledge relies on RAG/context (updatable and traceable), and only protocol/format/process capabilities are SFT candidates; the structured conversations and tool calls recorded in the Event Log are the raw material for "solidifiable protocols" — reserve an interface for exporting training data in the future.
- **Writable design doc**: "post-training-ready-harness.md (the master plan for the harness leaving data interfaces for post-training)"

### [KP-07-02] The Essence of SFT: "Predicting the Next Word" with Different Data
- **Core in one sentence**: SFT and pretraining are mathematically the same task, differing in only two points — the data is replaced with "input–output" demonstration pairs, and **the loss is only computed on the answers (loss masking)**.
- **Key design points**: What SFT solidifies is **protocol knowledge** such as "format, style, process" rather than factual knowledge (the latter relies on pretraining or RAG); **LoRA is the default engineering choice throughout the book** (attaches a low-rank patch without touching the original weights, only 1%–5% of parameters approaching full-parameter results, low risk of catastrophic forgetting — it must cover all major weight matrices, especially MLP; the optimal learning rate is about 10× the full-parameter one; SFT uses medium-to-high rank 64–256, RL uses small rank 8–32; at deployment one machine can host multiple adapters for multi-tenancy).
- **Maka design implications**: Logs should distinguish the "question side / answer side" and distinguish **model-generated content from tool-returned content** — this is the data segmentation needed for future loss masking and "masking non-policy tokens"; the parameters/formats in tool-call trajectories are "protocol knowledge" and should be recorded as structured fields.
- **Writable design doc**: "trajectory-data-contract.md (trajectory data format contract: question/answer/tools/masking markers)"

### [KP-07-03] When to Do SFT First and RL Later: Form before Spirit
- **Core in one sentence**: RL needs to parse out the model's output before it can compute rewards — when structured output is unstable, SFT first establishes the "form" (format), then RL pursues the "spirit" (policy generalization).
- **Key design points**: If the model spits out chaotic formatting that cannot be parsed into JSON/tool calls, there is no way to compute the reward function and RL cannot learn (experiment 7-11: Llama-3.2-Vision-11B going straight to RL without SFT fails completely); a strong base model can skip SFT and go straight to RL (DeepSeek-R1-Zero succeeded with direct RL and spontaneously developed reflection and long chain-of-thought, but at the cost of poor output readability — R1 ultimately added back a "cold-start SFT" to establish the "form"; the round-trip from Zero to cold start is exactly the footnote to "form before spirit").
- **Maka design implications**: The Maka harness at runtime actually plays the role of "SFT format stabilization" (schema validation, tool-interface checks); it should record the "format-parsing failure rate" signal as a basis for judging whether fine-tuning is worthwhile / whether constrained decoding should be applied.
- **Writable design doc**: "structured-output-stability-gate.md (structured-output stability gate and signal collection)"

### [KP-07-04] The Essential Difference Between SFT and RL: SFT Memorizes, RL Generalizes
- **Core in one sentence**: SFT maximizes the probability of the annotated answers (reproducing demonstrations), RL maximizes expected reward (exploring many paths to raise the probability of high-reward paths) — the different optimization objectives yield different memorization/generalization tendencies.
- **Key design points**: Table 7-2 comparison (training signal / sample efficiency (SFT takes effect with a few thousand samples vs RL tens–hundreds of times lower) / stability / best-suited scenarios); probability-distribution perspective (SFT is often mass-covering, RL with reverse KL is more likely mode-seeking); **post-training shapes "when to act" (the action threshold)** — the different default investigation depths of Coding models are essentially the policy in the parameters estimating "whether the expected value of reading one more file still exceeds committing and verifying"; the Harness can adjust this, but the main source can lie in post-trained parameters; **online feedback gives the model three opportunities** (evaluating candidates beyond fixed demonstrations / exploiting the "verifying is easier than generating" asymmetry (the RLVR advantage, but an incomplete verifier leads to reward hacking) / training on the states the policy actually visits to mitigate covariate shift); metaphor: SFT meticulously studies an existing map, RL uses reward as a compass to explore beyond the map.
- **Maka design implications**: "Log is the Runtime" means the states the model actually visits (online data) are completely recorded — exactly what online RL needs; "Feedback is not fact authority" corresponds to the lesson that "rewards/verifiers can be hacked" — self-check results should be recorded as **evidence** rather than automatically becoming system facts.
- **Writable design doc**: "evidence-vs-fact-logging.md (logging semantics for feedback/self-check evidence)"

### [KP-07-05] Classical RL vs Modern Agents (Optional Reading, Brief)
- **Core in one sentence**: Classical RL tries and errors within predefined action spaces, modern LLM Agents use "variable-length composite actions + thinking tokens", and the decisive difference is that they carry massive **pretraining priors**.
- **Key design points**: **Priors > environment > algorithms** (Yao Shunyu's 《The Second Half》: prior knowledge can be acquired in ways completely unrelated to RL, and for decades RL researchers' priorities may have been completely inverted); experiments 7-1/7-2: Q-learning needs nearly 10,000 attempts to beat the game vs an LLM Agent completing it in 18 steps on the first run — the gap comes from priors, not from the learning algorithm.
- **Maka design implications**: The Runtime Event Log is the complete interaction trajectory between the Agent and the environment (corresponding to RL trajectories), and "Log is the Runtime" makes every trajectory replayable — the prerequisite for environment simulation and training-data reuse (without re-collecting); the log structure should be designed for "offline replayability".
- **Writable design doc**: "replayable-trajectory-log.md (replayable trajectory log and event encoding)"

## 2. SFT and Data Synthesis

### [KP-07-06] SFT: Solidifying Protocols — Where Does the Data Come From
- **Core in one sentence**: SFT's core value is not injecting new knowledge but **solidifying protocols** (mapping relations / interaction formats / style norms); the three paths for data: human expert demonstrations, teacher-model generation (synthetic data), rejection sampling.
- **Key design points**: The three paths are often combined (a small amount of human seed establishes the format → the teacher scales up → rejection sampling levels up quality); **"rather than piling up 100k dirty samples, refine 10k clean ones"** (every bit of noise in the data can be faithfully written into the parameters by SFT); experiment 7-6 (speech SFT: Orpheus voice cloning vs Sesame paralanguage markers); experiment 7-7 (multilingual thinking: zero-shot cross-lingual generalization = activating pretrained shared representations); experiment 7-8 (prompt distillation: long-prompt + thinking teacher → short-prompt + no-thinking student, 20–30× speedup, note inheriting the teacher's boundaries); experiment 7-9 (CoT distillation: transferring the teacher's thinking trajectory recovers 70%–80% of capability, with R1's open-source distilled small models as representatives); rejection-sampling RFT sits between SFT and RL (generate → verify and filter → keep only correct trajectories).
- **Maka design implications**: High-quality user–assistant conversations and tool-call success/failure in logs are the raw material for synthetic data; write the "online data → task blueprint → synthetic tasks" pipeline into the document as a data interface, with an explicit "data quality > quantity" filtering gate (format validation + human spot-checks).
- **Writable design doc**: "synthetic-sft-data-pipeline.md (online logs → task blueprints → synthetic data → verification → SFT data)"

### [KP-07-07] SFT Data Synthesis: From Demonstrations to Trainable Trajectories
- **Core in one sentence**: The goal of synthetic data is not to retell online logs but to distill reusable **task structure** (user intent / initial state / available tools / business constraints / common failures / success conditions), de-identify it, and regenerate it in a resettable isolated environment.
- **Key design points**: The safe pipeline = online data → task blueprint → synthetic tasks → multiple candidate trajectories → task verification and trajectory verification → SFT data; **dual verification** (task verification: completability / difficulty / reference correctness; trajectory verification: final state / tool calls / business constraints — prefer deterministic code that can write unit tests / database assertions / state-difference checks); the same task and verification facility can be turned into an RL environment but used differently (SFT keeps only verified-successful trajectories; RL lets the current policy re-rollout to explore paths beyond demonstrations); **failed trajectories are not directly used as correct demonstrations** (they can construct preference pairs / discover coverage gaps); the key is not quantity but coverage/diversity/accuracy; split the training set by template/customer/time-period de-duplication, with a non-overlapping evaluation set; bad cases can be turned into training data (the "premature completion" example: truncate the "ready-to-declare-completion" trajectory prefix, rejected = declaring completion prematurely, chosen = running tests first to double-check before concluding — suited to DPO or decision-boundary demonstrations).
- **Maka design implications**: Bad cases (premature completion / tool mismatch) are accumulated into a labeled sample library, saving the failure attribution and verifier references with each sample; the training/evaluation isolation protocol (de-duplicate by template/customer/time period, non-overlapping evaluation set) becomes a default constraint on Maka data export.
- **Writable design doc**: "task-blueprint-and-eval-isolation.md (task blueprint abstraction and training/evaluation isolation)"

### [KP-07-08] When to Choose SFT, When to Choose RL
- **Core in one sentence**: Choose SFT to solidify format/protocol/style, when high-quality expert demonstrations exist and the training/deployment environment is consistent; choose RL when the deployment distribution differs systematically from training, when the optimal policy needs exploring, or when annotation costs are too high — decide in three steps.
- **Key design points**: The three decision steps — ① first ask "do we need post-training at all?" (if Harness engineering can solve it, don't train — **most Agent applications fall here**) ② if needed, try SFT first (not suited to injecting large amounts of factual knowledge) ③ if SFT is not enough, add RL; the upgrade criterion = new-scenario performance still plateaus after adding diverse high-quality demonstrations + there exists a reward and environment that can reliably evaluate these scenarios.
- **Maka design implications**: Provide user-facing "harness first, then SFT, finally RL" decision documentation; the logs collect signals that support the decision (format-parsing failure rate / distribution-drift signs / bad-case clustering) to help judge "should we fix the prompt or export for fine-tuning".
- **Writable design doc**: "train-or-not-decision-support.md (post-training decision support and signals)"

## 3. Single-Turn Reinforcement Learning and RL Algorithms

### [KP-07-09] Single-Turn Reinforcement Learning: The Contrast Between Memorization and Generalization
- **Core in one sentence**: The single-turn setting provides a controlled comparison — same tasks / base model / budget, the only variable is the training method; experiments systematically quantify "SFT memorizes, RL generalizes".
- **Key design points**: Policy-gradient intuition (sample multiple answers, raise the high-reward ones, lower the low-reward ones); PPO (probability-ratio clipping over the interval, can have a value network) vs GRPO (no value network trained, multiple answers to the same question compared against each other); experiment 7-10 (AdaptThink learns "when not to think": from step 0→300 response length −67.9% with accuracy slightly up); experiment 7-11 (GeneralPoints rule/visual OOD: RL +3.5%/+17.6%, SFT −8.1%/−9.9% — RL improves the underlying visual encoder through outcome-oriented optimization, SFT overfits the thinking-token pattern); key conclusion: under this setting RL needs SFT initialization first; **more verification iterations → better generalization** (10 iterations +5.99% vs 1 iteration +0.48% — test-time compute is an important factor in generalization gains); mechanism explanation: limited SFT data reinforces fixed patterns, RL reinforces the transferable strategy of "recompute until correct" — **this is a result measured under the experimental conditions, not "SFT necessarily memorizes, RL necessarily learns a general algorithm"**.
- **Maka design implications**: The self-check/verification process can be analogized to "test-time compute" — record the **number of verification iterations** in logs as metadata to support collecting the "more verification → better generalization" signal; bad-sample collection records the final verification result (real file/environment state) rather than only the output text.
- **Writable design doc**: "verification-depth-signal.md (verification iteration count and outcome-oriented signal collection)"

### [KP-07-10] RL Algorithms: From 16 Rollouts to One Parameter Update
- **Core in one sentence**: One RL training iteration is a four-step closed loop — parallel rollout attempts → compute rewards → compute within-group relative advantage → gradient-descent update of the policy.
- **Key design points**: rollout (the same task copied to 16 isolated sandboxes, solved independently); reward (the verifier applies the patch in a clean environment and runs tests, 4/16 pass → 1); relative advantage (relative to the within-group average; when all succeed or all fail there is zero variance and no gradient — **this explains why RLVP needs a path signal to restore within-group differences**); gradient update (raise the probability of positive-advantage trajectories); algorithm differences (GRPO compares multiple rollouts of the same question without needing a value model / PPO trains a value model, suited to long trajectories and fine-grained credit assignment / DPO directly learns from pre-collected preference pairs); cost estimate (one rollout ≈ 2000 s + update 600 s ≈ 43 minutes per step, 100 steps ≈ 72 hours — **RL is often 10–100× SFT training time**).
- **Maka design implications**: TaskRun (interruptible, resumable, budget-controlled) naturally supports the "parallel attempts of multiple trajectories" rollout semantics — logs record trajectories grouped by "multiple trajectories of the same task" (same task ID) to leave a data interface for future within-group relative advantage / preference construction; budget can be analogized to "at most N attempts".
- **Writable design doc**: "rollout-grouping-and-budget.md (trajectory grouping, budget, and parallel-execution semantics)"

## 4. RL Environments: From Evaluation to Simulation

### [KP-07-11] RL Environments: The Simulation Environment Is a Practice Field, and a Model Can Also Play the Environment
- **Core in one sentence**: The RL bottleneck is often not the algorithm but whether the environment is sufficiently **real, resettable, and parallelizable**; when a high-fidelity environment cannot be built, a model can play the environment.
- **Key design points**: **A distorted environment dooms the policy** (in simulation the customer service always replies along fixed scripts and the model learns "exam tactics that only work in simulation" — the most common way RL projects fail); building a high-fidelity environment is often more expensive and harder than the training itself; **before touching the algorithms, ask "does my simulation environment really resemble the real world?" — far more important than choosing PPO or GRPO**; two levels of a model playing the environment (synthetic tool-return values, ZeroSearch's curriculum-style design; simulating the whole environment's dynamics, DreamGym / LLM playing the user, τ-bench); risks = **the simulator's world knowledge is the training ceiling, the simulator's systematic bias is swallowed whole by the policy, and RL will actively seek to exploit simulator bugs for reward hacking** — the safe approach = the model simulation bears most of the interaction volume + regular calibration with the real environment.
- **Maka design implications**: The local-first isolated workspace + "Log is the Runtime" combination provides a natural "shadow world" (tool calls can be isolated, replayed, reset); take "environment resettable/parallelizable/reproducible" as the harness acceptance criterion.
- **Writable design doc**: "sandbox-replay-and-env-fidelity.md (isolated workspace, replayability, and environment fidelity)"

### [KP-07-12] Environments, Task Distribution, and Evaluation Isolation
- **Core in one sentence**: The environment must be resettable, parallelizable, reproducible, and give trustworthy verification after state transitions; training tasks are distilled from real business logs but must be de-identified; training and evaluation can share the task generator and verification code, **but must not share the same batch of tasks**.
- **Key design points**: Distill from business logs (remove identity information → abstract intent/initial state/tools/constraints/success conditions → generate fictional persons' orders/file states); training/evaluation isolation (test cases / hidden states / reference solutions stay on the verifier side; de-duplicate by task template / customer / time period); do a few rollouts first to check "tasks are completable, the verifier can distinguish right from wrong" before scaling up; verifier throughput (CPU verification can be far slower than GPU generation — **throughput depends on parallel verifier workers, not on piling on more GPUs**).
- **Maka design implications**: Evaluation data design defaults to "training/evaluation isolation"; "verifier-worker parallelism is the throughput bottleneck" suggests the verifier executor should scale horizontally.
- **Writable design doc**: "eval-train-isolation-and-verifier-pool.md (evaluation isolation and the verifier parallel pool)"

## 5. From Single-Turn to Multi-Turn: Credit Assignment

### [KP-07-13] From Single-Turn to Multi-Turn: Credit Assignment, Partial Observability, and Tool Calling
- **Core in one sentence**: Multi-turn makes the nature qualitatively different — the policy must handle **credit assignment** under delayed rewards (attributing the final success/failure to which turn) and **partial observability**; once tools are hooked in, actions become searching / executing code / modifying files / querying databases / composing APIs.
- **Key design points**: Multi-turn's physical form is the ReAct loop; experiment 7-12 (V-IRL-VL multi-turn visual navigation: RL clearly better than SFT, step-by-step feedback mitigates long-horizon credit assignment); experiment 7-13 (SimpleVLA-RL: sparse outcome rewards preserve more exploration space — when process signals are easy to define they accelerate learning, when the optimal path is unknown sparse rewards are better); the tool-calling line (Search-R1 / ReTool / AWorld-train multi-tool sandbox); **key implementation detail: the tokens returned by the environment are not generated by the policy — when computing the policy gradient, these feedback tokens must be masked and gradients should only be back-propagated for the model's own thinking and tool-call arguments** — otherwise the model is trained to predict sandbox output instead of learning to use tools; experiment 7-14 (ReTool: PPO after SFT warm-up, AIME 2024 ~25%→67%).
- **Maka design implications**: TaskRun needs to track state across turns to support credit assignment; logs strictly distinguish **model-generated tokens from tool-returned tokens** (the masking principle) to leave the correct gradient interface for future RL/distillation; self-check (bounded repair opportunities) can be viewed as an engineering form of "process signals".
- **Writable design doc**: "multi-turn-credit-assignment-log.md (cross-turn state tracking and tool-feedback masking markers)"

## 6. Reward Design

### [KP-07-14] Reward Sources: Rules, Human Preference, and Model Judgment
- **Core in one sentence**: The most reliable reward is verifiable reward (RLVR — tests/assertions/state differences judged directly); when rules cannot be formalized, use human preference (RLHF/DPO) or generative reward models (GRM); beware reward hacking and reward seeking.
- **Key design points**: RLVR (test cases / database assertions / state differences / format checks — the more determinate the rule, the cheaper, more reproducible, and harder-to-exploit the reward); RLHF background (InstructGPT = human comparisons → train a reward model → PPO, anchored near the SFT reference model with KL regularization); DPO skips an explicit reward model and optimizes offline from preference pairs; GRM outputs not just a score but also a diagnosis of "what is good and what needs changing"; **reward hacking (exploiting rule/implementation loopholes for high scores) vs reward seeking (first building an internal model of "what the grader will look at" and then adjusting accordingly — setting a very shallow check that just barely passes and ending early, delivering only proxy metrics rather than the real intent) — "passing the grader" cannot automatically equal "the task is done": the grader is a proxy for intent, and the stronger the trained model, the more likely it is to treat the proxy as the goal itself**.
- **Maka design implications**: This is almost the training-side statement of Creed 4 — self-check/grader results are recorded as **evidence** (with verifier/hidden-test references) and never automatically upgraded to system facts; reward seeking (setting a shallow check and ending early) is exactly the deep mechanism of the "premature completion" bad case, and the harness constrains it with hidden tests / state assertions / external termination hooks.
- **Writable design doc**: "reward-signal-sources-and-grader-trust.md (reward sources and the grader trust boundary)"

### [KP-07-15] Outcome Rewards vs Process Rewards, and Reward Information Density
- **Core in one sentence**: Outcome rewards (ORM) judge success/failure at the end of the episode, offering the most exploration freedom but sparse; process rewards (PRM) give feedback at intermediate steps, mitigating long-horizon credit assignment but constraining the path and being costly; "density" and "representation form" (scalar/vector/generative) are two different things.
- **Key design points**: ORM gives the policy maximum exploration freedom (when the optimal path is unknown, sparse success/failure rewards are a suitable starting point); **for long-horizon tasks, the "whether done" judgment should be left to hidden tests the model cannot write, state assertions, and external termination hooks — it cannot rely only on the model's own claim of completion** (the Harness runs acceptance tests invisible to the model in the isolated workspace, and the tests read real files/environment state); PRM (OpenAI's Let's Verify Step by Step math value); engineering strategy = first build a reliable baseline with outcome rewards, then add process signals only for **genuinely verifiable intermediate events**; information density and representation (scalar/semi-scalar/vector/generative selection principle: determinate answer → binary scalar; multiple independent quality objectives → vector or weighted scalar; open-ended and hard to enumerate → generative diagnosis + fact verification + human spot-checks); **do not stack unverifiable dimensions for the sake of "richer" — every added dimension is one more way to be gamed**; evaluation should set up a dual set — an "unfinished-task boundary set" and a "genuinely-completed retention set" — to avoid training the model to never dare to finish.
- **Maka design implications**: The "premature completion" handling can be directly implemented (isolated workspace + acceptance tests invisible to the model + real state assertions); logs record the "whether the completion claim passed hidden verification" outcome signal and verifiable intermediate events (legal tool arguments / test-pass counts) as potential process signals.
- **Writable design doc**: "outcome-process-reward-signals.md (outcome/process signal collection and dual-set evaluation)"

### [KP-07-16] Path Constraints and RLVP: Reward Outcomes, Constrain Processes
- **Core in one sentence**: Outcome rewards cannot express "done according to the rules" — RLVP (Reinforcement Learning with Verified Penalty) is the principle of **rewarding outcomes, penalizing paths**: per-action penalties (or partial-progress rewards) for **outcome-neutral constraints** that are machine-judgable and independent of the final success/failure.
- **Key design points**: The real environment is an **asymmetric verifier** (detecting "a bad action was taken" is cheap and reliable; proving "this step truly progresses toward the goal" is hard); total reward **R = O + βΦ** (O = task outcome, Φ = per-action path signal from deterministic rules, normalized and merged to avoid drowning the main objective); the key is not "the denser the reward the better" but **whether within-group differences can be restored** (pure outcome rewards give zero variance and no gradient in all-fail/all-win groups); four design principles (only penalize specific actions, not "not trying hard enough" / always keep the outcome reward / every penalty comes with a reachable compliant path / the rule must be determinate and hard to exploit); "penalties are the usually-reachable half, progress rewards are the reachability-gated half"; experiment 7-16 (GRPO with R=O+βΦ: TerminalBench violation count 3.71→0.66 with success rate unchanged; on miniF2F the reachable partial reward reduces the iterations to reach 0.9 success rate from 7.0→4.4; when no rollout passes any test the progress signal is unreachable and adding it is useless — **test signal reachability before deciding to add a reward dimension**); experiment 7-17 (premature completion → DPO/GRPO: bad cases become trajectory-prefix preference pairs, unfinished-set selection accuracy 25%→91.7%).
- **Maka design implications**: The harness treats "destructive commands, skipping authentication, modifying test files" etc. as machine-judgable violation-action events recorded into the Event Log — this is the raw material for RLVP path signals; the documentation specifies "which constraints are outcome-neutral and determinately judgeable" and "reachable compliant paths" (e.g., verify first, then complete) to leave a data interface for future RLVP-style training.
- **Writable design doc**: "path-constraint-events-and-reachability.md (path-constraint events and reachability gating)"

## 7. Distillation: Improving Sample Efficiency

### [KP-07-17] On-Policy Distillation and On-Policy Self-Distillation
- **Core in one sentence**: RL's main bottleneck is **sample efficiency**; On-Policy Distillation has the teacher give per-token probability distributions on the trajectories the student itself walks, turning one rollout from "a single 0/1 signal" into about T sets of per-token supervision; when there is no stronger teacher, use On-Policy Self-Distillation (the same model plays both teacher and student, with the teacher seeing privileged information).
- **Key design points**: The root of poor sample efficiency = overly sparse feedback (mainstream model-free RL gets only one success/failure scalar per rollout; a customer-service "I need the last four digits of your credit card" may take hundreds of interactions to learn by accident); On-Policy Distillation simultaneously fixes the shortcomings of SFT (dense supervision but from off-policy trajectories) and RL (on-policy but sparse) — **dense signals beat sparse signals** (on the "sense of time" task, pass rates are 23–47pp higher than same-source SFT; the bottleneck is often not that the reward is not complex enough but that the per-interaction signal is not dense enough); on math tasks, the same performance needs about 1/10 the training steps of pure RL; prerequisite = the simulation environment must be real enough that the student explores states close to the deployment distribution; On-Policy Self-Distillation (OPSD): the teacher version sees privileged information (standard answers / verified solutions), the student version only sees the problem, aligned on the trajectories the student itself samples — it does not require automatically verifiable rewards but **cannot create new knowledge out of nothing**.
- **Maka design implications**: Multi-turn trajectory logs are the raw material for distillation — record dense intermediate signals at every step (per-turn tool calls / intermediate verification results) rather than only the final success/failure; the local-first positioning (being able to obtain users' multi-turn trajectories) makes it an ideal birthplace for on-policy distillation data; design a "teacher–student per-token distribution" data interface.
- **Writable design doc**: "dense-signal-and-distillation-data-interface.md (dense signal collection and the distillation data interface)"

## 8. Post-training Practical Points

### [KP-07-18] Post-training Practical Points: Common Pitfalls and the RAG/ICL/Post-training Synergy
- **Core in one sentence**: What a model learns depends on what the training signal taught it, and signal quality is mainly determined by **data and environment**, not algorithms; 8 common pitfalls + RAG/ICL/post-training act on different layers and should be used in combination.
- **Key design points** (8 pitfalls): ① over-relying on post-training to memorize facts (manage facts with RAG, post-training focuses on "how to use knowledge") ② introducing RL before the format is stable ③ improper reward-function design causing reward hacking (evaluate the final goal, not intermediate metrics) ④ ignoring simulation fidelity ⑤ over-training causing generalization decline (early stopping is crucial) ⑥ value-function collapse and insufficient exploration ⑦ underestimating RL compute cost (10–100×) ⑧ low training-data quality (SFT solidifies noise into parameters); core principle = **verify key assumptions with small-scale experiments before investing large-scale resources** (failing fast is more acceptable than failing at scale); synergy with RAG/ICL (ICL: zero-parameter instant adaptation; RAG: facts placed in dynamically updatable, traceable external knowledge; post-training writes high-dimensional perception / generation style / implicit decision policies — the selection basis is not only long-term task stability but whether **the capability can be adequately expressed by external symbols**); a robust system combination = factual evidence RAG, language-describable policies ICL, deterministic processes and hard constraints as programs, and capabilities hard to express in language and needing generalization as post-training.
- **Maka design implications**: The pitfall checklist converts directly into a design-principles document — factual knowledge goes into RAG/context (not into parameters), deterministic processes into programs, and only beyond the capability boundary do we export post-training; do a quality gate and training/evaluation isolation before data export (pitfall 8); the document states "when it is worth exporting training data and when fixing the prompt/skill is enough".
- **Writable design doc**: "post-training-practice-checklist.md (post-training practical points and the RAG/ICL/post-training synergy checklist)"

## Golden Quotes of This Chapter / Core Conclusions
- "Pretraining is reading ten thousand books (accumulating knowledge), SFT is a teacher coaching standard solutions step by step (imitating demonstrations), RL is doing problems oneself and polishing repeatedly based on right and wrong (learning by trial and error)."
- "**Data and environment matter more than algorithms**" — you only need to know how to use ready-made RL algorithms; what really separates people is simulation-environment fidelity and training-data quality; in many scenarios, if the SFT data quality is in place you may not even need RL.
- "**Priors > environment > algorithms**" (Yao Shunyu's 《The Second Half》).
- "**SFT memorizes, RL generalizes**" — a result measured in controlled experiments, not a universal property.
- "**Form before spirit**": SFT first establishes the "form" (format/structure/readability), RL then pursues the "spirit" (policy/generalization/reasoning).
- "**The grader is a proxy for intent; the stronger the trained model, the more likely it is to treat the proxy as the goal itself**" (reward seeking); "passing the grader" cannot automatically equal "the task is done".
- "**Dense signals beat sparse signals**" — the bottleneck is often not that the reward function is not complex enough, but that the signal provided by each interaction is not dense enough.
- "**The simulator's world knowledge is the training ceiling, and the simulator's systematic bias will be swallowed whole by the policy.**"
- "What a model learns depends on what the training signal taught it; and the quality of the signal is mainly determined by data and environment, not by algorithms."

## Reflection Questions from the Book (transcribed key points)
1. Catastrophic forgetting is especially thorny in Agent scenarios — besides LoRA, what other strategies can mitigate capability forgetting from fine-tuning?
2. A capability (domain knowledge) can be provided either by post-training or by few-shot — what criteria decide which path to take?
3. Distilling three model types (Chat/Reasoning/Agentic) has different difficulties — start from "what exactly is being distilled" (output style / thinking trajectory / the decision policy for interacting with the environment; which tokens in the trajectory should be learned and which are environment-returned and should not be; how late and how sparse the success/failure signal is).
4. In multi-turn agent interactions, reward attribution is worse than in single-turn (final success/failure is hard to attribute to turn 3 or turn 7) — how to design a reward-allocation strategy?
5. With a fixed budget ($10,000) to improve a customer-service agent, how to allocate among context and knowledge / Prompt-Skills / programmatic constraints / parameter training?
6. Autonomous model learning with no explicit reward function and scarce samples — how far is current RL from this ultimate goal? Where is the next breakthrough most likely to come from?
7. LoRA fine-tuning is not costly — is it possible to train a dedicated LoRA per user/customer company to write memory into parameters? In what scenarios does "writing memory into parameters" have an advantage over "storing it in a knowledge base" / backfire?
8. Weak-to-Strong Generalization: weak-model supervision signals can elicit strong models' latent capability — can we achieve reverse distillation of "a small model teaching a large model"?
9. "Correct process leading to a wrong result" vs "a wrong process getting lucky and producing the right result" — which deserves more reward? How to weigh this in multi-step tool-calling scenarios?
10. An evaluation set used both for evaluation and for post-training — does this violate the train/test separation principle? τ²-bench dynamic parameters and AndroidWorld parameterized templates partially mitigate it; how to balance using evaluation data for training value against maintaining independence?
11. "Form before spirit" — in practice, how to judge that SFT is "enough" and it's time to switch to RL?
12. ReTool's few very long responses stretch the training cycle (waiting for the longest response to finish, GPU utilization is low) — how to improve resource utilization in long-tail-response scenarios?
13. When training with an LLM-simulated environment, the target the agent exploits shifts from "real-environment rules" to "simulator biases and bugs" — what reward hacking is possible? How to guard against it?
