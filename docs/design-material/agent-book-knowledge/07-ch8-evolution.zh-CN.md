# 第 8 章 · Agent 的持续进化 —— 知识点提取

> 来源：`book/chapter8.md`。本章与 Maka headless 自进化方向最相关。章节主线：从运行轨迹中获得学习信号 → 持续进化的四种方法（知识/指令/程序/参数）→ 构建可长期运行的持续进化闭环（双循环、验证发布回滚、完成≠进步、安全边界、睡眠学习）。

## 一、从运行轨迹中获得学习信号

### [KP-08-01] 保存经历 ≠ 从经历中学习：持续进化的起点是"评价"
- **一句话核心**：把轨迹存进记忆不等于学会新行为，学习发生在系统主动完成"评价、对照、归纳、验证"之后，而不是日志写入磁盘的那一刻。
- **关键设计要点**：部署后模型不会因一次推理自动改变参数；上下文学习/压缩只在"当前任务内"适应；原始轨迹既长又嘈杂（含有效策略、偶然成功、错误归因、不可信输入），跨案例比较不会自动发生；与第三章分工（用户记忆沉淀"用户与世界是什么样的"=记得更多；本章经验学习沉淀"在什么条件下应该怎样行动"=从聪明变熟练）；为什么不能直接让模型每次任务后训练自己（生产环境缺干净学习信号、局部更新造成遗忘/漂移/安全退化、错误经验/注入被固化放大）；现阶段的工程路径=把"学习"构造成模型外围的自主系统（记录证据→验证结果与过程→跨轨迹提取共性→决定更新知识/指令/程序/参数→修改先成候选版本过回归与安全检查）。
- **Maka 设计启示**：直接支撑"Log is the Runtime"——日志必须记录证据，但"日志=运行时"不等于"日志=学习"；Maka 需在 Task Event Log 之上叠加评价/归纳/验证层；SelfCheck 产生证据与一次有界修复机会，真正的行为改变由独立进化循环基于跨轨迹证据触发，避免把"记下了"当成"学会了"。
- **可写设计文档**：《Maka Design: 从 Runtime Event Log 到经验学习（评价层设计）》

### [KP-08-02] 学习信号的三类来源：环境结果、过程规则、LLM Rubric
- **一句话核心**：可靠学习信号按"越能形式化越靠代码/环境真值，难以形式化才交给 LLM"分为三类。
- **关键设计要点**：**环境结果**（结果验证，来自环境真实状态：测试/类型检查/订单状态，通常比模型自我描述可靠）；**过程规则**（过程验证，检查达成结果的路径是否合规——"结果正确≠过程正确"：删掉失败测试也能通过）；**LLM Rubric**（质量验证，无单一正确答案维度用 LLM-as-a-Judge 配合预定义量表逐项给分、引用轨迹证据、证据不足明确表示不确定）；关键判据：**错误的评价一旦进入长期知识/系统提示/训练数据，影响会跨后续任务不断放大——"评价优先于总结"**。
- **Maka 设计启示**：headless 自主循环中 Tool Result 与终止事实天然对应"环境结果"信号；SelfCheck 层拆成确定性过程检查（业务规则/权限/动作序列）与 LLM Rubric 质量检查，确定性部分绝不交给模型猜测；只有经过验证的信号才能进入 FeedbackObservation。
- **可写设计文档**：《Maka Design: 学习信号三类来源与 SelfCheck 信号接入》

### [KP-08-03] 三层轨迹验证结构 + 维度化诊断：不把结果压成一个标量
- **一句话核心**：轨迹评价是"三层验证+维度化结构化诊断"——底层结果、中层过程、上层质量各司其职，任何一层不能退化成单一总分。
- **关键设计要点**：三层结构（底层结果验证器读测试结果/数据库状态/工具返回"是否真的办成"→中间过程验证器查业务规则/权限/动作序列"是否以允许方式办成"→上层质量验证器按 Rubric 评语言与策略"是否办得合适"）；越靠下越依赖代码与环境真值；验证结果=**结构化诊断而非标量**（如"任务部分成功、规则遵从通过、一处无证据陈述、一处虚假承诺、回复重复解释政策三次"——维度化保留问题性质与证据位置）；维度化才能定位根因（无证据陈述→缺知识/缺引用要求/模型能力不足；虚假承诺→改提示词 vs 加"回复与工具状态一致性检查"）；LLM 验证器需校准（专家标注小批轨迹、高风险低置信度交第二模型或人工、模型版本变更后重跑校准集）；**验证器只负责给评价与证据，"应修改 Agent 哪个部分"由独立诊断与进化模块决定——避免同一个模型既当裁判又直接改写规则**。
- **Maka 设计启示**：SelfCheck 应当是"三层+多维度"验证器而非单一通过/失败；输出像"结构化诊断"写入 Task Event Log（含证据定位）供后续 Decision 阶段决定修知识/修提示/改 Harness；验证器与"生成修改"模块分离（裁判与进化解耦）。
- **可写设计文档**：《Maka Design: SelfCheck 三层验证结构与维度化诊断协议》

### [KP-08-04] 客服 Agent 轨迹评价 Rubric 七维度
- **一句话核心**：可诊断的 Rubric 覆盖"底线约束+服务质量"两类维度，比单一"用户是否满意"更有区分价值。
- **关键设计要点**：七维度——任务结果（核心诉求是否解决，证据=最终环境状态/工具结果）、规则遵从（是否违反政策/权限/流程，证据=政策库/动作轨迹）、隐私边界（是否泄露不应提供信息，证据=回复文本/数据访问记录）、事实可靠性（陈述是否有知识或工具结果支持，证据=引用来源/工具返回）、**承诺—行动一致性**（声称完成的操作是否真实发生，证据=回复与工具日志对照）、表达质量（自然简洁避免重复模板化）、合规变通（原方案不可行时是否找到允许替代路径）；前五项约束底线、后两项服务质量；**"承诺—行动一致性"尤其适合 Agent 场景**（传统文本评价只读最终回复会把"我已提交退款"当好服务；轨迹评价继续检查是否真调用退款工具、调用是否成功、订单状态是否改变）。
- **Maka 设计启示**：七维 Rubric 是 SelfCheck 具体化蓝本；"承诺—行动一致性"直接映射 Log-is-the-Runtime——把 LLM 声称操作与日志中真实工具调用、终止事实逐条对照，恰好是"Feedback is not fact authority"落地方式。
- **可写设计文档**：《Maka Design: SelfCheck 默认 Rubric（承诺—行动一致性优先）》

## 二、Agent 持续进化的四种方法

### [KP-08-05] 四种更新载体的选择依据与比较
- **一句话核心**：选择更新方式的首要依据不是经验出现多久，而是"**目标能力能否被某种载体自然表达**"；四种方式不互斥、可协同。
- **关键设计要点**：**经验知识库**（事实/经验规律/例外与来源——更新快可追溯按需检索，依赖检索与模型正确应用）；**Prompt 与 Skill**（需理解语境/例外/优先级但仍可自然语言说明的判断原则——可解释作用范围可控，易膨胀冲突被忽略）；**程序与 Harness**（可确定解析/可执行验证/高风险硬约束——可测试执行稳定成本低，开发维护成本较高）；**模型参数**（高维感知/生成风格/隐式策略——泛化强推理开销低，更新回归成本高）；协同示例（医疗影像参数识病灶+知识库最新指南+代码算风险指标；客服自然语气靠后训练、企业政策靠知识与 Skill、关键合规靠服务端代码）。
- **Maka 设计启示**：headless Decision 输出需明确"落到哪种载体"分流策略（工具结果类证据→经验知识/程序、SelfCheck 反馈→Prompt/Skill 候选、风格隐式策略→参数）；四载体对应不同发布回滚成本，直接影响预算与 continuation 设计。
- **可写设计文档**：《Maka Design: 自进化四载体分流与发布路径》

### [KP-08-06] 将经验沉淀为知识：三层数据 + 五步提炼管道
- **一句话核心**：把多次运行中反复出现的经验整理成可检索知识文档；"记录与整理分开"，证据不可变、知识可重写。
- **关键设计要点**：知识来源与第三章不同（从行动轨迹提取"在什么条件下应该怎样做"而非"用户与世界是什么样的"）；系统保留**三层数据**（不可变原始轨迹（审计）→单次运行分析（本次成败与候选教训）→多轨迹比较/聚类/归纳出的 Markdown 知识文档（适用场景/推荐策略/禁止做法/例外/证据来源/最近验证时间））；五步提炼管道（①保存不可变轨迹与环境结果②单次运行结构化分析③按任务族聚类建"哪些轨迹支持/反驳"证据表④达到支持门槛才写正式文档⑤在未参与提炼的新任务上测迁移）；Reflexion 自然语言反思可参与生成候选教训但**反思本身不是证据**——只有与环境结果相符、跨轨迹支持、新任务正向迁移的才进正式文档。
- **Maka 设计启示**：Task Event Log 是天然"不可变原始轨迹层"；实现"单次 TaskRun 分析"与"跨 TaskRun 聚类归纳"两个投影层产出可检索经验文档；"Log is the Runtime"保证重归纳不篡改原始证据、环境版本变化时可按来源精确撤销结论。
- **可写设计文档**：《Maka Design: TaskRun 经验知识提炼管道（三层数据）》

### [KP-08-07] 将经验写成指令：系统提示学习、最小 diff 与 Skill 学习
- **一句话核心**：当规律可用自然语言清楚表达且被多条轨迹反复证实，可把经验从"可参考"提升为"应遵守"的指令；修改应是最小可审计 diff。
- **关键设计要点**：作用域分层（作用于几乎所有任务的规则进系统提示词；只在某领域/项目/工具生效的复杂流程写成按需加载 Skill/项目指令文件）；Karpathy"系统提示学习"（人类第三种学习=想通方法后用语言提醒未来的自己；与 RL 区别=前者编辑文字、后者梯度下降）；修改规范（最小 diff、注明作用域、检查与现有规则矛盾、在"触发失败的边界案例"和"旧任务保留集"上同时评估）；离线优化路线（DSPy/OPRO/GEPA 面向评估集批量搜索）vs 生产系统最小 diff（持续维护、来源/审计/快速回滚）；Skill 学习（候选 Skill 说明何时加载/前置条件/操作步骤/已知陷阱/验证方法与来源轨迹；相同流程优先局部 patch、只有新独立能力才建新目录）；"AI 味"反馈拆成可检查模式（可正则/统计判断的进确定性检查、难判断的先人工金标集校准再入 Skill）；完整生命周期=**反馈→首个错误归因→Skill 或接口规范→合成数据→参数候选→边界集与保留集验证→灰度发布或回滚**。
- **Maka 设计启示**：FeedbackObservation→Decision 环节直接产出"最小 diff 候选指令"；AHE 目标协议的"可审计变更契约"与最小 diff/来源 manifest 一致；Skill 化是"Context is not history"的具体承载（可复用判断原则写成按需加载 Skill 而非塞进每次上下文）。
- **可写设计文档**：《Maka Design: 系统提示/Skill 最小 diff 学习与发布门槛》

### [KP-08-08] 将经验写成程序：可验证工作流、可证伪变更契约与 Harness 自修改
- **一句话核心**：当经验是稳定、重复、可验证的操作时，把轨迹"编译"成带参数、状态检查和版本信息的小程序；自我修改必须走可审计的软件发布流程。
- **关键设计要点**：可修改对象远不止新工具（操作层浏览器轨迹→参数化工作流、控制层工具路由/重试/熔断/压缩策略、验证层参数检查/状态验证器/回归测试、架构层新增 Reviewer Agent）；**浏览器工作流六步生命周期**（①捕获轨迹（动作参数+定位证据——定位信息只能用于再找元素不能证明完成）②参数化（字面量→模板变量）③定义状态检查（动作前/动作后/最终状态——**动作成功≠任务成功**，最终检查必须读真实页面或后端状态）④候选验证（沙盒重置完整回放全过才 validated；无重置回调的副作用任务只存候选供审计）⑤匹配与回放（Playwright 直执行不需逐步调 LLM）⑥失效与重学）；**危险假象：回放覆盖率 100% 但字段为空、任务从未完成——必须同时具备动作前验证、动作后验证和存前独立验证**（PreAct 报告重复任务 8.5-13 倍端到端加速）；**自我修改=可审计发布流程**（稳定版本建候选分支→Coding Agent 最小补丁→静态检查/单元测试/安全扫描/失败轨迹重放/旧任务回归→灰度部署；不覆盖稳定版本）；**每个修改请求应是可证伪的变更契约**（失败证据/推断根因/归属 Harness 组件/候选修改/预期修复行为/可能受损行为/分别验证两者的用例——AHE 概括为组件/经验/决策三层可观测性）；Self-Harness（候选生成器输入含"必须保留的成功行为+此前被拒绝的修改记录"构成有边界候选空间）。
- **Maka 设计启示**：headless"程序载体"自进化内置"变更契约"（每个自修改请求声明失败证据/预期修复/可能回退先过验证再进 canary）；浏览器工作流"动作前/后/最终三重状态检查"可类比为 Maka 对工具调用结果的验证契约，防止"调用了≠办成了"。
- **可写设计文档**：《Maka Design: 可证伪变更契约与 Harness 自修改发布流程》

### [KP-08-09] 将经验写入参数：表示性质决定载体，参数与外部方法协同
- **一句话核心**：知识/指令/程序都要求能力能被外部符号完整表达；高维感知、语言风格、隐式策略等必须走后训练写进模型参数。
- **关键设计要点**：难以符号化能力（医疗影像理解/自然的语音韵律/消除"AI 味"/长程规划——弯引号作用域判断处在中间地带：语法边界用程序解析、语境例外用 Skill、跨任务识别习惯才用后训练内化）；**是否参数化不由"任务是否长期稳定"单独决定：稳定性影响更新频率与成本，但能力的表示性质决定主要载体**；持续进化视角三种训练数据（高质量示范→SFT、明确偏好→成对数据、有可靠环境奖励交互→RL——进入训练前去隐私/滤错误轨迹/保留独立回归集，训练后检查通用能力与安全对齐是否遗忘）；参数学习与外部方法协同（特殊字符串复制=参数学逐 token 保真度+工具接口字节级校验与可回滚失败诊断）。
- **Maka 设计启示**：headless 自进化第一版不必实现参数载体，但设计中预留"参数内化"出口——SelfCheck 积累的 before/after 反馈对可转化为偏好训练数据，与"先验证、后入训"兼容。
- **可写设计文档**：《Maka Design: 参数化载体的预留接口与数据规范》

### [KP-08-10] 从更新产物到更新"更新方法"：五层优化尺度与可信根
- **一句话核心**：除"经验写到哪里"外还有正交轴——优化对象可从产物内容逐层扩大到产生/管理/验证产物的方法；不是五种新载体而是五种搜索尺度。
- **关键设计要点**：优化对象逐层扩大（**单条规则或记忆→结构化上下文→工作流→Harness 代码→产生候选方案的优化器代码**）；最内层（只改产物内容）作用面小易归因回滚应是默认选择，但反复重写整份 Prompt/记忆会退化（重要细节多轮改写后消失、相互制约条件被合并成过度抽象原则）；ACE（Agentic Context Engineering：上下文维护成带稳定标识符的条目集合、生成/反思/整理模块提增量更新、确定性逻辑合并去重而非每轮重写）；MCE（Meta Context Engineering：内外双循环——内层给定管理方法优化任务上下文产物、外层修改"搜索/选择/过滤/格式化"这些上下文操作本身）；AFlow/Meta-Harness（把工作流/Harness 表示为代码图按执行反馈搜索组合）；**优化层级并非越高越好**（明确可定位到单一组件的故障优先做可审计局部补丁，只有长期无法解决跨组件问题或管理方法本身成瓶颈才升级）；**可信根**（无论上升到哪层，评价器、权限边界和留出测试必须位于可修改范围之外——搜索空间越大可信根越重要）；Hermes 实验（自主阅读→对照→选题→修改→验证；前三轮被独立审查拒绝、每轮拒绝作为学习信号返回、第四轮接受——**拒绝是闭环的一部分而非失败终点**）。
- **Maka 设计启示**：自进化的"meta"方向遵循"默认最内层局部补丁，只有证据充分才升级尺度"；SelfCheck/预算/审计日志必须位于可修改范围之外（不可自我修改可信根）；ACE"稳定标识符条目集合"可作为 Maka 上下文管理进化蓝本。
- **可写设计文档**：《Maka Design: 自进化优化尺度分层与可信根边界》

## 三、构建可长期运行的持续进化闭环

### [KP-08-11] 在线执行与离线进化的双循环
- **一句话核心**：四种更新方式只有进入同一个自主循环才成为持续进化；生产系统采用"**在线只执行+记录证据、离线聚合+诊断+生成候选+验证发布**"的双循环，中间用版本化经验库与评估集连接。
- **关键设计要点**：双循环结构（在线执行循环只完成任务并记录证据、**不直接改写正式 Agent**；离线进化循环聚合轨迹/诊断根因/生成候选/过验证门槛发布新版本）；Voyager 三机制（自动课程生成器/技能库/迭代提示机制——3.3 倍独特物品、2.3 倍探索距离、科技树快 15.3 倍）；从问题定位到经验沉淀（同一表面问题可能对应不同修改方式——编造事实=缺知识 vs 提示没要求引用；虚假承诺=指令纠正 vs Harness 强制检查——进化模块先定位根因再选最小/最易验证/最易回滚修改对象；证据不足的偶发故障不立即触发学习继续积累样本）；升级路径随经验增加而变化（新策略先作经验文档供检索→多案例反复验证后升级：可自然语言描述的规则→Skill、步骤稳定无需理解→工具代码、反映广泛隐式决策→后训练）。
- **Maka 设计启示**："Log is the Runtime+Task Event Log"正是双循环在线侧；headless 明确"在线循环不改正式 Agent"，经验沉淀放离线/后台循环；TaskRun 可中断可恢复能力为离线聚合与候选验证提供持久化基础。
- **可写设计文档**：《Maka Design: 在线执行—离线进化双循环架构》

### [KP-08-12] 验证、发布与回滚：候选区、灰度、Harness 更新≠受益、分层评估
- **一句话核心**：所有修改先成候选而非覆盖生产；验证通过后灰度发布、关键指标恶化自动回滚；评估必须区分"更新器提出好修改"与"任务 Agent 真正受益"。
- **关键设计要点**：四类载体验证差异（知识文档验证检索后是否提高新任务表现；Prompt/Skill 检查边界案例与旧任务回归；程序在沙盒与重置环境跑测试；参数检查遗忘/安全/分布外）；验证后仍走灰度、指标恶化自动回滚到已知安全版本；**Harness 更新能力（harness-updating）≠ Harness 受益能力（harness-benefit）**——一个 Skill 写得完全正确但弱任务模型不在合适场景加载或加载后不遵循，最终成绩看起来"没有进化"，不能只用端到端分数反推更新器好坏；**分层评估四指标**（候选修改有效率/产物激活率/遵循成功率/留出任务增益）；**双向模型替换定位瓶颈**（固定候选 Harness 只换任务模型：强模型受益而弱模型从不激活→瓶颈在检索/路由；都能激活但只有强模型正确执行→瓶颈在指令遵循/长程规划；所有模型都退化→怀疑修改本身）；长期评价至少看五类结果（**回退**/泛化/Token 效率/安全性/长期工程质量）。
- **Maka 设计启示**：headless 内置"候选区→canary→正式"发布状态机与自动回滚；SelfCheck 只能改行为候选；自进化评估同时采集"候选修改有效率、激活率、遵循成功率"（呼应 Log-is-the-Runtime 可观测性优势）。
- **可写设计文档**：《Maka Design: 候选发布状态机、自动回滚与分层评估指标》

### [KP-08-13] 可验证闭环的边界：当"完成"不等于"进步"
- **一句话核心**：可验证闭环在 Coding/工具调用/业务状态变更上最可靠；开放式科研、战略规划、复杂产品设计中"流程完整≠推进真实目标"。
- **关键设计要点**：自动科研暴露问题三类（**实现漂移**——方案变难后逐渐退回训练数据中更熟悉但偏离假设的普通实现；**认识论上的过度乐观**——信号可能只是噪声却解释结果宣布发现、阴性结果被忽略；**隐性判断力不足**——不知什么基线重要/哪个异常值得追踪/何时放弃假设）；改变证据与监督结构四条（**结论与证据分离**（引用/数字/方法/结论分别记录证据来源、最终文稿只是证据图的一种呈现）；**保留负面结果**（失败实验/被拒候选/停止原因写入不可变日志与成功同等可检索）；**维护搜索多样性**（候选池保留暂时低分但不同质分支避免收敛成单一易得分模板）；**让人类在更高层介入**（定义问题/审查评价标准/解释反常/决定何时停止））；核心判据：**持续进化的上限取决于系统能否评价它真正关心的目标，而不只是最容易测量的代理指标**。
- **Maka 设计启示**：直接呼应"Feedback is not fact authority"——把"完成"与"进步"分开（SelfCheck 通过/任务完成是日志中的事实，是否构成"进步"需要长期指标与人工高层判断）；自进化默认只覆盖"结果可自动验证"任务族，开放式任务保留人类在问题定义与评价标准层介入。
- **可写设计文档**：《Maka Design: 完成≠进步的边界与开放任务人工介入协议》

### [KP-08-14] 持续进化的安全边界：三道隔离
- **一句话核心**：自我进化系统除了验证"是否更强"，还必须限制"谁能改什么、依据来自哪里"；错误经验、注入和劣质验证器都可能把一次错误变成长期风险。
- **关键设计要点**：风险形态（提示注入若被总结成经验可跨会话反复生效；自动搜索恶意包封装成工具从一次沙盒扩散到所有任务；有缺陷的验证器持续批准看似进步实际退化的候选）；**第一道边界——证据与指令隔离**（原始网页/工具输出及其 LLM 摘要都属不可信证据，不能当指令执行、不能直接纳入 Skill 长期能力；LLM 总结只是提高可读性的转换不是净化过程；按固定 schema 提取主张/原文位置/采集时间保留原文来源；提取字符串绝不能作为指令执行；模型置信度只是未经验证估计不能当批准门槛；候选过确定性 schema/允许列表/来源检查以版本化 PR 提交；独立于生成者的 reviewer 对照原始证据审查、高风险 Skill 人工批准）；**第二道边界——候选能力与正式能力隔离**（新知识/Prompt/Skill/程序/参数先入不可服务真实流量的候选区；新代码与外部依赖过沙盒/权限检查/供应链扫描/行为测试全过才服务真实流量）；**第三道边界——安全机制不可自我修改**（业务 Agent 可改 Prompt/Skill/知识库/工具，但不能修改批准自身更新的验证器/测试用例/发布门槛/审计日志/稳定版本备份——否则只需降低测试阈值或删失败用例就能把退化伪装成进步）。
- **Maka 设计启示**：三道边界原样映射进 Maka——Event Log 中"不可信证据"（工具输出/网页/用户输入）与"已批准指令"分库；headless 候选目录与正式目录隔离；SelfCheck/验证器/审计日志/预算配置不可被 Agent 自修改——与 AHE 目标协议和"Log is the Runtime"（日志不可变）天然契合。
- **可写设计文档**：《Maka Design: 自进化安全边界（三道隔离与可信根）》

### [KP-08-15] 睡眠学习：整合、遗忘与能力保鲜
- **一句话核心**："睡眠学习"是对离线整合的认知类比（不必夜间运行）——在线 Agent 只完成当前任务并追加不可变证据，后台进程在空闲/门控条件下批量整合、合并、冲突消解、候选更新并回归。
- **关键设计要点**：五步周期——①**触发**（时间间隔/新增轨迹数/存储容量/错误频率门槛+无高优先级在线任务）②**定向**（读正式知识/Prompt/Skill 目录及版本了解已有能力与不可修改边界）③**采集与整合**（从近期已评价轨迹找新信号/合并重复/标记冲突与适用条件/优先生成局部补丁）④**验证与审批**（迁移集/保留集/安全集评估，高风险待人工批准）⑤**修剪与索引**（更新索引，长期不用或被新证据推翻的标过期/归档/删除，保留来源与回滚版本）；把采集与整理分开的价值（防止偶发成功/网络故障/恶意输入立刻改写长期能力；可用更大批量更便宜模型做整理）；Claude Code 自动记忆（MEMORY.md 索引+按主题拆分详细文件、会话启动只加载索引有界前缀其余按需、索引接近上限要求合并或移走细节）；Hermes 后台进化（有界 MEMORY.md/USER.md+SQLite/FTS5 历史会话检索返回原始消息而非 LLM 摘要避免检索与生成混成不可审计步骤+按需 Skill；工具调用多/从错误死路恢复/收到用户纠正/发现非显然工作流时后台复盘创建或局部修订 Skill；独立 Curator 跟踪使用/陈旧/归档、空闲期确定性修剪、变更前存快照可回滚）。
- **Maka 设计启示**：headless Task Event Log 是睡眠学习完美输入源——后台"整理进程"在预算允许/空闲时对 TaskRun 日志做整合与修剪产出经验文档/Skill 候选并过审批；"Log is the Runtime"保证整理不改写原始证据、错误整理按快照回滚。
- **可写设计文档**：《Maka Design: 睡眠学习周期（触发—定向—整合—验证—修剪）》

## 本章金句 / 核心结论
- "**保存经历不等于从经历中学习**"——学习发生在系统主动完成"评价、对照、归纳、验证"之后，而不是日志写入磁盘的那一刻。
- "用户记忆让 Agent **记得更多**，经验学习才让它**从聪明变得熟练**。"
- "持续进化的起点不是'总结'，而是'**评价**'。"
- "越靠下的指标越应依赖代码和环境真值，只有难以形式化的部分才交给语言模型。"
- "**反思本身不是证据**；只有与环境结果相符、得到跨轨迹支持并在新任务上显示正向迁移的内容，才应进入正式经验文档。"
- "选择更新方式的首要依据不是经验出现了多久，而是**目标能力能否被某种载体自然表达**。"
- "把'自我修改'转化为可审计的软件发布流程。"
- "**动作执行成功与任务成功是两件事**"；"回放覆盖率 100% 不代表任务完成"——必须同时具备动作前验证、动作后验证和存前独立验证。
- "持续进化的完整生命周期是：反馈 → 首个错误归因 → Skill 或接口规范 → 合成数据 → 参数候选 → 边界集与保留集验证 → 灰度发布或回滚。"
- "**Harness 更新能力 ≠ Harness 受益能力**。"
- "**单元测试全部通过，只证明当前可观察行为满足测试，并不证明代码库数月后仍易于维护。**"
- "持续进化的上限，最终取决于系统能否评价它真正关心的目标，而不只是最容易测量的代理指标。"
- "一个 Agent 只需降低测试阈值或删除失败用例，就能把退化伪装成进步"——所以安全机制不可自我修改。
- "拒绝不是失败终点，而是自我改进闭环的一部分"（Hermes 实验）。

## 书中思考题（转录要点）
1. 一条经验由三次成功+一次失败轨迹支持，失败发生在较新 API 版本——判断是经验被推翻还是适用条件变化？
2. 用户满意度上升但规则违规率也上升——为什么不能把满意度当单一学习信号？如何设计护栏指标？
3. 同一"虚假承诺"问题可通过 Prompt、Harness 检查或参数训练缓解——依据哪些证据选择修改位置？
4. Agent 能修改工具和验证器却不应修改批准自身更新的可信根——如何划分这两部分权限与代码边界？
5. 经验知识库不断增长后检索错误和知识冲突抵消学习收益——如何设计版本、时效和淘汰机制？
6. 参数学习擅长语言风格难保证硬性业务规则——为医疗客服设计参数/知识/Skill/代码约束协同的持续进化方案。
