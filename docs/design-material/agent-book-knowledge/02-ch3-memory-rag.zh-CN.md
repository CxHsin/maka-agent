# 第 3 章 · 用户记忆和知识库 —— 知识点提取

> 来源：`book/chapter3.md`。两条主线：**用户记忆**（个体个性化、持久可审查）与**知识库/共享知识**（集体知识），共用向量检索、知识压缩等底层技术，同面临信息冲突、知识过期、检索不准。

## 一、用户记忆系统

### [KP-03-01] 用户记忆的本质：从对话到预测模型
- **一句话核心**：用户记忆不是"记录用户说过每句话"，而是投入额外 LLM 算力，把散落在冗长对话里的关键信息显式提取、压缩成"关于用户的简洁而有效的预测模型"。
- **关键设计要点**：三个关键特征——**选择性**（只留对未来有用的事实）、**抽象化**（提炼通用偏好而非绑定某次）、**结构化**（Markdown/JSON 便于检索）；对比上下文学习：用户记忆**持久、可审查**，上下文学习**临时、会话结束即消失**。
- **Maka 设计启示**：Local memory 应定位为**由 Runtime Event Log 派生的投影**——记忆不是把对话原文追加进存储，而是由后台 LLM 任务从日志中"提取+压缩"出可审查的持久事实。
- **可写设计文档**：《Maka Local Memory：从 Runtime Event Log 到持久记忆的提取管道设计》

### [KP-03-02] 记忆能力评估：三层次框架
- **一句话核心**：把记忆能力分解为"基础回忆→多会话检索→主动服务"三个递进层次，作为衡量各项检索技术贡献的标尺。
- **关键设计要点**：学术基准 LoCoMo（约 300 轮、最多 35 会话）；八项能力（个人信息保留/偏好追踪/上下文切换/记忆更新/多会话连续性/复杂思考/时间感知/冲突解决）；**第一层基础回忆**（精确返回直接提供的信息）、**第二层多会话检索**（跨对象跨时期检索并推理判断）、**第三层主动服务**（综合很久以前的会话提供预见性帮助，如订国际航班时主动关联数月前护照信息并预警过期）。评估方法：每层 20 用例、只保留记忆状态不可回看原始会话、LLM-as-a-judge 评分。
- **Maka 设计启示**：为 Local memory 建立同款三层次评估基线（SQLite 测试夹具 + LLM-as-a-judge）；"只保留记忆、不回看原始对话"印证"Context is not history"——评估的就是投影而非原文。
- **可写设计文档**：《Maka Local Memory 三层次评估框架与回归测试方案》

### [KP-03-03] 记忆设计维度：层次结构（放哪里）与认知科学基础（存什么）
- **一句话核心**：记忆设计三套正交维度——**放哪里（轨迹/长期记忆/业务状态）、怎么存（存储格式）、存什么（情景/语义/程序）**。
- **关键设计要点**：**轨迹**=一次运行完整历史（append-only 只增不改、审计用）；**用户长期记忆**=跨会话持久存储（偏好/摘要/知识点）；**业务状态**=开发者定义的高层状态抽象；认知映射：工作记忆↔上下文窗口、情景记忆↔语义记忆↔程序记忆；轨迹不可变、工作记忆是动态子集。
- **Maka 设计启示**：Runtime Event Log=轨迹层（append-only、可审计）；Local memory=跨会话投影；SQLite 可分别建模：`events`（只增）、`memories`（可改可淘汰）、`task_state`（业务状态）；schema 带 `kind: episodic|semantic|procedural`。
- **可写设计文档**：《Maka 记忆分层与 Runtime Event Log 存储模型（轨迹/长期记忆/业务状态）》

### [KP-03-04] 用户记忆的四种存储格式
- **一句话核心**：同一条用户信息可按粒度与结构复杂度分四级渐进式存储——Simple Notes、Enhanced Notes、JSON Cards、Advanced JSON Cards，核心张力是"简单性 vs 表达力"。
- **关键设计要点**：Simple Notes=最小不可再分事实（O(1) 极低开销、关联性丢失）；Enhanced Notes=完整上下文段落（语义完整、更新复杂）；JSON Cards=类别→子类别→键值对（支持部分更新、刚性结构）；Advanced JSON Cards=每卡片加 **backstory**（信息来源叙事背景）、**person/relationship**（解决消歧——"张医生"同时是牙医和心脏科医生）和时间戳。实践标准：**关键且少量**用 Advanced JSON Cards 保可检索性，**大量且非关键**用 Simple Notes 控成本，多数生产系统混合模式。实验 3-2：Simple Notes 成本最低但跨会话关联失分；Advanced JSON Cards 消歧最好但维护调用更贵更慢。
- **Maka 设计启示**：SQLite `memories` 表加 `format` 字段实现混合模式；利用 UPDATE 语义实现 JSON Cards 部分更新；四种格式可做成可切换写入策略供评估复现。
- **可写设计文档**：《Maka Local Memory 存储格式与混合模式策略（SQLite schema 设计）》

### [KP-03-05] 进阶知识表示：可执行代码（User as Code）
- **一句话核心**：把用户记忆的"表示介质"从文本换成**可执行代码**——用带类型 Python 对象保存状态、函数编码约束规则，聚合/冲突发现/约束执行从 LLM"心算"变成确定性代码。
- **关键设计要点**：两阶段更新=**记忆阶段**（每次会话后把事实追加到**只增不删的事实日志**）+ **结构化阶段**（周期性从完整日志重新生成整份带类型 Python）——本质是数据库经典模式 **"预写日志 WAL + 周期性检查点 checkpoint"** 首次用于 LLM 记忆。三大确定性能力：聚合统计（正确率接近 100%）、冲突发现（药物过敏交叉比对）、约束执行（护照距出发不足 180 天自动报警）。出处：*User as Code: Executable Memory for Personalized Agents* (arXiv:2606.16707)。
- **Maka 设计启示**：TypeScript 下把关键规则化本地记忆建模为可校验类型化对象+纯函数约束；"WAL+checkpoint"直接对应 Maka 的 Runtime Event Log（只增证据）+ Compaction/检查点（结构化投影）。
- **可写设计文档**：《Maka 可执行记忆：将本地记忆表示为类型化状态与约束函数》

### [KP-03-06] 记忆框架案例：Mem0 与 Memobase
- **一句话核心**：两个开源记忆框架给出两种理念——Mem0 从"写入时消歧"演进到"仅追加写入+检索时推理"，Memobase 聚焦"用户画像+事件记忆"。
- **关键设计要点**：Mem0 v3（仅追加 ADD、语义+BM25+实体三路混合检索+时间排序）：LoCoMo 71.4→92.5、LongMemEval 67.8→94.4，避免错误 UPDATE/DELETE 丢历史、减 LLM 调用；Memobase=Profile（可配置槽位）+ Event Memory（时间线）+ 缓冲批处理摊薄成本。参考架构：情景/语义/程序三类长期记忆 + 工作记忆一层；**现实框架只实现其中一两种——按业务需要取舍比追求大而全更符合工程现实**。
- **Maka 设计启示**：Mem0 v3"仅追加+混合检索+时间排序"与信条 1/2 高度同构；SQLite 存"带时间戳多版本事实 + FTS/向量/实体三路检索"；记忆提取做成异步、批量、可暂停/恢复的后台任务。
- **可写设计文档**：《Maka Local Memory 冲突处理策略：写时消歧 vs 检索时推理（对比与选型）》

### [KP-03-07] 记忆压缩与整理机制
- **一句话核心**：长期累积记忆会"存储爆炸"并拉低检索准确率，需多层次压缩策略——重要性筛选、聚类摘要、抽象泛化、版本化冲突检测；这是**存储层**整理算法，与第二章单次会话的上下文压缩作用层次不同。
- **关键设计要点**：重要性评分四因素（访问频率/时间衰减/情感强度/信息独特性）；聚类（相似记忆分组生成代表摘要、原始存档二级存储）；抽象泛化（具体→语义/程序记忆）；冲突检测用**版本化方法**（保留历史版本+标记最新版；当前地址只留最新、工作经历保留完整历史）。
- **Maka 设计启示**：记忆整理做成**离线/后台批任务**，且遵守信条 2——整理只改变"下一次推理看到什么"（投影/检索视图），不删除 Event Log 原始证据；被压缩的详细记忆进二级存档而非物理删除。
- **可写设计文档**：《Maka 记忆压缩与定期整理后台任务设计（重要性评分/聚类/版本化）》

### [KP-03-08] 隐私保护：日志脱敏
- **一句话核心**：让 Agent 既能用用户信息提供个性化服务，又不让敏感数据暴露在 LLM 上下文与系统日志中——用**本地小模型**做 PII 检测与脱敏（而非云端 API）。
- **关键设计要点**：为什么必须本地部署——日志本身可能含敏感信息，发云端脱敏违背隐私初衷；通过 Ollama 调本地 Qwen3 0.6B；识别三类敏感内容（结构化/半结构化/自然语言表达）；JSON Schema 结构化输出；LLM 脱敏召回率 95%+、显著降低假阳性；超高吞吐用正则+LLM 混合。
- **Maka 设计启示**：Event Log 是"日志即运行时"，隐私风险集中——应在事件进入日志/上下文之前加**脱敏前置过滤器**（本地小模型+正则混合），保留"脱敏后仍可审计"的映射（敏感值替换为占位 token 而非不可逆删除）；脱敏结论带置信度、允许人工复核（不盲目信任单次小模型判断）。
- **可写设计文档**：《Maka 日志脱敏与隐私边界设计（本地 PII 检测、脱敏前置、审计映射）》

## 二、RAG 基础

### [KP-03-09] RAG 管道与文档分块（Chunking）
- **一句话核心**：RAG = 检索相关片段→注入上下文→LLM 基于上下文生成；**检索器质量决定上限——检索不到相关片段，LLM 再强也无米之炊**。
- **关键设计要点**：三种分块策略——固定大小（512 token、重叠 50-100）、**递归/结构感知（生产系统最常用默认）**、语义切分（嵌入相似度断崖处下刀）；块大小常见起点 256-1024 token、重叠 10%-20%；**分块固有缺陷：切断片段与原始上下文联系**（"该公司收入增长 3%"——哪家哪季？），由上下文感知检索（KP-03-17）解决。
- **Maka 设计启示**：本地知识库入 SQLite 先做结构感知分块，**写入时保留"来源上下文元数据"**（原文位置/标题/时间戳）；避免把"Context is not history"误读为"块即全部"。
- **可写设计文档**：《Maka 知识库入库管道：分块策略与来源元数据设计》

### [KP-03-10~11] 稠密嵌入 与 稀疏嵌入
- **KP-03-10 稠密嵌入**：词/句→高维向量，余弦相似度度量方向（语义）非长度；Word2Vec 无法处理一词多义，BERT/BGE-M3 靠自注意力做上下文感知表示；**ANN 索引**（ANNOY 树 vs HNSW 图：构建速度/内存/增量更新/精度对比——选索引策略与选嵌入模型同等重要）。
- **KP-03-11 稀疏嵌入**：TF-IDF→BM25（词频饱和 k1 + 长度归一化 b）；倒排索引；精确匹配适合技术代码/人名，读不懂同义表达；学习型稀疏（SPLADE/BGE-M3 稀疏分支）介于稀疏与稠密之间。
- **Maka 设计启示**：本地优先选本机可跑的上下文感知嵌入模型（BGE-M3 类）；SQLite 内置 **FTS5** 实现 BM25 风格全文检索（人名/卡号/命令/术语查询），与向量检索互补；嵌入是"派生索引"应可重建。
- **可写设计文档**：《Maka 向量检索基础设施：嵌入模型与 ANN 索引选型》＋《Maka 本地全文检索：SQLite FTS5/BM25 落地与中文分词》

### [KP-03-12] 混合检索：融合、神经重排序与质量指标
- **一句话核心**：稠密懂语义漏关键词、稀疏精确读不懂同义词——混合检索两引擎都跑，难点在整合分布迥异的得分。
- **关键设计要点**：三阶段流水线（并行检索→结果融合→神经重排序）；融合方法：归一化加权求和 或 **RRF 倒数排名融合**（`Σ 1/(k+rank)`，k≈60，只看排名丢相关性信号）；重排序用 Cross-Encoder（拼接查询+文档逐词比对）精度远高 Bi-Encoder，**重排序不替代融合**；质量指标 recall@k（书口径=hit rate/success@k）、MRR、nDCG；"没有哪种单一检索策略在所有场景可靠，稠密+稀疏+重排序组合才是生产级"。
- **Maka 设计启示**：本地检索"FTS5(BM25)+向量"双路+RRF 融合，重排序作为可选慢路径（仅关键查询启用控延迟）；用 recall@k/MRR 在评估集上度量使检索质量可回归。
- **可写设计文档**：《Maka 混合检索流水线：FTS5+向量+RRF+可选重排序》

## 三、超越扁平文本：知识组织与检索

### [KP-03-13] 结构化索引：RAPTOR 与 GraphRAG
- **一句话核心**：扁平分块忽略知识内在结构与跨文档关联；模型注意力是"基于相似度的软检索"而非能总结归纳的思考引擎——必须在**索引阶段投入计算资源主动提炼、抽象、结构化**。
- **关键设计要点**：两个案例（100 只猫计数、Xfinity 优惠规则）说明 top-k 截断与"统计/归纳"天然矛盾，需预生成摘要/规则并索引。**RAPTOR**=树状层次（聚类→父节点摘要→递归到根，多粒度检索）；**GraphRAG**=实体关系图（多跳关系推理、实体消歧），局限=NL→三元组语义降级（条件/时间依赖丢失）、提取错误污染知识；推荐**分层互补**（完整自然语言保语义 + 结构化元数据索引检索）。何时需要：查询常需跨文档综合或多层次导航才值得投入（成本与延迟显著增加）。
- **Maka 设计启示**：本地个人数据规模小，默认混合检索、按需启用结构化索引（多跳/实体消歧垂直场景局部启用实体索引）；务必保自然语言原文；索引构建受预算约束。
- **可写设计文档**：《Maka 知识组织选型：混合检索优先 + 结构化索引按需启用的决策矩阵》

### [KP-03-14] 文件系统范式：OpenViking 的 L0/L1/L2 与链接索引
- **一句话核心**：把上下文（记忆/资源/技能）映射为虚拟文件系统中的目录和文件（唯一 URI），以 L0/L1/L2 三层摘要按需加载 + Markdown 纯文本为底层表达。
- **关键设计要点**：`viking://` 树；**L0 摘要（约 100 token 一句话）→ L1 概览（约 2000 token）→ L2 全文**，大部分查询到 L1 即可完成决策，与 Skills 渐进式披露同源；Markdown 纯文本（可读可改可 Git 回滚）而非专用数据库；**被忽视的前提：文件之间必须建立链接与索引**（`.abstract/.overview` 是纵向层次，还需横向关联——像 Wikipedia 条目互链+索引页）；**必须在写入提示词里写明确：每新增条目先检索并链接相关已有条目、更新索引页**（强模型自发回指、不少模型只孤立追加）。
- **Maka 设计启示**：本地文件优先气质天然契合；Local memory/知识库暴露为 `maka://memories/...` 树形命名空间；L0/L1/L2 与信条 2 同构（常驻轻量摘要、按需拉全文）；写入提示词必须显式要求"先检索再链接、维护索引"，否则知识退化成孤岛。
- **可写设计文档**：《Maka 知识文件系统范式：命名空间、L0/L1/L2 渐进披露与链接索引约定》

### [KP-03-15] 知识更新：增量更新与定期整理（Proposer-Reviewer）
- **一句话核心**：上线知识库同时需要两条节奏——**事件触发的增量更新**及时吸收新证据、**周期触发的全量整理**消除长期累积问题；两条路径都走"**把知识库当代码库、把每次变更当 PR**"的提议者-审核者闭环。
- **关键设计要点**：增量四步（Proposer 提交 PR——先检索相关已有知识再增删改、维护链接索引时间元数据证据引用 → Reviewer 独立审核——对照原始证据逐断言核对、返回指向证据和行号的可执行意见 → 迭代至收敛（设最大迭代/预算，超限转人工）→ 合入后发布（CI 查格式/链接/权限，重建索引））；**三层分离：原始证据层（只增不改）→ 知识层（可修订）→ 服务层（可重建的派生索引）**；Proposer/Reviewer **必须是 Agent 不是两次固定 LLM 调用**（要主动搜索、追溯证据、跑检查）；异源互审（能力相近、不同模型家族）+ 权限强制分工（Proposer 只写工作分支、Reviewer 只读证据、只有合并流程更新主分支）；定期整理三项核心（去重去旧合并/回到原始数据核查/冲突解决与场景限定 qualification——若在不同时间/对象/地域/任务都成立就把适用场景写进知识而非删一条）；**检索必须按调用者权限过滤，绝不让越权文档进入上下文**（权限过滤下推到检索层）；失效内容检测与下线（版本号+生效/失效时间元数据）。
- **Maka 设计启示**：三层分离正是"Log is the Runtime + Context is not history"的落地（证据层=Event Log、知识层=Local memory 投影、服务层=SQLite 派生索引）；本地知识更新做成可审计 Proposer-Reviewer 流程（TaskRun 预算+continuation 支撑长审核），证据引用指向 Event Log 事件 ID；异源互审+权限分工对本地单机同样适用（两个本地模型轮换+工作分支/主库隔离）。
- **可写设计文档**：《Maka 知识更新治理：Proposer-Reviewer 审核闭环与三层存储分离》

### [KP-03-16] 智能体化 RAG（Agentic RAG）
- **一句话核心**：把 RAG 从被动的"检索-生成"单向管道升级为"由 Agent 主导的、动态的、迭代的探索过程"——知识库检索被封装成 Agent 可随时调用的**工具**，走 ReAct 循环。
- **关键设计要点**：工具化封装（`knowledge_base_search`），Agent 思考→行动→观察→评估信息是否充分→迭代精确查询；实验 3-8 消融：简单问题非智能体 RAG 更快且质量相当，**复杂多跳问题差距显著**（智能体 RAG 专家式多轮）；价值是"**解决问题**而非'回答问题'"，牺牲响应速度换复杂问题鲁棒性与质量；**安全边界（间接提示注入）**：检索进上下文的外部文档是最典型载体，防御=指令/数据分离（来源标记）+ 不让检索内容直接触发高风险操作。
- **Maka 设计启示**：Local memory/知识库检索做成 **agent 可调用工具**（`search_user_memory`/`search_knowledge`）而非自动注入；调用记录/检索轨迹全部进 Event Log（可回放可审计）；检索结果必须带来源标记、绝不直接触发副作用动作。
- **可写设计文档**：《Maka 智能体化检索：search_user_memory 工具契约与安全来源标记》

### [KP-03-17] 上下文感知检索（Contextual Retrieval）与双层记忆架构
- **一句话核心**：分块固有缺陷是切断片段与上下文联系；Anthropic 解法是在**向量化索引之前**用 LLM 给每个块生成"上下文前缀摘要"再索引（做加法）；反用到用户记忆+常驻 Advanced JSON Cards，构成支撑"主动服务"的**双层记忆架构**。
- **关键设计要点**：索引期（非运行期）为块生成前缀（"[本段节选自 ACME 公司 2025 Q2 财务报告]"）；同时增强 BM25（增加可精确匹配关键词）与稠密（注入语义背景）；成本经 prompt caching 可控（每百万文档 token 约 1 美元）；Anthropic 数据：结合 BM25 检索失败率降 49%，再加重排序降 67%；与第二章"上下文感知压缩"划清界限（一个是索引期对文本块做加法、一个是运行期对对话历史做减法）。**双层记忆架构**：Advanced JSON Cards 常驻上下文提供"概览"+ 上下文感知检索按需取回"细节"——第三层"主动服务"第一次在工程上落地（既要全局概览又要精确细节）。
- **Maka 设计启示**：写入知识库/记忆检索块时**先生成上下文前缀再嵌入**（索引期"加背景"）；Local memory 采用双层：SQLite 中 JSON Cards 常驻（量小可控）+ 上下文感知索引的原始对话块按需检索。
- **可写设计文档**：《Maka 双层记忆架构：常驻 JSON Cards + 上下文感知检索，及索引前缀生成策略》

### [KP-03-18] 深度知识提取与多模态记忆
- **一句话核心**：面对海量结构化案例数据，RAG 需从"信息检索"跃迁到"知识发现"——先把非结构化案情提炼为结构化 JSON，再用因子分析量化权重，让 Agent"读懂"数据而非只检索数据。
- **关键设计要点**：两阶段知识发现（知识提取与结构化：定义"全面又一致"的 Schema；因子分析：**自下而上因子发现**——让 LLM 自由列出影响判决的因素构建贴合数据的模块化 Schema；one-hot 开关位编码类别避免数值大小误导；聚类找"案件原型"构建因子重要性层次模型）；应用：Agent 对话式信息收集（按重要性提问补全关键因素→检索最相似原型→给出有判例支撑的分析）；**多模态记忆三思路**：①存原始数据+文本描述；②存嵌入到上下文中（**每个嵌入 1 token，1000 token 区域可容纳 1000 张人脸**）；③存嵌入到模型参数（fact-LoRA 间接推理失灵——"把事实存进去是一回事，让模型知道何时该取用它，则是另一回事"）。
- **Maka 设计启示**：知识库不必只是检索仓库——对结构化数据集可跑"自下而上因子发现+因子重要性模型"离线任务产出可复用决策逻辑；多模态先落地思路一/二（媒体文件+文本描述，或关键嵌入作为 1-token 上下文区域）。
- **可写设计文档**：《Maka 深度知识发现与多模态记忆路线图（数据驱动的因子建模 + 媒体嵌入存储）》

## 本章金句 / 核心结论
- "用户记忆是持久的、可审查的，上下文学习则是临时的、会话结束就消失。"
- "轨迹是流水账，用户长期记忆是档案"——前者单次会话只增不改，后者跨会话反复改写/合并/淘汰。
- "按业务需要取舍，比追求'大而全'更符合工程现实。"
- Mem0 v3："仅追加写入+混合检索+时间排序"，LoCoMo 71.4→92.5。
- "没有哪种单一检索策略在所有场景下都可靠。把稠密、稀疏和重排序组合起来，才是构建生产级 RAG 系统的正确做法。"
- "把知识库当成代码库，把每次知识变更当成一个 Pull Request"；"索引是可重建的派生物，Git 中已审核的知识才是真正的来源。"
- "检索必须按调用者的权限过滤，绝不能让越权文档进入某个用户的上下文"——权限过滤下推到检索层。
- "Agentic RAG 的价值在于其'解决问题'而非'回答问题'的能力。"
- "双层记忆架构——Advanced JSON Cards 常驻上下文提供'概览'、上下文感知检索按需取回'细节'——是三层次框架中最高层'主动服务'的具体实现路径。"
- "把事实存进去是一回事，让模型知道何时该取用它，则是另一回事。"
