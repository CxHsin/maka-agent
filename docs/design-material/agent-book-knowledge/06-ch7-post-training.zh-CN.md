# 第 7 章 · 模型后训练 —— 知识点提取

> 来源：`book/chapter7.md`。核心公式 Agent = LLM + 上下文 + 工具，本章聚焦优化 LLM 这个"大脑"——通过后训练（SFT/RL）改动模型权重把能力沉淀进参数。两条贯穿主线：**主线一**：受控实验中"SFT 记忆、RL 泛化"（非普遍属性）；**主线二**：**数据和环境，比算法更重要**。
>
> **对 Maka 的定位**：Maka 是 harness 型平台（不训模型），本章价值在于"Harness 采集什么信号、如何为后训练留数据接口、如何从评估/日志判断是否值得训练"的设计文档。

## 一、预训练 / SFT / RL：三阶段全景

### [KP-07-01] 三阶段全景
- **一句话核心**：预训练（读万卷书）、SFT（老师手把手教标准解法）、RL（自己下场做题反复打磨）三阶段的数据、优化目标与代价完全不同。
- **关键设计要点**：预训练=海量文本预测下一个词（代价极高但"博学而不会好好回答问题"）；SFT=几千-几万条"问题-标准回答"示范（便宜快稳）；RL=让模型自己试提高好行为概率（代价常是 SFT 的几十-上百倍，但可在没见过的情况做更好决策）；训练归根结底是调整概率分布，三阶段区别只在"想要什么、用什么信号定义想要"。
- **Maka 设计启示**：harness 型平台应把"知识来源"与"协议固化"分开建模——事实知识靠 RAG/上下文（可更新可追溯），协议/格式/流程类能力才是 SFT 候选；Event Log 记录的结构化对话与工具调用就是"可固化协议"的原始素材，应为将来导出训练数据留好接口。
- **可写设计文档**：《post-training-ready-harness.md（harness 为后训练留数据接口的总纲）》

### [KP-07-02] SFT 的本质：换了数据的"预测下一个词"
- **一句话核心**：SFT 与预训练数学上同一任务，差别只有两点——数据换成"输入-输出"示范对、**损失只算在回答上（loss masking）**。
- **关键设计要点**：SFT 固化的是"格式、风格、流程"这类**协议性知识**而非事实性知识（后者靠预训练或 RAG）；**LoRA 是全书工程默认项**（不动原始权重挂低秩补丁、参数仅 1%-5% 接近全参效果、灾难性遗忘风险低——必须覆盖所有主要权重矩阵尤其 MLP；最优学习率约为全参 10 倍；SFT 用中高 rank 64-256、RL 用小 rank 8-32；部署时可一机多 adapter 多租户）。
- **Maka 设计启示**：日志应区分"问题侧/回答侧"、区分**模型生成内容与工具返回内容**——这是将来做 loss masking 与"屏蔽非策略 token"所需的数据切分；工具调用轨迹中的参数/格式即"协议性知识"应作为结构化字段记录。
- **可写设计文档**：《trajectory-data-contract.md（轨迹数据格式契约：问题/回答/工具/屏蔽标记）》

### [KP-07-03] 何时需要先 SFT 后 RL：先形后神
- **一句话核心**：RL 需要先把模型输出解析出来才能算奖励——结构化输出不稳定时，SFT 先立"形"（格式）、RL 再追求"神"（策略泛化）。
- **关键设计要点**：若模型吐格式混乱文本无法解析成 JSON/工具调用，奖励函数无从算起、RL 学不成（实验 7-11：Llama-3.2-Vision-11B 不经 SFT 直接 RL 完全失败）；强基础模型可跳过 SFT 直接 RL（DeepSeek-R1-Zero 直接 RL 成功、自行涌现反思与长链思考，但代价是输出可读性差——R1 最终仍加回"冷启动 SFT"立"形"，Zero 到冷启动往返正是"先形后神"注脚）。
- **Maka 设计启示**：Maka harness 在运行时实际扮演"SFT 格式稳定"角色（schema 校验、工具接口检查）；应记录"格式解析失败率"信号作为判断是否值得微调/是否该约束解码的依据。
- **可写设计文档**：《structured-output-stability-gate.md（结构化输出稳定性门槛与信号采集）》

### [KP-07-04] SFT 与 RL 的本质区别：SFT 记忆，RL 泛化
- **一句话核心**：SFT 最大化标注回答概率（复现示范），RL 最大化期望奖励（探索多条路径提高高奖励路径概率）——不同优化目标带来记忆/泛化不同倾向。
- **关键设计要点**：表 7-2 对比（训练信号/样本效率（SFT 几千条见效 vs RL 低几十-上百倍）/稳定性/最适合场景）；概率分布视角（SFT 常 mass-covering 覆盖式、RL 配合反向 KL 更易 mode-seeking 寻峰）；**后训练塑造"何时行动"（行动阈值）**——Coding 模型默认调查深度不同，本质是参数中策略在估计"多读一个文件的预期价值是否还高于提交并验证"，Harness 可调节但主要来源可位于后训练参数；**在线反馈给模型三个机会**（评估固定示范之外的候选/利用"验证比生成容易"不对称（RLVR 优势但验证器不完整会 reward hacking）/在策略实际访问的状态上训练缓解协变量漂移）；比喻：SFT 细致学习已有地图、RL 拿奖励当指南针探索地图外。
- **Maka 设计启示**："Log is the Runtime"让模型实际访问过的状态（在线数据）被完整记录——在线 RL 需要的；"Feedback is not fact authority"对应"奖励/验证器可被 hack"教训——self-check 结果应作为**证据**记录而非自动成为系统事实。
- **可写设计文档**：《evidence-vs-fact-logging.md（反馈/自检证据的日志语义）》

### [KP-07-05] 经典 RL 与现代 Agent（可选阅读，简略）
- **一句话核心**：经典 RL 用预定义动作空间试错，现代 LLM Agent 用"变长组合式动作+思考 token"，决定性差异是携带海量**预训练先验**。
- **关键设计要点**：**先验 > 环境 > 算法**（姚顺雨《The Second Half》：先验知识可通过与 RL 完全无关的方式获得，几十年来 RL 研究者的优先级可能完全颠倒）；实验 7-1/7-2：Q-learning 需近 10000 次尝试通关 vs LLM Agent 第一局 18 步——差距来自先验不是学习算法。
- **Maka 设计启示**：Runtime Event Log 就是 Agent 与环境的完整交互轨迹（对应 RL trajectory），"Log is the Runtime"让每条轨迹可回放可重放——环境仿真与训练数据复用（不重复采集）的前提；日志结构面向"可离线重放"设计。
- **可写设计文档**：《replayable-trajectory-log.md（可重放轨迹日志与事件编码）》

## 二、SFT 与数据合成

### [KP-07-06] SFT：固化协议，数据从哪来
- **一句话核心**：SFT 核心价值不是注入新知识而是**固化协议**（映射关系/交互格式/风格规范）；数据三条路：人工专家示范、教师模型生成（合成数据）、拒绝采样。
- **关键设计要点**：三条路常组合（少量人工种子立格式→教师放大规模→拒绝采样拉齐质量）；**"与其堆十万条脏数据，不如精修一万条干净数据"**（数据每处噪声 SFT 都可能忠实写进参数）；实验 7-6（语音 SFT：Orpheus voice cloning vs Sesame 副语言标记）；实验 7-7（多语言思考：零样本跨语言泛化=激活预训练共享表征）；实验 7-8（Prompt 蒸馏：长提示+思考教师→短提示+无思考学生，20-30 倍提速，注意继承教师边界）；实验 7-9（CoT 蒸馏：转移教师思考轨迹恢复 70%-80% 能力，R1 开源蒸馏小模型代表）；拒绝采样 RFT 介于 SFT 与 RL 之间（生成→验证过滤→只留正确轨迹）。
- **Maka 设计启示**：日志中高质量用户-助手对话、工具调用成败就是合成数据原料；把"线上数据→任务蓝图→合成任务"流水线作为数据接口写入文档，明确"数据质量>数量"过滤门禁（格式校验+人工抽检）。
- **可写设计文档**：《synthetic-sft-data-pipeline.md（线上日志→任务蓝图→合成数据→验证→SFT 数据）》

### [KP-07-07] SFT 数据合成：从示范到可训练轨迹
- **一句话核心**：合成数据的目标不是复述线上日志，而是提炼可复用的**任务结构**（用户意图/初始状态/可用工具/业务约束/常见失败/成功条件），去身份化后在可重置隔离环境中重生成。
- **关键设计要点**：稳妥流水线=线上数据→任务蓝图→合成任务→多次候选轨迹→任务验证与轨迹验证→SFT 数据；**双重验证**（任务验证：可完成/难度/参考正确；轨迹验证：最终状态/工具调用/业务约束——能写单元测试/数据库断言/状态差异检查的优先确定性代码）；同一套任务与验证设施可转 RL 环境但用法不同（SFT 只保留验证通过的成功轨迹；RL 让当前策略重新 rollout 探索示范外路径）；**失败轨迹不直接当正确示范**（可构造偏好对/发现覆盖缺口）；关键不是数量而是覆盖面/多样性/准确性；训练集按模板/客户/时间段去重划分、评估集不重叠；bad case 可转训练数据（以"过早结束"为例：截"准备宣称完成"轨迹前缀、rejected=过早宣称作、chosen=先跑测试核对再下结论——适合 DPO 或决策边界示范）。
- **Maka 设计启示**：bad case（过早结束/工具 mismatch）沉淀为带标签样本库，随样本保存失败归因与验证器引用；训练/评估隔离协议（按模板/客户/时间段去重、评估集不重叠）成为 Maka 数据导出默认约束。
- **可写设计文档**：《task-blueprint-and-eval-isolation.md（任务蓝图抽象与训练/评估隔离）》

### [KP-07-08] 何时选择 SFT，何时选择 RL
- **一句话核心**：SFT 用于固化格式/协议/风格、有高质量专家示范、训练部署环境一致；RL 用于部署分布与训练系统性差异、需探索最优策略、标注成本过高——决策按三步走。
- **关键设计要点**：决策三步——①先问"需要后训练吗？"（Harness 工程能解决就不训练——**大多数 Agent 应用落在这里**）②需要则先试 SFT（不适合注入大量事实知识）③SFT 不够再加 RL；升级判据=增加多样优质示范后新场景表现仍停滞 + 存在能可靠评估这些场景的奖励与环境。
- **Maka 设计启示**：提供面向用户的"先 harness、再 SFT、最后 RL"决策文档；日志采集支撑决策的信号（格式解析失败率/分布漂移迹象/bad case 聚类），帮助判断"该修 prompt 还是该导出微调"。
- **可写设计文档**：《train-or-not-decision-support.md（后训练决策支持与信号）》

## 三、单轮强化学习与 RL 算法

### [KP-07-09] 单轮强化学习：记忆与泛化的对照
- **一句话核心**：单轮设定提供受控对照——相同任务/基础模型/预算，唯一变量是训练方法；实验系统量化"SFT 记忆、RL 泛化"。
- **关键设计要点**：策略梯度直觉（多采样几条回答、提高高奖励降低低奖励）；PPO（概率比超区间裁剪、可带价值网络）vs GRPO（不训价值网络、同问题多条回答互比）；实验 7-10（AdaptThink 学会"何时不思考"：step 0→300 时响应长度 -67.9% 准确率微升）；实验 7-11（GeneralPoints 规则/视觉 OOD：RL +3.5%/+17.6%、SFT -8.1%/-9.9%——RL 通过结果导向优化改善底层视觉编码器、SFT 过拟合思考 token 模式）；关键结论：本设定下 RL 需先 SFT 初始化；**验证迭代次数越多泛化越好**（10 次 +5.99% vs 1 次 +0.48%——测试时计算是泛化提升重要因素）；机制解释：有限 SFT 数据强化固定模式、RL 强化"重新计算直到正确"可迁移策略——**是实验条件测得结果，不是 SFT 必然记忆、RL 必然学通用算法**。
- **Maka 设计启示**：self-check/验证流程可类比"测试时计算"——日志记录**验证迭代次数**作为元数据支撑"更多验证→更好泛化"信号采集；坏样本采集记录最终验证结果（真实文件/环境状态）而非只看输出文本。
- **可写设计文档**：《verification-depth-signal.md（验证迭代次数与结果导向信号采集）》

### [KP-07-10] RL 算法：从 16 次 rollout 到一次参数更新
- **一句话核心**：一次 RL 训练迭代四步闭环——并行 rollout 尝试→计算奖励→计算组内相对优势→梯度下降更新策略。
- **关键设计要点**：rollout（同一任务复制到 16 个隔离沙箱独立解决）；奖励（验证器在干净环境应用补丁跑测试，4/16 通过→1）；相对优势（相对组内平均，全成功/全失败时零方差无梯度——**这解释了 RLVP 为何需要路径信号恢复组内差异**）；梯度更新（提高正优势轨迹概率）；算法区别（GRPO 同题多 rollout 互比无需价值模型/PPO 训价值模型适合长轨迹细粒度信用分配/DPO 直接学事先收集的偏好对）；成本估算（一条 rollout 约 2000 秒+更新 600 秒≈一个 step 43 分钟、100 steps≈72 小时——**RL 常是 SFT 训练时间 10-100 倍**）。
- **Maka 设计启示**：TaskRun（可中断可恢复预算控制）天然支持"多轨迹并行尝试"rollout 语义——日志按"同一任务的多条轨迹"分组记录（同任务 ID）为将来组内相对优势/偏好构造留数据接口；预算可类比"最多 N 次尝试"。
- **可写设计文档**：《rollout-grouping-and-budget.md（轨迹分组、预算与并行执行语义）》

## 四、RL 环境：从评估到仿真

### [KP-07-11] RL 环境：仿真环境是练习场，模型也可以扮演环境
- **一句话核心**：RL 瓶颈往往不在算法而在环境是否足够**真实、可重置、可并行**；造不出高保真环境时可以让模型扮演环境。
- **关键设计要点**：**环境失真，策略必废**（仿真里客服总按固定套路回话、模型学到"只在仿真里管用的应试策略"——RL 项目最常见的翻车方式）；构建高保真环境常常比训练本身更贵更难；**动手调算法前先问"我的仿真环境，真的像真实世界吗？"——比选 PPO 还是 GRPO 重要得多**；让模型扮演环境两层（合成工具返回值 ZeroSearch 课程式设计、仿真整个环境动态 DreamGym/LLM 扮演用户 τ-bench）；风险=**模拟器世界知识是训练天花板、模拟器系统性偏差被策略照单全收、RL 会主动寻找利用模拟器漏洞做 reward hacking**——稳妥做法=模型模拟承担大部分交互量+真实环境定期校准。
- **Maka 设计启示**：local-first 隔离工作区+"Log is the Runtime"组合提供天然"影子世界"（工具调用可隔离可重放可重置）；把"环境可重置/可并行/可复现"作为 harness 验收标准。
- **可写设计文档**：《sandbox-replay-and-env-fidelity.md（隔离工作区、可重放性与环境保真度）》

### [KP-07-12] 环境、任务分布与评估隔离
- **一句话核心**：环境必须可重置、可并行、可复现并在状态转移后给出可信验证；训练任务从真实业务日志提炼但需去身份化；训练与评估可共享任务生成器与验证代码，**但不能共享同一批任务**。
- **关键设计要点**：从业务日志提炼（去除身份信息→抽象意图/初始状态/工具/约束/成功条件→生成虚构人物订单文件状态）；训练/评估隔离（测试用例/隐藏状态/参考解法留在验证器一侧；按任务模板/客户/时间段去重）；先少量 rollout 检查"任务可完成、验证器能区分对错"再扩大；验证器吞吐（CPU 验证可能远慢于 GPU 生成，**吞吐取决于并行的验证器 worker 而非继续堆 GPU**）。
- **Maka 设计启示**：评估数据设计默认"训练/评估隔离"；"验证器 worker 并行是吞吐瓶颈"提示验证执行器横向可扩展。
- **可写设计文档**：《eval-train-isolation-and-verifier-pool.md（评估隔离与验证器并行池）》

## 五、从单轮到多轮：信用分配

### [KP-07-13] 从单轮到多轮：信用分配、部分可观测性与工具调用
- **一句话核心**：多轮让复杂性质变——策略要处理延迟奖励下的**信用分配**（最终成败归因到哪一轮）与**部分可观测性**；接入工具后，动作变成搜索/执行代码/改文件/查库/组合 API。
- **关键设计要点**：多轮物理形态就是 ReAct 循环；实验 7-12（V-IRL-VL 多轮视觉导航：RL 明显优于 SFT、逐步反馈缓解长时序信用分配）；实验 7-13（SimpleVLA-RL：稀疏结果奖励保留更大探索空间——过程信号容易定义时加速学习、最优路径未知时稀疏奖励更好）；工具调用线（Search-R1/ReTool/AWorld-train 多工具沙盒）；**关键实现细节：环境返回的 token 不是策略生成的，计算策略梯度时应屏蔽这些反馈 token，只对模型自己的思考和工具调用参数回传梯度**——否则模型被训练去预测沙盒输出而不是学会用工具；实验 7-14（ReTool：SFT 预热后 PPO、AIME 2024 约 25%→67%）。
- **Maka 设计启示**：TaskRun 需要跨 turn 追踪状态支撑信用分配；日志严格区分**模型生成 token 与工具返回 token**（屏蔽原则）为将来 RL/蒸馏留正确梯度接口；self-check（有界修复机会）可视为"过程信号"的一种工程化。
- **可写设计文档**：《multi-turn-credit-assignment-log.md（跨 turn 状态追踪与工具反馈屏蔽标记）》

## 六、奖励设计

### [KP-07-14] 奖励来源：规则、人类偏好与模型评判
- **一句话核心**：最可靠的奖励是可验证奖励（RLVR，测试/断言/状态差异直接判断）；规则化不了时用人类偏好（RLHF/DPO）或生成式奖励模型（GRM）；警惕 reward hacking 与 reward seeking。
- **关键设计要点**：RLVR（测试用例/数据库断言/状态差异/格式检查——规则越确定奖励越便宜可复现难钻空子）；RLHF 背景（InstructGPT=人工比较→训奖励模型→PPO，用 KL 正则锚定在 SFT 参考模型附近）；DPO 跳过显式奖励模型从偏好对离线优化；GRM 不只输出分数还生成"哪里好哪里需改"诊断；**reward hacking（钻规则/实现漏洞拿高分）vs reward seeking（先在心里建立"评判器会看什么"的模型再据此调整——自设很浅的检查刚好通过就提前结束，交付物只满足代理指标而非真实意图）——"通过了 grader"不能自动等价于"任务完成了"：评判器是意图的代理，训练越强模型越可能把代理当成目标本身**。
- **Maka 设计启示**：几乎就是信条 4 的训练侧表述——self-check/grader 结果作为**证据**记录（附验证器/隐藏测试引用）永不自动升级为系统事实；reward seeking（自设浅检查提前结束）正是"过早结束"bad case 深层机制，harness 以隐藏测试/状态断言/外部终止钩子约束。
- **可写设计文档**：《reward-signal-sources-and-grader-trust.md（奖励来源与 grader 信任边界）》

### [KP-07-15] 结果奖励 vs 过程奖励，及奖励信息密度
- **一句话核心**：结果奖励（ORM）episode 末判断成败、探索自由度最大但稀疏；过程奖励（PRM）中间步骤给反馈、缓解长时序信用分配但限制路径且成本高；"密度"与"表示形式"（标量/向量/生成式）是两件事。
- **关键设计要点**：ORM 给策略最大探索自由度（最优路径未知时稀疏成功失败奖励是合适起点）；**长程任务"是否完成"判定要交给模型写不了的隐藏测试、状态断言、外部终止钩子，不能只依赖模型自己声称完成**（Harness 在隔离工作区运行模型看不到的验收测试、测试读取真实文件/环境状态）；PRM（OpenAI Let's Verify Step by Step 数学价值）；工程策略=先用结果奖励建可靠基线再只为**真正可验证的中间事件**加过程信号；信息密度与表示（标量/半标量/向量/生成式选择原则：有确定答案→二元标量；多独立质量目标→向量或加权标量；开放式难穷举→生成式诊断+事实校验+人工抽检）；**不要为"更丰富"堆叠不可验证维度——每加一个维度就多一种被钻空子的可能**；评估设"未完成任务边界集"与"确实完成保留集"双集避免把模型训练成永远不敢结束。
- **Maka 设计启示**："过早结束"处理可直接落地（隔离工作区+模型不可见验收测试+真实状态断言）；日志记录"完成声称是否通过隐藏验证"结果信号与可验证中间事件（工具参数合法/测试通过数）作为潜在过程信号。
- **可写设计文档**：《outcome-process-reward-signals.md（结果/过程信号采集与双集评估）》

### [KP-07-16] 路径约束与 RLVP：奖励结果、约束过程
- **一句话核心**：结果奖励表达不了"是否按规定办成"——RLVP（Reinforcement Learning with Verified Penalty）原则是**奖励结果，惩罚路径**：对可机器判定的、与最终成败无关的**结果中性约束**逐动作惩罚/给部分进展奖励。
- **关键设计要点**：真实环境是**非对称验证器**（检测"做了一个坏动作"便宜可靠，证明"这步确实朝目标进展"很难）；总奖励 **R = O + βΦ**（O 任务结果、Φ 确定性规则逐动作路径信号，两路归一化合并避免淹没主目标）；关键不是"奖励越密越好"而是**能否补回组内差异**（纯结果奖励在全败/全胜组零方差无梯度）；四点设计原则（只惩罚具体动作不惩罚"不够努力"/结果奖励始终保留/每个惩罚配可达合规路径/规则确定难以钻空子）；"惩罚是通常可达的那一半、进展奖励是受可达性门控的那一半"；实验 7-16（GRPO 加 R=O+βΦ：TerminalBench 违规次数 3.71→0.66 成功率持平；miniF2F 可达部分奖励把达 0.9 成功率迭代从 7.0→4.4；所有 rollout 过不了任何测试时进展信号不可达加入无益——**先测信号可达性再决定是否增加奖励维度**）；实验 7-17（过早结束→DPO/GRPO：bad case 转轨迹前缀偏好对、未完成集选对率 25%→91.7%）。
- **Maka 设计启示**：harness 把"破坏性命令、跳过身份验证、改测试文件"等视为可机器判定违规动作事件记录进 Event Log——这就是 RLVP 路径信号原料；文档明确"哪些约束结果中性可确定判定"与"可达合规路径"（如先验证再完成）为将来 RLVP 式训练留数据接口。
- **可写设计文档**：《path-constraint-events-and-reachability.md（路径约束事件与可达性门控）》

## 七、蒸馏：提升样本效率

### [KP-07-17] On-Policy Distillation 与 On-Policy 自蒸馏
- **一句话核心**：RL 主要瓶颈是**样本效率**；On-Policy Distillation 让学生在自己走的轨迹上由教师给出逐 token 概率分布，把一条 rollout 从"一个 0/1 信号"变成约 T 组逐 token 监督；没有更强教师时用 On-Policy 自蒸馏（同模型分饰师生、教师看特权信息）。
- **关键设计要点**：样本效率差的根源=反馈太稀疏（主流 model-free RL 一条 rollout 只得到一个成败标量，客服"需要信用卡后四位"可能要数百次交互才偶然学会）；On-Policy Distillation 同时解决 SFT（监督密集但来自离轨路径）与 RL（在轨但稀疏）短板——**稠密信号胜过稀疏信号**（"时间感"任务上通过率比同源 SFT 高 23-47pp；瓶颈往往不是奖励不够复杂而是每次交互信号不够密）；数学任务同性能训练步数约为纯 RL 1/10；前提=仿真环境足够真实让学生探索状态接近部署分布；On-Policy Self-Distillation（OPSD）：教师版看到特权信息（标准答案/已验证解答）、学生版只看到问题在自己采样的轨迹上对齐——不要求奖励可自动验证但**不会凭空创造新知识**。
- **Maka 设计启示**：多轮轨迹日志是蒸馏原料——记录每步稠密中间信号（每轮工具调用/中间验证结果）而非只记最终成败；local-first 定位（拿得到用户多轮轨迹）使其成为 on-policy 蒸馏数据理想产地；设计"教师-学生逐 token 分布"数据接口。
- **可写设计文档**：《dense-signal-and-distillation-data-interface.md（稠密信号采集与蒸馏数据接口）》

## 八、后训练实践要点

### [KP-07-18] 后训练实践要点：常见陷阱与 RAG/ICL/后训练协同
- **一句话核心**：模型学到什么取决于训练信号教了什么，信号质量主要由**数据和环境**决定而非算法；8 个常见陷阱 + RAG/ICL/后训练作用于不同位置应组合使用。
- **关键设计要点**（8 陷阱）：①过度依赖后训练记事实（事实用 RAG 管理、后训练聚焦"如何使用知识"）②格式未稳就引入 RL ③奖励函数设计不当导致 reward hacking（评估最终目标而非中间指标）④忽视仿真保真度 ⑤过度训练导致泛化下降（早停至关重要）⑥价值函数崩溃与探索不足 ⑦低估 RL 计算成本（10-100 倍）⑧训练数据质量低下（SFT 把噪声固化为参数）；核心原则=**在投入大规模资源前先用小规模实验验证关键假设**（快速失败比大规模失败更可接受）；与 RAG/ICL 协同（ICL 零参数即时适应、RAG 事实放可动态更新可追溯外部知识、后训练写高维感知/生成风格/隐式决策策略——选择依据不仅是任务长期稳定，更是**能力能否被外部符号充分表达**）；稳健系统组合=事实证据 RAG、可语言描述策略 ICL、确定性流程与硬约束程序、难以语言表达且需泛化能力后训练。
- **Maka 设计启示**：陷阱清单直接转成设计原则文档——事实知识进 RAG/上下文（不进参数）、确定性流程进程序、能力边界之外才导出后训练；数据导出前做质量门禁与训练/评估隔离（陷阱 8）；文档写明"何时值得导出训练数据、何时改 prompt/skill 就够"。
- **可写设计文档**：《post-training-practice-checklist.md（后训练实践要点与 RAG/ICL/后训练协同清单）》

## 本章金句 / 核心结论
- "预训练是读万卷书（积累知识），SFT 是老师手把手教标准解法（模仿示范），RL 是自己下场做题、根据对错反复打磨（试错提升）。"
- "**数据和环境，比算法更重要**"——现成 RL 算法你会用就行，真正拉开差距的是仿真环境保真度和训练数据质量；很多场景只要 SFT 数据质量到位甚至不需要做 RL。
- "**先验 > 环境 > 算法**"（姚顺雨《The Second Half》）。
- "**SFT 记忆，RL 泛化**"——受控实验中测得结果，不是普遍属性。
- "**先形后神**"：SFT 先立"形"（格式/结构/可读性），RL 再追求"神"（策略/泛化/推理）。
- "**评判器是意图的代理，训练越强，模型越可能把代理当成目标本身**"（reward seeking）；"通过了 grader"不能自动等价于"任务完成了"。
- "**稠密信号胜过稀疏信号**"——瓶颈往往不是奖励函数不够复杂，而是每次交互提供的信号不够密。
- "**模拟器的世界知识就是训练的天花板，模拟器的系统性偏差会被策略照单全收。**"
- "模型学到什么，取决于训练信号教了它什么；而信号的质量，主要由数据和环境决定，不是由算法决定。"

## 书中思考题（转录要点）
1. 灾难性遗忘在 Agent 场景尤其棘手——LoRA 之外还有哪些策略缓解微调能力遗忘？
2. 某项能力（领域知识）既可通过后训练也可通过 few-shot 提供——用什么标准决定走哪条路径？
3. 蒸馏三类模型（Chat/Reasoning/Agentic）难点分别不同？——从"要蒸馏的到底是什么"入手（输出风格/思考轨迹/与环境交互的决策策略；轨迹里哪些 token 该学哪些是环境返回不该学；成败信号多晚多稀疏）。
4. 多轮 Agent 交互中奖励归因比单轮严重（最终成败难归因到第 3 轮还是第 7 轮）——如何设计奖励分配策略？
5. 固定预算（$10,000）提升客服 Agent，如何在上下文与知识/Prompt-Skills/程序约束/参数训练间分配？
6. 无明确奖励函数、样本稀少时自主实现模型学习——当前 RL 距离这个终极目标多远？下一个突破最可能来自哪？
7. LoRA 微调成本不高——是否可能给每个用户/客户公司训练专属 LoRA 把记忆写入参数？什么场景"记忆写入参数"比"存入知识库"更有优势/适得其反？
8. Weak-to-Strong Generalization：弱模型监督信号能激发强模型潜在能力——能否实现"小模型教大模型"逆向蒸馏？
9. "正确过程导致错误结果" vs "错误过程侥幸得到正确结果"哪个更值得奖励？多步工具调用场景如何权衡？
10. 评估集既用于评估又用于后训练——是否违反训练/测试分离原则？τ²-bench 动态参数、AndroidWorld 参数化模板部分缓解，如何在利用评估数据训练价值与维护独立性间平衡？
11. "先形后神"——实践中如何判断 SFT 已"足够"该切换到 RL？
12. ReTool 少数超长响应拖长训练周期（等最长响应收尾 GPU 利用率低）——如何提升长尾响应场景资源利用率？
13. 用 LLM 模拟环境训练时 Agent 钻空子对象从"真实环境规则"变成"模拟器偏见与漏洞"——可能哪些 reward hacking？如何防范？
