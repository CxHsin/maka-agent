# 第 2 章 · 上下文工程 —— 知识点提取

> 来源：`book/chapter2.md`（全书最关键一章）。章节主线：**给模型看什么、怎么组织，比模型本身有多聪明更影响最终结果。** 回答"怎样以更低成本向模型提供信息充分的 $c_t$（截至当前的完整交互上下文）"，按"静态前缀 + 轨迹"骨架展开：KV Cache → 提示工程 → 提示注入 → Agent Skills → 状态栏 → 上下文压缩。
>
> **对 Maka 的整体启示一句话**：本章几乎所有机制（状态栏、压缩、Skills、子 Agent 隔离、缓存稳定性）都能统一为 **"Runtime Event Log 是唯一事实源，各种上下文视图（system/tools/Skill 目录/状态栏/剪枝/Compaction/恢复）都是日志的投影"**，且"只增不改的日志 + 可变的投影"恰好同时满足 KV Cache 前缀稳定性与"Context is not history"两条信条。

## 一、上下文：决定能力上限

### [KP-02-01] 上下文质量决定 Agent 能力上限
- **一句话核心**：模型智力只是基础，上下文质量才是 Agent 能力的真正关键；中等模型+精心组织的上下文往往胜过顶级模型在信息匮乏下的盲目摸索。
- **关键设计要点**：Coding Agent 最低信息需求三类（实时代码上下文/流程规范/环境信息）；上下文工程更是组织问题（"对远程工作友好的团队也对 AI Agent 友好"）；ReAct 定义 $c_t$ = 截至当前的完整交互历史；模型 API 无状态、每次调用由框架重新构造上下文，生产系统可压缩但**不能悄悄丢掉决定下一步行动所需的信息**。
- **Maka 设计启示**：直接支撑"Log is the Runtime"——Event Log 就是必须完整留存的"交互历史"；剪枝/Compaction 必须显式声明"什么被从下一次推理中拿掉了、为什么可丢"。
- **可写设计文档**：《Runtime Event Log 事件模型与上下文投影规范》

## 二、API 消息结构与 Agent 核心循环

### [KP-02-02] API 消息结构与四种消息角色
- **一句话核心**：模型 API 的核心是消息列表；四种角色（system/user/assistant/tool）+ 独立 `tools` 字段 = 上下文五个组成部分。
- **关键设计要点**：system 最高优先级、通常一条放最前；assistant 原样放回让模型"看到"自己的决策；tool 用 `tool_call_id` 关联；静态前缀（System+Tools）会话中不变，轨迹动态增长——"前面不能动、后面可以压缩"。
- **Maka 设计启示**：Event Log 角色/事件类型应与此对齐但更细（还需记录框架注入元信息、工具 schema 加载）；日志保留角色标记与 tool_call_id 关联，保证任何时刻能重放出合法 API 消息列表。
- **可写设计文档**：《消息角色与 Event Log 事件类型映射表》

### [KP-02-03] Agent 核心循环：多轮工具调用交互协议
- **一句话核心**：核心循环是"请求→工具调用→执行→送回结果→再请求"；**模型负责决策，框架负责执行**。
- **关键设计要点**：模型返回工具调用请求而非答案；第二次请求必须含第一次完整历史；无依赖调用可并行、有依赖串行；终止判断=模型输出文本（无 tool_calls）；输出 token 顺序固定"内部思考→文本→工具调用"。
- **Maka 设计启示**：TaskRun 循环驱动与"模型决策、框架执行"职责划分一致；每轮迭代可重放/可中断/可续跑（日志即循环状态）。
- **可写设计文档**：《TaskRun 循环事件协议与并行工具调用建模》

### [KP-02-04] max_iterations 与卡死/重复调用
- **一句话核心**：最简 Agent 核心是"while 循环+判断"；框架核心工作=管理 messages 列表；生产代码必须加 max_iterations 上限，否则可能永远重复相同工具调用。
- **关键设计要点**：滑动窗口丢关键工具结果→Agent"忘记"→反复执行相同调用陷入循环（实验 2-3 实证）；常见陷阱：把工具结果误当 user 消息、模型数不清次数。
- **Maka 设计启示**：预算机制与 max_iterations 同源，都应是 Event Log 上的投影/检查点；卡死/重复调用应作为可观测信号写入日志（同工具连续 N 次、无新信息增量），供 headless 预算中断与 self-check 引用。
- **可写设计文档**：《循环终止条件与预算/防卡死策略》

### [KP-02-05] 上下文构成：静态前缀 + 动态轨迹
- **一句话核心**：每次 API 调用 = 不变的系统提示词与工具定义（静态前缀）+ 不断增长的对话历史（轨迹）；理解它才能理解"为什么前面不能动、后面可以压缩"。
- **Maka 设计启示**："上下文投影"正是此结构产物——Event Log 是唯一事实源，System Prompt/工具集/Tool Result 剪枝/Compaction/状态栏都是投影时组装的视图；改投影不影响已记录证据。
- **可写设计文档**：《上下文投影（Context Projection）架构：从 Event Log 到模型请求》

## 三、KV Cache 友好的上下文设计

### [KP-02-06] KV Cache 友好设计三条铁律
- **一句话核心**：KV Cache 复用已算过的 K/V，前提是**前缀 token 序列字节级不变**。
- **关键设计要点**：① 系统提示词和工具定义一旦确定就不要改（改动越靠前，延迟/成本影响越大）；② 动态信息永远追加到末尾；③ 使用标准 API 格式、不要自行拼接消息。反例：system 里加 `Current time: {{now}}` → 首 token 延迟 0.5s→3-5s、月账单近翻倍。
- **Maka 设计启示**：剪枝与 Compaction 必须遵守"静态前缀不动"纪律；状态栏/时间戳等动态信息一律 append；任何"改写已有消息"的实现都按此审查。
- **可写设计文档**：《KV Cache 友好上下文布局规范（三条铁律）》

### [KP-02-07] Chat Template 与 Token 结构
- **一句话核心**：结构化消息由 Chat Template 转为线性 token 流（特殊标记划分角色边界）；不只是缓存地基，更决定多轮工具调用/思维链保留能否正确工作。
- **关键设计要点**：把工具结果当 user 消息会被误识别为新查询→收走历史思维链；**历史思维链回传策略因模型而异且在快速演变**（DeepSeek R1 剥离全部→V4 强制回传全部、Kimi K2/GLM-5 同；Claude 要求客户端原样回传带签名的 thinking block）——使用前须查最新文档。
- **Maka 设计启示**：日志保留 API 层消息而非 token 流；多模型支持让思维链回传成为 per-provider 投影参数，日志中保留完整 assistant 消息（含 reasoning/thinking 字段）才能按模型重放。
- **可写设计文档**：《多 Provider 消息投影与思维链回传策略》

### [KP-02-08] KV Cache 原理与约束
- **一句话核心**：无缓存时 prefill 注意力计算随上下文**平方级 N² 增长**；有缓存时仍随长度线性变慢，显存/带宽成瓶颈；缓存只认 token 字节前缀不变性。
- **关键设计要点**：注意力可视化（实验 2-2）——**注意力储存池**（首 token 可 >70% 权重）、思考与输出双三角形、**Lost in the Middle**（开头结尾高注意力、中间易忽视）。
- **Maka 设计启示**：剪枝/压缩/状态栏尊重"改动点越靠前代价越大"；"把最关键信息放开头或结尾"同时是提示词设计与日志投影排序的指导原则。
- **可写设计文档**：《上下文布局与注意力位置偏好指南》

### [KP-02-09] 常见错误上下文管理模式（实验 2-3 实测）
- **一句话核心**：五种看似无害的模式系统性破坏 KV Cache 甚至核心能力——动态系统提示词、动态用户配置、工具定义动态排序、滑动窗口对话历史、文本格式化。
- **关键设计要点**：滑动窗口既破坏前缀一致性又丢关键结果（错误率显著上升、频繁陷入循环）；工具定义**保持固定顺序对选工具能力几乎无影响但性能提升显著**；文本格式化真正破坏是偏离训练格式→模型消耗注意力推断角色边界。**偏离标准格式往往是在给自己挖坑**。
- **Maka 设计启示**：Event Log 天然"只增不改"，规避滑动窗口与改写前缀问题；但 Tool Result 剪枝/Compaction 是对历史做减法，必须警惕重蹈覆辙——剪掉的关键证据要在日志留痕、可回溯。
- **可写设计文档**：《剪枝与压缩的反模式清单（对照实验 2-3）》

### [KP-02-10] KV Cache 与 Prompt Cache：两个层级的缓存
- **一句话核心**：KV Cache=单次请求内 token 生成加速；Prompt Cache=跨请求复用相同前缀（Anthropic/DeepSeek/GPT-5 约 1/10 成本）。
- **Maka 设计启示**：投影稳定性直接决定 Prompt Cache 命中率；日志记录每次请求 prompt/cached token 作为上下文健康度指标。
- **可写设计文档**：《Prompt Cache 命中率观测与投影稳定性指标》

### [KP-02-11] 缓存作为架构约束
- **一句话核心**：生产级系统中缓存不是事后优化而是**架构约束**——当 Prompt Cache 经济效益显著时，缓存一致性反过来主导架构选择（Claude Code 实践）。
- **关键设计要点**：提示词结构由缓存边界决定；动态注入的工具 schema "追加到末尾且冻结"保持前缀稳定。
- **Maka 设计启示**：剪枝替换决策一旦做出就"冻结"（避免反复重建缓存）；缓存约束应前置进架构设计。
- **可写设计文档**：《缓存经济性作为架构约束》

## 四、提示工程与提示注入

### [KP-02-12~16] 提示工程要点
- **KP-02-12 提示工程全景**：语气/风格（人格）、结构化（格式）、流程驱动 vs 规则堆砌（组织方式）、业务规则细化（内容）、Few-shot 示例（何时给例子）、工具定义设计（何时用/边界/示例）。实验 2-4 消融：信息组织打乱→成功率 -30%+；移除工具描述→调用错误率 +45%。
- **KP-02-13 工具定义设计**：把"何时用、边界、反例、示例、代价"写进描述（与第四章工具描述艺术同源）。
- **KP-02-14 动态提示词**：动态信息追加末尾、不用模板渲染 system prompt。
- **KP-02-15 提示注入攻防（核心威胁）**：每个感知工具都是潜在注入入口（网页隐藏元素/PDF 元数据/图片 EXIF）；上下文层防御核心是帮模型分清**"指令"与"数据"**——来源标记（`<external_content source=...>`）、结构化角色（严格用 Chat Template 角色体系）、输入清洗（只作辅助）；**新增注入面：第三方 Skill 藏恶意指令（安装前必须审查如同审查代码）、状态栏投毒**（状态栏被高度信任，若源自外部污染数据会被反向利用）。上下文层防御只是第一道防线。
- **Maka 设计启示**：Event Log 应在注入点记录"来源标记"（webpage/doc/email/external）；"Feedback is not fact authority"延伸——外部内容/Skill/状态栏都属"低权威输入"，自检结论不得自动升格为系统事实，防止注入内容借自检"洗白"。
- **可写设计文档**：《来源标记、指令/数据分离与注入审计（安全设计）》

## 五、动态提示词与 Agent Skills

### [KP-02-18] Agent Skills：可组合单元与渐进式披露
- **一句话核心**：Skill 是"按需加载的专业知识包"，采用渐进式披露——先给目录摘要（数百 token），需要时再加载完整正文，避免提示词无限膨胀。
- **关键设计要点**：系统提示词膨胀两大问题（浪费 token、注意力稀释=上下文腐化）；**三层结构**（YAML 元数据 name+description 常驻 → 核心流程 SKILL.md 按需加载 → 细则子文档）；Skill 可捆绑可执行代码工具和模板；**description 要像路由条件而非功能介绍——"Use when / Don't use when"+反例，反例不是可选项**（宽泛描述频繁误触发、补反例后准确率回升）；Skill 是自包含知识模块（pip/npm 式生态）；选择 Agent 交互模式应对齐模型厂商训练方法论。
- **Maka 设计启示**：Skill 加载/正文注入都是日志事件（目录常驻 system、正文追加进轨迹）；Maka 可把 Skills 作为"能力即内容"插件体系（类似 opencli adapter），复用"description 带反例"路由规范。
- **可写设计文档**：《Agent Skills 插件模型与渐进式披露实现》

### [KP-02-19] Skills 在上下文中的位置、缓存代价与工具关系
- **一句话核心**：元数据目录=稳定前缀（持续复用 Prompt Cache）；完整正文=调用时进轨迹；"对 KV Cache 友好"并非零成本。
- **关键设计要点**：Skill 目录放 system prompt（Claude Code）或激活工具 description 的固定前缀位置；**Skill+通用执行器模式下工具数量始终很少（第五章约 7 个核心工具）**。
- **Maka 设计启示**：tool 集应"小且稳定"，Skill 目录是稳定前缀、正文追加进轨迹——都在 Event Log 上有对应事件；优先少工具+Skill 而非堆砌工具定义。
- **可写设计文档**：《Skills 的上下文布局与 KV Cache 成本模型》

## 六、Agent 状态栏

### [KP-02-20] 状态栏：理论基础（检索而非推理 + 上下文蒸馏）
- **一句话核心**：状态栏是框架在上下文末尾持续注入的结构化状态摘要；理论基础是**"上下文学习像检索而非推理"——上下文窗口是一台只有一半的检索引擎**（检索很强、没有提炼层）。
- **关键设计要点**：模型不擅长在一次前向传播中"归纳统计"，任何关于已有内容的结论每次都要现算；把分散的隐式状态提炼为显式知识（"本次是第 3 次呼叫"→错误率大幅降低）。上下文蒸馏研究：①弱模型补回准确率（2B 小模型追平不带状态栏的前沿大模型）；②强模型省下效率（思考量/延迟/花费降约一个数量级）；③思考量从"随上下文持续增长"变"基本恒定"。**三条实战经验**：①状态栏用代码维护别拿大模型维护（20 行正则达标准答案级）；②不要删掉原始上下文（状态栏是有损投影，只算"预想会被问到"的维度，没算到的维度断崖崩塌）；③把状态栏准确率当一线生产指标盯（**模型几乎无条件相信状态栏**，写错会原样进最终答案，投毒风险要认真对待）。
- **Maka 设计启示**："代码确定性维护 + 不删原始证据"与"Log is the Runtime / Context is not history"高度同构——状态栏是日志的投影（代码可重算），原始轨迹仍在日志。
- **可写设计文档**：《Agent 状态栏投影：确定性生成与可靠性指标》

### [KP-02-21] 状态栏构成与在上下文中的位置
- **一句话核心**：状态栏含任务规划（TODO）、事件侧信道信息、环境当前状态观察摘要三类元信息；API 层面作为一条 **user 角色消息**插入上下文末尾（借用 user 消息槽位），用 `<agent_status>` 标签包裹。
- **关键设计要点**：末尾+标签=紧邻新 token 最高注意力+追加不破坏缓存；**这里的 user 只是协议层面的技术选择，不等于"终端用户输入"**。五种状态栏技术（实验 2-8）：时间戳跟踪、工具调用计数器、TODO 列表管理（15 vs 21 次迭代）、详细错误信息（替代方案成功率 60%→95%）、系统状态感知；组合产生涌现效应；对模型无侵入、无需微调。
- **Maka 设计启示**：状态栏是"Log is the Runtime"的最佳投影样例；"借用 user 槽位"这一协议细节必须记录清楚（日志区分"真实 user 事件"与"框架注入 user 槽位事件"）。
- **可写设计文档**：《状态栏构成标准与注入协议（含 user 槽位借用约定）》

### [KP-02-22] 状态更新两种实现与缓存代价
- **一句话核心**："追加不破坏缓存"只在单次注入成立；状态更新有两种实现——每轮替换 vs 持久追加，各有明确缓存代价。
- **关键设计要点**：每轮替换=只留一份最新状态但移除旧状态使之后缓存失效（末尾、失效范围只限最近几轮）；持久追加（Claude Code `<system-reminder>`）=完全缓存友好但陈旧状态累积。取舍：更新频繁且轨迹长→追加；轨迹短或单条状态很大→替换。
- **Maka 设计启示**：日志保留全量历史状态事件，投影层按轨迹长度/更新频率选择替换或追加。
- **可写设计文档**：《状态栏更新策略与缓存代价权衡（append vs replace）》

## 七、上下文压缩策略

### [KP-02-23] 压缩：为什么需要 + 上下文学习内部机制
- **一句话核心**：压缩两个动机——长度/成本约束，以及（更深层）**提升思考质量**：总结后的高密度知识比原始形式更利于模型使用，因为"上下文学习本质上是检索而非推理"。
- **关键设计要点**：宠物店 100 笼 90 黑 10 白——思维链每次从零数一遍、成本累积；提前写"黑 90 白 10"→模型立即检索到结论。**上下文腐化（Context Rot）vs 溢出（Overflow）**：腐化是"装得下但找不到了"，更隐蔽，决策质量悄然下滑。设计原则：**不要让模型被动在海量信息中检索，要主动提供提炼过的结构化知识**；上下文学习是快速适配机制而非真正学习。
- **Maka 设计启示**：Compaction 不是丢证据而是"把需思考才能得到的结论变成可检索知识"；警惕上下文腐化（窗口没满也应在质量下滑前压缩）。
- **可写设计文档**：《压缩动机模型与上下文腐化检测》

### [KP-02-24] 压缩与 KV Cache：看似矛盾，实则互补
- **一句话核心**：压缩在两次 API 调用之间由框架对消息列表做预处理——静态前缀永不动、只压缩轨迹中的 tool results。
- **关键设计要点**：压缩对象是 tool results（摘要替换使替换点之后缓存失效）；**最好在上下文接近阈值时批量压缩而非每轮都压**。
- **Maka 设计启示**：Tool Result 剪枝与 Compaction 应落在"调用间隙的投影预处理"层，与日志隔离——正是"Log is the Runtime / Context is not history"的架构分界。
- **可写设计文档**：《压缩调度：时机、位置与批量触发策略》

### [KP-02-25] 生产级分层压缩机制（Claude Code 五层）
- **一句话核心**：成熟系统把多种策略组合为分层压缩，不同类型信息保质期不同。
- **关键设计要点**（五层）：①工具结果预算控制（大输出存磁盘、模型看摘要、替换决策**冻结**保缓存一致性）；②噪声直接删除（对噪声做摘要只是浪费 token）；③API 层微压缩（服务端上下文编辑，适合即将溢出时）；④归档式摘要（**像 git log 保留每轮独立记录，而非 git squash 合并**）；⑤全量压缩（LLM 驱动、最后手段、分两阶段，**配连续失败熔断器**——生产数据表明大量会话困在反复压缩失败循环里）。
- **Maka 设计启示**：剪枝=噪声删除+预算控制，Compaction=归档式/全量压缩；熔断器思想与预算/有界修复一致；"归档式摘要=git log 式逐轮记录"与 Event Log 天然兼容。
- **可写设计文档**：《分层压缩机制与熔断策略（对齐 Claude Code 五层）》

### [KP-02-26] 压缩策略设计原则与对架构的启示
- **一句话核心**：四条设计原则（信息价值非均匀、语义完整性、任务相关性、**压缩即理解**），且"压缩即理解"对架构有深层启示。
- **关键设计要点**：架构启示一：压缩模块本身需要接近主模型的语言理解能力→**"模型调用模型"的递归架构**；启示二：压缩策略与任务类型耦合（检索保留广度、分析保留深度、创作保留灵感触发点）。经济性：上下文感知压缩使 token 减少 75%+。**压缩最易丢的不是细节，而是早期架构决策、约束背后的理由、失败路径**→显式保留优先级：①架构决策和关键约束：不得摘要；②已修改文件列表与关键变更：完整保留；③验证状态（pass/fail）：必须保留；④未解决 TODO 与回滚笔记：必须保留；⑤工具输出：可删除，仅留 pass/fail 结论。
- **Maka 设计启示**：保留优先级清单应直接成为 Compaction 的系统提示/约束；"Context is not history"=压缩改变下次推理看到什么但原始证据仍在日志。
- **可写设计文档**：《压缩保留优先级清单与任务类型自适应策略》

### [KP-02-27] 隔离优于压缩：子 Agent 上下文隔离
- **一句话核心**：比压缩更釜底抽薪——把产生海量中间内容的任务委派给独立子 Agent，子 Agent 只回传几百 token 结论。
- **关键设计要点**：主 Agent 亲自搜索→数万 token 原始代码进主上下文成永久噪声；委派搜索子 Agent→主上下文只加两条消息。**本质是用隔离代替压缩**（压缩是有损的事后补救、隔离让噪声从一开始绝缘）；代价：任务描述必须自包含、目标明确。
- **Maka 设计启示**：直接支撑 TaskRun/Headless 持久任务——子任务各自独立 Task Event Log 与上下文，主日志只记"派发任务+收到结论"两事件；"任务描述必须自包含"应成为派生 TaskRun 的强制契约。
- **可写设计文档**：《子 Agent 上下文隔离与 TaskRun 委派契约》

## 本章金句 / 核心结论
- "人和模型一样，最重要的是 Context"（翁家翌）；"AI 跟人并不在同一个环境里面"。
- "给模型看什么、怎么组织，比模型本身有多聪明往往更影响最终的结果。"
- "AI Agent 就像一个永远的新员工：给足背景信息能干得很好，什么都不告诉它再聪明也是白搭；构建 AI 原生团队首先是一场文档化运动。"
- KV Cache 三条铁律："系统提示词和工具定义一旦确定就不要改""动态信息永远追加到末尾""使用标准 API 格式，不要自行拼接消息"。
- "上下文窗口是一台只有一半的检索引擎"——检索很强、没有"提炼层"。
- "状态栏是对原始上下文的一次有损投影"；"模型几乎无条件相信状态栏"。
- "上下文学习更像是一种快速适配机制，而非真正的学习。"
- "上下文腐化是'装得下但找不到了'，比溢出（'装不下了'）更隐蔽。"
- "压缩即理解"；"压缩最容易丢失的不是细节本身，而是早期的架构决策、约束背后的理由和失败的路径。"
- "隔离优于压缩：压缩是有损的、需要额外 LLM 调用的事后补救；隔离让噪声从一开始就与主上下文绝缘。"
