# Chapter 4 · Tools — Knowledge Point Extraction

> Source: `book/chapter4.md`. Core argument of this chapter: **the quality of tool design determines the upper bound of an Agent's capability, while the asynchronous architecture determines whether the Agent can run reliably in the real world.**

## I. Tool Taxonomy

### [KP-04-01] The five-category tool classification: direction of invocation × object acted upon
- **Core idea in one line**: examine tools through "who initiates this interaction" and "what it acts upon"; each of the five categories occupies a distinct position.
- **Key design points**: perception tools (Agent-initiated, gathering information, granularity trade-offs and output-volume control); execution tools (Agent-initiated, changing the world, **safety constraints are the design core**); collaboration tools (driving sub-agents/humans, motivation = parallelism and heterogeneous division of labor); user-communication tools (conveying information to the user, where "speaking" itself must become an explicit tool call); event-triggered tools (**Agent registers, external party triggers**, involving the two moments of "registration" and "triggering").
- **Maka design implications**: the tool system should explicitly annotate which of the five categories each tool belongs to; user-communication tools and event-triggered tools enter the Runtime Event Log as first-class citizens (recorded at the same level as reply_to_user and bash), not hidden outside the session UI.
- **Writable design doc**: "Maka Tool Taxonomy & Event Typology"

## II. General Principles of Tool Design

### [KP-04-02] Forms of capability expression: dedicated tools vs. skill + generic executor
- **Core idea in one line**: Agent capabilities have two expression forms — structured dedicated code tools versus the "natural-language skill document + generic executor" approach; the choice depends on a three-dimensional decision framework.
- **Key design points**: three dimensions of decision — **parameter complexity** (nested/multi-field joint validation → dedicated structured schema is more robust; simple parameters → CLI is reliable), **change frequency** (frequently changing → skill maintenance cost is far lower), **model capability** (SOTA models can use skill + executor to reduce the number of tools; weaker models need structured schema guidance). Each dedicated tool costs hundreds of tokens, and proliferating their count breaks the KV Cache.
- **Maka design implications**: Read/Write/Edit/Bash/Glob/Grep are exactly the "generic executor" route; complex capabilities should be settled into skill documents rather than creating new dedicated tools for each operation; schema validation should be reserved for the few tools with complex parameters.
- **Writable design doc**: "Maka Capability-Expression Decision Guide (Dedicated Tool vs. Skill)"

### [KP-04-03] Tool-granularity trade-offs and generality design
- **Core idea in one line**: overly fine granularity causes the tool count to explode (with >100 tools even the most advanced LLM tends to mispick); overly coarse granularity makes a single tool too complex; generality follows "generic tools are better than dedicated tools unless there is a clear safety/permission/performance reason."
- **Key design points**: the merging criterion = functional similarity + overlap of usage scenarios (`extract_pdf/docx/pptx` → unified `read_document(file_type=...)`); counterexamples that should not be merged (image OCR vs. video keyframes — parameter/latency differences are large); **the LLM itself has strong reasoning and code-generation abilities that should be leveraged rather than constrained** (a generic `code_interpreter` replaces a dozen dedicated calculators); generality boundary = operations with special permissions/complex configuration/safety risks still need dedicated wrapping (grep syntax varies → a dedicated grep tool).
- **Maka design implications**: Glob and Grep being split into two tools, and unified Read covering multiple formats, is precisely "merge the similar, separate the heterogeneous"; the permission policy determines which operations must be specialized.
- **Writable design doc**: "Maka Tool Granularity & Generality Design Specification"

### [KP-04-04] The art of tool descriptions
- **Core idea in one line**: the core of a tool description is to let the LLM know "**when to use it**" rather than merely "what it can do," and "clearly listing boundary conditions often matters more than describing the capability itself."
- **Key design points**: when to use > what it can do; **the root cause of most invocation failures is not that the model doesn't know what the tool can do, but that it doesn't know what the tool cannot do**; parameter descriptions should use concrete examples instead of abstract specifications; return values should also be described; long-running tools should note the execution cost to guide invocation order; attach 1–5 real invocation examples per tool (examples can raise invocation accuracy from ~72% to ~90%); debugging principle: **when the Agent frequently picks the wrong tool, check the tool description first rather than doubting the model's capability.**
- **Maka design implications**: bake the five fields "when to use / boundaries / counterexamples / examples / cost" into the tool schema as a mandatory specification; feed descriptions together with actual invocations into error-classification analysis to inform description revision.
- **Writable design doc**: "Maka Tool Schema Description Specification & Automated Validation"

### [KP-04-05] Fidelity of parameter passing
- **Core idea in one line**: there must be no systematic deviation between the world the model perceives and the world the tool operates on — tools must not silently modify input/output parameters without the model's knowledge.
- **Key design points**: the silent-input-transformation anti-pattern (Cursor silently converting curly quotes to straight quotes → repeated "no match found" with the model unable to self-diagnose); the silent-parameter-injection anti-pattern (an IDE bash appending markers to `git commit`); if normalization is truly necessary, it must be stated in the tool description and the model must be informed in the return value.
- **Maka design implications**: the tool parameter-passing layer must be "passed through and traced" — the parameters actually passed to Bash/Edit go into the Event Log verbatim; the watchdog/permission layer may reject or rewrite, but any rewrite must be recorded as an explicit event, never silent (echoing "Log is the Runtime").
- **Writable design doc**: "Maka Tool Parameter Fidelity Specification (Transparency Contract)"

### [KP-04-06] Three generations of tool-design evolution
- **Core idea in one line**: tool design evolves from "API wrapping" to "ACI (Agent-Computer Interface)," and then to "optimizing tools for invocation, chaining, and discovery."
- **Key design points**: first generation = one tool per API endpoint (too fine); second generation = ACI principles (tools should correspond to Agent goals, be friendly to Agents rather than humans); third generation answers three questions — invoked accurately (example-driven), discovered (dynamic discovery instead of injecting everything at once), and chained (**code-orchestrated execution: the LLM generates a script in one shot, intermediate variables stay in the execution environment, and only the final result returns** — batch-extracting fields across multiple crawled web pages reduced token consumption by roughly two orders of magnitude).
- **Maka design implications**: the Event Log natively supports third-generation "code orchestration" (intermediate results go to the log, not the context; only the final result returns to the model's context); the docs should clarify how the two paradigms, "tool-call sequences" and "script orchestration," coexist.
- **Writable design doc**: "Maka Tool Evolution & Code-Orchestration Support"

## III. The Tool Ecosystem: MCP

### [KP-04-07] MCP protocol ecosystem and trust model
- **Core idea in one line**: MCP is the "socket standard" of the AI tool ecosystem (develop once, use everywhere); but connecting third-party servers introduces a new trust boundary.
- **Key design points**: standardized tool descriptions (JSON Schema), flexible transport (stdio/Streamable HTTP), separation of resources and tools; MCP's limitation = it only standardizes capability interaction, **not a complete event runtime** (event architectures spanning sessions/multiple event sources/offline wake-up need to be layered above the protocol); four risk categories in the trust model — **tool-description poisoning** (description enters the context along with the definition = a prompt-injection variant, effective on every session), malicious or hijacked servers, **same-name tool shadowing** (intercepting sensitive parameters), and credential-management risk; mitigations = review descriptions as untrusted input before connecting, lock server versions, least-privilege credentials, and an independent sidecar security review at runtime.
- **Maka design implications**: when integrating MCP, "integration review" should be hardened into a process (description audit + version locking + least-privilege credentials); dynamic availability defaults to "do not auto-expose all MCP tools wholesale," decoupling whether to adopt MCP from whether to inject everything.
- **Writable design doc**: "Maka MCP Integration & Trust Model (Trust & Review Policy)"

### [KP-04-08] MCP context-overhead management and progressive disclosure
- **Core idea in one line**: MCP ecosystem expansion brings huge tool-definition overhead; progressive disclosure with "give little by default, load on demand" is needed to control context.
- **Key design points**: scale of overhead — just 5 MCP servers can introduce ~55,000 tokens of tool definitions (nearly 30% of a 200K context); Cursor's approach (tool-name index → on-demand definition lookup) cut tokens by **46.9%** in A/B testing; Pi Coding Agent's trade-offs (deliberately not baking MCP into the core, `pi-mcp-adapter`'s model sees only ~200 tokens of proxy tools by default, "search → view definition → invoke"); two independent decisions — the backend keeps MCP ecosystem compatibility, the frontend does progressive disclosure via CLI + skills or proxy tools.
- **Maka design implications**: "dynamic availability" is precisely progressive disclosure put into practice — by default only basic tool names are exposed and the full schema is injected on demand; tool definitions are projectable, reclaimable resources, not context that must always be resident.
- **Writable design doc**: "Maka Tool Context Budget & Progressive Disclosure"

## IV. Perception Tools

### [KP-04-09] Perception-tool interface design and the three paths to multimodal perception
- **Core idea in one line**: perception tools face the challenge that "returned volume far exceeds processing capacity," requiring careful design at both the interface layer (pagination/explicit truncation/caching/parallelism) and the multimodal output form.
- **Key design points**: search-type tools return structured candidate lists (title/location/summary) rather than full text; read-type tools support offset/limit and **truncation must be explicitly visible** ("displayed lines 1–200 of 5000 total" — silent truncation is dangerous); the read-only dividend = results can be cached and run in parallel; three paths for multimodal perception: native multimodality (highest capability ceiling, token-hungry), extraction to text (saves tokens, loses layout/figures), and tool-ized multimodal analysis (`analyze_image/pdf/audio` takes "file + question" and returns text conclusions, leaving only a short Q&A in context).
- **Maka design implications**: the Read tool must implement explicit truncation + offset/limit and write the truncation fact into the Event Log (what the model sees = a projection of the log); read-only tool results can be cached/parallelized, providing a replayable basis for recovery.
- **Writable design doc**: "Maka Perception-Tool Interface Specification (Truncation / Pagination / Caching / Multimodality)"

## V. Execution Tools (Safety-Mechanism Focus)

### [KP-04-10] Layered design of execution-tool safety mechanisms
- **Core idea in one line**: execution-tool safety cannot rely on a single mechanism; it needs multiple layers of protection — input validation, permission control, proposer-reviewer, sidecar, sandbox isolation, automated verification, observability, and idempotency semantics stacked layer upon layer.
- **Key design points**: layer one, input validation (path traversal / command injection, where **fast failure is the key** — reject immediately upon detecting an anomaly, don't attempt "smart" correction); permission control (restrict working directory, command blacklist, quotas and rate limiting); **the blacklist is only the most basic protection** (attackers can bypass with obfuscated commands; semantic parsing that understands actual intent is more robust); sandbox isolation increases in strength: **process-level (low-risk local execution) → container (Docker, shared kernel, escapable) → microVM/VM (Firecracker, hardware-level, strongest)**; a venv is not a sandbox; containers/microVMs should have CPU/memory/disk/network limits set.
- **Maka design implications**: the permission policy explicitly states "fast failure over smart correction"; the watchdog is responsible for semantic-level risk judgment (going beyond blacklist matching); the Bash isolation tier, resource limits, and permission policy are configured in pairs and written to the log.
- **Writable design doc**: "Maka Execution-Tool Safety Layers (Input Validation / Permission / Sandbox)"

### [KP-04-11] The proposer-reviewer mechanism (pre-approval and post-verification)
- **Core idea in one line**: use an independent second perspective to inspect the output of the first perspective — pre-approval (Proposer proposes + Reviewer approves) and post-verification (modality switching to check results).
- **Key design points**: model selection — the proposing and approving models **come from different families but have similar capability** (cognitive diversity avoids making the same mistakes and having the same blind spots; similar capability ensures the reviewer can keep up); the underlying prompt rules are consistent, with different focuses (proposal emphasizes action orientation, approval emphasizes risk control); **the rejection reason is added to the trajectory as a tool-call result** (reusing the Agent's ability to handle tool failures); optimizations: risk-tiered approval (high-risk mandatory review, low-risk direct execution) + escalation to human oversight; suitable for irreversible, high-impact operations. Post-verification = **modality switching** (code rendered for visual inspection, config actually run in the sandbox) — different modalities complement each other; a single modality tends to fall into the same blind spot.
- **Maka design implications**: Self-check producing evidence and one bounded repair opportunity can be borrowed directly — a self-check rejection enters the Event Log as a tool-call-level event, letting the Agent digest it through its existing failure-handling path (consistent with "Feedback is not fact authority").
- **Writable design doc**: "Maka Proposer-Reviewer & Self-Check Audit (Proposer-Reviewer)"

### [KP-04-12] The sidecar mechanism: safety validation running in parallel with the main reasoning
- **Core idea in one line**: the sidecar is a lightweight LLM call that accompanies the main Agent's reasoning loop; rather than reviewing the final output, it independently judges the main Agent's **behavior** (each tool call), runs in parallel with streaming output, and acts as a gate over the reviewed calls.
- **Key design points**: difference from proposer-reviewer — the sidecar judges simple classification problems ("is this command dangerous"), so a lightweight model suffices; **the key to preventing prompt injection: the sidecar deliberately reads only structured fields (`{tool: "bash", command: "rm -rf /tmp/data"}`) and does not read the main model's free-form text** (attackers can smuggle language into user input/web pages); rejection circuit breaker (on consecutive rejections, don't retry infinitely — fall back to asking the user to judge manually); "display" and "allow" are split and run in parallel (the UI first shows progress hints while the background runs the safety check).
- **Maka design implications**: the watchdog adopts the "structured input + independent lightweight judgment + gating + rejection circuit breaker" pattern; every safety judgment is itself a log event (auditable) — a safety check is not an opaque external referee, but a replayable fact in the log.
- **Writable design doc**: "Maka Watchdog / Sidecar Safety-Validation Design"

### [KP-04-13] Execution-tool engineering essentials: verification loops, long output, observability, idempotency, and cancellation
- **Core idea in one line**: execution tools additionally need four kinds of engineering support: "automated-verification feedback loops, truncation and persistence of long output, observability, and idempotency and cancellation semantics."
- **Key design points**: automated-verification loop (after write_file writes code, immediately run the linter for the file type, with the structured error list as part of the tool return value); long-output truncation (when above threshold, return a few head lines + a few tail lines + a note about omitted middle + the save path); observability (logging/auditing/performance metrics/alerts); **idempotency and cancellation** — operations carry a unique identifier for server-side deduplication, or use "query first, then mutate"; non-idempotent operations (sending email/making calls/transferring money) use a **two-stage "pre-check–confirm"** (stage one validates and rehearses, returning a confirmation token; stage two executes with the token; on failure, don't re-send in place).
- **Maka design implications**: "Log is the Runtime" directly provides the data foundation for observability; abort semantics should be combined with idempotency design; Bash/Edit long-output truncation strategies should be codified as a documentation standard.
- **Writable design doc**: "Maka Execution-Tool Engineering Specification (Verification / Truncation / Audit / Idempotency / Cancellation)"

## VI. Collaboration Tools

### [KP-04-14] Collaboration tools and human-in-the-loop
- **Core idea in one line**: collaboration tools let the Agent delegate subtasks to other Agents or humans; the core is sub-agent lifecycle primitives + prompt elements + the HITL learning loop.
- **Key design points**: **specialized division of labor beats the "all-round" Agent**; four elements of the sub-agent prompt (clear role, explicit context-source labeling with `[FROM_MAIN_AGENT]`/`[FROM_USER]`/`[TOOL_RESULT]` to prevent source confusion and prompt injection, task boundaries, standardized output format); three groups of interface primitives (spawn and cancel, messaging, discovery `list_agents`); HITL: timeout and degradation ("fall back to a conservative strategy if no response in 5 minutes"), feedback loops (approvals/rejections with reasons constitute evidence-backed feedback data — which can be distilled into the knowledge base/skills, with high-dimensional implicit preferences becoming post-training data).
- **Maka design implications**: TaskRun natively supports subtask modeling — spawn_subagent starts a child TaskRun, with events entering the same Task Event Log; HITL approvals/rejections serve as evidence-backed log facts for arbitration over "whether feedback becomes fact."
- **Writable design doc**: "Maka Collaboration Tools & HITL Decision Loop"

## VII. Event-Driven Asynchronous Agents

### [KP-04-15] Why asynchrony and event-driven mechanics are needed
- **Core idea in one line**: a synchronous Agent can only "wait in line to be called," unable to handle three real assistant capabilities: asynchronous execution as the norm, dynamic priority judgment over events, and smooth interruption recovery; **"LLM training assumes synchrony / real deployment demands asynchrony" is the fundamental contradiction running through all engineering trade-offs.**
- **Key design points**: event-driven architecture — all inputs (user messages / tool returns / external callbacks / scheduled triggers) are uniformly modeled as an **event stream**; OpenClaw's three mechanisms (Hooks lifecycle events / Cron scheduling / Heartbeat polling) — only Cron/Heartbeat let the Agent "move on its own" without user messages, but they lack an immediate channel for third-party event sources; the PineClaw Channel mechanism (real-time event channel between the Gateway and the Pine API, with instant push) solves placing OTP calls on behalf of the user / three-party confirmation. Core value: **true "proactive service" requires not only the Agent periodically checking the world, but also the world proactively notifying the Agent.**
- **Maka design implications**: "A task may outlive a Turn" precisely needs the event-stream model — the Task Event Log unifies user messages / tool returns / external callbacks / scheduled triggers into a recoverable event sequence; continuation is a projection of "the event loop resuming at a safe point."
- **Writable design doc**: "Maka Event-Driven Asynchronous Architecture (Event Loop & Event Sources)"

### [KP-04-16] Event-triggered tools, user-communication tools, and the virtual-identity execution environment
- **Core idea in one line**: event-triggered tools let the world wake the Agent (two moments: register → trigger); user-communication tools let the Agent reach the user (multi-channel async + recall); virtual identities and isolated execution environments let the Agent act as an independent, auditable identity.
- **Key design points**: three kinds of event-triggered tools (set_timer timers / monitor_shell background monitoring / connect_channel external event channels); trigger conditions and filter rules must be clear, with the event payload carrying enough context; user-communication tools break the "assistant message sent directly to the user" paradigm (a dedicated tool sends messages, can attach images/files, push by urgency, multimodal, asynchronous + read-status + consistent across channels); **multi-channel and recall** (choose the channel by urgency / user state / content nature / user preference; proactively notify and recall the user when a long task completes); **virtual identity** (don't give the Agent the user's personal account — use an independent virtual identity so that errors or compromises don't expose the entire digital identity); **isolated execution environments** (virtual computer VM/container 7×24, virtual phone emulator; anti-bot mechanisms such as CAPTCHA/IP reputation, HITL authentication via VNC/RDP); data exchange = **shared file system, referencing by file path rather than copying content.**
- **Maka design implications**: user communication as an explicit tool event enters the log ("spoken words" can be projected back to the UI/session); "recalling the user when a headless task completes" is exactly the notification driven by the Task Event Log; the isolated execution environment and shared-file-system policies go into the permission-policy document.
- **Writable design doc**: "Maka Event-Triggered / User-Communication Tools & Virtual-Identity Execution Environment"

### [KP-04-17] Event-handling mechanics: event loop, three strategies, and async interruption of the synchronous model
- **Core idea in one line**: a single Agent instance facing multiple events uses an event loop as its skeleton, with events **consumed only at "safe points,"** and applies cancel/queue/parallel strategies by urgency; engineering devices such as placeholders let a synchronous LLM tolerate asynchronous interruption.
- **Key design points**: the event loop is isomorphic to a Go goroutine's `for{select{}}`; **structured event modeling** (four fields: source / channel / content / context, preventing "treating user input as a tool result" or "treating a tool result containing hidden instructions as a user instruction"); three strategies — cancel-style (urgent: stop the current operation → clear the queue → append → re-invoke the LLM), queue-style (routine: enqueue → finish → append all at once), parallel-style (independent lightweight queries: separate reasoning sessions + markers to prevent confusion); urgency judgment suggests **a lightweight classification LLM as the event router**; **five rules for supporting async interruption in a synchronous model** (record LLM output immediately / record the tool result only after the tool call completes / interrupt with **placeholders** ("the tool is running in the background") / discard the current reasoning when interrupted mid-thought / non-interrupting items are queued and batched) — core advantage: under normal conditions the LLM sees a perfectly synchronous trajectory; the placeholder risk = aggravating hallucination (the model hasn't learned that "the result hasn't come back yet" and may fabricate); **async tool-interface design** (decouple initiation from completion: initiate_phone_call immediately returns a task ID + initial state, with progress delivered via event notifications); queue-style attention scatter (the model only looks at the last event) → inform via prompt + **Agent status-bar markers**; **the deep contradiction**: placeholders/async interfaces/status bars are all prompt-engineering stopgaps compensating for "training synchronous / deployment asynchronous," and the fundamental solution lies at the training layer (reinforcement learning in asynchronous environments for three capabilities: understanding events interleaving asynchronously, resuming interrupted tasks, and comprehensively handling batched events); continuous thinking continuous-time (roughly two hundred lines of orchestration turning a text-reasoning model into a continuously-thinking Agent that listens while it thinks).
- **Maka design implications**: the Task Event Log is exactly the "structured event stream" — event modeling (source / channel / content / context) maps directly onto the log schema; the three strategies combined with budget/continuation provide scheduling semantics for "interruptible, resumable persistent tasks"; placeholders and status-bar markers can be borrowed as UI/context presentation rules for log projection.
- **Writable design doc**: "Maka Event-Handling Strategies & Async Interrupt of the Synchronous Model (Async Interrupt & Resume)"

## VIII. Proactive Tool Discovery and Progressive Disclosure of Skills

### [KP-04-18] Proactive tool discovery and progressive disclosure of skills
- **Core idea in one line**: when tools grow from a dozen to hundreds or thousands, the Agent should shift from "passively accepting all schemas" to "proactively declaring gaps, with the system injecting on demand," or switch to a skill directory consulted "on demand."
- **Key design points**: full injection fails (thousands of tools fill the context and selection accuracy drops); **model-native proactive discovery** (MCP-Zero: the Agent generates structured request blocks, with two-level semantic routing from server-level to tool-level, saving ~98% of tokens across ~2,800 tools); hierarchical matching and degradation (first locate by server, then match tools; if everything is below threshold, explicitly return "not found"); **dynamic loading and the KV Cache** (append the new tool schema to the end of the context, keeping the static prefix stable for full reuse; "append to the end" happens only in the discovery turn, and from then on it stays at its position in the trajectory and hits the cache); mainstream implementations (OpenAI's tool_search + defer_loading, Claude Code's lazy MCP-tool loading, Codex BM25); **progressive disclosure of skills** (no embedded index infrastructure needed — at startup only a few hundred tokens of the directory are visible, sub-documents are read when needed, browsed via ordinary file reading); the native-tool vs. skill trade-off (native tools use JSON for inputs/outputs and are more robust with complex parameters; skills are fully natural language, friendly to human authors but more demanding of the model, and more error-prone with complex parameters — complex structured parameters are best written to a JSON file and imported via the command line); skills and the KV Cache (an editable, composable KV Cache pre-compiles and caches each skill, with RoPE repositioning for paste in O(L)).
- **Maka design implications**: "dynamic availability" supports both paths at once — local/core tools use a static prefix; external/MCP tools go through "proxy tools or a tool-search meta-tool + on-demand injection fixed at the position of first injection"; skill directories + progressive disclosure are consistent with "Context is not history" (tool definitions are projectable resources).
- **Writable design doc**: "Maka Proactive Tool Discovery & Progressive Disclosure of Skills (Discovery & Progressive Disclosure)"

## Golden Quotes / Core Conclusions of This Chapter
- "The quality of tool design determines the upper bound of an Agent's capability, while the asynchronous architecture determines whether the Agent can run reliably in the real world."
- "One bottom line running through all tool design is the fidelity of parameter passing: there must be no systematic deviation between the world the model perceives and the world the tools operate on."
- "The root cause of most tool-invocation failures is not that the model doesn't know what the tool can do, but that it doesn't know what the tool cannot do."
- "Generic tools are better than dedicated tools unless there is a clear safety, permission, or performance reason — the LLM itself has strong reasoning and code-generation abilities, and we should leverage that ability rather than constrain it."
- "True 'proactive service' requires not only that the Agent can periodically check the world, but also that the world can proactively notify the Agent."
- "Events are consumed only at the boundary of each loop iteration"; cancellation does not "forcibly cut off at an arbitrary moment, but checks at safe points whether it has been asked to stop."
- "Under normal conditions what the LLM sees is a perfect synchronous trajectory... only when interruption is truly necessary do we introduce the placeholder — that 'necessary compromise.'"
- "Whether to adopt MCP" and "whether to expose all MCP tool definitions at session start" are two independent decisions.
- "Skills transform the 'tool selection' problem into a 'knowledge retrieval' problem — and the latter is exactly what large language models excel at."

## Discussion Questions from the Book (transcribed key points)
1. MCP standardization makes complex interaction patterns (streaming / bidirectional / stateful) hard to express — what capability does MCP most need to extend?
2. When event-queue priority judgment requires semantic understanding, should a rule engine or another LLM make the judgment? What are the costs of each?
3. How do you choose when multiple MCP servers provide functionally overlapping tools? When same-name tools behave slightly differently, can the Agent perceive and exploit the differences?
4. Independent virtual identity vs. operating accounts as the user's own identity — which scenario calls for which? (Trust/authorization vs. security boundary)
5. When 20 events are backlogged in the queue, how should presentation order/format be organized so the model doesn't miss key information?
6. Where else can the "execute–verify–feedback" loop be applied? For which operations does the cost/risk of verification exceed the operation itself?
7. Besides proactive discovery, what other solutions exist for the "tool explosion" of thousands of tools? (Referencing human-expert strategies)
