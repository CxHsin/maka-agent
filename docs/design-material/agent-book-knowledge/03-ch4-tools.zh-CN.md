# 第 4 章 · 工具 —— 知识点提取

> 来源：`book/chapter4.md`。本章核心论点：**工具设计的质量决定了 Agent 的能力上限，而异步架构决定了 Agent 能否在真实世界中可靠运行。**

## 一、工具分类

### [KP-04-01] 五类工具分类：调用方向 × 作用对象
- **一句话核心**：从"这次交互由谁发起"和"作用于什么"审视工具，五类工具各自定位不同。
- **关键设计要点**：感知工具（Agent 主动、获取信息，粒度权衡与输出量控制）；执行工具（Agent 主动、改变世界，**安全约束是设计核心**）；协作工具（驱动子 Agent/人类，动机=并行与异构分工）；用户沟通工具（向用户传递信息，"说话"本身要成为显式工具调用）；事件触发工具（**Agent 注册、外部触发**，涉及"注册"与"触发"两个时刻）。
- **Maka 设计启示**：工具系统显式标注每类属于五类哪一类；用户沟通工具与事件触发工具作为一等公民进入 Runtime Event Log（reply_to_user 与 bash 同级记录），不藏在会话 UI 之外。
- **可写设计文档**：《Maka 工具分类与事件模型（Tool Taxonomy & Event Typology）》

## 二、工具设计通用原则

### [KP-04-02] 能力表达形式：专用工具 vs Skill + 通用执行器
- **一句话核心**：Agent 能力有两种表达形态——结构化专用代码工具与"自然语言 Skill 文档+通用执行器"，选择取决于三维决策框架。
- **关键设计要点**：三维决策——**参数复杂度**（嵌套/多字段联合校验→专用结构化 schema 更稳；简单参数→CLI 可靠）、**变更频率**（频繁变化→Skill 维护成本远低）、**模型能力**（SOTA 模型可用 Skill+执行器减少工具数；弱模型需结构化 schema 引导）。每个专用工具占数百 token、数量膨胀破坏 KV Cache。
- **Maka 设计启示**：Read/Write/Edit/Bash/Glob/Grep 正是"通用执行器"路线；复杂能力应沉淀为 Skill 文档而非为每个操作新建专用工具；schema 校验保留给参数复杂的少数工具。
- **可写设计文档**：《Maka 能力表达决策指南（专用工具 vs Skill）》

### [KP-04-03] 工具粒度权衡与通用性设计
- **一句话核心**：粒度过细导致工具数量激增（>100 个时最先进 LLM 也易选错）、粒度过粗使单工具过于复杂；通用性遵循"通用工具优于专用工具，除非有明确安全/权限/性能理由"。
- **关键设计要点**：整合判据=功能相似性+使用场景重叠度（`extract_pdf/docx/pptx` → 统一 `read_document(file_type=...)`）；不应整合反例（图片 OCR vs 视频关键帧，参数/延迟差异大）；**LLM 本身有强大思考与代码生成能力应利用而非限制**（通用 `code_interpreter` 代替十几个专用计算器）；通用性边界=特殊权限/复杂配置/安全风险操作仍要专用封装（grep 语法各异→专门 grep 工具）。
- **Maka 设计启示**：Glob 与 Grep 分成两个工具、统一 Read 覆盖多格式，正是"相似整合、异构分离"；权限策略决定哪些操作必须专用化。
- **可写设计文档**：《Maka 工具粒度与通用性设计规范》

### [KP-04-04] 工具描述的艺术
- **一句话核心**：工具描述的核心是让 LLM 知道"**什么时候用**"而非只是"能做什么"，且"清晰列出边界条件往往比描述能力本身更重要"。
- **关键设计要点**：何时用 > 能做什么；**大多数调用失败的根因不是模型不知道工具能做什么，而是不知道不能做什么**；参数描述用具体例子代替抽象规范；返回值也要描述；长耗时工具注明执行代价引导调用顺序；每工具附 1-5 个真实调用示例（示例可将调用准确率从 ~72% 提升到 ~90%）；调试原则：**Agent 频繁选错工具时优先检查工具描述而非怀疑模型能力**。
- **Maka 设计启示**：工具 schema 内置"何时用/边界/反例/示例/代价"五字段作为强制规范；描述与实际调用一起纳入错误分类分析反哺描述修正。
- **可写设计文档**：《Maka 工具 Schema 描述规范与自动校验》

### [KP-04-05] 参数传递的保真性
- **一句话核心**：模型感知到的世界与工具操作的世界之间不能存在系统性偏差——工具不得在模型不知情时静默修改输入/输出参数。
- **关键设计要点**：静默输入转换反模式（Cursor 把弯引号静默转直引号→反复"未找到匹配"、模型无法自我诊断）；静默参数注入反模式（IDE bash 给 git commit 附加标记）；若确需规范化必须在工具描述说明并在返回中告知模型。
- **Maka 设计启示**：工具参数传递层必须"透传且留痕"——真实传给 Bash/Edit 的参数原样进 Event Log；watchdog/权限可以拒绝/改写，但任何改写作为显式事件记录、绝不静默（呼应 Log is the Runtime）。
- **可写设计文档**：《Maka 工具参数保真性规范（Transparency Contract）》

### [KP-04-06] 工具设计演进三代
- **一句话核心**：工具设计从"API 封装"演进到"ACI（Agent-Computer Interface）"，再到"优化工具被调用、串联与发现"。
- **关键设计要点**：第一代=每个 API 端点一个工具（过细）；第二代=ACI 原则（工具应对应 Agent 目标、对 Agent 而非人友好）；第三代回答三个问题——准确调用（示例驱动）、被发现（动态发现不一次全注入）、被串联（**代码编排执行：LLM 一次性生成脚本、中间变量留在执行环境、只有最终结果返回**——抓多网页批量提字段 token 消耗降低约两个数量级）。
- **Maka 设计启示**：Event Log 天然支持第三代"代码编排"（中间结果进日志不进上下文、只有最终结果回模型上下文）；文档应明确"工具调用序列"与"脚本编排"两种范式如何共存。
- **可写设计文档**：《Maka 工具演进与代码编排支持》

## 三、工具生态：MCP

### [KP-04-07] MCP 协议生态与信任模型
- **一句话核心**：MCP 是 AI 工具生态的"插座标准"（一次开发、处处可用）；但接入第三方服务器引入新的信任边界。
- **关键设计要点**：标准化工具描述（JSON Schema）、传输层灵活（stdio/Streamable HTTP）、资源与工具分离；MCP 局限=只标准化能力交互，**不是完整事件运行时**（跨会话/多事件源/离线唤醒的事件架构需在协议之上分层构建）；信任模型四类风险——**工具描述投毒**（description 随定义进上下文=提示注入变种、每次会话生效）、恶意/被劫持服务器、**同名工具遮蔽 tool shadowing**（截获敏感参数）、凭证管理风险；缓解=接入前把 description 当不可信输入审查、锁定服务器版本、最小权限凭证、运行时 Sidecar 独立安全审查。
- **Maka 设计启示**：接入 MCP 应把"接入审查"固化为流程（描述审计+版本锁定+最小权限凭证）；动态可用性默认"不自动全量暴露 MCP 工具"，把是否采用 MCP 与是否全量注入解耦。
- **可写设计文档**：《Maka MCP 接入与信任模型（Trust & Review Policy）》

### [KP-04-08] MCP 上下文开销管理与渐进式披露
- **一句话核心**：MCP 生态扩张带来巨大工具定义开销，需用"默认少给、按需加载"的渐进式披露控制上下文。
- **关键设计要点**：开销量级——仅 5 个 MCP 服务器就可能引入约 55,000 token 工具定义（200K 上下文近三成）；Cursor 方案（工具名索引→按需查定义）A/B 减少 **46.9%** token；Pi Coding Agent 取舍（核心刻意不内置 MCP、`pi-mcp-adapter` 模型默认只见约 200 token 代理工具、"搜索→查看定义→调用"）；两个独立决策——后端保留 MCP 生态兼容、前端以 CLI+Skills 或代理工具做渐进式披露。
- **Maka 设计启示**："动态可用性"正是渐进式披露落地——默认只暴露基础工具名、按需注入完整 schema；工具定义是可投影、可回收的资源，不是必须常驻的上下文。
- **可写设计文档**：《Maka 工具上下文预算与渐进式披露（Progressive Disclosure）》

## 四、感知工具

### [KP-04-09] 感知工具接口设计与多模态感知三路径
- **一句话核心**：感知工具面临"返回量远超处理能力"的挑战，需在接口层（分页/显式截断/缓存/并行）与多模态输出形态上精心设计。
- **关键设计要点**：搜索类返回结构化候选列表（标题/位置/摘要）而非全文；读取类支持 offset/limit、**截断必须显式可见**（"已显示第 1-200 行，共 5000 行"——静默截断危险）；只读红利=结果可缓存、可并行；多模态感知三路径：原生多模态（能力上限最高、耗 token）、提取为文本（token 更省、丢版式图表）、工具化多模态分析（`analyze_image/pdf/audio` 接受"文件+问题"返回文本结论，上下文只留简短问答）。
- **Maka 设计启示**：Read 工具必须实现显式截断+offset/limit，并把截断事实写进 Event Log（模型所见=日志投影）；只读工具结果可缓存/并行，为恢复提供可重放依据。
- **可写设计文档**：《Maka 感知工具接口规范（截断/分页/缓存/多模态）》

## 五、执行工具（安全机制重点）

### [KP-04-10] 执行工具安全机制的层次化设计
- **一句话核心**：执行工具安全不能依赖单一机制，需多层防护——输入验证、权限控制、提议者-审核者、Sidecar、沙盒隔离、自动验证、可观测性、幂等语义层层叠加。
- **关键设计要点**：第一层输入验证（路径遍历/命令注入，**关键是快速失败**——发现异常立即拒绝，不尝试"智能"修正）；权限控制（限制工作目录、命令黑名单、配额限速）；**黑名单只是最基础防护**（攻击者可变形命令绕过，更健壮是语义解析理解实际意图）；沙盒隔离强度递增：**进程级（低风险本地执行）→ 容器（Docker，共享内核可逃逸）→ microVM/虚拟机（Firecracker，硬件级最强）**；venv 不是沙盒；容器/microVM 设 CPU/内存/磁盘/网络上限。
- **Maka 设计启示**：权限策略明确"快速失败优先于智能修正"；watchdog 负责语义级风险判断（超越黑名单匹配）；Bash 隔离层级、资源上限与权限策略成对配置并写入日志。
- **可写设计文档**：《Maka 执行工具安全层次（Input Validation / Permission / Sandbox）》

### [KP-04-11] 提议者-审核者机制（事前审批与事后验证）
- **一句话核心**：用独立第二视角检验第一视角产出——事前审批（Proposer 提议 + Reviewer 审批）与事后验证（模态切换检验结果）。
- **关键设计要点**：模型选择——提议与审批模型**来自不同家族但能力相似**（认知多样性避免同错同盲、能力相近确保审批者跟得上）；提示词底层规则一致、关注点差异（提议强调行动导向、审批强调风险控制）；**拒绝理由作为工具调用结果加入轨迹**（复用 Agent 处理工具失败能力）；优化：风险分级审批（高风险必审、低风险直执）+ 人类监督升级；适用于不可逆、影响重大操作。事后验证=**模态切换**（代码渲染成视觉检查、配置在沙盒实际运行）——不同模态互补、单一模态易陷同一盲区。
- **Maka 设计启示**：Self-check 产生证据和一次有界修复机会可直接借鉴——自检拒绝作为一条工具调用级事件进入 Event Log，让 Agent 用既有失败处理路径消化（与 Feedback is not fact authority 吻合）。
- **可写设计文档**：《Maka 提议者-审核者与自检审计（Proposer-Reviewer）》

### [KP-04-12] Sidecar 机制：与主思考并行的安全校验
- **一句话核心**：Sidecar 是伴随主 Agent 思考循环运行的轻量级 LLM 调用，不审最终输出而独立判断主 Agent 的**行为**（每次工具调用），对流式输出并行、对被审调用起门控作用。
- **关键设计要点**：与提议者-审核者区别——Sidecar 判简单分类问题（"命令是否危险"）、轻量模型足够；**防提示注入关键：Sidecar 刻意只读结构化字段（`{tool:"bash", command:"rm -rf /tmp/data"}`），不读主模型自由文本**（攻击者可在用户输入/网页夹带话术）；拒绝熔断器（连续拒绝不无限重试，回退请求用户手动判断）；"展示"与"放行"拆开并行（界面先显示进度提示、后台跑安全检查）。
- **Maka 设计启示**：watchdog 采用"结构化输入+独立轻量判断+门控+拒绝熔断"模式；每次安全判断本身就是一条日志事件（可审计）——安全检查不是黑盒外部裁判，而是日志中的可回放事实。
- **可写设计文档**：《Maka Watchdog / Sidecar 安全校验设计》

### [KP-04-13] 执行工具工程要点：验证闭环、长输出、可观测性、幂等与取消
- **一句话核心**：执行工具还需"自动验证反馈闭环、长输出截断持久化、可观测性、幂等性与取消语义"四类工程支撑。
- **关键设计要点**：自动验证闭环（write_file 写码后立即按文件类型跑 linter，结构化错误列表作为工具返回值一部分）；长输出截断（超阈值返头尾各若干行+中间提示省略+保存路径）；可观测性（日志/审计/性能指标/告警）；**幂等与取消**——操作带唯一标识服务端去重或"先查询后变更"；不可幂等操作（发邮件/拨电话/转账）用**"预检-确认"两段式**（第一段校验预演返回确认令牌、第二段凭令牌执行，失败不就地重发）。
- **Maka 设计启示**：Log is the Runtime 直接为可观测性提供数据底座；abort 语义结合幂等设计；Bash/Edit 长输出截断策略应作为文档规范。
- **可写设计文档**：《Maka 执行工具工程规范（验证/截断/审计/幂等/取消）》

## 六、协作工具

### [KP-04-14] 协作工具与人工介入
- **一句话核心**：协作工具让 Agent 把子任务委托给其他 Agent 或人类，核心是子 Agent 生命周期原语 + 提示词要素 + HITL 学习闭环。
- **关键设计要点**：**专业化分工优于"全能"Agent**；子 Agent 提示词四要素（角色清晰、上下文来源明确标注 `[FROM_MAIN_AGENT]`/`[FROM_USER]`/`[TOOL_RESULT]` 防来源混淆与提示注入、任务边界、输出格式标准化）；接口三组原语（启动与取消 spawn/cancel、消息传递、发现 list_agents）；HITL：超时与降级（"5 分钟无响应采用保守策略"）、反馈循环（批准/拒绝及理由构成带证据的反馈数据——可归纳进知识库/Skill、高维隐式偏好成后训练数据）。
- **Maka 设计启示**：TaskRun 天然支持子任务建模——spawn_subagent 即启动子 TaskRun、事件进同一 Task Event Log；HITL 的批准/拒绝作为带证据日志事实，供"反馈是否成为事实"的仲裁使用。
- **可写设计文档**：《Maka 协作工具与 HITL 决策闭环》

## 七、事件驱动的异步 Agent

### [KP-04-15] 为什么需要异步与事件驱动机制实现
- **一句话核心**：同步 Agent 只能"排队叫号"，无法应对异步执行常态、事件优先级动态判断、中断恢复流畅性三项真实助理能力；**"LLM 训练假设同步 / 真实部署要求异步"是贯穿所有工程取舍的根本矛盾**。
- **关键设计要点**：事件驱动架构——所有输入（用户消息/工具返回/外部回调/定时触发）统一建模为**事件流**；OpenClaw 三机制（Hooks 生命周期事件/Cron 定时/Heartbeat 轮询）——只有 Cron/Heartbeat 让 Agent 无用户消息也能"自己动起来"，但对第三方事件源缺乏即时通道；PineClaw Channel 机制（Gateway 与 Pine API 间实时事件通道、即时推送）解决代打电话 OTP/三方确认。核心价值：**真正的"主动服务"不仅需要 Agent 定时检查世界，更需要世界主动通知 Agent**。
- **Maka 设计启示**："A task may outlive a Turn"正需要事件流模型——Task Event Log 把用户消息/工具返回/外部回调/定时触发统一为可恢复事件序列；continuation 即"事件循环在安全点恢复"的投影。
- **可写设计文档**：《Maka 事件驱动异步架构（Event Loop & Event Sources）》

### [KP-04-16] 事件触发工具、用户沟通工具与虚拟身份执行环境
- **一句话核心**：事件触发工具让世界能唤醒 Agent（注册→触发两时刻）；用户沟通工具让 Agent 能触达用户（多渠道异步+召回）；虚拟身份与隔离执行环境让 Agent 以独立、可审计身份行动。
- **关键设计要点**：事件触发三类（set_timer 定时器/monitor_shell 后台监控/connect_channel 外部事件通道）；触发条件与过滤规则要清晰、事件载荷含足够上下文；用户沟通工具打破"assistant 消息直发用户"范式（专门工具发消息、可附图/附件/按紧急度带推送、多模态、异步+已读状态+多渠道一致）；**多渠道与召回**（按紧急程度/用户状态/内容性质/用户偏好选渠道；长任务完成时主动通知召回）；**虚拟身份**（不给 Agent 用户个人账号，独立虚拟身份——出错或被攻破不暴露全部数字身份）；**隔离执行环境**（虚拟电脑 VM/容器 7×24、虚拟手机模拟器；反机器人机制 CAPTCHA/IP 信誉、HITL 认证 VNC/RDP）；数据交换=**共享文件系统、以文件路径引用传递而非内容拷贝**。
- **Maka 设计启示**：用户沟通作为显式工具事件进日志（"说出口的话"可投影回 UI/会话）；headless 任务"完成时召回用户"正是 Task Event Log 驱动的通知；隔离执行环境与共享文件系统策略写入权限策略文档。
- **可写设计文档**：《Maka 事件触发/用户沟通工具与虚拟身份执行环境》

### [KP-04-17] 事件处理机制：事件循环、三策略与同步模型异步打断
- **一句话核心**：一个 Agent 实例面对多事件，以事件循环为骨架、**事件只在"安全点"被消费**，按紧急度采取取消式/队列式/并行式三策略；用占位符等工程手段让同步 LLM 容忍异步打断。
- **关键设计要点**：事件循环与 Go goroutine `for{select{}}` 同构；**结构化事件建模**（来源/渠道/内容/上下文四字段，防"把用户输入当工具结果"或"把藏指令的工具结果当用户指令"）；三策略——取消式（紧急：停当前操作→清队列→追加→重调 LLM）、队列式（常规：入队→完成→一次性追加）、并行式（独立轻量查询：独立推理会话+标记防混淆）；紧急度判定建议**轻量分类 LLM 作事件路由器**；**同步模型支持异步打断五条规则**（LLM 输出立即记录/工具调用完成才记 tool result/打断用**占位符**（"工具正在后台执行"）/思考中打断丢弃当前思考/非打断入队批处理）——核心优势：常态下 LLM 看到完美同步轨迹；占位符风险=加剧幻觉（模型没学会"结果还没回来"可能编造）；**异步工具接口设计**（解耦启动与完成：initiate_phone_call 立即返回任务 ID+初始状态、进展靠事件通知）；队列式注意力分散（模型只看最后事件）→提示词告知+**Agent 状态栏标记**；**深层矛盾**：占位符/异步接口/状态栏都是提示工程弥补"训练同步/部署异步"的权宜之计，根本解法在训练层（异步环境强化学习三能力：理解事件异步穿插、恢复被打断任务、批量事件综合处理）；持续思考 continuous-time（约两百行编排把文本思考模型变持续思考 Agent、边听边想）。
- **Maka 设计启示**：Task Event Log 正是"结构化事件流"——事件建模（来源/渠道/内容/上下文）直接落到日志 schema；三策略与 budget/continuation 结合为"可中断、可恢复的持久任务"提供调度语义；占位符与状态栏标记可借鉴为日志投影的 UI/上下文呈现规则。
- **可写设计文档**：《Maka 事件处理策略与同步模型异步打断（Async Interrupt & Resume）》

## 八、主动工具发现与 Skills 渐进式披露

### [KP-04-18] 主动工具发现与 Skills 渐进式披露
- **一句话核心**：工具从十几个增长到成百上千时，让 Agent 从"被动接受全部 schema"变为"主动声明缺口、系统按需注入"，或改用 Skill 目录"按需查阅"。
- **关键设计要点**：全量注入失效（上千工具塞满上下文、选择精度下降）；**模型原生主动发现**（MCP-Zero：Agent 生成结构化请求块、服务器级→工具级两层语义路由，约 2800 工具省 ~98% token）；层次化匹配与降级（先按服务器定位再匹配工具、都低于阈值明确返回"未找到"）；**动态加载与 KV Cache**（把新工具 schema 追加到上下文末尾、静态前缀保持稳定完全复用；"追加到末尾"只发生在被发现那一轮，此后固定在轨迹原位置命中缓存）；主流实现（OpenAI tool_search + defer_loading、Claude Code MCP 工具延迟加载、Codex BM25）；**Skill 渐进式披露**（不需要嵌入索引基础设施——启动只见目录数百 token、需要时再读子文档，靠通用文件阅读翻阅）；模型原生工具 vs Skill 取舍（原生用 JSON 定输入输出、参数复杂时更稳；Skill 全自然语言、对人类编写者友好但对模型要求更高、参数复杂时更易错——复杂结构化参数建议写 JSON 文件再命令行导入）；Skills 的 KV Cache（可编辑可组合的 KV Cache 把每个 skill 预编译缓存、RoPE 重定位粘贴 O(L)）。
- **Maka 设计启示**："动态可用性"同时支持两条路径——本地/核心工具静态前缀、外部/MCP 工具走"代理工具或工具搜索元工具+按需注入且固定于首次注入位置"；Skill 目录化+渐进式披露与 Context is not history 一致（工具定义是可投影资源）。
- **可写设计文档**：《Maka 主动工具发现与 Skill 渐进式披露（Discovery & Progressive Disclosure）》

## 本章金句 / 核心结论
- "工具设计的质量决定了 Agent 的能力上限，而异步架构决定了 Agent 能否在真实世界中可靠运行。"
- "贯穿所有工具设计的一条底线是参数传递的保真性：模型感知到的世界与工具操作的世界之间不能存在系统性的偏差。"
- "大多数工具调用失败的根因不是模型不知道工具能做什么，而是不知道工具不能做什么。"
- "通用工具优于专用工具，除非存在明确的安全、权限或性能理由——LLM 本身具有强大的思考和代码生成能力，我们应该利用这种能力而不是限制它。"
- "真正的'主动服务'不仅需要 Agent 能定时检查世界，更需要世界能主动通知 Agent。"
- "事件只在每轮循环的边界被消费"；取消"不在任意时刻强行掐断，而是在安全点检查是否被要求停止"。
- "常态下 LLM 看到的是完美的同步轨迹……只有在确实需要打断时才引入占位符这个'必要的妥协'。"
- "是否采用 MCP"与"是否会话开始就暴露所有 MCP 工具定义"是两个独立决策。
- "Skills 把'工具选择'问题转化为'知识检索'问题——后者正是大语言模型擅长的。"
