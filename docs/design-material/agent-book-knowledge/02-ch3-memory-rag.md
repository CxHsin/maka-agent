# Chapter 3 · User Memory and Knowledge Base — Knowledge Point Extraction

> Source: `book/chapter3.md`. Two main threads: **user memory** (individual personalization, persistent and auditable) and **knowledge base/shared knowledge** (collective knowledge). They share underlying techniques such as vector retrieval and knowledge compression, and face the same challenges of information conflict, knowledge staleness, and inaccurate retrieval.

## I. User Memory Systems

### [KP-03-01] The Essence of User Memory: From Conversation to Predictive Model
- **One-sentence core**: User memory is not about "recording every word the user says" but about investing extra LLM compute to explicitly extract and compress key information scattered across lengthy conversations into a "concise and effective predictive model about the user."
- **Key design points**: Three key characteristics — **selectivity** (keep only facts useful for the future), **abstraction** (distill general preferences rather than binding to a single instance), **structure** (Markdown/JSON for ease of retrieval); contrast with in-context learning: user memory is **persistent and auditable**, while in-context learning is **temporary and disappears when the session ends**.
- **Maka design implication**: Local memory should be positioned as a **projection derived from the Runtime Event Log** — memory is not appending raw conversation text into storage, but having a background LLM task "extract + compress" auditable persistent facts from the logs.
- **Writable design doc**: "Maka Local Memory: An Extraction Pipeline Design from Runtime Event Log to Persistent Memory"

### [KP-03-02] Memory Capability Evaluation: A Three-Tier Framework
- **One-sentence core**: Decompose memory capability into three progressive tiers — "basic recall → multi-session retrieval → proactive serving" — as a yardstick for measuring the contribution of each retrieval technique.
- **Key design points**: Academic benchmark LoCoMo (~300 turns, up to 35 sessions); eight capabilities (personal info retention/preference tracking/context switching/memory updating/multi-session continuity/complex reasoning/temporal awareness/conflict resolution); **Tier 1 basic recall** (accurately return directly provided information), **Tier 2 multi-session retrieval** (retrieve across objects and time spans, then reason and judge), **Tier 3 proactive serving** (synthesize sessions from long ago to provide anticipatory help, e.g., proactively linking passport info from months ago when booking an international flight and warning of expiry). Evaluation method: 20 cases per tier, keep only memory state with no access to the original conversation, LLM-as-a-judge scoring.
- **Maka design implication**: Build an equivalent three-tier evaluation baseline for Local memory (SQLite test fixtures + LLM-as-a-judge); "keeping only memory without looking back at the original conversation" corroborates "Context is not history" — what is being evaluated is the projection, not the raw text.
- **Writable design doc**: "Maka Local Memory Three-Tier Evaluation Framework and Regression Test Plan"

### [KP-03-03] Memory Design Dimensions: Hierarchy (Where to Store) and Cognitive Science Foundations (What to Store)
- **One-sentence core**: Three orthogonal dimensions of memory design — **where to store (trajectory/long-term memory/business state), how to store (storage format), what to store (episodic/semantic/procedural)**.
- **Key design points**: **Trajectory** = complete history of a single run (append-only, for auditing); **user long-term memory** = persistent cross-session storage (preferences/summaries/knowledge points); **business state** = developer-defined high-level state abstraction; cognitive mapping: working memory ↔ context window, episodic memory ↔ semantic memory ↔ procedural memory; the trajectory is immutable, working memory is a dynamic subset.
- **Maka design implication**: Runtime Event Log = trajectory layer (append-only, auditable); Local memory = cross-session projection; SQLite can model each separately: `events` (append-only), `memories` (mutable/evictable), `task_state` (business state); schema carries `kind: episodic|semantic|procedural`.
- **Writable design doc**: "Maka Memory Layering and Runtime Event Log Storage Model (Trajectory/Long-Term Memory/Business State)"

### [KP-03-04] Four Storage Formats for User Memory
- **One-sentence core**: The same piece of user information can be stored at four progressive levels by granularity and structural complexity — Simple Notes, Enhanced Notes, JSON Cards, Advanced JSON Cards; the core tension is "simplicity vs expressiveness."
- **Key design points**: Simple Notes = minimal indivisible facts (O(1) extremely low overhead, but associations lost); Enhanced Notes = complete contextual paragraphs (semantically complete, but expensive to update); JSON Cards = category → subcategory → key-value pairs (support partial updates, rigid structure); Advanced JSON Cards = each card adds **backstory** (the narrative background of the information source), **person/relationship** (solving disambiguation — "Dr. Zhang" is simultaneously a dentist and a cardiologist), and timestamps. Practical standard: use Advanced JSON Cards for **key and few** facts to preserve retrievability, use Simple Notes for **many and non-critical** facts to control cost; most production systems use a hybrid mode. Experiment 3-2: Simple Notes are cheapest but lose points on cross-session association; Advanced JSON Cards have the best disambiguation but maintenance calls are more expensive and slower.
- **Maka design implication**: Add a `format` field to the SQLite `memories` table to enable hybrid mode; leverage UPDATE semantics to implement partial updates of JSON Cards; the four formats can be made switchable write strategies for reproducible evaluation.
- **Writable design doc**: "Maka Local Memory Storage Formats and Hybrid-Mode Strategy (SQLite Schema Design)"

### [KP-03-05] Advanced Knowledge Representation: Executable Code (User as Code)
- **One-sentence core**: Swap the "representation medium" of user memory from text to **executable code** — use typed Python objects to hold state, functions to encode constraint rules, so that aggregation/conflict discovery/constraint enforcement move from LLM "mental math" to deterministic code.
- **Key design points**: Two-phase update = **memory phase** (after each session, append facts to an **append-only fact log**) + **structuring phase** (periodically regenerate the entire typed Python from the full log) — essentially the classic database pattern **"write-ahead log WAL + periodic checkpoint"** applied to LLM memory for the first time. Three deterministic capabilities: aggregate statistics (~100% accuracy), conflict discovery (cross-checking drug allergies), constraint enforcement (automatic alert when passport validity is under 180 days before departure). Source: *User as Code: Executable Memory for Personalized Agents* (arXiv:2606.16707).
- **Maka design implication**: In TypeScript, model key rule-based local memories as validated typed objects + pure-function constraints; "WAL+checkpoint" maps directly to Maka's Runtime Event Log (append-only evidence) + Compaction/checkpoint (structured projection).
- **Writable design doc**: "Maka Executable Memory: Representing Local Memory as Typed State and Constraint Functions"

### [KP-03-06] Memory Framework Case Studies: Mem0 and Memobase
- **One-sentence core**: Two open-source memory frameworks embody two philosophies — Mem0 evolves from "disambiguation at write time" to "append-only writes + reasoning at retrieval time," while Memobase focuses on "user profiles + event memory."
- **Key design points**: Mem0 v3 (append-only ADD, triple-path hybrid retrieval of semantic + BM25 + entities, plus temporal sorting): LoCoMo 71.4→92.5, LongMemEval 67.8→94.4, avoids losing history from erroneous UPDATE/DELETE and reduces LLM calls; Memobase = Profile (configurable slots) + Event Memory (timeline) + buffered batching to amortize cost. Reference architecture: three types of long-term memory (episodic/semantic/procedural) plus one working-memory layer; **real-world frameworks implement only one or two of these — making trade-offs based on business needs is more in line with engineering reality than pursuing a big, all-encompassing design**.
- **Maka design implication**: Mem0 v3's "append-only + hybrid retrieval + temporal sorting" is highly isomorphic with tenets 1/2; store "timestamped, multi-version facts + FTS/vector/entity triple-path retrieval" in SQLite; build memory extraction as an asynchronous, batched background task that can be paused/resumed.
- **Writable design doc**: "Maka Local Memory Conflict Handling Strategy: Disambiguation at Write Time vs Reasoning at Retrieval Time (Comparison and Selection)"

### [KP-03-07] Memory Compression and Consolidation Mechanisms
- **One-sentence core**: Long-term accumulated memory will "explode in storage" and drag down retrieval accuracy, requiring multi-level compression strategies — importance filtering, clustering summarization, abstraction/generalization, versioned conflict detection; this is a **storage-layer** consolidation algorithm, operating at a different level than the single-session context compression of Chapter 2.
- **Key design points**: Importance scoring with four factors (access frequency/time decay/emotional intensity/information uniqueness); clustering (group similar memories, generate representative summaries, archive originals in secondary storage); abstraction/generalization (concrete → semantic/procedural memory); conflict detection uses a **versioned approach** (keep historical versions + mark the latest version; for the current address keep only the latest, for work history preserve the full history).
- **Maka design implication**: Memory consolidation should be an **offline/background batch task** and comply with Tenet 2 — consolidation only changes "what the next inference sees" (projection/retrieval view), never deletes the raw evidence in the Event Log; compressed detailed memories go to secondary archive rather than physical deletion.
- **Writable design doc**: "Maka Memory Compression and Periodic Consolidation Background Task Design (Importance Scoring/Clustering/Versioning)"

### [KP-03-08] Privacy Protection: Log Sanitization
- **One-sentence core**: Let the Agent both use user information to provide personalized service and keep sensitive data out of the LLM context and system logs — use a **local small model** for PII detection and sanitization (instead of a cloud API).
- **Key design points**: Why local deployment is a must — logs themselves may contain sensitive information, and sending them to the cloud for sanitization defeats the whole purpose of privacy; invoke a local Qwen3 0.6B via Ollama; recognize three types of sensitive content (structured/semi-structured/natural-language expressions); JSON Schema structured output; LLM sanitization achieves 95%+ recall and significantly reduces false positives; for extremely high throughput use a regex + LLM hybrid.
- **Maka design implication**: The Event Log is "log as runtime," where privacy risk concentrates — a **pre-filter for sanitization** (local small model + regex hybrid) should be inserted before events enter the log/context, preserving an "auditable-after-sanitization" mapping (sensitive values replaced with placeholder tokens rather than irreversibly deleted); sanitization conclusions carry confidence scores and allow human review (don't blindly trust a single small-model judgment).
- **Writable design doc**: "Maka Log Sanitization and Privacy Boundary Design (Local PII Detection, Pre-Sanitization, Audit Mapping)"

## II. RAG Fundamentals

### [KP-03-09] RAG Pipeline and Document Chunking
- **One-sentence core**: RAG = retrieve relevant chunks → inject into context → LLM generates based on context; **the retriever's quality sets the ceiling — if relevant chunks can't be retrieved, no matter how strong the LLM is, you can't cook without rice**.
- **Key design points**: Three chunking strategies — fixed-size (512 tokens, 50–100 overlap), **recursive/structure-aware (the most common default in production systems)**, semantic splitting (cut where embedding similarity drops off a cliff); common starting chunk sizes of 256–1024 tokens with 10%–20% overlap; **inherent chunking flaw: it severs the connection between a chunk and its original context** ("the company's revenue grew 3%" — which company, which quarter?), addressed by contextual retrieval (KP-03-17).
- **Maka design implication**: For ingesting a local knowledge base into SQLite, do structure-aware chunking first and **retain "source context metadata" at write time** (original location/title/timestamp); avoid misreading "Context is not history" as "the chunk is everything."
- **Writable design doc**: "Maka Knowledge Base Ingestion Pipeline: Chunking Strategy and Source Metadata Design"

### [KP-03-10~11] Dense Embeddings and Sparse Embeddings
- **KP-03-10 Dense embeddings**: words/sentences → high-dimensional vectors, cosine similarity measures direction (semantics) rather than length; Word2Vec cannot handle polysemy, while BERT/BGE-M3 use self-attention for context-aware representation; **ANN indexes** (ANNOY trees vs HNSW graphs: comparison of build speed/memory/incremental updates/precision — choosing an index strategy matters as much as choosing an embedding model).
- **KP-03-11 Sparse embeddings**: TF-IDF → BM25 (term-frequency saturation k1 + length normalization b); inverted index; exact matching suits technical code/person names but cannot read synonymous expressions; learned sparsity (SPLADE/BGE-M3 sparse branch) sits between sparse and dense.
- **Maka design implication**: For local-first, choose a context-aware embedding model that can run on the machine (BGE-M3 class); use SQLite's built-in **FTS5** to implement BM25-style full-text search (person names/card numbers/commands/term queries), complementing vector retrieval; embeddings are "derived indexes" and should be rebuildable.
- **Writable design docs**: "Maka Vector Retrieval Infrastructure: Embedding Model and ANN Index Selection" + "Maka Local Full-Text Search: SQLite FTS5/BM25 Implementation and Chinese Word Segmentation"

### [KP-03-12] Hybrid Retrieval: Fusion, Neural Reranking, and Quality Metrics
- **One-sentence core**: Dense search understands semantics but misses keywords; sparse search is exact but can't read synonyms — hybrid retrieval runs both engines, and the difficulty lies in fusing scores with wildly different distributions.
- **Key design points**: Three-stage pipeline (parallel retrieval → result fusion → neural reranking); fusion methods: normalized weighted sum or **RRF reciprocal rank fusion** (`Σ 1/(k+rank)`, k≈60, using only ranks and losing relevance signal); reranking uses a Cross-Encoder (concatenate query + document and compare token-by-token) with far higher precision than a Bi-Encoder, **reranking does not replace fusion**; quality metrics recall@k (book's definition = hit rate/success@k), MRR, nDCG; "no single retrieval strategy is reliable in all scenarios — the combination of dense + sparse + reranking is what makes a production-grade system."
- **Maka design implication**: Local retrieval as "FTS5(BM25) + vector" dual path + RRF fusion, with reranking as an optional slow path (enabled only for critical queries to control latency); use recall@k/MRR measured on an evaluation set so retrieval quality is regression-testable.
- **Writable design doc**: "Maka Hybrid Retrieval Pipeline: FTS5 + Vector + RRF + Optional Reranking"

## III. Beyond Flat Text: Knowledge Organization and Retrieval

### [KP-03-13] Structured Indexing: RAPTOR and GraphRAG
- **One-sentence core**: Flat chunking ignores the internal structure of knowledge and cross-document relationships; model attention is a "similarity-based soft retrieval" rather than a thinking engine that can summarize and generalize — one must **invest compute at the indexing stage to actively distill, abstract, and structure**.
- **Key design points**: Two cases (counting 100 cats, Xfinity promotion rules) show that top-k truncation is inherently at odds with "statistics/induction," requiring pre-generated summaries/rules to be indexed. **RAPTOR** = tree-like hierarchy (clustering → parent-node summaries → recurse to root, multi-granularity retrieval); **GraphRAG** = entity-relationship graph (multi-hop relationship reasoning, entity disambiguation), with limitations: NL→triple semantic degradation (conditions/temporal dependencies lost), extraction errors polluting the knowledge; recommendation: **complementary layering** (full natural language preserves semantics + structured metadata index for retrieval). When needed: only worth the investment when queries frequently require cross-document synthesis or multi-level navigation (cost and latency increase significantly).
- **Maka design implication**: Local personal data is small in scale, so default to hybrid retrieval and enable structured indexing on demand (enable entity indexes locally for vertical scenarios requiring multi-hop/entity disambiguation); be sure to preserve the natural-language originals; index construction is budget-constrained.
- **Writable design doc**: "Maka Knowledge Organization Selection: Decision Matrix for Hybrid-Retrieval-First + On-Demand Structured Indexing"

### [KP-03-14] The Filesystem Paradigm: OpenViking's L0/L1/L2 and Link Indexing
- **One-sentence core**: Map context (memory/resources/skills) to directories and files in a virtual filesystem (unique URIs), with on-demand loading via the L0/L1/L2 three-tier summaries and Markdown plain text as the underlying representation.
- **Key design points**: `viking://` tree; **L0 summary (~100-token one-liner) → L1 overview (~2000 tokens) → L2 full text**, most queries can complete decisions at L1, sharing the same origin as Skills' progressive disclosure; Markdown plain text (readable, editable, Git-rollback-able) rather than a dedicated database; **an overlooked prerequisite: links and indexes must be established between files** (`.abstract/.overview` are the vertical hierarchy, but horizontal associations are also needed — like Wikipedia entries interlinking + index pages); **it must be written explicitly into the writing prompt: each new entry must first retrieve and link related existing entries, and update the index page** (strong models self-refer back spontaneously; many models only append in isolation).
- **Maka design implication**: The local-file-first temperament is a natural fit; expose Local memory/knowledge base as a `maka://memories/...` tree namespace; L0/L1/L2 is isomorphic with Tenet 2 (resident lightweight summaries, pull full text on demand); the writing prompt must explicitly require "retrieve first, then link, and maintain the index," otherwise knowledge degrades into isolated islands.
- **Writable design doc**: "Maka Knowledge Filesystem Paradigm: Namespace, L0/L1/L2 Progressive Disclosure, and Link Indexing Conventions"

### [KP-03-15] Knowledge Updates: Incremental Updates and Periodic Consolidation (Proposer-Reviewer)
- **One-sentence core**: Going live with a knowledge base requires two rhythms at once — **event-triggered incremental updates** to absorb new evidence promptly, and **periodically triggered full consolidation** to eliminate long-accumulated problems; both paths run the proposer-reviewer closed loop of "**treat the knowledge base as a codebase, treat every change as a PR**."
- **Key design points**: Four incremental steps (Proposer submits a PR — first retrieve related existing knowledge before adding/deleting/modifying, maintain link/index/time metadata/evidence references → Reviewer independently reviews — check every assertion against original evidence, return actionable opinions pointing to evidence and line numbers → iterate until convergence (set a max iteration/budget; escalate to humans when exceeded) → publish after merge (CI checks format/links/permissions, rebuilds indexes)); **three-layer separation: original evidence layer (append-only) → knowledge layer (revisable) → serving layer (rebuildable derived indexes)**; Proposer/Reviewer **must be Agents, not two fixed LLM calls** (they must actively search, trace evidence, and run checks); heterogeneous cross-review (similar capability, different model families) + permission-enforced division of labor (Proposer writes only to a working branch, Reviewer reads only evidence, only the merge process updates the main branch); three core periodic consolidation tasks (dedupe/stale-removal/merge, cross-check against original data, conflict resolution with qualification — if something holds across different times/objects/regions/tasks, write the applicable scenario into the knowledge rather than deleting an entry); **retrieval must filter by the caller's permissions — never let an unauthorized document enter the context** (push permission filtering down to the retrieval layer); stale-content detection and retirement (version numbers + effective/expiry time metadata).
- **Maka design implication**: The three-layer separation is precisely the realization of "Log is the Runtime + Context is not history" (evidence layer = Event Log, knowledge layer = Local memory projection, serving layer = SQLite derived indexes); build local knowledge updates as an auditable proposer-reviewer process (TaskRun budget + continuation to support long reviews), with evidence references pointing to Event Log event IDs; heterogeneous cross-review + division of labor applies to local single machines too (two local models taking turns + working branch/main store isolation).
- **Writable design doc**: "Maka Knowledge Update Governance: Proposer-Reviewer Review Closed Loop and Three-Layer Storage Separation"

### [KP-03-16] Agentic RAG
- **One-sentence core**: Upgrade RAG from a passive one-way "retrieve-generate" pipeline to a "dynamic, iterative exploration process led by the Agent" — knowledge base retrieval is encapsulated as a **tool** the Agent can call at any time, running through a ReAct loop.
- **Key design points**: Tool encapsulation (`knowledge_base_search`), Agent thinks → acts → observes → evaluates whether information is sufficient → iterates to refine the query; Experiment 3-8 ablation: for simple questions, non-agentic RAG is faster and of comparable quality, **while the gap is significant for complex multi-hop questions** (agentic RAG's expert-style multi-turn); the value is "**solving problems** rather than 'answering questions'," trading response speed for robustness and quality on complex problems; **security boundary (indirect prompt injection)**: external documents retrieved into the context are the most typical vector; defense = instruction/data separation (source marking) + never letting retrieved content directly trigger high-risk operations.
- **Maka design implication**: Make Local memory/knowledge base retrieval an **Agent-callable tool** (`search_user_memory`/`search_knowledge`) rather than automatic injection; all call records/retrieval trajectories go into the Event Log (replayable and auditable); retrieval results must carry source markers and never directly trigger side-effecting actions.
- **Writable design doc**: "Maka Agentic Retrieval: search_user_memory Tool Contract and Secure Source Marking"

### [KP-03-17] Contextual Retrieval and the Two-Tier Memory Architecture
- **One-sentence core**: The inherent chunking flaw is severing the connection between a chunk and its context; Anthropic's solution is to use an LLM to generate a "contextual prefix summary" for each chunk **before vectorizing/indexing** (adding), then applying it in reverse to user memory + resident Advanced JSON Cards to form the **two-tier memory architecture** that supports "proactive serving."
- **Key design points**: At index time (not run time), generate a prefix for each chunk ("[This section is excerpted from ACME Inc.'s FY2025 Q2 financial report]"); this simultaneously strengthens BM25 (adding exactly matchable keywords) and dense search (injecting semantic background); cost is manageable via prompt caching (~$1 per million document tokens); Anthropic's data: combined with BM25, retrieval failure rate drops 49%, and adding reranking brings it to 67%; draw a clear line against Chapter 2's "context-aware compression" (one is additive on text chunks at index time, the other is subtractive on conversation history at run time). **Two-tier memory architecture**: Advanced JSON Cards resident in the context provide the "overview" + contextual retrieval fetches "details" on demand — the Tier-3 "proactive serving" is implemented in engineering for the first time (needing both global overview and precise details).
- **Maka design implication**: When writing knowledge base/memory retrieval chunks, **generate the contextual prefix first, then embed** (adding "background" at index time); adopt the two-tier approach for Local memory: JSON Cards resident in SQLite (small and controllable in volume) + contextually indexed raw conversation chunks retrieved on demand.
- **Writable design doc**: "Maka Two-Tier Memory Architecture: Resident JSON Cards + Contextual Retrieval, and Index Prefix Generation Strategy"

### [KP-03-18] Deep Knowledge Extraction and Multimodal Memory
- **One-sentence core**: Faced with massive structured case data, RAG must leap from "information retrieval" to "knowledge discovery" — first distill unstructured case facts into structured JSON, then use factor analysis to quantify weights, so the Agent can "read" the data rather than merely retrieve it.
- **Key design points**: Two-stage knowledge discovery (knowledge extraction and structuring: define a "comprehensive yet consistent" schema; factor analysis: **bottom-up factor discovery** — let the LLM freely list the factors influencing verdicts to build a modular schema that fits the data; one-hot switch bits to encode categories and avoid misleading numeric magnitudes; cluster to find "case archetypes" and build a factor-importance hierarchical model); application: Agent conversational information gathering (ask questions by importance to fill key factors → retrieve the most similar archetype → give an analysis backed by precedents); **three approaches to multimodal memory**: ① store raw data + text description; ② store embeddings in context (**each embedding costs 1 token, a 1000-token region can hold 1000 faces**); ③ store embeddings in model parameters (fact-LoRA's indirect reasoning fails — "storing a fact is one thing; getting the model to know when to use it is another").
- **Maka design implication**: The knowledge base needn't be just a retrieval repository — for structured datasets you can run "bottom-up factor discovery + factor-importance model" offline tasks to produce reusable decision logic; for multimodality, first implement approaches ①/② (media files + text descriptions, or key embeddings as 1-token context regions).
- **Writable design doc**: "Maka Deep Knowledge Discovery and Multimodal Memory Roadmap (Data-Driven Factor Modeling + Media Embedding Storage)"

## Chapter Gold Quotes / Core Conclusions
- "User memory is persistent and auditable; in-context learning, by contrast, is temporary and disappears when the session ends."
- "The trajectory is a running account; user long-term memory is an archive" — the former is append-only within a single session, the latter is repeatedly rewritten/merged/evicted across sessions.
- "Making trade-offs based on business needs is more in line with engineering reality than chasing a big, all-encompassing design."
- Mem0 v3: "append-only writes + hybrid retrieval + temporal sorting," LoCoMo 71.4→92.5.
- "No single retrieval strategy is reliable in all scenarios. Combining dense, sparse, and reranking is the right way to build a production-grade RAG system."
- "Treat the knowledge base as a codebase, and treat every knowledge change as a Pull Request"; "indexes are rebuildable derived artifacts; the reviewed knowledge in Git is the true source of truth."
- "Retrieval must be filtered by the caller's permissions — never let an unauthorized document enter a user's context" — push permission filtering down to the retrieval layer.
- "The value of agentic RAG lies in its ability to 'solve problems' rather than 'answer questions.'"
- "The two-tier memory architecture — Advanced JSON Cards resident in the context providing the 'overview,' contextual retrieval fetching 'details' on demand — is the concrete implementation path for 'proactive serving,' the highest tier of the three-tier framework."
- "Storing a fact is one thing; getting the model to know when to use it is another."

## Thinking Questions from the Book (Transcribed Key Points)
1. When the same user provides contradictory information (two addresses) across different sessions, how should the memory system handle the conflict?
2. When the original documents are messy/contradictory, contextual retrieval propagates and amplifies errors — how can an "information quality" signal be introduced at the retrieval stage?
3. A model that doesn't know what it doesn't know cannot correctly trigger a search — how should agentic RAG's "metacognition" problem be solved?
4. Converting charts into text descriptions loses spatial relationships — give a concrete example and design a preservation scheme.
5. Is the entire knowledge system (chunking/indexing/retrieval pipeline) itself a form of "hand-crafted design"? Once models are strong enough, will it be replaced by "full input"?
6. After model capabilities improve, do domain knowledge bases still matter? Will the foundation model contain all domain knowledge?
7. What types of queries are RAPTOR trees and GraphRAG graphs respectively best at answering?
8. In what scenarios does the filesystem paradigm have an advantage over traditional vector-database RAG?
9. Can data-driven discovery of "adjudication factors" reach the quality of human-expert hand-written rules?
10. Design incremental + periodic consolidation for a Markdown memory base; if the Reviewer uses the same model as the Proposer and only sees the chunks the Proposer selected, what errors will be merged? (Improve from three aspects: model independence, evidence coverage, tool permissions.)
