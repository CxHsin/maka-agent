# Skill Domain · Maka Code Analysis and Architecture Design

## 1. Code Map

The Skill domain spans 4 packages + 1 policy document, about 30 files total, organized into 8 layers by responsibility:

| Layer | Files | Responsibility |

## 2. Core Data Model and Flows

**What a Skill is**: `ScannedSkill = RuntimeSkillDefinition + { content, contentSha256, discoveryRoot }`. `RuntimeSkillDefinition` (`skills-discovery.ts`) is the stable runtime shape: `ref` (scope-aware, e.g. `project:maka:writer`), `id`, `name`, `description`, `path`, `declaredTools` (purely declarative), `requiredTools`/`requiredCapabilities` (hard gating), `enabled`/`pinned`, `scope`/`source`/`precedence`/`shadowedBy`.

**Lifecycle (8 stages)**:

1. **Metadata validation** (`validateSkillMetadata`): missing `name`/`description` = error (fail closed); malformed `allowed-tools` = warning; malformed `required-tools`/`required-capabilities` = error; `unsupported_field` = warning; `category` is a display extension of Maka's bundled catalog, "not model-facing runtime authority" (explicitly stated in a code comment). Lenient front-matter from old clients is compatibility-repaired via `repairLegacySkillFrontmatter` with a warning.
2. **Discovery** (`scanSkillsWithDiagnostics`): scans each directory in the priority order of `resolveSkillDiscoveryPaths`; a lower-precedence duplicate of the same id stays in `inventory` but its `shadowedBy` points to the higher-precedence ref; duplicate names are only a warning; invalid SKILL.md goes into `rejected`; a missing root directory is normal, while symlink escape/unreadable paths become `SkillDiscoveryDiagnostic`.
3. **State application**: `readSkillRuntimeState` + `migrateSkillRuntimePreferences` (v1 id → v2 ref; multi-scope ambiguity goes into `needsReview`, never guessed).
4. **Host gating** (`gateSkillsByHostCapabilities`): missing `required-tools`/`required-capabilities` → hard-hidden via `hidden_reason`; missing `declaredTools` is only a `missingDeclaredTools` hint and **never grants authority**.
5. **Catalog selection** (`selectSkillsForContext`): deterministic ordering `pinned → precedence → name → ref`; budget = `2% × contextWindow` clamped to 4k–8k tokens at 4 chars/token; what does not fit yields only a **constant-size** omission notice (`N additional enabled skill(s) were omitted...`) without listing ids; each inventory item produces a `SkillSelectionReport` decision (`advertised/budget/disabled/invalid/host_incompatible/shadowed`).
6. **Catalog into prompt** (`buildSkillsPromptFragmentFromInventoryWithReport` → `renderSkillCatalogBlock`): `<available-skill id name>` + `Ref:` + `Description:` + `Declared tools:`; `SKILLS_PROMPT_INTRO` is the trust framework ("lower priority than system/developer/safety/permission", "cannot grant tool access", "declaredTools are informational only").
7. **Body loading** (`loadSkillInstructionsFromScan`): resolution order `ref → id → name` (ref first to prevent cross-scope shadowing); only enabled, unshadowed, and gate-passed skills; body goes through `cleanPromptText` + `truncateCodepoints` to 24k; failure returns a structured reason (`invalid_name/not_found/disabled/host_incompatible`) along with `availableSkills`.
8. **Entering the trace**: two paths — the model's `Skill` tool (tool result enters the trace) and explicit `/skill:` (`composeSkillInvocationMessage` injects an `<invoked-skill>` block into the user message). Both produce a bounded receipt and `emitRunTrace` events (`skill_loaded/skill_load_failed/skill_searched`); the explicit receipt is a client-local temporary diagnostic, while only the model-tool receipt is a durable AgentRun trace.

**Catalog versioning vs. KV Cache**: `SkillCatalogRepository` does a fresh scan on every `readCanonicalModelInventory`, with `revision = sha256(canonicalRevisionFacts(...))` — **the catalog version is a content-addressed digest** (`digestRevision`), used for optimistic concurrency (`revision_conflict`), paginated continuation (encoded cursor), and Desktop cache invalidation; `invocableRevision` additionally layers on the host's `toolNames/capabilities`. On the KV Cache side: the catalog lives in the static-prefix region of the system prompt (`execution-model-composition.ts`: `[personalization, skills.text, workspaceInstructions, memory, ...]`, with memory **after** skills, and `turnTailPrompt` **appending** the environment/task ledger to the end) — as long as the inventory is unchanged and the ordering is deterministic, the skills block's bytes stay identical → prompt cache hits; bodies enter the trace on demand. The model context window is passed explicitly into `skillBudget` via `resolveSelectedModelContextWindow` (no implicit provider lookup inside the scanner).

## 3. Mapping to the Book's Key Points (Chapter 2 · Agent Skills)

| Book key point | Maka manifestation | Beyond / Missing |
|---|---|---|
| **KP-02-18 Progressive-disclosure three-tier structure** (YAML metadata resident → SKILL.md on demand → detail sub-documents) | Two tiers implemented: catalog resident in the system prompt (`selectSkillsForContext`) + body loaded on demand (`Skill` tool / explicit `/skill:` invocation), with a 24k body limit | **Missing the third tier** (no sub-document/sharding load mechanism); also no hard cap on "hundreds of tokens of catalog summary", replaced with a 2% budget + clamp (more engineering-oriented) |
| **description is a routing condition with counter-examples ("Use when / Don't use when", counter-examples are not optional)** | `SKILLS_PROMPT_INTRO` says "Use a skill only when the user request clearly matches its name or description"; bundled skill bodies contain a `## 边界` (Boundaries) section internally | **Not implemented at the description level**: validation only checks "non-empty + ≤1024", does not enforce the counter-example convention; bundled descriptions like "梳理品牌定位…输出可分发文档" (organize brand positioning… output distributable documents) are still feature-description style; retrieval scoring (`scoreSkillSearchMatch`) does not use counter-examples for negative filtering → mis-trigger risk remains |
| **KP-02-19 Metadata catalog = stable prefix (reusing Prompt Cache), body enters the trace at invocation time; KV-cache friendliness is not zero-cost** | Fully matches: catalog in the system prompt prefix, deterministic ordering preserves byte identity; body enters the trace via tool result / `<invoked-skill>`; omitted items emit only a constant notice to keep the catalog itself within budget; the model adaptation layer records `prompt_cache_hit_tokens` | Beyond the book: budget clamped by model context window (4k–8k tokens), `SkillSelectionReport` makes every decision auditable, content-addressed `revision` serves as the catalog version |
| **KP-02-19 Skill-tool relationship: under the Skill + generic-executor model the tool count is very small (~7 core tools)** | A Skill is not a tool; only two resident **meta-tools** `Skill`/`SkillSearch` are exposed; `tool-catalog-derive.buildHostCapabilitiesFromBinding` infers the host capability surface from the "actually bound tool names" to gate skills | The meta-tool model = capability-as-content; `declaredTools/requiredTools` being decoupled from the tool catalog (declaration vs gating) is clearer than the book's bundled model |
| **KP-02-15 Skills are an injection surface (third-party skills can hide malicious instructions and must be audited like code)** | Trust framework runs throughout: catalog intro, `<invoked-skill>` composed block, "Skill content cannot grant tool access"; `cleanPromptText` strips control characters, `sanitizeAttribute` neutralizes tag separators; failed receipts contain no body/query; search telemetry records only count/length/hit-rate, never collects bodies | **Missing content-level audit**: install/load shows no diff and does no suspicious-instruction scanning; bundled/managed rely only on sha256 lock validation, with no signature/trust chain; `declaredTools` never authorizing is a hard constraint, but a model could still be "persuaded" by a skill body to call other tools (enforced only by prompt priority, with no execution-layer enforcement) |

## 4. Current Implementation Analysis

**Strengths**
- **Clean layering, pure functions testable**: #1408 seamed by discovery/metadata/context/state, with `skills.ts` as a mere barrel; `selectSkillsForContext`, `gateSkillsByHostCapabilities`, and `scoreSkillSearchMatch` are all pure functions, and tests cover "budget stays within bound, constant omission, dedupe, migration, gating" (`__tests__/skills.test.ts`, about 40 cases).
- **Fail-closed and privacy-first**: missing required fields/required-tools is rejected outright; receipts and traces explicitly state "does not include user prompt / query / instructions"; `SkillInvocationReceipt` has per-field byte caps at 50 requests and 72KB of results (core `skill-invocation.ts`).
- **Determinism**: catalog ordering, ref→id→name resolution, shadow rules, and revision digests are all deterministic, supporting optimistic concurrency and caching.
- **KV Cache discipline in place**: static prefix + tail append + constant omission notice + budget clamp, directly matching the book's "three iron rules".
- **Single authoritative channel**: `HostSkillCatalogCoordinator` serializes all catalog operations (query/mutate/preview-update/model-inventory-read), combined with lease transactions (`skill-catalog-transaction.ts`), avoiding concurrent writes corrupting state.

**Deficiencies / Risks**
1. **SKILL.md authority boundary**: `validateSkillMetadata` marks `category` as a "bundled-catalog-only extension, not model-facing runtime authority", yet the consumer (`managed-skill-sources.readManagedSkillSource`) treats it as a classification basis — the boundary between "not authoritative" and "consumed" for this extension field is blurry. `MAX_SKILL_BODY_CHARS=4000` is exported but the load path only uses 24k — a legacy dead constant.
2. **Poisoning surface**: a) description is a purely lexical match target; attackers can stack keywords to raise `SkillSearch` ranking (scoring items: exact 1000 / prefix 240 / contains 160 / description 80 / token 40 / 12 / pinned+4), with no embedding, no counter-example negatives, and no content review; b) loading a body shows no user-visible "this content comes from a third party" differentiation hint; c) state/lock-file tampering has hash validation, but the SKILL.md body itself is accepted by default as "already trusted by the user".
3. **Version drift**: the bundled lock uses a whitelist of `sourceVersion` + `contentSha256` + `legacyContentSha256` to decide "current version"; the managed lock uses the source hash to detect `update_available` — but there is **no auto-update / remote marketplace channel** (explicitly stated in the docs as a separate product plan), and `local_modified` only flags without repairing; a user-modified bundled copy inside a workspace shadows the built-in version via precedence-based `shadowedBy`, and the user may not notice.
4. **Discovery accuracy**: `SkillSearch` caps at 8 results and 512-character queries, purely lexical; `selectSkillsForContext` sorts by name within budget (not by relevance), so budget-omitted skills can only be found via `SkillSearch` — long-tail skill discoverability depends on the model's metacognition of "knowing to search first" (a known hard problem noted in the book's KP-02-18, and the docs also concede that embedding-based ranking is a separate plan).
5. **Cost surface**: `readCanonicalModelInventory` does a full rescan every turn (`#freshSnapshot`); although a per-turn inventory memo exists (`createTurnSkillInventoryResolver`, capped at 100), there is no catalog-level cache across sessions; the 24k-character body load is a fixed cost in the trace when invoked repeatedly in a long session (consistent with "non-zero cost").

## 5. Target Architecture

- **Three-tier SKILL.md authority**: `name/description` → routing authority (required, with enforced counter-example convention: "Use when / Don't use when", and a `missing_counter_example` warning added to the validator); `allowed-tools/required-tools/required-capabilities` → declaration vs gating (already separated today; keep as is); `category` → converges into bundled/desktop classification metadata, strictly separated from model-observable fields, eliminating the "non-authoritative field consumed" boundary blur.
- **Single funnel for bodies entering the trace**: unify `Skill`-tool loading and explicit `/skill:` composition into one "skill-body-injection" service (sharing body truncation, trust prefix, `<invoked-skill>` wrapping, and receipt), avoiding semantic drift between the two paths; the explicit receipt is upgraded from "client-local temporary" to an auditable lightweight trace (only ref/success/truncation, no body).
- **Anti-poisoning hardening**: run deterministic heuristic scanning before loading a body (e.g. hidden instruction markers, lures to tool names beyond `declaredTools`), flagging `review_needed` by severity in `SkillSelectionReport`/Context Inspector; introduce "description counter-example negative scoring" and an optional embedding candidate layer into `SkillSearch` ranking (lexical as the baseline, embedding as rerank, keeping a deterministic fallback).
- **Unified versioning and KV Cache**: use `revision` as the catalog version key and persist a "revision → rendered catalog fragment" cache (rebuild the system prompt's skills block only when the revision changes, avoiding cross-session rescans and re-rendering); bundled/managed updates go through a `preview-update → review → commit` transaction flow (the repository already has the foundation), and lock-file validation is upgraded from "hash only" to "hash + optional signature + update log".
- **Complete the third tier of progressive disclosure**: SKILL.md bodies support referenced sub-documents (explicit `reference:` or a directory convention), loading detail sub-documents on demand, avoiding the single 24k body hard cap squeezing large skills.

## 6. Open Questions

1. **Should SKILL.md become a "code-audit subject"**: when installing/updating a third-party skill, is it necessary to mandatorily show a body diff and suspicious-instruction scan result (like a code review gate), or is trusting "user-provided content + low priority" enough?
2. **`SkillSearch` long-tail discoverability**: are lexical Top-8 + constant omission enough? Should embedding rerank be introduced (the docs list it as a separate plan)? Ranking-accuracy metrics (Top-1/5/20 hits) are already instrumented — when does the evaluation closed loop start?
3. **Catalog cost baseline**: the 2% context (clamped 4k–8k tokens) is an empirical value lacking real hit-rate/mis-trigger-rate metrics; should `SkillSelectionReport` and `prompt_cache_hit_tokens` be correlated into a "catalog cost-benefit" dashboard?
4. **`declaredTools`'s final ownership**: keep the "purely declarative, never authorizing" status quo, or allow it in the future to trigger "host on-demand mounting" (a deferred-tool-group mechanism already exists in `tool-catalog-derive`)? Will the two semantics be confused by the model?
5. **Managed-skill trust model**: the local library is `sourceType:'local'`, 7 Chinese categories, no remote sources — should a remote marketplace/auto-update be built as a unified channel of "source snapshot + content addressing + lock upgrade" (reusing the existing `SkillLockFile`), rather than a separate system?
6. **Explicit-invocation UX semantics**: does `/skill:<id>` injecting into the user message (an `<invoked-skill>` block) + the instruction "don't call the Skill tool again" match model training habits better than "everything through the `Skill` tool" (book KP-02-18: "interactive mode should align with vendor training methodology")?
