# 第 6 章 · Agent 的评估 —— 知识点提取

> 来源：`book/chapter6.md`。评估对象是**模型与 Harness 的组合体**而非模型本身；评估体系首要价值不是给当前系统打分，而是**让你能快速、可靠地跟上模型的演进**。三层结构：评估设计（指标→环境→数据集）→ 评估方法（怎么判）→ 评估驱动的决策（统计显著性+可观测性+系统改进）。

## 一、评估的总前提

### [KP-06-01] 评估对象是「模型 × Harness」组合体；model swap 与消融是两种不同归因手段
- **一句话核心**：Agent 表现不佳时，改进方向可能不是换模型而是优化 Harness；完善的评估体系必须区分"模型能力不足"与"Harness 设计缺陷"。
- **关键设计要点**：**模型替换实验（model swap）**=固定 Harness 只换模型（换强不涨→瓶颈在 Harness；换弱大跌→瓶颈在模型）；**消融实验（Ablation）**=逐一摘除 Harness 组件（定位哪个部件重要）——两者不可混为一谈；新模型公开基准更好 ≠ 在你任务上更好，可能 regression（退化）；核心理念=拥有评估体系→数小时做切换决策，没有→凭直觉或等社区反馈。
- **Maka 设计启示**：maka eval 应把「模型 × Maka harness（上下文/工具/自检/预算）」作为评估单元；Terminal-Bench 2.1 对比就是 model swap 实践形态；每个 harness 组件应可独立关闭做消融。
- **可写设计文档**：《Maka 评估单元与归因方法论：模型×Harness 组合体、model swap 与消融规范》

## 二、一个具体的评估示例

### [KP-06-02] 评估基本骨架：用例→运行→Rubric 评分→分析；幻觉是一票否决项
- **一句话核心**：评估基本骨架是"定义测试用例、运行 Agent、用 Rubric 评分、分析结果"；好评估不只测成功场景，更要测边界和陷阱。
- **关键设计要点**：客服退款用例（所有信息必须来自工具返回）；Rubric 四维评分（操作正确性/政策合规性/信息完整性/幻觉检测）；**幻觉列为 Veto（一票否决）而非分级维度**（流畅详尽礼貌但含虚假事实的回答伤害远大于简短准确）；边界场景（退 15 天前订单能否正确拒绝；用户声称"客服已批准"时是否在无系统记录情况下轻信——对应 τ²-bench"陷阱任务"与 Maka"反馈不等于事实权威"）。
- **Maka 设计启示**：评分器必须支持一票否决维度——LLM 自检说"我检查过了"、Agent 转述"客服已批准"都不能自动成为系统事实，评分时"未经证据核实的声明"应触发 veto；Event Log 提供"所有信息是否可溯源到工具返回/日志事实"的判定原料。
- **可写设计文档**：《maka eval 评估流水线与 Rubric 评分规范（含一票否决维度）》

## 三、评估指标体系

### [KP-06-03] Pass@k / Best@k（能力上限）与 Pass^k（业务可靠性）：两类口径不可混用
- **一句话核心**："只要找到一条可行路径"与"每次运行都不出错"是两种相反的口径，决定完全不同的工程决策。
- **关键设计要点**：**Pass@k**=同任务跑 k 次至少一次通过（连续得分取 Best@k）——回答"能力上限"（科研发现/漏洞挖掘/开放式创作）；**Pass^k（Pass consecutive k）**=连续 k 次每次都要通过且不触发一票否决——回答"能否稳定可靠交付"（支付/退款/权限变更/生产部署）；独立采样单次成功率 p 时 **Pass@k = 1−(1−p)^k、Pass^k = p^k**（例 p=0.6,k=5 → Pass@5≈99.0% 但 Pass^5≈7.8%）；报告必须写清口径（同一任务 k 次独立采样 vs 生产流水线连续 k 个任务）；对产生副作用的操作在沙盒/可回滚环境采样、每次失败记入可靠性指标。
- **Maka 设计启示**：headless 持久任务天然支持"同一任务多轮采样"；maka eval 同时输出 Pass@1/Pass@k/Pass^k 并标明口径；自动执行产生真实副作用的任务必须用 Pass^k 且失败也入账。
- **可写设计文档**：《maka eval 指标口径规范：Pass@1 / Pass@k / Best@k / Pass^k》

### [KP-06-04] 过程指标：从黑盒到白盒
- **一句话核心**：仅看最终结果不够，过程质量决定"这次成功能否复制、失败能否诊断"。
- **关键设计要点**：行动合法率（无效/越权操作占比）；工具调用正确率（参数语义合理）；路径效率（步数/冗余动作/回退次数——需人类专家或启发式基线定义"合理步数"）；检索覆盖率（充分探索信息空间还是只看第一页）；成本与延迟（请求次数/Token 花费区分输入输出考虑 KV Cache 复用/墙钟时间定位瓶颈）。
- **Maka 设计启示**：Runtime Event Log 记录了每一次工具调用/结果/终止事实——过程指标可作为日志的直接投影零成本计算，与"Log is the Runtime"完全自洽；过程指标应成为 eval 报告的固定栏目而非事后补记。
- **可写设计文档**：《基于 Runtime Event Log 的过程指标计算规范》

### [KP-06-05] 安全、鲁棒性与轨迹/结果双重覆盖
- **一句话核心**：安全指标零容忍（一次严重违规整体否决）；鲁棒性衡量面对不确定性稳定性；"轨迹（说了/做了什么）"与"结果（系统最终变成什么样）"必须双重覆盖。
- **关键设计要点**：安全合规指标（敏感操作/数据外泄/违规内容——零容忍与幻觉一票否决同理）；鲁棒性四维（随机种子敏感性/页面变化适应性/API 抖动容忍/长时记忆干扰）；**轨迹 vs 结果双重覆盖**（Agent"说订票已完成"是轨迹信息、数据库确有订单才是结果验证；只看轨迹漏掉"说了但没做到"）；Anthropic 案例（Agent 发现政策漏洞给更便宜方案——按预设路径打分会判失败、按最终结果用户受益——两类评测都要覆盖）。
- **Maka 设计启示**：信条 1 正是"轨迹（事件日志）与结果（最终事实）都在日志里"——评估器可同时检查日志中 Agent 声称的事实与最终状态事实；安全零容忍作为 veto 维度（对外通信/文件删除/密钥写入）。
- **可写设计文档**：《maka eval 安全零容忍与轨迹/结果双重覆盖规范》

### [KP-06-06] 人工抽检、评判者校准与对抗式评审
- **一句话核心**：自动评估再可靠也要定期人工抽检，放量使用 LLM 评判前必须先做**评判者校准**；对抗式评审用红队主动构造"表面完美实则错误"案例。
- **关键设计要点**：人工抽检覆盖不同类型/成功失败/边界分数模糊案例；**评判者校准**——先构建人工标注金标集（100-200 个），测量评判模型与人类一致率（Cohen's kappa，达标如 >0.7 后才放量；评判模型或 Rubric 每次更新都要重新校准）——"没有这一步，LLM 评判的分数只是另一个模型的意见"；对抗式评审（表面完美含隐蔽错误/关键词堆砌/利用评判偏见骗高分）；多评委机制（独立评判加权/一致性检查、分歧标记人工）。
- **Maka 设计启示**：eval 内置"评判者校准"环节——为 judge 模型建 Maka 金标集追踪 kappa（支撑信条 4：judge 高分不等于事实，必须有与人类校准的证据背书）；对抗式评审专门针对"self-check 声称通过但实际未修复"。
- **可写设计文档**：《maka eval 评判者校准与对抗式评审流程》

## 四、自动评估环境

### [KP-06-07] 评估环境五要素 + 工具调用型范式（Verifiers 层次化）
- **一句话核心**：可重复的自动评估环境由五个要素构成；工具调用型范式用层次化环境+可执行验证，不依赖人工或 LLM 评判。
- **关键设计要点**：五要素（数据集初始状态+目标描述+可选参考/环境状态真实性与可控性平衡/工具接口提供**原子操作**而非高层抽象迫使规划与组合/评分 Rubric/执行协议与终止条件）；Verifiers 框架层次化（SingleTurnEnv/ToolEnv/StatefulToolEnv/SandboxEnv）；支持并行采样与轨迹缓存；工具失败返回**清晰错误信息而非简单失败标志**让 Agent 从错误中学习。
- **Maka 设计启示**：eval 明确声明评估环境五要素；headless/终端以工具调用型为主——判分优先确定性验证器（退出码/输出文件/日志事实），不依赖 judge，与"日志即运行时"一致；TaskRun 生命周期作为"执行协议/终止条件"天然实现。
- **可写设计文档**：《maka eval 评估环境五要素与工具调用型环境规范》

### [KP-06-08] 人机交互型评估环境：渐进式信息透露、用户模拟与双控环境
- **一句话核心**：真实用户很少一开始就清晰描述需求——**渐进式信息透露（Progressive Information Disclosure）**是人机交互型评估与传统 benchmark 的根本区别。
- **关键设计要点**：用户模拟（LLM 扮演用户、按需逐步透露信息、有**有限耐心**——沟通低效时终止对话任务失败）；τ-bench 双重验证+二元奖励（数据库最终状态+对话中是否输出必要关键信息，但任务层汇总为 0/1——"漏掉非关键字段"与"完全失败"同分）；**τ²-bench 两点增量**（①双控环境 Dual-Control——用户模拟器也能操作同一共享环境、贴近技术支持 ②更精确任务规范与组合式任务生成）；工具调用型 vs 人机交互型分野（行动正确性 vs 沟通策略合理性）。
- **Maka 设计启示**：headless 持久任务评估要建模"环境侧也能改变状态"（用户/外部服务中途修改文件或状态→Agent 必须通过工具观察到变化，呼应 Context is not history）；渐进式信息透露写成 maka eval 的对话/任务协议。
- **可写设计文档**：《人机交互型任务评估协议：渐进式信息透露、用户模拟与双控环境》

## 五、评估任务数据集的设计

### [KP-06-09] 任务数据集设计五大核心挑战
- **一句话核心**：数据集是"剧本"——设计糟糕的数据集即使跑在完美环境里得到的也只是噪声。
- **关键设计要点**：①明确性与开放性张力（GAIA"概念简单但路径开放"）；②真实性与可控性平衡（SWE-Bench Verified 人工专家验证筛 500 高质量任务）；③多样性与系统性协调（AndroidWorld 116×20 应用参数化生成无限变体）；④评估成本与覆盖（SWE-bench Verified 2294→500 成本降约 80%）；⑤**数据泄漏防范**（GAIA 答案独特+专创互联网不存在的附件；SWE-bench-Live 时间新鲜度；τ²-bench 动态参数；Terminal-Bench **金丝雀标识符 canary GUID**）。
- **Maka 设计启示**：local-first 评估集内置防泄漏机制（canary GUID/参数化变体/时间新鲜度）；成本维度（Terminal-Bench 2.1 对比实验成本分析）是"挑战四"落地。
- **可写设计文档**：《maka eval 评估集防泄漏、规模与成本控制规范》

### [KP-06-10] 任务描述精确性、复杂度层次化与任务分布系统性
- **一句话核心**：好的任务描述使验证可机械化、可用参数化模板生成变体；复杂度分层让失败能诊断到具体能力；任务分布系统覆盖能力/难度/场景/边界。
- **关键设计要点**：GAIA 精确性（信息源约束/时间范围/格式严格匹配）；τ²-bench 情境化（已知信息与任务指令分离+**事实锚定要求 Grounding Requirement**——必须根据工具调用实际返回回答不能编造）；Terminal-Bench 可机械化验证（`build-linux-kernel-qemu` 真从源码构建内核加自定义 printk 在 QEMU 运行——**Agent 无法伪造输出蒙混过关**）；AndroidWorld 参数化模板（防记忆/增多样性/支持对比实验，验证基于最终 UI 状态而非操作序列）；**复杂度层次化**（GAIA L1 工具使用/L2 多步规划/L3 长序列思考，分别对应提示工程/规划机制/分层架构后训练）；任务分布系统性（τ²-bench 陷阱任务、OSWorld 操作×应用双维矩阵跨 3 OS、Terminal-Bench 跨技术栈组合任务）。
- **Maka 设计启示**：任务描述"可机械化验证优先"（终端输出/退出码/文件状态/日志事实）；复杂度分层让失败可诊断到具体能力；参数化模板+headless 批量运行低成本生成回归变体。
- **可写设计文档**：《maka eval 任务描述、复杂度分层与任务分布规范（含参数化模板）》

### [KP-06-11] 可验证性、客观性保障与数据质量迭代（含评估/训练隔离红线）
- **一句话核心**：验证必须客观可执行——能深度检查最终状态、能区分"真解决"与"引入新 bug"；数据质量靠高淘汰率人工筛选与社区化迭代，评估环境构造可复用但题目必须与训练数据隔离。
- **关键设计要点**：SWE-Bench Verified 双重验证（**FAIL_TO_PASS** 修复前失败修复后通过 + **PASS_TO_PASS** 修复前后都通过——区分"问题被解决"与"没引入新 bug"）；τ²-bench 多层检查；OSWorld 深度检查（134 个独立评估函数+完整 OS 权限）；**数据质量控制**（2294 题抽 1699 人工评估、93 名开发者、最终仅 500 通过=**29% 高淘汰率**是对评估质量的必要投资）；OSWorld-Verified 15 个月 300+ 问题四类系统性迭代（环境/描述/验证/初始状态）、50 倍并行加速、轨迹公开可复现；**红线：评估环境与后训练环境同源可复用构造机制，但评估集具体题目必须与训练数据严格隔离**。
- **Maka 设计启示**：判分"确定性验证器优先"——对照 Maka 日志/文件/进程/终端输出深度验证；双验证（FAIL_TO_PASS/PASS_TO_PASS）映射到"修复前失败/修复后通过"回归集管理；评估集版本化、canary、轨迹公开存档可复现。
- **可写设计文档**：《maka eval 可验证性、数据质量与评估集迭代规范（含训练隔离红线）》

## 六、自动化评估方法

### [KP-06-12] LLM-as-a-Judge 核心与 Rubric 四准则
- **一句话核心**：开放式任务没有标准答案可自动对比，用 LLM 依据专家定义的 Rubric 评判；Rubric 必须遵循 Scale AI 的四准则。
- **关键设计要点**：局限=评判模型偏见（最典型**长度偏差**——给更长回答高分）+ 多次评判波动；长度偏差三防范（Rubric 显式惩罚冗长/配对前控制长度相近/定期审计"高分-长度相关性"）；**Rubric 四准则**（Scale AI）：①基于专家指导（捕捉核心事实与推理步骤）②全面覆盖（事实/逻辑/完整/安全+明确**陷阱 Pitfall**）③标准重要性权重（必要项/重要项/可选项/**一票否决 Veto**——防关键词堆砌式奖励作弊）④自包含评估（每项独立可操作、不依赖评价者领域知识——避免"回应展示深刻理解"改为"引用了至少两个权威理论并准确解释如何支持结论"）；**奖励作弊 Reward Hacking**（找高分捷径：幻觉/讨好/关键词堆砌/回避棘手问题）；Rubric 是迭代产物（试用收集分歧逐步完善成详尽判例集+边界案例）。
- **Maka 设计启示**：开放式维度（自检报告/计划合理性/错误解释）用四准则 Rubric+veto；"judge 高分"仅作为证据之一而非事实权威（信条 4）；把评分理由、judge 模型与版本、Rubric 版本写入评估记录。
- **可写设计文档**：《LLM-as-a-Judge 与 Rubric 四准则落地指南（含长度偏差审计）》

### [KP-06-13] 同源模型问题、多源异构评判与多模态 LLM-as-a-Judge
- **一句话核心**：Agent 与评判模型同源时，Agent 会学会利用评判者偏好与盲点（古德哈特定律）——缓解靠**多源异构评判**。
- **关键设计要点**：**同源模型问题**（Agent 学钻评分漏洞避开评判者不擅长检测的错误——"当一个度量指标变成优化目标时就不再是好的度量指标"）；**多源异构评判**（Agent 用 Claude→评判用 GPT-5+Gemini，不同家族偏见正交难以同时欺骗；相同 Rubric 保证同目标；部署用单模型快速评估、定期完整多源质量审计）；多模态四方向（TTS 评估发现 WER 抓不到的韵律问题；ASR 语义影响判断"转账一千变一万"；UI 评估用 Proposer-Reviewer 机制；视频剪辑关键帧验证）；实验 6-6 教训：**"选什么参考答案/参考图片/参考音频，本身就是评估设计"**（审慎定义"像不像参考音色"是否应计入总分）。
- **Maka 设计启示**：eval 默认多源异构评判（尤其 headless/terminal 真假难辨）；judge 家族/版本/Rubric 版本/候选参考哈希作为评估记录必填字段；**agent 自己审自己日志的同源问题尤其严重——必须强制引入异构 judge**。
- **可写设计文档**：《多源异构评判与多模态 judge 扩展规范》

### [KP-06-14] 失败归因：从整条轨迹定位首个错误
- **一句话核心**：端到端评估只回答成功/失败，要驱动修复必须做失败归因——标出主要错误类别、**首次出现不可接受行为的步骤**、对应工具调用或模型输出，并附可复核证据；**首个错误才是根因，后续错误多为连锁反应**。
- **关键设计要点**：生产 bad case 三类信号（用户明确纠正/点踩负面反馈/事后通过检查发现不该做的事）；可借助 LLM 但不能完全依赖（失败归因往往反映**产品问题**）；错误分类随产品完善可达数百类；Coding Agent 六类初始错误分类（流程规范缺失/工具调用错误/作用域敏感文档格式错误/精确复制错误/模型执行异常/任务完成度逻辑判断）；**精确复制错误**（old_string 差一字符/空格/换行/转义/Unicode——沿"原始字节→工具返回→序列化→模型输入→模型输出→工具匹配"逐层比较定位首次 byte/token 分歧；若模型输出正确而传输层改变，根因归 Harness/工具而非模型）；结构化归因记录（JSON/YAML 引用步骤号/工具名/观察证据、区分根因后果/可恢复性/置信度；多类别按"最早且能解释后续失败"选主因）；保存上下文（目标/环境状态/版本/完整轨迹供回归）。
- **Maka 设计启示**：Event Log 是失败归因的天然数据源——"首个偏离事件"可直接在事件日志中定位（哪个工具调用/哪条 Compaction 之后开始走偏），这是"Log is the Runtime"对评估的最大杠杆；eval 产出结构化归因记录并连同目标/状态/版本/轨迹归档。
- **可写设计文档**：《失败归因与结构化归因记录规范（基于 Runtime Event Log）》

### [KP-06-15] 端到端回归任务与轨迹前缀回归任务
- **一句话核心**：修复目标写成两类互补回归任务——端到端回归验证完整工作流不被破坏；**轨迹前缀回归冻结首个错误之前的上下文、只测"下一步决策边界"是否被修好**（对高可靠生产 Agent 往往更重要）。
- **关键设计要点**：端到端回归（从初始状态+请求跑完整任务，接近生产但难判断失败在哪步）；轨迹前缀回归（把已有上下文/对话/工具返回/环境状态**冻结**，只要求思考并执行下一步/几步——成本更低、隔离单个策略或工具问题）；**答案=可接受动作集合而非唯一动作**（"先读仓库规则""先询问用户""拒绝危险操作"+列出**禁止动作**）；由归因构造数据集；实验 6-5（11 bad case×3 记忆编码，三种表示各 6/11 但失败位置不同——**改变上下文表示方式不会自动修复应用策略**）；核心论断：**"获得一条信息和正确将它用于当前决策是两种不同能力"**。
- **Maka 设计启示**：TaskRun 可从途状态恢复——"冻结前缀、只测下一步"在架构上天然可行（恢复即从某事件点重放/接续）；eval 维护两类回归集（端到端+轨迹前缀边界集）；可接受动作集合恰好表达"Self-check 后是否采取有界修复动作"这类决策边界。
- **可写设计文档**：《端到端与轨迹前缀回归集构建规范（含可接受动作集合）》

### [KP-06-16] 配对比较与模型排名：Elo / Bradley-Terry 与位置偏差
- **一句话核心**："A 和 B 哪个更好？"用两两对决的相对比较替代绝对打分——Elo 在线更新+ Bradley-Terry 统计基础构成排名，但必须防位置偏差。
- **关键设计要点**：Elo（分差→预期胜率、爆冷更大调整）；Bradley-Terry 是其统计基础；Chatbot Arena（匿名随机对决、不需定义绝对标准、结果取决于用户提什么问题）；**位置偏差 Position Bias**（LLM 评判系统性偏向某位置——标准缓解=交换顺序各评一次取平均、两次一致才计入不一致记平局或送人工）；从评估到训练（配对比较是 GRPO 信号源——同一问题采样多候选用相对优劣估计优势、省去 critic 价值网络）。
- **Maka 设计启示**：eval comparison 功能升级为"配对比较+交换顺序+Elo/Bradley-Terry 排名"规范协议用于模型选型与 Harness 变体对比；报告采用配对差异（同一任务上谁胜出）而非只报绝对分差。
- **可写设计文档**：《配对比较与模型排名协议（交换顺序、Elo/Bradley-Terry、偏差审计）》

## 七、评估驱动的模型选型

### [KP-06-16续] 模型选型关键维度、行为策略、成本分析与持续迭代
- **一句话核心**：模型选择不是"选最强"，而是按应用场景在吞吐、延迟、成本、性能、可靠性之间做评估驱动的权衡；选型不是一次性的。
- **关键设计要点**：吞吐延迟（TTFT=排队+Prefill、Decode 决定出字速度与思考时长、**p95 尾部延迟**比均值更反映体验）；成本（便宜但成功率低的模型因重试实际更贵；算每任务平均成本与成本-性能比）；**预算—能力曲线**（RE-Bench：2 小时预算最佳 Agent 约人类专家 4 倍，但人类从增加时间预算获益更大——短预算领先不能外推成长时间运行能力）；多模型协同（轻量处理简单、强模型复杂、专门模型子任务——必须验证整体效益，警惕"9.9 vs 9.11"这类简单题被丢给轻量模型出错）；**模型行为策略（行动阈值）**（实验 6-8 固定 Harness：GPT-5.6-sol 首次修改前平均 6.89 次工具调用/读 4.67 文件，Claude Sonnet 5 为 4.56/3.56——支持"行动策略随模型而变"、不支持"多读或早改必然更好"）；**成本三层分解**（模型推理成本含**上下文累积效应**（每轮重发历史累积、KV Cache 缓解）与**思考 token 成本**（不展示但计费）；工具调用成本（一次网页搜索 2000-5000 token 且在后续每轮反复计费）；基础设施成本）；**成本优化可独立开关**（实验 6-9：稳定前缀省 28.3%、压缩历史省 17.5%、两者同开省 30.0%——**不能把各自节省比例相加**）；持续迭代（"在我的特定任务上 Gemini 是否比 Claude 好？好多少？切换成本是什么？"——做差异化路由而非盲目全量切换）。
- **Maka 设计启示**：已有成本分析实践（信条 1/3 下 Token 与事件都入日志）；把"预算-能力曲线、TTFT/思考延迟、成本三层分解、独立开关上下文优化"纳入 eval 模型选型报告；差异化路由与"预算驱动的 headless 任务"天然契合（每个 TaskRun 声明模型与预算档位）。
- **可写设计文档**：《模型选型与差异化路由决策流程（含预算能力曲线与成本三层分解）》

## 八、评估结果的统计显著性

### [KP-06-17] 统计显著性：标准误、配对分析、多随机种子与多重比较
- **一句话核心**：评估集有限、模型输出有随机性，分数差异可能只是抽样噪声；判断"值得切换/发布"要满足：分差超过噪声、在配对分析中成立、并能复现。
- **关键设计要点**：标准误 SE(p)≈√(p(1−p)/n)（100 用例 70%→95% CI 约 ±9pp——"73% vs 70%"不足以支持切换）；**配对分析**（同一批任务逐题记录谁胜出，McNemar 检验或配对 bootstrap，而非直接相减两个独立成功率）；每配置用**多个随机种子（3-5 次）**报告均值与波动（单次运行只能筛选方向）；预期收益 2-3pp 而评估集几十题→先扩大样本（标准误按 1/√n 缩小）；**多重比较**（并行验证多假设收紧阈值或独立复跑）；实务标准=分差超噪声+配对成立+能复现。
- **Maka 设计启示**：eval comparison 输出内置统计显著层（置信区间、McNemar/配对 bootstrap、多随机种子均值±波动）；Terminal-Bench 对比与模型切换决策必须过显著性门槛（呼应信条 3：一次 run 的证据只支持与规模相称的结论）。
- **可写设计文档**：《maka eval 报告统计显著性规范（置信区间、配对检验、种子策略）》

## 九、Agent 的可观测性

### [KP-06-18] Agent 可观测性：Trace/Span 模型、标准协议与"生产轨迹回流成评估资产"
- **一句话核心**：Agent 系统同样的输入可能产生不同输出、执行路径极复杂、思考不透明——可观测性通过日志/指标/追踪推断内部发生了什么；**最有价值的去向是把生产轨迹回流成评估资产**。
- **关键设计要点**：价值四方面（问题诊断/持续优化基础/成本管理（跨任务差一两个数量级）/积累数据供后训练）；**Trace 数据结构=span 树**（一次任务=一条 trace；每个 LLM 调用/工具调用/检索=一个 span 记录输入输出/起止时间/token/错误；父子关系构成执行树）；标准协议=**OpenTelemetry + OpenInference**（采集与分析解耦、避免平台锁定）；LangSmith 类平台（异步批量采集不影响响应延迟、A/B 测试、提示词版本管理）；**回流成评估资产**（生产轨迹筛选失败可疑案例→**脱敏**→沉淀为评估集新用例与回归测试——"今天线上暴露的失败模式，明天就成为守住这条底线的回归用例"）。
- **Maka 设计启示**：Runtime Event Log 天然可投影成 span 树（TaskRun=trace 根、消息/工具调用/结果/终止事实=span 叶子）；与 OpenTelemetry/OpenInference 对齐避免平台锁定；建立"生产 bad case→脱敏→回归集"闭环流水线让评估集持续生长。
- **可写设计文档**：《Maka 可观测性：Runtime Event Log → span 树与评估资产回流闭环》

## 十、从 Benchmark 报告到系统改进

### [KP-06-19] 迭代闭环 + 生产级 Agent 的内部评估基础设施
- **一句话核心**：看到分数下降先检查评测系统本身再动 Agent；每轮证据只支持与它规模相称的下一步；最好的 Agent 产品把 ML 实验方法论（消融/AB/特性开关/提示词回归/隐私感知）系统性嵌入产品工程。
- **关键设计要点**：**先查评测系统再动 Agent**（分数下降可能源于评测系统自身：资源不足/评分器 bug/用例与生产脱节——跟模型退化数字上一模一样）；读懂报告=发现问题的艺术（AndroidWorld 总 88% 但失败集中在 4 项 SystemWifiTurn* 中 3 项——先找失败簇再回放轨迹分清看/想/做/验）；**一轮只改一个变量**（AndroidWorld H1 加导航提示无效→H5 换 UIAutomator 元素树 25%→100%→H5C 删无语义节点 100% 不变 token 减半——①提示词补不回模型根本看不到的信息，先检查输入 ②输入不是越多越好 ③没换模型仅调整 Harness 表示就解决了"能不能做成"与"是否划算"）；**内部评估基础设施五组件**：①消融基础设施（总开关同时禁用多特性造"裸模型"基线、开关在启动路径**极早期注入**、每个主要特性都可独立关闭、定期消融发现"特性债务"）②AB 测试方法论（**多臂而非二元**揭示剂量效应、**区分机制指标与目标指标**（改计划文件长度是机制、真正目标是降低会话级成本）、**设置护栏指标**（目标改善但用户满意度/操作数/错误率变差就停）、记录基线统计）③**双层特性开关系统**（编译时开关=物理移除代码、运行时开关=服务端下发+本地缓存；特性开关是一等公民架构组件而非调试工具；每个特性曝光事件每会话最多记录一次防污染）④**提示词敏感性评估**（提示词是核心"代码"却缺版本控制——可**确定性渲染**（同配置同输出）、版本化快照、每次变更在评估集跑回归像代码跑 CI）⑤**隐私感知的分析**（用类型系统强制——分析接口只接受特殊类型包装的值、类型名即审计线索，把隐私约束从文档规范变成编译时强制）。
- **Maka 设计启示**："Context is not history"/"Feedback is not fact authority"对应可独立关闭的组件（Tool Result 剪枝/LLM Compaction/Self-check/预算）——全部做成消融开关纳入 eval（消融基线）；TaskRun/Task Event Log 支撑"一轮证据→一轮下一步"迭代 SOP；评估报告写明"结论适用哪里、哪些底线没过、下一轮验证什么"；AB 的"机制 vs 目标"尤其关键（改剪枝阈值是机制、真正关心成功率与成本是目标）。
- **可写设计文档**：《从 Benchmark 报告到系统改进的迭代 SOP》＋《组件级消融开关与 AB 测试（机制/目标/护栏指标）规范》

## 十一、仿真环境：从评估到后训练的桥梁

### [KP-06-20] 仿真环境：RLVR 奖励函数化、reset 语义、吞吐与领域随机化
- **一句话核心**：评估的终点不是打分而是改进，改进的最强形态是训练——评估环境演化为仿真环境：一个让 Agent 反复练习、自动打分的虚拟操场。
- **关键设计要点**：仿真 vs 评估核心区别（交互频率极高数百万次 vs 数千次、需要随机化防死记硬背、必须提供即时反馈）；**评估资产→训练信号**（一套定义清晰的 Rubric/验证器本质就是可验证奖励 RLVR 的奖励函数——判分脚本直接就是奖励脚本）；训练两个新要求（**可靠 reset 语义**——每 episode 重置到干净初始状态否则梯度被污染；**远高于评估的吞吐**——环境并行度与单实例开销决定训练可行性）；数字环境（AWorld 26 个 MCP 服务器 126 工具、14.6 倍加速、无状态设计高效并行）；具身环境（RoboTwin2 双臂、**动作分块 Action Chunking**——模型一次规划多个连续动作实现实时控制）；**领域随机化 Domain Randomization**（物理参数/视觉外观/传感器噪声大范围随机缩小 sim-to-real gap；适度随机化提泛化、过度随机化任务过难）。
- **Maka 设计启示**：TaskRun/预算/continuation 天然适合承载仿真式评估（每 episode 从干净初始状态启动对应 TaskRun 干净会话；恢复/重放日志可作为低成本"重置+热启动"手段；判分脚本与 RLVR 奖励函数同源——eval 验证器将来可直接复用为后训练奖励）；领域随机化思想用于 Maka 评估（随机化延迟/超时/API 抖动/环境状态变化测鲁棒性）。
- **可写设计文档**：《从 maka eval 到仿真环境的演进设计（reset 语义、吞吐与领域随机化）》

## 本章金句 / 核心结论
- "评估的对象不应只是模型，而应是模型与 Harness 的组合体。"
- "评估体系的首要价值不是给当前系统打分，而是让你能快速、可靠地跟上模型的演进。"
- "Pass^k 回答的是'Agent 能否稳定可靠地交付'，而不是'能否偶尔创造奇迹'。"
- "没有（评判者校准）这一步，LLM 评判的分数只是'另一个模型的意见'，而非人类判断的可靠代理。"
- "评估环境是'舞台'，数据集是'剧本'——一个设计糟糕的数据集，即使跑在完美的环境里，得到的也只是噪声。"
- "数据泄漏时，评估测的就是记忆力而非泛化能力，好比考试前把答案背下来了。"
- "获得一条信息和正确将它用于当前决策是两种不同能力。"
- "古德哈特定律：当一个度量指标变成优化目标时，它就不再是好的度量指标。"
- "选什么参考答案、参考图片或参考音频，本身就是评估设计。"
- "看到 Agent 表现下降时，应先检查评测系统本身，再动 Agent。"
- "几项上下文优化同时使用时，必须在完整任务中一起实测，不能把各自的节省比例直接相加。"（28.3% + 17.5% ≠ 30%）
- "一轮证据只支持与它规模相称的下一步。"
- "每个主要特性都应是可独立关闭的，团队应定期验证每个特性的实际贡献。"
- "我改变的东西（机制）和我真正关心的东西（目标）是同一个吗？如果不是，以目标为准。"
- "特性开关不是调试工具，而是一等公民级的架构组件。"
- "从一开始就把隐私约束设计进去，而非事后加装。"

## 书中思考题（转录要点）
1. LLM-as-a-Judge"自我评估"是否存在系统性盲区（风格偏好与人类不一致）？如何检测校正？
2. 评估集防泄漏的"猫鼠游戏"有终局吗？设计一种从根本上抵抗数据泄漏的评估方法。
3. 主观维度（"是否有帮助""语气是否恰当"）如何设计可靠 Rubric？
4. 模拟用户本身是 LLM——它是否系统性低估情绪激动/表达不清用户？如何验证模拟用户质量？
5. Bradley-Terry 假设偏好传递性但人类偏好常违反——非传递偏好在 Agent 评估出现在哪些场景？
6. 单次成功率 60% 的 Agent，如何结合失败/重试/副作用成本决定报哪个指标、取多大 k？
7. 行为空间巨大、验证一个假设需数百次运行——如何在有限预算下最大化评估信息量？
8. AndroidWorld 完整元素树 25%→100% 但 token 2.498×；精简后 100% 不变 token 0.506×——设计自动裁剪规则？
9. 渐进式信息透露如何影响评估结果？模拟用户信息透露策略与真实差异较大时结论还可靠吗？
