# Chapter 6 · Evaluating Agents — Knowledge Point Extraction

> Source: `book/chapter6.md`. The object of evaluation is the **combination of model and Harness**, not the model itself; the primary value of an evaluation system is not to score the current system, but to **let you keep up with model evolution quickly and reliably**. Three-layer structure: evaluation design (metrics → environment → datasets) → evaluation methods (how to judge) → evaluation-driven decisions (statistical significance + observability + system improvement).

## 1. The Overall Premise of Evaluation

### [KP-06-01] The object of evaluation is the "model × Harness" combination; model swap and ablation are two different attribution methods
- **Core in one sentence**: When an agent performs poorly, the improvement direction may be to optimize the Harness rather than swap the model; a sound evaluation system must distinguish "insufficient model capability" from "Harness design flaws".
- **Key design points**: **Model swap** = fix the Harness and swap only the model (swapping in a stronger model with no improvement → the bottleneck is in the Harness; swapping in a weaker model with a big drop → the bottleneck is in the model); **ablation** = remove Harness components one by one (locating which component matters) — the two must not be conflated; a new model scoring better on public benchmarks ≠ better on your task, and it may be a regression; core idea = with an evaluation system you can make swap decisions in hours; without one, you rely on intuition or wait for community feedback.
- **Maka design implications**: maka eval should treat "model × Maka harness (context/tools/self-check/budget)" as the evaluation unit; the Terminal-Bench 2.1 comparison is a practical form of model swap; every harness component should be independently disableable for ablation.
- **Writable design doc**: "Maka Evaluation Unit and Attribution Methodology: Model × Harness Combination, Model Swap, and Ablation Specifications"

## 2. A Concrete Evaluation Example

### [KP-06-02] Basic evaluation skeleton: cases → run → rubric scoring → analysis; hallucination is a veto item
- **Core in one sentence**: The basic evaluation skeleton is "define test cases, run the agent, score with a rubric, analyze the results"; a good evaluation tests not only success scenarios but also boundaries and pitfalls.
- **Key design points**: Customer-service refund case (all information must come from tool returns); four-dimensional rubric scoring (operational correctness / policy compliance / information completeness / hallucination detection); **hallucination is treated as a Veto (one-vote override) rather than a graded dimension** (a fluent, detailed, polite answer that contains false facts does far more harm than a short, accurate one); boundary scenarios (whether a refund order placed 15 days ago can be correctly rejected; whether a user's claim that "customer service has approved" is blindly trusted in the absence of system records — corresponding to τ²-bench "trap tasks" and Maka's "feedback is not fact authority").
- **Maka design implications**: The scorer must support veto dimensions — an LLM self-check saying "I've checked it" or an agent relaying "customer service has approved" cannot automatically become system facts; at scoring time, "claims not verified by evidence" should trigger a veto; the Event Log provides the raw material to determine "whether all information is traceable to tool returns/log facts".
- **Writable design doc**: "maka eval Evaluation Pipeline and Rubric Scoring Specification (Including Veto Dimensions)"

## 3. The Evaluation Metric System

### [KP-06-03] Pass@k / Best@k (capability ceiling) vs Pass^k (business reliability): the two yardsticks must not be conflated
- **Core in one sentence**: "As long as one viable path is found" and "no error on every run" are two opposite yardsticks that drive completely different engineering decisions.
- **Key design points**: **Pass@k** = at least one pass out of k runs of the same task (the best continuous score is Best@k) — answers "capability ceiling" (research discovery / vulnerability hunting / open-ended creation); **Pass^k (Pass consecutive k)** = must pass on each of k consecutive runs without ever triggering a veto — answers "whether it can deliver reliably and stably" (payments / refunds / permission changes / production deploys); for an independent single-run success rate p, **Pass@k = 1−(1−p)^k and Pass^k = p^k** (e.g., p=0.6, k=5 → Pass@5≈99.0% but Pass^5≈7.8%); reports must clearly state the yardstick (k independent samples of the same task vs. k consecutive tasks in a production pipeline); sample operations that cause side effects in a sandbox/reversible environment, and record every failure into the reliability metric.
- **Maka design implications**: headless persistent tasks naturally support "multi-round sampling of the same task"; maka eval should output Pass@1/Pass@k/Pass^k simultaneously and label the yardstick; tasks that automatically execute with real side effects must use Pass^k and count failures too.
- **Writable design doc**: "maka eval Metric Yardstick Specification: Pass@1 / Pass@k / Best@k / Pass^k"

### [KP-06-04] Process metrics: from black box to white box
- **Core in one sentence**: Looking only at the final result is not enough; process quality determines "whether this success can be reproduced and whether this failure can be diagnosed".
- **Key design points**: legal-action rate (share of invalid/over-authority operations); tool-call correctness (parameter semantics are reasonable); path efficiency (step count / redundant actions / number of rollbacks — human experts or heuristic baselines are needed to define "reasonable step count"); retrieval coverage (fully exploring the information space or only looking at the first page); cost and latency (request count / token spend, distinguishing input from output, considering KV-cache reuse, using wall-clock time to locate bottlenecks).
- **Maka design implications**: The Runtime Event Log records every tool call/result/termination fact — process metrics can be computed as a direct projection of the log at zero cost, fully consistent with "Log is the Runtime"; process metrics should be a fixed column of the eval report, not an afterthought.
- **Writable design doc**: "Process Metric Computation Specification Based on the Runtime Event Log"

### [KP-06-05] Safety, robustness, and dual coverage of trajectory/result
- **Core in one sentence**: Safety metrics are zero-tolerance (one serious violation vetoes the whole thing); robustness measures stability in the face of uncertainty; "trajectory (what was said/done)" and "result (what the system ultimately became)" must both be covered.
- **Key design points**: Safety/compliance metrics (sensitive operations / data exfiltration / violating content — zero tolerance, just like the hallucination veto); four robustness dimensions (random-seed sensitivity / adaptability to page changes / tolerance of API jitter / interference from long-horizon memory); **dual coverage of trajectory vs result** (the agent "saying the booking is complete" is trajectory information; the database actually containing the order is result verification; looking only at trajectory misses "said but didn't do"); the Anthropic case (the agent finds a policy loophole and gives a cheaper solution — scored against the preset path it would be judged a failure; scored by final user benefit it succeeds — both types of evaluation must be covered).
- **Maka design implications**: Creed 1 is exactly "trajectory (event log) and result (final facts) are both in the log" — the evaluator can check both the facts the agent claims in the log and the final-state facts; safety zero-tolerance serves as a veto dimension (external communication / file deletion / secret writes).
- **Writable design doc**: "maka eval Safety Zero-Tolerance and Trajectory/Result Dual Coverage Specification"

### [KP-06-06] Human spot-checking, judge calibration, and adversarial review
- **Core in one sentence**: However reliable automated evaluation is, it needs periodic human spot-checks; before scaling up the use of LLM judging, you must first do **judge calibration**; adversarial review uses red-teaming to actively construct "superficially perfect but actually wrong" cases.
- **Key design points**: Human spot-checks cover different types / successes and failures / boundary cases with ambiguous scores; **judge calibration** — first build a human-labeled gold set (100–200 cases), measure agreement between the judge model and humans (Cohen's kappa; only scale up after meeting a bar such as >0.7; re-calibrate whenever the judge model or rubric is updated) — "without this step, LLM-judged scores are just one more model's opinion"; adversarial review (superficially perfect but containing hidden errors / keyword stuffing / exploiting judge bias to cheat high scores); multi-judge mechanism (independent judging with weighting / consistency checks, with disagreements flagged for humans).
- **Maka design implications**: eval should build in a "judge calibration" stage — create a Maka gold set for judge models and track kappa (supporting Creed 4: a high judge score is not fact; it must be backed by evidence of calibration against humans); adversarial review specifically targets "self-check claims passed but actually not fixed".
- **Writable design doc**: "maka eval Judge Calibration and Adversarial Review Process"

## 4. Automated Evaluation Environments

### [KP-06-07] Five elements of an evaluation environment + the tool-calling paradigm (hierarchical Verifiers)
- **Core in one sentence**: A repeatable automated evaluation environment consists of five elements; the tool-calling paradigm uses hierarchical environments plus executable verification, relying on neither humans nor LLM judges.
- **Key design points**: The five elements (dataset initial state + goal description + optional reference / balancing environment-state authenticity and controllability / tool interfaces providing **atomic operations** rather than high-level abstractions to force planning and composition / a scoring rubric / an execution protocol and termination conditions); the Verifiers framework is hierarchical (SingleTurnEnv/ToolEnv/StatefulToolEnv/SandboxEnv); it supports parallel sampling and trajectory caching; tool failures return **clear error messages rather than a simple failure flag**, letting the agent learn from errors.
- **Maka design implications**: eval should explicitly declare the five evaluation-environment elements; headless/terminal environments are primarily tool-calling-style — prefer deterministic verifiers (exit codes / output files / log facts) over judges for scoring, consistent with "log is the runtime"; the TaskRun lifecycle naturally implements "execution protocol/termination conditions".
- **Writable design doc**: "maka eval Evaluation Environment Five Elements and Tool-Calling Environment Specification"

### [KP-06-08] Human-interaction evaluation environments: progressive information disclosure, user simulation, and dual-control environments
- **Core in one sentence**: Real users rarely describe their needs clearly at the outset — **progressive information disclosure** is the fundamental difference between human-interaction evaluation and traditional benchmarks.
- **Key design points**: User simulation (an LLM plays the user, discloses information progressively on demand, and has **limited patience** — it terminates the conversation and fails the task when communication is inefficient); τ-bench dual verification + binary reward (database final state + whether the conversation outputs the necessary key information, but the task level aggregates to 0/1 — "missing a non-key field" and "complete failure" score the same); **τ²-bench's two increments** (① a Dual-Control environment — the user simulator can also operate the same shared environment, closer to tech support ② more precise task specifications and compositional task generation); the divide between tool-calling vs human-interaction paradigms (action correctness vs communication-strategy reasonableness).
- **Maka design implications**: headless persistent-task evaluation must model "the environment side can also change state" (a user/external service modifying files or state mid-task → the agent must observe the change through tools, echoing "Context is not history"); progressive information disclosure should be written into maka eval's conversation/task protocol.
- **Writable design doc**: "Human-Interaction Task Evaluation Protocol: Progressive Information Disclosure, User Simulation, and Dual-Control Environments"

## 5. Designing Evaluation Task Datasets

### [KP-06-09] Five core challenges in task dataset design
- **Core in one sentence**: The dataset is the "script" — a badly designed dataset run in a perfect environment still yields only noise.
- **Key design points**: ① The tension between clarity and openness (GAIA's "simple concepts but open paths"); ② the balance between authenticity and controllability (SWE-Bench Verified's manual expert verification filters 500 high-quality tasks); ③ coordinating diversity and systematicity (AndroidWorld's 116×20 app-parameterized generation of unlimited variants); ④ evaluation cost vs coverage (SWE-bench Verified 2294→500 cut cost ~80%); ⑤ **data-leakage prevention** (GAIA's unique answers plus original attachments that don't exist on the internet; SWE-bench-Live's time freshness; τ²-bench's dynamic parameters; Terminal-Bench's **canary GUID**).
- **Maka design implications**: local-first evaluation sets should build in anti-leak mechanisms (canary GUID / parameterized variants / time freshness); the cost dimension (Terminal-Bench 2.1 comparison experiment cost analysis) is "challenge four" in practice.
- **Writable design doc**: "maka eval Evaluation-Set Leakage Prevention, Scale, and Cost-Control Specification"

### [KP-06-10] Precision of task descriptions, complexity hierarchy, and systematic task distribution
- **Core in one sentence**: Good task descriptions make verification mechanizable and let parameterized templates generate variants; complexity layering lets failures be diagnosed to specific capabilities; the task distribution systematically covers capability / difficulty / scenario / boundary.
- **Key design points**: GAIA precision (information-source constraints / time range / strict format matching); τ²-bench contextualization (separating known information from task instructions + **Grounding Requirement** — answers must be based on what tool calls actually returned, not fabricated); Terminal-Bench mechanizable verification (`build-linux-kernel-qemu` actually builds a kernel from source plus a custom printk run in QEMU — **the agent cannot fake output to slip through**); AndroidWorld parameterized templates (preventing memorization / increasing diversity / supporting comparison experiments, with verification based on final UI state rather than action sequences); **complexity hierarchy** (GAIA L1 tool use / L2 multi-step planning / L3 long-horizon thinking, corresponding respectively to prompt engineering / planning mechanisms / hierarchical architectures and post-training); systematic task distribution (τ²-bench trap tasks, OSWorld's action × application two-dimensional matrix across 3 OSes, Terminal-Bench composite tasks across technology stacks).
- **Maka design implications**: task descriptions should prioritize "mechanizable verification" (terminal output / exit code / file state / log facts); complexity layering lets failures be diagnosed to specific capabilities; parameterized templates + headless batch runs cheaply generate regression variants.
- **Writable design doc**: "maka eval Task Description, Complexity Layering, and Task Distribution Specification (Including Parameterized Templates)"

### [KP-06-11] Verifiability, objectivity guarantees, and data-quality iteration (including the evaluation/training isolation red line)
- **Core in one sentence**: Verification must be objective and executable — able to deeply inspect the final state and to distinguish "really solved" from "introduced a new bug"; data quality comes from high-rejection-ratio human filtering and community-driven iteration; the evaluation environment can be reused in construction, but the specific items in the evaluation set must be isolated from training data.
- **Key design points**: SWE-Bench Verified dual re-verification (**FAIL_TO_PASS** — failed before the fix, passed after the fix + **PASS_TO_PASS** — passed both before and after the fix — distinguishing "problem solved" from "no new bug introduced"); τ²-bench multi-layer checks; OSWorld deep checks (134 independent evaluation functions + full OS privileges); **data-quality control** (2294 problems, 1699 human-evaluated, 93 developers, only 500 finally passing = **the 29% high rejection ratio is a necessary investment in evaluation quality**); OSWorld-Verified 15 months, 300+ problems, four categories of systematic iteration (environment / description / verification / initial state), 50× parallel speedup, public reproducible trajectories; **red line: the evaluation environment and the post-training environment share the same source and reusable construction mechanism, but the specific evaluation-set items must be strictly isolated from the training data**.
- **Maka design implications**: scoring should prefer "deterministic verifiers" — deep verification against Maka logs/files/processes/terminal output; dual verification (FAIL_TO_PASS/PASS_TO_PASS) maps to "failed before fix / passed after fix" regression-set management; versioned evaluation sets, canaries, and publicly archived trajectories for reproducibility.
- **Writable design doc**: "maka eval Verifiability, Data Quality, and Evaluation-Set Iteration Specification (Including the Training-Isolation Red Line)"

## 6. Automated Evaluation Methods

### [KP-06-12] LLM-as-a-Judge core and the four rubric criteria
- **Core in one sentence**: Open-ended tasks have no standard answer to compare automatically, so an LLM judges them against an expert-defined rubric; the rubric must follow Scale AI's four criteria.
- **Key design points**: Limitations = judge-model bias (most typically **length bias** — giving longer answers higher scores) plus fluctuation across judging runs; three defenses against length bias (the rubric explicitly penalizes verbosity / match lengths before pairwise comparison / periodically audit the "high-score-length correlation"); **the four rubric criteria** (Scale AI): ① based on expert guidance (capturing core facts and reasoning steps) ② comprehensive coverage (facts / logic / completeness / safety + explicit **Pitfalls**) ③ criterion importance weighting (required / important / optional items / **Veto** — preventing keyword-stuffing-style reward cheating) ④ self-contained evaluation (each item independently actionable, not dependent on the rater's domain knowledge — instead of "the response demonstrates deep understanding" use "cites at least two authoritative theories and accurately explains how they support the conclusion"); **Reward Hacking** (finding shortcuts to high scores: hallucination / sycophancy / keyword stuffing / dodging hard questions); the rubric is an iterative product (trial use, collecting disagreements, and progressively refining it into a detailed precedent set plus boundary cases).
- **Maka design implications**: open-ended dimensions (self-check reports / plan reasonableness / error explanations) use a four-criterion rubric + veto; "high judge score" is only one piece of evidence, not fact authority (Creed 4); write the scoring rationale, judge model and version, and rubric version into the evaluation record.
- **Writable design doc**: "LLM-as-a-Judge and Four-Criterion Rubric Implementation Guide (Including Length-Bias Auditing)"

### [KP-06-13] Same-source model problem, multi-source heterogeneous judging, and multimodal LLM-as-a-Judge
- **Core in one sentence**: When the agent and the judging model come from the same source, the agent learns to exploit the judge's preferences and blind spots (Goodhart's law) — mitigation relies on **multi-source heterogeneous judging**.
- **Key design points**: **The same-source model problem** (the agent learns to game scoring loopholes and dodge errors the judge is bad at detecting — "when a metric becomes an optimization target, it ceases to be a good metric"); **multi-source heterogeneous judging** (agent uses Claude → judge with GPT-5 + Gemini; biases across different families are orthogonal and hard to fool simultaneously; the same rubric guarantees the same objective; deployment uses a single model for fast evaluation with periodic full multi-source quality audits); multimodal in four directions (TTS evaluation finds prosody problems that WER can't catch; ASR semantic impact judges "transfer a thousand becomes ten thousand"; UI evaluation uses a Proposer-Reviewer mechanism; video-editing keyframe verification); experiment 6-6 lesson: **"choosing what reference answer / reference image / reference audio is itself evaluation design"** (carefully define whether "sounding like the reference voice" should count toward the total score).
- **Maka design implications**: eval defaults to multi-source heterogeneous judging (especially where headless/terminal truth is hard to distinguish); judge family/version, rubric version, and candidate-reference hash are required fields of the evaluation record; **the same-source problem of an agent reviewing its own log is especially severe — heterogeneous judges must be forced in**.
- **Writable design doc**: "Multi-Source Heterogeneous Judging and Multimodal Judge Extension Specification"

### [KP-06-14] Failure attribution: locating the first error across the whole trajectory
- **Core in one sentence**: End-to-end evaluation only answers success/failure; to drive fixes you must do failure attribution — mark the main error category, the **step where unacceptable behavior first appears**, the corresponding tool call or model output, and attach re-checkable evidence; **the first error is the root cause; later errors are mostly chain reactions**.
- **Key design points**: Three signals for production bad cases (explicit user corrections / negative feedback via dislikes / post-hoc checks discovering things that shouldn't have been done); LLMs can help but can't be fully relied on (failure attribution often reflects **product problems**); error categorization can reach hundreds of classes as the product matures; Coding Agent's six initial error categories (missing process norms / tool-call errors / scope-sensitive document-format errors / exact-copy errors / abnormal model execution / task-completion logic misjudgment); **exact-copy errors** (old_string off by one character / space / newline / escape / Unicode — compare layer by layer along "raw bytes → tool return → serialization → model input → model output → tool matching" to locate the first byte/token divergence; if the model output is correct but the transport layer changed it, attribute the root cause to the Harness/tool, not the model); structured attribution records (JSON/YAML referencing step numbers / tool names / observed evidence, distinguishing root cause vs consequence / recoverability / confidence; with multiple categories, choose the "earliest one that can explain the later failures" as the primary cause); preserve context (goal / environment state / version / full trajectory) for regression.
- **Maka design implications**: The Event Log is the natural data source for failure attribution — "the first deviation event" can be located directly in the event log (which tool call, or after which Compaction, the trajectory started going wrong), which is "Log is the Runtime"'s biggest leverage for evaluation; eval outputs structured attribution records and archives them together with goal / state / version / trajectory.
- **Writable design doc**: "Failure Attribution and Structured Attribution Record Specification (Based on the Runtime Event Log)"

### [KP-06-15] End-to-end regression tasks and trajectory-prefix regression tasks
- **Core in one sentence**: A fix is written as two complementary types of regression tasks — end-to-end regression verifies the complete workflow isn't broken; **trajectory-prefix regression freezes the context before the first error and tests only whether "the next decision boundary" has been fixed** (often more important for high-reliability production agents).
- **Key design points**: End-to-end regression (run the complete task from the initial state + request, close to production but hard to tell where failure occurs); trajectory-prefix regression (**freeze** the existing context / conversation / tool returns / environment state, and only require thinking and executing the next step or few steps — lower cost, isolates a single policy or tool problem); **the answer is a set of acceptable actions rather than a single action** ("first read the repo rules" / "first ask the user" / "refuse the dangerous operation" plus a list of **forbidden actions**); construct datasets from attribution; experiment 6-5 (11 bad cases × 3 memory encodings, each representation 6/11 but failing at different positions — **changing how context is represented does not automatically fix application policies**); core claim: **"obtaining a piece of information and correctly applying it to the current decision are two different capabilities"**.
- **Maka design implications**: TaskRun can resume from mid-state — "freeze the prefix, test only the next step" is architecturally natural (resume = replay/continue from a certain event point); eval maintains two types of regression sets (end-to-end + trajectory-prefix boundary sets); the acceptable-action set exactly expresses decision boundaries such as "after a self-check, whether to take a bounded fix action".
- **Writable design doc**: "End-to-End and Trajectory-Prefix Regression Set Construction Specification (Including Acceptable Action Sets)"

### [KP-06-16] Pairwise comparison and model ranking: Elo / Bradley-Terry and position bias
- **Core in one sentence**: "Which is better, A or B?" uses head-to-head pairwise relative comparison instead of absolute scoring — Elo online updates + the Bradley-Terry statistical foundation form the ranking, but you must guard against position bias.
- **Key design points**: Elo (score difference → expected win probability, with larger adjustments on upsets); Bradley-Terry is its statistical foundation; Chatbot Arena (anonymous random pairings, no need to define absolute standards, results depend on what questions users ask); **Position Bias** (LLM judging systematically favors a certain position — the standard mitigation is to swap the order and judge each once, average the results, count only cases where both agree, and otherwise record a tie or send to humans); from evaluation to training (pairwise comparison is a signal source for GRPO — sample multiple candidates on the same problem and estimate advantage from relative quality, eliminating the need for a critic value network).
- **Maka design implications**: the eval comparison feature should be upgraded into a protocol of "pairwise comparison + order swapping + Elo/Bradley-Terry ranking" for model selection and Harness-variant comparison; reports should use pairwise differences (who wins on the same task) rather than only absolute score deltas.
- **Writable design doc**: "Pairwise Comparison and Model Ranking Protocol (Order Swapping, Elo/Bradley-Terry, Bias Auditing)"

## 7. Evaluation-Driven Model Selection

### [KP-06-16-cont.] Model-selection key dimensions, behavior strategy, cost analysis, and continuous iteration
- **Core in one sentence**: Model selection is not "pick the strongest"; it is an evaluation-driven tradeoff across throughput, latency, cost, performance, and reliability according to the application scenario; selection is not a one-time event.
- **Key design points**: Throughput and latency (TTFT = queueing + Prefill, Decode determines output speed and thinking duration, **p95 tail latency** reflects experience better than the mean); cost (a cheap model with a low success rate is actually more expensive because of retries; compute average cost per task and the cost-performance ratio); **budget-capability curve** (RE-Bench: with a 2-hour budget the best agent is about 4× a human expert, but humans benefit more from increased time budgets — leading under a short budget cannot be extrapolated to long-horizon capability); multi-model collaboration (lightweight models for simple tasks, strong models for complex ones, specialized models for subtasks — must verify the overall benefit, and beware simple questions like "9.9 vs 9.11" being sent to a lightweight model and getting wrong); **model behavior strategy (action thresholds)** (experiment 6-8 with fixed Harness: GPT-5.6-sol averages 6.89 tool calls before its first modification / reads 4.67 files, Claude Sonnet 5 is 4.56/3.56 — supports "action strategy varies with the model", does not support "reading more or acting earlier is necessarily better"); **three-layer cost breakdown** (model inference cost including the **context accumulation effect** (re-sending history every round, mitigated by the KV cache) and the **thinking-token cost** (not shown but billed); tool-call cost (a single web search is 2000–5000 tokens and is billed repeatedly in every later round); infrastructure cost); **cost optimizations can be toggled independently** (experiment 6-9: stable prefix saves 28.3%, history compression saves 17.5%, both together save 30.0% — **you cannot add the individual savings together**); continuous iteration ("on my specific task, is Gemini better than Claude? by how much? what is the switching cost?" — do differential routing instead of blindly switching everything).
- **Maka design implications**: cost-analysis practice already exists (under Creeds 1/3, tokens and events all enter the log); put "budget-capability curve, TTFT/thinking latency, three-layer cost breakdown, independently toggleable context optimization" into the eval model-selection report; differential routing fits naturally with "budget-driven headless tasks" (each TaskRun declares a model and budget tier).
- **Writable design doc**: "Model Selection and Differential Routing Decision Process (Including Budget-Capability Curve and Three-Layer Cost Breakdown)"

## 8. Statistical Significance of Evaluation Results

### [KP-06-17] Statistical significance: standard error, paired analysis, multiple random seeds, and multiple comparisons
- **Core in one sentence**: The evaluation set is finite and model outputs are stochastic, so score differences may be only sampling noise; judging "worth switching/releasing" requires: the score gap exceeds the noise, holds up in paired analysis, and can be reproduced.
- **Key design points**: Standard error SE(p)≈√(p(1−p)/n) (100 cases at 70% → 95% CI about ±9pp — "73% vs 70%" is not enough to support a switch); **paired analysis** (record who wins task by task on the same batch, using McNemar's test or paired bootstrap, rather than directly subtracting two independent success rates); use **multiple random seeds (3–5 runs)** per configuration and report mean and spread (a single run can only screen directions); if the expected gain is 2–3pp but the evaluation set has only a few dozen problems → enlarge the sample first (the standard error shrinks as 1/√n); **multiple comparisons** (tighten the threshold when validating multiple hypotheses in parallel, or re-run independently); the practical standard = gap exceeds noise + holds in pairing + reproducible.
- **Maka design implications**: eval comparison output should build in a statistical-significance layer (confidence intervals, McNemar/paired bootstrap, multi-seed mean ± spread); Terminal-Bench comparisons and model-switch decisions must pass the significance bar (echoing Creed 3: the evidence from one run only supports conclusions proportionate to its scale).
- **Writable design doc**: "maka eval Report Statistical Significance Specification (Confidence Intervals, Paired Tests, Seed Strategy)"

## 9. Agent Observability

### [KP-06-18] Agent observability: Trace/Span model, standard protocols, and "production trajectories flowing back into evaluation assets"
- **Core in one sentence**: An agent system can produce different outputs for the same input, its execution paths are extremely complex, and its thinking is opaque — observability infers what happens inside via logs / metrics / traces; **the most valuable direction is flowing production trajectories back into evaluation assets**.
- **Key design points**: Four sources of value (problem diagnosis / the foundation for continuous optimization / cost management (differing by one or two orders of magnitude across tasks) / accumulating data for post-training); **the Trace data structure = a span tree** (one task = one trace; each LLM call / tool call / retrieval = one span recording input-output / start-end time / tokens / errors; parent-child relationships form an execution tree); standard protocols = **OpenTelemetry + OpenInference** (decoupling collection from analysis, avoiding platform lock-in); LangSmith-style platforms (asynchronous batch collection that doesn't impact response latency, A/B testing, prompt version management); **flowing back into evaluation assets** (filter suspicious failure cases from production trajectories → **de-identify** → settle them into new evaluation-set cases and regression tests — "the failure patterns exposed in production today become the regression cases that hold the baseline tomorrow").
- **Maka design implications**: The Runtime Event Log can naturally project into a span tree (TaskRun = trace root, messages / tool calls / results / termination facts = span leaves); align with OpenTelemetry/OpenInference to avoid platform lock-in; build a "production bad case → de-identification → regression set" closed-loop pipeline so the evaluation set keeps growing.
- **Writable design doc**: "Maka Observability: Runtime Event Log → Span Tree and Evaluation Asset Flow-Back Closed Loop"

## 10. From Benchmark Reports to System Improvement

### [KP-06-19] Iteration closed loop + internal evaluation infrastructure for production-grade agents
- **Core in one sentence**: When you see a score drop, check the evaluation system itself first before touching the agent; each round of evidence only supports the next step proportionate to its scale; the best agent products systematically embed ML experimental methodology (ablation / AB / feature flags / prompt regression / privacy awareness) into product engineering.
- **Key design points**: **Check the evaluation system first, then the agent** (a score drop may come from the evaluation system itself: insufficient resources / scorer bugs / cases disconnected from production — numerically indistinguishable from model degradation); reading a report well is the art of finding problems (AndroidWorld 88% overall but failures concentrated in 3 of the 4 SystemWifiTurn* items — first find the failure cluster, then replay trajectories to separate see/think/do/verify); **change only one variable per round** (AndroidWorld H1 adding navigation hints no effect → H5 switching to the UIAutomator element tree 25%→100% → H5C removing meaningless nodes, 100% unchanged, tokens halved — ① a prompt cannot make up for information the model fundamentally cannot see; check the input first ② more input is not always better ③ without swapping the model, merely adjusting the Harness representation resolved "whether it can be done" and "whether it's worthwhile"); **internal evaluation infrastructure, five components**: ① ablation infrastructure (a master switch that disables multiple features at once to create a "bare model" baseline, switches injected **very early in the startup path**, every major feature independently disableable, periodic ablations to discover "feature debt") ② AB testing methodology (**multi-armed rather than binary** to reveal dose effects, **distinguish mechanism metrics from target metrics** (changing plan-file length is a mechanism; the real goal is reducing session-level cost), **set guardrail metrics** (stop if the target improves but user satisfaction / operation count / error rate worsen), record baseline statistics) ③ **a two-layer feature-flag system** (compile-time flags = physically remove code, runtime flags = server-side delivery + local cache; feature flags are first-class architecture components, not debugging tools; record each feature's exposure event at most once per session to prevent contamination) ④ **prompt-sensitivity evaluation** (prompts are core "code" yet lack version control — use **deterministic rendering** (same config, same output), versioned snapshots, and run regression on the evaluation set for every change just as code runs CI) ⑤ **privacy-aware analytics** (enforce with a type system — analysis interfaces only accept values wrapped in special types, the type name itself is an audit trail, turning privacy constraints from a documented norm into compile-time enforcement).
- **Maka design implications**: "Context is not history" / "Feedback is not fact authority" correspond to independently disableable components (Tool Result pruning / LLM Compaction / Self-check / budget) — make them all ablation switches in eval (ablation baseline); TaskRun / Task Event Log supports a "one round of evidence → one next step" iteration SOP; the evaluation report should state "where the conclusion applies, which baselines failed, and what to verify next round"; AB's "mechanism vs target" distinction is especially important (changing the pruning threshold is a mechanism; what you truly care about — success rate and cost — is the target).
- **Writable design doc**: "Iteration SOP from Benchmark Reports to System Improvement" + "Component-Level Ablation Switches and AB Testing (Mechanism/Target/Guardrail Metric) Specification"

## 11. Simulation Environments: The Bridge from Evaluation to Post-Training

### [KP-06-20] Simulation environments: RLVR reward functionalization, reset semantics, throughput, and domain randomization
- **Core in one sentence**: The endpoint of evaluation is not scoring but improvement, and the strongest form of improvement is training — the evaluation environment evolves into a simulation environment: a virtual playground where the agent practices repeatedly and is scored automatically.
- **Key design points**: Core differences between simulation and evaluation (extremely high interaction frequency, millions vs thousands of times / randomization is needed to prevent rote memorization / immediate feedback must be provided); **evaluation assets → training signals** (a well-defined rubric/verifier is essentially a reward function for verifiable-reward RLVR — the scoring script is directly the reward script); two new requirements for training (**reliable reset semantics** — each episode must reset to a clean initial state or gradients get contaminated; **throughput far above evaluation** — environment parallelism and per-instance overhead determine training feasibility); digital environments (AWorld's 26 MCP servers, 126 tools, 14.6× speedup, stateless design for efficient parallelism); embodied environments (RoboTwin2 dual arms, **Action Chunking** — the model plans multiple consecutive actions at once to achieve real-time control); **Domain Randomization** (randomizing physical parameters / visual appearance / sensor noise over a wide range shrinks the sim-to-real gap; moderate randomization improves generalization, excessive randomization makes tasks too hard).
- **Maka design implications**: TaskRun / budget / continuation naturally suit simulation-style evaluation (each episode starting from a clean initial state corresponds to a clean TaskRun session; resume/replay logs can serve as a low-cost "reset + warm start" mechanism; scoring scripts and RLVR reward functions are homologous — eval verifiers can later be reused directly as post-training rewards); apply the domain-randomization idea to Maka evaluation (randomize latency / timeouts / API jitter / environment-state changes to test robustness).
- **Writable design doc**: "Evolution Design from maka eval to Simulation Environments (Reset Semantics, Throughput, and Domain Randomization)"

## Golden Quotes of This Chapter / Core Conclusions
- "The object of evaluation should not be only the model, but the combination of the model and the Harness."
- "The primary value of an evaluation system is not to score the current system, but to let you keep up with model evolution quickly and reliably."
- "Pass^k answers whether the agent can deliver reliably and stably, not whether it can occasionally work miracles."
- "Without the (judge-calibration) step, LLM-judged scores are just 'one more model's opinion', not a reliable proxy for human judgment."
- "The evaluation environment is the 'stage' and the dataset is the 'script' — a badly designed dataset, even run in a perfect environment, yields only noise."
- "When data leaks, the evaluation is measuring memory rather than generalization — it's like memorizing the answers before the exam."
- "Obtaining a piece of information and correctly applying it to the current decision are two different capabilities."
- "Goodhart's law: when a metric becomes an optimization target, it ceases to be a good metric."
- "Choosing what reference answer, reference image, or reference audio is itself evaluation design."
- "When you see agent performance drop, check the evaluation system itself first, then touch the agent."
- "When several context optimizations are used together, they must be measured together on the complete task; you cannot simply add the individual savings." (28.3% + 17.5% ≠ 30%)
- "One round of evidence only supports the next step proportionate to its scale."
- "Every major feature should be independently disableable, and the team should periodically verify each feature's actual contribution."
- "Is what I changed (the mechanism) the same as what I truly care about (the target)? If not, defer to the target."
- "Feature flags are not debugging tools; they are first-class architecture components."
- "Design privacy constraints in from the start, rather than bolting them on afterwards."
- "Observe → hypothesize → experiment → verify → new understanding → new hypothesis" — agent engineering shifts from experience-driven 'alchemy' to data-driven scientific engineering.

## Reflection Questions from the Book (transcribed key points)
1. Does LLM-as-a-Judge "self-evaluation" have systematic blind spots (style preferences inconsistent with humans)? How to detect and correct them?
2. Does the "cat-and-mouse game" of evaluation-set leakage prevention have an endgame? Design an evaluation method that fundamentally resists data leakage.
3. How to design reliable rubrics for subjective dimensions ("is it helpful" / "is the tone appropriate")?
4. The simulated user is itself an LLM — does it systematically underestimate emotionally agitated / inarticulate users? How to validate the quality of the simulated user?
5. Bradley-Terry assumes preference transitivity, but human preferences often violate it — in which scenarios does nontransitive preference appear in agent evaluation?
6. For an agent with a single-run success rate of 60%, how to decide which metric to report and how large a k to take, given the costs of failure / retry / side effects?
7. The action space is huge, and validating one hypothesis needs hundreds of runs — how to maximize the information gained from evaluation under a limited budget?
8. AndroidWorld full element tree 25%→100% but tokens 2.498×; after pruning 100% unchanged with tokens 0.506× — design automatic pruning rules?
9. How does progressive information disclosure affect evaluation results? When the simulated user's disclosure strategy differs greatly from reality, are the conclusions still reliable?
