# Afterword · Back to Agent = LLM + Context + Tools — Knowledge Point Extraction

> Source: `book/afterword.md` (43 lines). Afterword theme: return to the core formula; two clouds on the horizon (real-time streaming interaction, continuously accumulating experience from success and failure); the model and Agent co-evolve.

## Afterword Theme (Background Framework)
- **Back to the core formula**: all ten chapters of the book unfold within the three words of `Agent = LLM + Context + Tools`; Chapter 1 establishes a three-level understanding of the formula (implementation level / intuitive level / academic level) and the "workflow → autonomous Agent" orchestration spectrum.
- **The book's three-layer structure**: ①Building (Chapters 2–5: context engineering / memory and knowledge bases / tools / code generation); ②Evaluation and evolution (Chapters 6–8: evaluation / post-training / continuous evolution); ③Interaction and collaboration (Chapters 9–10: multimodal real-time interaction / multi-Agent collaboration). Chapter 8 is the book's convergence point where "how to build an Agent" shifts to "how to make an Agent get better over the long term."
- **Two clouds on the horizon**: by analogy with Kelvin's two clouds in 1900 (→relativity and quantum mechanics), the two clouds on the Agent sky are ①real-time streaming interaction and ②continuously accumulating experience from success and failure.
- **Model and Agent co-evolve**: harness fallback → model internalization → Harness deletion → becoming training signals again, a self-reinforcing flywheel; the model will "eat the Harness layer by layer" but never finish; the flywheel is the deepest moat; the three questions (what it sees / what it can do / how to verify whether it did it right) never go out of date.

## Knowledge Points

### [KP-11-01] Back to the Core Formula: Agent = LLM + Context + Tools
- **One-sentence core**: all knowledge in the book can be traced back to the two variables "context (what it sees)" and "tools (what it can do)"; the formula is an anchor of judgment that keeps you clear-headed in the face of model iteration.
- **Key design point**: the three never-outdated questions — **what it sees, what it can do, how to verify whether it did it right** — describe the basic way an intelligent system interacts with the world, not the usage of any particular model.
- **Maka design insight**: the four creeds are precisely the engineering answers to the three questions — "Context is not history" governs "what it sees", "Log is the Runtime" makes tool calls and results enter the log, i.e. the record of "what it can do", and "Feedback is not fact authority" governs "how to verify whether it did it right"; design documents should tie the creeds back to the formula so they do not turn the page with any specific model API.
- **Design document to write**: "Maka Design Principles and the Mapping to Agent = LLM + Context + Tools"

### [KP-11-02] The First Cloud on the Horizon: From Turn-by-Turn to Real-Time Streaming Interaction
- **One-sentence core**: today most Agents are still in the request–response mode of "you finish a sentence, it thinks through a whole chunk, and spits it out all at once", but the real world does not stop to wait for it to finish thinking; moving toward real-time has two parallel paths, one architectural and one in inference.
- **Key design points**: Path 1 (architecture does fast/slow separation: real-time and intelligence are almost orthogonal, and a single model can hardly handle both — a fast model up front maintains conversational tempo while a slow model in the background thinks deeply); Path 2 (make inference itself faster: push decode speed to the extreme so turn-by-turn waiting nearly vanishes — Xiaomi MiMo-V2.5-Pro-UltraSpeed, 1T parameters on a single 8-GPU node at 1000 tokens/s (FP4 + speculative decoding); Taalas HC1 with an 8B model fused into a 6nm chip at ~17,000 tokens/s with <100ms responses, at the cost that updates require re-fabricating the chip); a "living" Agent should be able to listen while thinking, speak while thinking, and proactively discover "what it should handle."
- **Maka design insight**: TaskRun / Task Event Log / budget / continuation happen to provide the runtime skeleton for fast/slow separation — the front-end interaction is one task, and the back-end deep thinking is another interruptible/resumable task; both the fast and slow paths write to the same Event Log, and Turn boundaries must not block task progress; Headless long-running tasks are naturally the host for the "slow model in the background."
- **Design document to write**: "Maka Fast/Slow Separation and the Asynchronous TaskRun Event Model"

### [KP-11-03] The Second Cloud on the Horizon: Continuously Accumulating Experience from Success and Failure (Small World vs Big World)
- **One-sentence core**: today's model is "a genius with an excellent memory who cannot learn anything new" — after each task, most of the pitfalls stepped in and tricks found are thrown away along with the context; whether this is a real problem depends on the two hypotheses of the small world / big world.
- **Key design points**: **Small-world hypothesis** (a model with trillions of parameters has already absorbed general knowledge, and learning once is enough; the work of frontier labs is essentially "distilling" capabilities from every industry into the same large model, with the bottleneck being whether there is enough data); **big-world hypothesis** (knowledge belonging to a specific user/company — code conventions / team tastes / client temperaments — is not in the training corpus and keeps changing, so it can only be continuously learned on the job — pointing to memory (Chapter 3) and continuous evolution (Chapter 8)); four carriers for settling experience (**knowledge documents, instructions, programs, or model parameters updated after filtering**).
- **Maka design insight**: "Context is not history" directly answers "experience is thrown away along with the context" — Maka retaining recorded evidence and only changing what the next inference sees is precisely the engineering implementation of "not discarding experience as one-off context"; "Feedback is not fact authority" suggests that the success/failure of self-checks and experiments must pass through filtering and settling (documents / instructions / programs / parameter signals) before they can become facts.
- **Design document to write**: "Maka Experience Settlement Pipeline: From Runtime Event Log to Knowledge/Feedback Signals"

### [KP-11-04] The Model's Endgame Capability Is Learning and Adaptation, Not Memory
- **One-sentence core**: "AI for AI" and "AI for Science" will push Agents to frontiers where no ready-made answer exists, and there they can only learn autonomously from the success and failure of one experiment after another; the model's strongest capability will ultimately be not remembering, but learning and adapting.
- **Key design points**: the big-world hypothesis fills in the layer that "training once cannot cover" (specific/private/rapidly changing situational knowledge); sources of learning signals (task success/failure / repeated trial and error in experiments / real business feedback); directly linked to memory (cross-session extended information) and continuous evolution (turning production experience into controlled updates) — making Chapter 8 the book's convergence point.
- **Maka design insight**: Task Event Log + budget + resumability are the runtime conditions for "letting the Agent learn autonomously through one experiment after another" — a failed TaskRun should not be cleared away as one-off context, but retained as raw evidence that can be reviewed, analyzed, and upgraded into learning signals.
- **Design document to write**: "Maka Autonomous Learning Loop: Organizing and Feeding Back Failed-Experiment Evidence"

### [KP-11-05] The Self-Reinforcing Flywheel: Harness and Model Co-Evolve
- **One-sentence core**: the layered fallback logic piled up in the harness (multi-level context compression / retry / pessimistic permissions) records precisely where the model is not yet solid right now; the remedy in turn becomes the next round of training signals, forming a self-reinforcing flywheel.
- **Key design points**: the three-stage flywheel (**users raise real hard problems → the application-layer harness compensates for what the model cannot do well → the remedy settles into training signals for the model's next iteration**); when the model internalizes these constraints, the corresponding harness code can be deleted; empirical evidence (Anthropic uses Claude Code to let the model and harness feed each other; in one experiment, changing only the harness without changing the model raised accuracy from 52.8% to 66.5% — today's harness has such leverage precisely because the model has not gotten there yet).
- **Maka design insight**: Maka's pruning / LLM Compaction / Self-check / permission fallback are all harness layers for "where the current model is not solid" — design them as **observable, deletable modules that can be upgraded into training signals**; every harness rule should leave evidence in the Event Log of "why this fallback exists", so that after model internalization it can be safely dismantled and its runtime evidence fed back as signals.
- **Design document to write**: "Maka Harness Lifecycle: Observability and Retirement of Fallback Logic"

### [KP-11-06] Will the Model Eat the Harness — Yes, Layer by Layer, But It Never Finishes
- **One-sentence core**: the model will "eat the Harness layer by layer", but this "eating" never ends — the Harness will not disappear; it just keeps migrating toward new capability frontiers as the model advances.
- **Key design points**: answering the cliffhanger from Chapter 1 (**yes, layer by layer** — the interaction model of Chapter 9 is a specimen: interruption/interjection, which once relied on external harnesses, has already been built into the model); three reasons it can never be fully eaten (①training happens on a monthly scale and while the model can afford to wait, the business cannot; ②the model cannot internalize all the constraints and preferences of real businesses, so there is always a newest boundary needing external logic as a fallback; ③each generation of model opens a new capability frontier, and the frontier is exactly where the model is least solid); the reading of the "bitter lesson" in the Agent era (general methods will ultimately win, but every stretch of road inside the word "ultimately" was paved by the Harness).
- **Maka design insight**: "Log is the Runtime" and "multi-level context compression / Compaction" are exactly the Agent-era specimens of harness fallback — when designing, accept that "these layers will be eaten", and the architecture must be **layered, replaceable, with clear boundaries** (so that internalized layers can be safely deleted without harming the log and evidence foundation); at the same time, know that a new layer will always appear at the newest capability frontier.
- **Design document to write**: "Maka Layered Architecture Evolution and Harness Retirement Strategy"

### [KP-11-07] The Flywheel Is the Deepest Moat — Depending on Which End You Stand On
- **One-sentence core**: the more tightly real business, feedback data, and model iteration interlock, the harder it is for others to catch up from outside; this flywheel is the deepest moat of this era, and the play depends on which end of the flywheel you stand on.
- **Key design points**: **the end that builds models** (moat = get the flywheel spinning: make real-scenario feedback flow back into training as quickly as possible); **the end that builds applications on top of the model** (the harness is the sharpest short-term technical lever, but stay clear-headed — every constraint the model internalizes erases a batch of advantages built solely on harness; the application layer's truly lasting moat lies beyond technology: **exclusive data, solid distribution channels, user trust, network effects, and the complex scenarios AI cannot handle in the short term that must be completed through human–Agent collaboration** — the play = use the harness to buy time, and use that time to build barriers beyond technology).
- **Maka design insight**: Maka's (local-first application layer) Runtime Event Log and self-check feedback system are precisely the technical vehicle for "feedback reflow" — the place where runtime evidence is organized into reusable assets; strategically, Maka's moat is clearly not some harness trick (which will be flattened by internalization), but local-first trust, evidence sovereignty, the log asset, and complex "human + Agent collaboration" workflows.
- **Design document to write**: "Maka Strategic Positioning: Flywheel Position, Moat, and Barriers Beyond Technology"

### [KP-11-08] No Need to Worry About Frameworks Going Out of Date — Three Unchanging Questions
- **One-sentence core**: the model iterates every few months, and specific APIs/products/leaderboards all turn the page, but the three questions "what it sees, what it can do, how to verify whether it did it right" will not go out of date.
- **Key design points**: the three questions describe not the usage of a particular model but the basic way an intelligent system interacts with the world; once you master them, no matter what new capabilities the next generation of model brings, you know which position in the formula to put them in; the book's mission is not to teach the usage of some API but to give a set of judgment that keeps you clear-headed amid waves of technology.
- **Maka design insight**: the four creeds should serve as "a stable architecture across generations of models" rather than temporary patches bound to one generation's capabilities; design documents should make explicit that the creeds answer the three unchanging questions, and when a new model appears, first ask "which position in the formula" before deciding which harness layers to retire.
- **Design document to write**: "Maka Cross-Generation Evolution Principles: Creed and Architecture Review Driven by the Three Questions"
