# Chapter 8 · Agent Continuous Evolution — Knowledge Point Extraction

> Source: `book/chapter8.md`. This chapter is the most relevant to Maka's headless self-evolution direction. The chapter's main line: obtaining learning signals from run trajectories → the four methods of continuous evolution (knowledge / instruction / program / parameters) → building a long-running continuous evolution closed loop (dual loops, verification/release/rollback, completion ≠ progress, safety boundaries, sleep learning).

## 1. Obtaining Learning Signals from Run Trajectories

### [KP-08-01] Saving experiences ≠ learning from experiences: the starting point of continuous evolution is "evaluation"
- **One-sentence core**: Storing trajectories into memory is not the same as learning new behavior; learning happens after the system actively completes "evaluation, comparison, induction, verification", not at the moment the log is written to disk.
- **Key design points**: After deployment the model does not automatically change its parameters because of a single inference; in-context learning / compression only adapts "within the current task"; raw trajectories are both long and noisy (containing valid strategies, chance successes, misattributions, and untrustworthy input), and cross-case comparison does not happen automatically; division of labor with Chapter 3 (user memory sediments "what the user and the world are like" = remembering more; this chapter's experiential learning sediments "how to act under what conditions" = going from clever to skilled); why you cannot simply let the model train itself after every task (production environments lack clean learning signals; local updates cause forgetting / drift / safety regression; erroneous experiences / injections get solidified and amplified); the current engineering path = constructing "learning" as an autonomous system outside the model (record evidence → verify results and process → extract commonalities across trajectories → decide whether to update knowledge / instructions / programs / parameters → modifications first become candidate versions that pass regression and safety checks).
- **Maka design implications**: Directly supports "Log is the Runtime" — the log must record evidence, but "log = runtime" does not equal "log = learning"; Maka needs to layer evaluation / induction / verification on top of the Task Event Log; SelfCheck produces evidence and one bounded repair opportunity, while real behavioral change is triggered by an independent evolution loop based on cross-trajectory evidence, avoiding treating "recorded" as "learned".
- **Writable design doc**: "Maka Design: From the Runtime Event Log to Experiential Learning (Evaluation-Layer Design)"

### [KP-08-02] The three types of learning-signal sources: environment results, process rules, LLM Rubric
- **One-sentence core**: Reliable learning signals are divided into three types according to "the more formalizable, the more they rely on code / environmental ground truth; only what is hard to formalize is handed to the LLM".
- **Key design points**: **Environment results** (result verification, from the real state of the environment: tests / type checks / order status — usually more reliable than the model's self-description); **process rules** (process verification, checking whether the path that reached the result is compliant — "correct result ≠ correct process": deleting the failing test also passes); **LLM Rubric** (quality verification — for dimensions with no single correct answer, use LLM-as-a-Judge with a predefined scale, scoring item by item, citing trajectory evidence, and explicitly stating uncertainty when evidence is insufficient); key criterion: **once an erroneous evaluation enters long-term knowledge / system prompts / training data, its impact keeps amplifying across subsequent tasks — "evaluation comes before summarization"**.
- **Maka design implications**: In the headless autonomous loop, Tool Results and termination facts naturally correspond to the "environment result" signal; the SelfCheck layer splits into deterministic process checks (business rules / permissions / action sequences) and LLM Rubric quality checks, and the deterministic part is never handed over to the model to guess; only verified signals may enter FeedbackObservation.
- **Writable design doc**: "Maka Design: Three Types of Learning-Signal Sources and SelfCheck Signal Integration"

### [KP-08-03] Three-layer trajectory verification structure + dimensionalized diagnosis: don't compress the result into a single scalar
- **One-sentence core**: Trajectory evaluation is "three-layer verification + dimensionalized structured diagnosis" — the bottom layer (result), middle layer (process), and top layer (quality) each do their own job, and no layer may degenerate into a single total score.
- **Key design points**: The three-layer structure (bottom-layer result verifiers read test results / database state / tool returns to determine "whether it was really accomplished" → middle-layer process verifiers check business rules / permissions / action sequences to determine "whether it was accomplished in an allowed way" → top-layer quality verifiers use a Rubric to judge language and strategy, "whether it was done appropriately"); the lower the layer, the more it relies on code and environmental ground truth; the verification result is a **structured diagnosis rather than a scalar** (e.g., "task partially succeeded, rule compliance passed, one evidence-free claim, one false promise, reply explained the policy three times" — dimensionalization preserves the nature of the problem and the location of the evidence); only dimensionalization allows root causes to be located (an evidence-free claim → missing knowledge / missing citation requirements / insufficient model capability; a false promise → change the prompt vs. add a "reply-to-tool-state consistency check"); LLM verifiers need calibration (experts annotate a small batch of trajectories; high-risk / low-confidence items go to a second model or humans; re-run the calibration set after model-version changes); **the verifier is only responsible for producing evaluations and evidence — "which part of the Agent should be modified" is decided by an independent diagnosis and evolution module, avoiding the same model acting as both judge and directly rewriting the rules**.
- **Maka design implications**: SelfCheck should be a "three-layer + multi-dimensional" verifier rather than a single pass/fail; output a "structured diagnosis" written to the Task Event Log (including evidence location) for the later Decision stage to decide whether to fix knowledge / fix prompts / change the Harness; the verifier is separated from the "modification generation" module (judge and evolution are decoupled).
- **Writable design doc**: "Maka Design: SelfCheck Three-Layer Verification Structure and Dimensionalized Diagnosis Protocol"

### [KP-08-04] The seven dimensions of the customer-service Agent trajectory evaluation Rubric
- **One-sentence core**: A diagnosable Rubric covers two categories of dimensions — "bottom-line constraints + service quality" — with more discriminative value than a single "is the user satisfied".
- **Key design points**: Seven dimensions — task result (whether the core request was resolved, evidence = final environment state / tool results), rule compliance (whether policies / permissions / processes were violated, evidence = policy library / action trajectory), privacy boundary (whether information that should not be provided was leaked, evidence = reply text / data-access records), factual reliability (whether statements are supported by knowledge or tool results, evidence = cited sources / tool returns), **promise–action consistency** (whether claimed operations actually happened, evidence = cross-checking replies against the tool log), expression quality (natural and concise, avoiding repetitive templating), compliant workarounds (whether an allowed alternative path was found when the original plan was infeasible); the first five constrain the bottom line, the last two are service quality; **"promise–action consistency" is especially suited to Agent scenarios** (traditional text evaluation that reads only the final reply would treat "I have submitted the refund" as good service; trajectory evaluation goes on to check whether the refund tool was really called, whether the call succeeded, and whether the order state changed).
- **Maka design implications**: The seven-dimensional Rubric is the concrete blueprint for SelfCheck; "promise–action consistency" maps directly onto Log-is-the-Runtime — comparing the operations the LLM claims with the real tool calls and termination facts in the log, item by item, is exactly the way to implement "Feedback is not fact authority".
- **Writable design doc**: "Maka Design: SelfCheck Default Rubric (Promise–Action Consistency First)"

## 2. The Four Methods of Agent Continuous Evolution

### [KP-08-05] The selection basis and comparison of the four update carriers
- **One-sentence core**: The primary basis for choosing an update method is not how long the experience has existed, but "**whether the target capability can be naturally expressed by some carrier**"; the four methods are not mutually exclusive and can work together.
- **Key design points**: **Experiential knowledge base** (facts / experiential rules / exceptions and sources — fast to update, traceable, on-demand retrieval, but depends on retrieval and the model correctly applying it); **Prompt and Skill** (judgment principles that require understanding context / exceptions / priorities but can still be explained in natural language — interpretable, controllable scope, but prone to bloat and conflicting rules being ignored); **Programs and Harness** (deterministically parseable / executably verifiable / high-risk hard constraints — testable, stable execution, low running cost, but higher development and maintenance cost); **model parameters** (high-dimensional perception / generation style / implicit policies — strong generalization, low inference overhead, but high update-regression cost); synergy examples (medical imaging parameters identify lesions + the knowledge base holds the latest guidelines + code computes risk metrics; customer-service natural tone relies on post-training, enterprise policy on knowledge and Skills, critical compliance on server-side code).
- **Maka design implications**: The headless Decision output needs an explicit "which carrier" routing strategy (tool-result-type evidence → experiential knowledge / programs, SelfCheck feedback → Prompt/Skill candidates, implicit style policies → parameters); the four carriers correspond to different release/rollback costs, directly affecting budget and continuation design.
- **Writable design doc**: "Maka Design: Self-Evolution Four-Carrier Routing and Release Paths"

### [KP-08-06] Sedimenting experience into knowledge: three layers of data + a five-step distillation pipeline
- **One-sentence core**: Organize the experiences that recur across many runs into retrievable knowledge documents; "recording and organizing are separated" — evidence is immutable, knowledge is rewritable.
- **Key design points**: Knowledge sources differ from Chapter 3 (extracting "what to do under what conditions" from action trajectories rather than "what the user and the world are like"); the system retains **three layers of data** (immutable raw trajectories (audit) → single-run analysis (this run's success/failure and candidate lessons) → Markdown knowledge documents distilled from multi-trajectory comparison / clustering / induction (applicable scenarios / recommended strategies / forbidden practices / exceptions / evidence sources / last verification time)); the five-step distillation pipeline (① save immutable trajectories and environment results ② structured single-run analysis ③ cluster by task family and build an evidence table of "which trajectories support / contradict" ④ write a formal document only after reaching the support threshold ⑤ test transfer on new tasks not involved in the distillation); Reflexion natural-language reflection may participate in generating candidate lessons, but **reflection itself is not evidence** — only content that matches environment results, is supported across trajectories, and transfers positively to new tasks enters the formal documents.
- **Maka design implications**: The Task Event Log is the natural "immutable raw trajectory layer"; implement two projection layers — "single TaskRun analysis" and "cross-TaskRun clustering/induction" — to produce retrievable experience documents; "Log is the Runtime" guarantees that re-induction does not tamper with the original evidence, and when environment versions change, conclusions can be precisely retracted by source.
- **Writable design doc**: "Maka Design: TaskRun Experiential-Knowledge Distillation Pipeline (Three Layers of Data)"

### [KP-08-07] Writing experience into instructions: system-prompt learning, minimal diffs, and Skill learning
- **One-sentence core**: When a rule can be clearly expressed in natural language and is repeatedly confirmed by multiple trajectories, experience can be promoted from "consultable" to "must-be-obeyed" instructions; modifications should be minimal auditable diffs.
- **Key design points**: Scope layering (rules that apply to almost all tasks go into the system prompt; complex processes that only take effect in a certain domain / project / tool are written as on-demand-loaded Skills / project instruction files); Karpathy's "system-prompt learning" (the third kind of human learning = after figuring out a method, using language to remind your future self; difference from RL = the former edits text, the latter does gradient descent); modification norms (minimal diff, note the scope, check for conflicts with existing rules, evaluate on both the "boundary cases that triggered the failure" and the "old-task retention set"); the offline optimization route (DSPy / OPRO / GEPA batch-search against an evaluation set) vs. production-system minimal diffs (continuous maintenance, provenance / audit / fast rollback); Skill learning (a candidate Skill states when to load it / preconditions / operation steps / known pitfalls / verification methods and source trajectories; prefer local patches for the same process, and only create a new directory for genuinely new independent capabilities); split "AI-flavored" feedback into checkable patterns (what can be judged by regex / statistics goes into deterministic checks; what is hard to judge is first calibrated against a human gold set and then added to the Skill); the complete lifecycle = **feedback → first-error attribution → Skill or interface specification → synthetic data → parameter candidates → boundary-set and retention-set verification → canary release or rollback**.
- **Maka design implications**: The FeedbackObservation→Decision stage directly produces "minimal-diff candidate instructions"; the "auditable change contract" of the AHE target protocol is consistent with the minimal-diff / provenance manifest; Skill-ification is the concrete carrier of "Context is not history" (reusable judgment principles written as on-demand-loaded Skills rather than stuffed into every context).
- **Writable design doc**: "Maka Design: System-Prompt/Skill Minimal-Diff Learning and Release Thresholds"

### [KP-08-08] Writing experience into programs: verifiable workflows, falsifiable change contracts, and Harness self-modification
- **One-sentence core**: When the experience is a stable, repeatable, verifiable operation, "compile" the trajectory into a small program with parameters, state checks, and version information; self-modification must go through an auditable software release process.
- **Key design points**: The modifiable objects go far beyond new tools (operation layer: browser trajectories → parameterized workflows; control layer: tool routing / retry / circuit-breaking / compaction strategies; verification layer: parameter checks / state verifiers / regression tests; architecture layer: adding a Reviewer Agent); **the six-step lifecycle of a browser workflow** (① capture the trajectory (action parameters + locator evidence — locator information can only be used to re-find elements, it cannot prove completion) ② parameterize (literals → template variables) ③ define state checks (pre-action / post-action / final state — **action success ≠ task success**, the final check must read the real page or backend state) ④ candidate verification (only validated when a sandbox-reset full replay passes completely; side-effecting tasks with no reset callback only store the candidate for audit) ⑤ matching and replay (Playwright executes directly without calling the LLM step by step) ⑥ invalidation and relearning); **the dangerous illusion: 100% replay coverage but empty fields, the task never completed — you must have pre-action verification, post-action verification, and independent verification before saving** (PreAct reports 8.5–13× end-to-end speedup on repeated tasks); **self-modification = auditable release process** (create a candidate branch from the stable version → Coding Agent minimal patch → static checks / unit tests / security scans / failing-trajectory replay / old-task regression → canary deployment; never overwrite the stable version); **every modification request should be a falsifiable change contract** (failure evidence / inferred root cause / attributed Harness component / candidate modification / expected fixed behavior / potentially damaged behavior / cases that verify each separately — AHE summarizes this as three-layer observability of component / experience / decision); Self-Harness (the candidate generator's input includes "success behaviors that must be preserved + records of previously rejected modifications", forming a bounded candidate space).
- **Maka design implications**: The headless "program carrier" self-evolution has "change contracts" built in (every self-modification request declares failure evidence / expected fix / possible regressions, and passes verification before entering canary); the browser workflow's "pre-action / post-action / final triple state checks" can be analogized as Maka's verification contract for tool-call results, preventing "called ≠ accomplished".
- **Writable design doc**: "Maka Design: Falsifiable Change Contracts and the Harness Self-Modification Release Process"

### [KP-08-09] Writing experience into parameters: the representation property decides the carrier; parameters work with external methods
- **One-sentence core**: Knowledge / instructions / programs all require the capability to be completely expressible by external symbols; high-dimensional perception, language style, implicit policies, etc., must go through post-training to be written into the model parameters.
- **Key design points**: Capabilities that are hard to symbolize (medical-image understanding / natural speech prosody / eliminating the "AI flavor" / long-horizon planning — the curly-quote scope judgment sits in the middle ground: use programs to parse the syntactic boundaries, Skills for contextual exceptions, and post-training internalization only for cross-task recognition habits); **whether to parameterize is not decided by "whether the task is long-term stable" alone: stability affects update frequency and cost, but the representation property of the capability decides the primary carrier**; three types of training data from the continuous-evolution perspective (high-quality demonstrations → SFT, explicit preferences → paired data, reliable environment-reward interactions → RL — de-identify / filter erroneous trajectories / keep an independent regression set before training, and check after training whether general capabilities and safety alignment have been forgotten); parameter learning works with external methods (copying special strings = the parameter model learns per-token fidelity + the tool interface does byte-level verification with rollback-capable failure diagnosis).
- **Maka design implications**: The first version of headless self-evolution does not need to implement the parameter carrier, but the design reserves a "parameter internalization" exit — the before/after feedback pairs accumulated by SelfCheck can be converted into preference training data, compatible with "verify first, train later".
- **Writable design doc**: "Maka Design: Reserved Interfaces and Data Specifications for the Parameterized Carrier"

### [KP-08-10] From updating artifacts to updating the "update method": five levels of optimization scale and the root of trust
- **One-sentence core**: Besides "where the experience is written", there is an orthogonal axis — the optimization object can be expanded layer by layer from artifact content to the methods that produce / manage / verify artifacts; these are not five new carriers but five search scales.
- **Key design points**: The optimization object expands layer by layer (**a single rule or memory → structured context → workflows → Harness code → the optimizer code that produces candidate solutions**); the innermost layer (only changing artifact content) has a small surface, is easy to attribute and roll back, and should be the default choice — but repeatedly rewriting the entire Prompt/memory degrades (important details disappear after many rounds of rewriting; mutually constraining conditions get merged into over-abstracted principles); ACE (Agentic Context Engineering: maintain the context as a collection of entries with stable identifiers, let generation/reflection/organization modules propose incremental updates, use deterministic logic for merging/dedup instead of rewriting every round); MCE (Meta Context Engineering: dual inner/outer loops — the inner loop optimizes the task-context artifact given a management method, the outer loop modifies the context operations themselves: "search / select / filter / format"); AFlow / Meta-Harness (represent workflows / the Harness as code graphs and search over combinations guided by execution feedback); **a higher optimization level is not always better** (failures clearly attributable to a single component should get auditable local patches first; only escalate for long-unresolved cross-component problems or when the management method itself becomes the bottleneck); **root of trust** (no matter which level you rise to, the evaluator, permission boundaries, and held-out tests must lie outside the modifiable scope — the larger the search space, the more important the root of trust); the Hermes experiment (autonomous read → cross-check → choose a topic → modify → verify; the first three rounds were rejected by independent review, each round's rejection was fed back as a learning signal, and the fourth round was accepted — **rejection is part of the closed loop, not the endpoint of failure**).
- **Maka design implications**: The "meta" direction of self-evolution follows "default to the innermost local patch, only escalate the scale with sufficient evidence"; SelfCheck / budget / audit logs must lie outside the modifiable scope (the root of trust must not be self-modifiable); ACE's "entry set with stable identifiers" can serve as the blueprint for evolving Maka's context management.
- **Writable design doc**: "Maka Design: Self-Evolution Optimization-Scale Layering and Root-of-Trust Boundaries"

## 3. Building a Long-Running Continuous Evolution Closed Loop

### [KP-08-11] The dual loop of online execution and offline evolution
- **One-sentence core**: Only when the four update methods enter the same autonomous loop do they become continuous evolution; production systems use the dual loop of "**online only executes + records evidence, offline aggregates + diagnoses + generates candidates + verifies and releases**", connected in the middle by a versioned experience library and evaluation sets.
- **Key design points**: The dual-loop structure (the online execution loop only completes tasks and records evidence, **without directly rewriting the formal Agent**; the offline evolution loop aggregates trajectories / diagnoses root causes / generates candidates / passes the verification threshold and releases new versions); Voyager's three mechanisms (automatic curriculum generator / skill library / iterative prompting mechanism — 3.3× unique items, 2.3× exploration distance, tech tree 15.3× faster); from problem location to experience sedimentation (the same surface problem can correspond to different modification approaches — fabricating facts = missing knowledge vs. the prompt not requiring citations; false promises = instruction correction vs. Harness-enforced checks — the evolution module first locates the root cause and then chooses the smallest / most easily verifiable / most easily rollback-able modification object; sporadic failures with insufficient evidence do not immediately trigger learning and continue to accumulate samples); the escalation path changes as experience accumulates (new strategies first become experience documents for retrieval → after repeated multi-case verification they are upgraded: rules describable in natural language → Skills, stable steps that need no understanding → tool code, widely reflected implicit decisions → post-training).
- **Maka design implications**: "Log is the Runtime + Task Event Log" is exactly the online side of the dual loop; headless makes explicit that "the online loop does not modify the formal Agent", and experience sedimentation lives in the offline / background loop; TaskRun's interruptibility and resumability provide the persistence foundation for offline aggregation and candidate verification.
- **Writable design doc**: "Maka Design: Online Execution–Offline Evolution Dual-Loop Architecture"

### [KP-08-12] Verification, release, and rollback: candidate zone, canary, Harness updating ≠ benefiting, and layered evaluation
- **One-sentence core**: All modifications first become candidates rather than overwriting production; after verification passes, release via canary and auto-rollback when key metrics worsen; evaluation must distinguish "the updater proposed a good modification" from "the task Agent truly benefited".
- **Key design points**: Verification differences across the four carriers (knowledge documents: verify whether retrieval improves performance on new tasks; Prompt/Skill: check boundary cases and old-task regressions; programs: run tests in sandbox and reset environments; parameters: check forgetting / safety / out-of-distribution); even after verification, still go through canary, and auto-rollback to the last known safe version when metrics worsen; **harness-updating capability ≠ harness-benefit capability** — a Skill written perfectly correctly may still show "no evolution" in final scores if a weak task model does not load it in the right scenarios or does not follow it once loaded, so you cannot reverse-infer the quality of the updater from end-to-end scores alone; **four layered-evaluation metrics** (candidate-modification effectiveness rate / artifact activation rate / adherence success rate / held-out-task gain); **bidirectional model swap to locate the bottleneck** (fix the candidate Harness and swap only the task model: a strong model benefits but a weak model never activates → the bottleneck is in retrieval/routing; both activate but only the strong model executes correctly → the bottleneck is in instruction adherence / long-horizon planning; all models degrade → suspect the modification itself); long-term evaluation should look at at least five kinds of outcomes (**regressions** / generalization / token efficiency / safety / long-term engineering quality).
- **Maka design implications**: Headless has a built-in "candidate zone → canary → formal" release state machine with auto-rollback; SelfCheck can only change behavior into candidates; self-evolution evaluation collects "candidate-modification effectiveness, activation rate, adherence success rate" at the same time (echoing the observability advantage of Log-is-the-Runtime).
- **Writable design doc**: "Maka Design: Candidate Release State Machine, Auto-Rollback, and Layered Evaluation Metrics"

### [KP-08-13] The boundary of the verifiable closed loop: when "completion" does not equal "progress"
- **One-sentence core**: The verifiable closed loop is most reliable on Coding / tool calling / business-state changes; in open-ended research, strategic planning, and complex product design, "a complete process ≠ advancing the real goal".
- **Key design points**: Automated research exposes three classes of problems (**implementation drift** — when the plan gets harder, gradually falling back to more familiar but hypothesis-diverging ordinary implementations from the training data; **epistemic over-optimism** — interpreting results as discoveries when the signal may just be noise, and ignoring negative results; **insufficient tacit judgment** — not knowing which baseline matters / which anomaly is worth tracking / when to abandon a hypothesis); four ways to change the evidence and supervision structure (**separate conclusions from evidence** (record the evidence sources for citations / numbers / methods / conclusions separately, and the final manuscript is only one presentation of the evidence graph); **retain negative results** (failed experiments / rejected candidates / reasons for stopping are written into immutable logs and are as retrievable as successes); **maintain search diversity** (keep temporarily low-scoring but non-homogeneous branches in the candidate pool to avoid converging on a single easy-to-score template); **let humans intervene at a higher level** (define problems / review evaluation criteria / explain anomalies / decide when to stop)); the core criterion: **the ceiling of continuous evolution depends on whether the system can evaluate the goals it truly cares about, not just the most easily measured proxy metrics**.
- **Maka design implications**: Directly echoes "Feedback is not fact authority" — separate "completion" from "progress" (SelfCheck passing / task completion are facts in the log; whether they constitute "progress" requires long-term metrics and human high-level judgment); self-evolution by default only covers the task families whose "results can be automatically verified", and open-ended tasks retain human intervention at the problem-definition and evaluation-criteria level.
- **Writable design doc**: "Maka Design: The Completion ≠ Progress Boundary and the Human-Intervention Protocol for Open Tasks"

### [KP-08-14] The safety boundary of continuous evolution: three isolations
- **One-sentence core**: Besides verifying "whether it is stronger", a self-evolving system must also constrain "who can modify what, and where the basis comes from"; erroneous experiences, injections, and poor verifiers can all turn a one-time mistake into a long-term risk.
- **Key design points**: Risk forms (a prompt injection, if summarized into experience, can take effect repeatedly across sessions; an automatically searched-for malicious package wrapped as a tool spreads from one sandbox to all tasks; a flawed verifier keeps approving candidates that look like progress but actually regress); **the first boundary — evidence/instruction isolation** (raw web pages / tool outputs and their LLM summaries are all untrusted evidence: they cannot be executed as instructions and cannot be directly incorporated into Skills as long-term capabilities; an LLM summary is a readability transformation, not a purification process; extract claims / original-text locations / collection timestamps in a fixed schema and retain the original sources; extracted strings must never be executed as instructions; model confidence is only an unverified estimate and cannot serve as an approval threshold; candidates pass deterministic schema / allow-list / source checks and are submitted as versioned PRs; a reviewer independent of the generator reviews against the original evidence, and high-risk Skills require human approval); **the second boundary — candidate-capability/formal-capability isolation** (new knowledge / Prompts / Skills / programs / parameters first enter a candidate zone that cannot serve real traffic; new code and external dependencies serve real traffic only after passing sandbox / permission checks / supply-chain scans / behavior tests); **the third boundary — safety mechanisms must not be self-modifiable** (business Agents may modify Prompts / Skills / the knowledge base / tools, but must not modify the verifiers / test cases / release thresholds / audit logs / stable-version backups that approve their own updates — otherwise merely lowering the test threshold or deleting failing cases would disguise regression as progress).
- **Maka design implications**: The three boundaries map into Maka as-is — in the Event Log, "untrusted evidence" (tool outputs / web pages / user input) and "approved instructions" are stored in separate libraries; the headless candidate directory is isolated from the formal directory; SelfCheck / verifiers / audit logs / budget configuration cannot be self-modified by the Agent — naturally consistent with the AHE target protocol and "Log is the Runtime" (the log is immutable).
- **Writable design doc**: "Maka Design: Self-Evolution Safety Boundaries (Three Isolations and the Root of Trust)"

### [KP-08-15] Sleep learning: consolidation, forgetting, and capability freshness
- **One-sentence core**: "Sleep learning" is a cognitive analogy for offline consolidation (it need not run at night) — the online Agent only completes the current task and appends immutable evidence, while background processes, under idle / gated conditions, batch-consolidate, merge, resolve conflicts, update candidates, and run regression.
- **Key design points**: The five-step cycle — ①**trigger** (time interval / new-trajectory count / storage capacity / error-frequency thresholds + no high-priority online tasks) ②**orientation** (read the formal knowledge / Prompt / Skill directories and versions to understand existing capabilities and the non-modifiable boundary) ③**collect and consolidate** (find new signals from recently evaluated trajectories / merge duplicates / mark conflicts and applicable conditions / prefer generating local patches) ④**verify and approve** (evaluate on the transfer set / retention set / safety set, high-risk items await human approval) ⑤**prune and index** (update the index; mark items unused for a long time or overturned by new evidence as expired / archived / deleted, keeping sources and rollback versions); the value of separating collection from organization (prevents sporadic successes / network failures / malicious input from immediately rewriting long-term capabilities; a larger batch with cheaper models can do the organizing); Claude Code automatic memory (a MEMORY.md index + detailed files split by topic; the session startup loads only a bounded prefix of the index and the rest on demand; when the index approaches its limit it asks to merge or move details out); Hermes background evolution (bounded MEMORY.md/USER.md + SQLite/FTS5 historical-session retrieval that returns raw messages rather than LLM summaries to avoid mixing retrieval and generation into an unauditable step + on-demand Skills; when tool calls are many / recovery from a wrong dead-end happens / a user correction is received / a non-obvious workflow is discovered, a background review creates or locally revises a Skill; an independent Curator tracks usage / staleness / archival, deterministically prunes during idle periods, and takes snapshots before changes for rollback).
- **Maka design implications**: The headless Task Event Log is the perfect input source for sleep learning — background "organization processes", when budget permits / idle, consolidate and prune TaskRun logs to produce experience documents / Skill candidates and pass approval; "Log is the Runtime" guarantees that organization does not rewrite the original evidence, and erroneous organization rolls back by snapshot.
- **Writable design doc**: "Maka Design: The Sleep-Learning Cycle (Trigger–Orient–Consolidate–Verify–Prune)"

## Golden Quotes of This Chapter / Core Conclusions
- "**Saving experiences is not the same as learning from experiences**" — learning happens after the system actively completes "evaluation, comparison, induction, verification", not at the moment the log is written to disk.
- "User memory lets the Agent **remember more**; only experiential learning makes it **go from clever to skilled**."
- "The starting point of continuous evolution is not 'summarization', but '**evaluation**'."
- "The lower the metric, the more it should rely on code and environmental ground truth; only what is hard to formalize is handed to the language model."
- "**Reflection itself is not evidence**; only content that matches environment results, is supported across trajectories, and shows positive transfer on new tasks should enter the formal experience documents."
- "The primary basis for choosing an update method is not how long the experience has existed, but **whether the target capability can be naturally expressed by some carrier**."
- "Turn 'self-modification' into an auditable software release process."
- "**Successful execution of an action and task success are two different things**"; "100% replay coverage does not mean the task is complete" — you must have pre-action verification, post-action verification, and independent verification before saving.
- "The complete lifecycle of continuous evolution is: feedback → first-error attribution → Skill or interface specification → synthetic data → parameter candidates → boundary-set and retention-set verification → canary release or rollback."
- "**Harness updating capability ≠ Harness benefiting capability**."
- "**All unit tests passing only proves that the current observable behavior satisfies the tests; it does not prove the codebase will still be easy to maintain months later.**"
- "The ceiling of continuous evolution ultimately depends on whether the system can evaluate the goals it truly cares about, not just the most easily measured proxy metrics."
- "An Agent only needs to lower the test threshold or delete failing cases to disguise regression as progress" — so safety mechanisms must not be self-modifiable.
- "Rejection is not the endpoint of failure, but part of the self-improvement closed loop" (Hermes experiment).

## Reflection Questions from the Book (transcribed key points)
1. An experience is supported by three successful trajectories and one failing trajectory, and the failure occurred on a newer API version — judge whether the experience has been overturned or whether the applicable conditions have changed?
2. User satisfaction rises but so does the rule-violation rate — why can't satisfaction be used as a single learning signal? How to design guardrail metrics?
3. The same "false-promise" problem can be mitigated through the Prompt, Harness checks, or parameter training — based on what evidence do you choose the modification location?
4. An Agent can modify tools and verifiers but must not modify the root of trust that approves its own updates — how to draw the permission and code boundaries between these two parts?
5. As the experiential knowledge base keeps growing, retrieval errors and knowledge conflicts cancel out the learning gains — how to design versioning, freshness, and retirement mechanisms?
6. Parameter learning is good at language style but cannot guarantee hard business rules — design a continuous-evolution scheme for a medical customer-service agent in which parameters / knowledge / Skills / code constraints work together.
