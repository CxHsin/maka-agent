# 引言 + 第 1 章 · Agent 基础知识 —— 知识点提取

> 来源：`book/introduction.md` + `book/chapter1.md`。本章是全书地基，建立 **Agent = Model + Harness** 与 **上下文 = 静态前缀 + 轨迹** 的统一概念框架。

## 引言（5 个知识点）

### [KP-00-01] 核心公式：Agent = LLM + 上下文 + 工具（三种映射）
- **一句话核心**：Agent 的最小工程公式只有一句——`Agent = LLM + 上下文 + 工具`，三者缺一不可；公式只在"Agent 边界之内"谈实现，不包含与之交互的环境。
- **关键设计要点**：
  - 实现层：LLM（决策内核，含预训练知识+后训练策略）+ 上下文（观察/记忆/领域知识/自身状态/任务进展）+ 工具（感知或改变外部世界的接口）。
  - 直觉层：大脑（LLM）+ 眼睛（上下文）+ 手脚（工具）；"眼睛"是粗略类比——上下文还包括工具定义。
  - RL 层：LLM↔Policy、上下文↔Observation Space、工具↔Action Space。
- **Maka 设计启示**：Maka 的 core/runtime 正是公式实现；"Log is the Runtime"把三个组件的交互统一落进 Event Log，使公式三组件都能从日志投影，而非散落 UI/会话私有状态。
- **可讨论问题**：Q1 Event Log 是否完整覆盖公式三组件（缺哪块日志，恢复就缺哪块证据）？Q2 "上下文是环境在 Agent 内部的表示，不是环境本身"对 Session/Context 建模的约束？
- **可写设计文档**：《Maka 核心公式：LLM + 上下文 + 工具 与 Runtime Event Log 的组件映射》

### [KP-00-02] 实践在前，命名在后
- **一句话核心**：不是 Anthropic 发明 Skill/harness/loop engineering 概念、Agent 才跟着用；是大量 Agent 早就在做，业界才总结命名。
- **关键设计要点**：
  - 作者在 Pine AI 的实践：Skill 流行前已用动态加载提示词、命令行执行工具、系统状态栏；harness 流行前已用类似 Claude Code 的方法解决工具调用不稳定/幻觉/危险操作/越权/指令不遵循；loop engineering 流行前已用**提议者-审核者（proposer-reviewer）**解决"模型过早认为任务完成"。
  - 赶在名词之前知道怎么做靠两点：**(1) 对能力上限要求极高的真实业务**；(2) **建立评估机制**。
- **Maka 设计启示**：设计文档里的架构决策应由真实失败模式/需求推导，而不是追新名词。Maka 的 self-check/eval 就是把"先有实践、再有名词"工程化。
- **可讨论问题**：Q1 Maka 是否记录并回放"导致出错的真实案例"驱动设计？Q2 "模型过早认为任务完成"在 Maka 对应什么？
- **可写设计文档**：《Maka 设计决策的实证来源：真实失败模式 → 架构原则的推导链》

### [KP-00-03] 评估是科学方法论的地基
- **一句话核心**：没有评估就没有进步；评估让你分辨一次改动是"真的变好"还是"只是运气"。
- **Maka 设计启示**：凡是改动 Event Log schema、上下文剪枝策略、self-check 逻辑，都应先跑回归评估再合入；Log 也是评估数据源——真实轨迹可直接作为评估集。
- **可讨论问题**：Q1 Maka 的 eval 集是否覆盖"日志驱动的恢复正确性"这类 Maka 特有能力？Q2 剪枝改动"真变好 vs 运气"需要怎样统计口径？
- **可写设计文档**：《Maka 评估方法论：以 Event Log 为数据源的回归评估闭环》

### [KP-00-04] 好的设计原则穿越模型迭代周期
- **一句话核心**：不管底层模型如何升级，成功的 Agent 系统遵循相同架构模式——原则描述的是智能系统与世界交互的基本模式，而非某个模型的用法。
- **关键设计要点**：模型半年一代（GPT-5.2→5.5、Opus 4.5→4.8）；Agentic RL 把工具调用训进参数；"代码生成+文件系统"成主流范式；Sutton 视角：Agent 能通过生成代码自举与自我进化。
- **Maka 设计启示**：直接支撑"Log is the Runtime"与"Context is not history"——它们描述与模型无关的交互/记录模式。设计文档应把原则与具体模型能力解耦。
- **可讨论问题**：Q1 四条信条哪条会随模型能力被"吃掉"？哪条是交互模式永不过时？Q2 模型原生内置长链稳定调用时，Headless 预算/恢复如何演进？
- **可写设计文档**：《Maka 架构原则的模型无关性论证》

### [KP-00-05] 术语约定：思考 vs 推理
- **一句话核心**：reasoning 译为"思考"（中间推导），inference 译为"推理"（前向计算与部署），避免一词双义。
- **Maka 设计启示**：Event Log 若记录 reasoning 字段，语义应是"思考过程"（可解释性/连贯性证据），避免日志 schema 歧义。
- **可写设计文档**：《Maka 消息模型术语与 reasoning 字段语义规范》

## 第 1 章（10 个知识点）

### [KP-01-01] 现代 Agent = LLM + 上下文 + 工具（边界与 Model–Harness 结构）
- **一句话核心**：公式只描述 Agent 边界内的实现；Model 负责策略决策，Harness 是 Agent 边界内环绕模型的运行与治理层（构造上下文、暴露工具、维护循环状态、实施权限/验证/纠正）。
- **关键设计要点**：Harness 可以创建/隔离/代理一个环境，却不包含环境自身状态与转移规律；"上下文只是环境在 Agent 内部的表示，不是环境本身"。
- **Maka 设计启示**：packages/core（会话/事件/权限/连接）与 runtime（AgentRun/上下文/恢复）的分界对应"Agent 边界"；外部环境必须作为 connections 显式建模，不能误当成 Agent 内部状态；Event Log 只记边界内事件，边界外变化经工具结果事件间接呈现。
- **可写设计文档**：《Maka 的 Agent/Environment 边界与连接（Connections）建模》

### [KP-01-02] 观察空间与动作空间：模型与世界的接口
- **一句话核心**：模型固定时，提升 Agent 表现最主要的系统工程手段是重新定义/扩展观察空间与动作空间（即扩展上下文和工具）。
- **关键设计要点**：没有通过观察通道进入上下文的信息，对模型就像不存在；没有被动作接口允许的操作，模型只能停留在文字建议上。Manus = 三路线观察/动作空间并集；OpenClaw = 本地 Gateway + 用户数字生活接入。
- **Maka 设计启示**：扩展观察空间不只是堆历史消息，而是系统性地把任务所需数据纳入上下文、把所需操作封装成工具；connections 机制就是观察/动作空间的扩展点。
- **可写设计文档**：《Maka 观察空间与动作空间：接口扩展能力模型》

### [KP-01-03] 工具：五类工具 + 工具调用四步流程 + 通用 vs 专用
- **一句话核心**：工具设计核心原则是"通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作"。
- **关键设计要点**：五类（感知/执行/协作/事件触发/用户沟通）；四步流程（声明→模型决策→执行→结果追加）；工具调用=ReAct 基础；代码沙盒需限时/限 CPU/限内存/限输出；长程任务用受控虚拟工作目录；高风险操作封装为参数明确、权限受限、全程可审计的专用工具。
- **Maka 设计启示**：五类工具是分类学基础（尤其事件触发对应 TaskRun 触发方式）；虚拟工作目录思想对应 Maka 沙盒/工作区的路径与容量限定。
- **可写设计文档**：《Maka 工具分类学与沙盒安全基线》

### [KP-01-04] LLM：Agent 的大脑与内部思考
- **一句话核心**：LLM 独特能力是"内部思考"——行动前先规划推演，不改变外部环境却显著提升行动质量。
- **Maka 设计启示**：reasoning 作为独立消息成分保留进 Event Log（消融证明剥离会导致前后决策矛盾）；需定义思考在日志/UI/剪枝三处的处理策略。
- **可写设计文档**：《Maka 的 reasoning 消息处理与剪枝策略》

### [KP-01-05] 上下文：五个组件 + 静态前缀/动态轨迹 + 消融实验结论
- **一句话核心**：上下文由静态前缀（系统提示词+工具定义）与动态轨迹（用户消息+模型回复+工具结果）构成；消融实验证明去掉任一组件都显著退化。
- **关键设计要点**：消融结论——去掉工具定义→丧失行动能力；缺工具结果→反复调同一工具陷入无限循环；剥离思考→决策矛盾；缺历史→失忆重做。模型回复最多含三部分（reasoning/content/tool_calls）。
- **Maka 设计启示**：上下文五组件都是 Event Log 的投影（静态前缀是配置型事件，动态轨迹是消息事件）；任何剪枝必须保留"工具结果反馈与最近 reasoning"这类闭环关键成分。
- **可写设计文档**：《Maka 上下文投影：五组件 ↔ Event Log 映射与剪枝边界》

### [KP-01-06] 模型即 Agent：RL 内化的是决策策略，不是工具执行
- **一句话核心**：RL 内化"何时调、调哪个、传什么参数"的决策策略；工具本身及执行仍在模型外的基础设施；编排循环没消失，只是从客户端移到服务端、决策权交给模型。
- **关键设计要点**：苦涩的教训——方向认同、节奏务实：模型会持续吃掉 Harness，但这个"吃"远比直觉慢；模型此刻的能力边界就是 Harness 此刻的价值。Kimi K3（2.8 万亿 MoE、100 万 token、长链工具调用稳定 200-300 次）；GPT-5.6 Freeform Tool Calling。
- **Maka 设计启示**：即使模型不断内化能力，Harness 职责（上下文管理/工具接口/权限/验证/恢复）不减反增；"模型每内化一层，Harness 卸下一层、转兜新前沿"。
- **可写设计文档**：《Maka 与"模型即 Agent"：决策权交接与 Harness 职责再分配》

### [KP-01-07] 学习机制：三种时间尺度
- **一句话核心**：上下文适应（任务内、临时）+ 外部产物更新（知识文档/Prompt/Skill/程序，跨任务、可审计）+ 参数更新（高维能力、部署成本高）。
- **Maka 设计启示**："Context is not history"在这个框架下更清晰：上下文适应改变"下一次推理看到什么"；artifact 更新应作为可审计产物由 Maka 管理（版本化、可回滚）。
- **可写设计文档**：《Maka 三时间尺度学习：上下文适应、artifact 更新与日志驱动进化》

### [KP-01-08] ReAct 循环：思考→行动→观察，轨迹与循环不变量
- **一句话核心**：ReAct 是把 LLM、上下文、工具串联的核心机制；Agent 的上下文 = 静态前缀 + 轨迹；必须设计明确停止条件（任务完成/最大迭代/不可恢复错误）。
- **关键设计要点**：多币种汇总示例 3 迭代 4 工具调用；可解释可调试；思考题提示：累计缓存读取量随轮数近似二次方增长。
- **Maka 设计启示**：Event Log 就是"轨迹"的持久化形态；TaskRun 需把 max_iterations/无工具调用/错误/任务完成作为一等终止条件，并把"循环不变量检测"（重复同一工具/陷入循环）纳入运行时监控。
- **可写设计文档**：《Maka ReAct 循环与 Event Log 的轨迹投影模型》

### [KP-01-09] Harness 工程：Agent = Model + Harness（五要素）
- **一句话核心**：生产形态下 `Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正`；生产级 Agent 的重心转向"不做错事"（约束/验证/纠正），Claude Code 的 Harness 绝大部分代码都在做保障机制。
- **关键设计要点**：五要素核心原则——上下文=信息充分性；工具=接口清晰；约束=故障安全默认值（默认拒绝、显式开放）；验证=输入隔离（只看结构化数据、不看模型自由文本，防提示注入）；纠正=确认无法恢复前不暴露中间态。Claude Code 保障机制：流程状态管理、多层压缩、权限分类、熔断器、错误恢复。
- **Maka 设计启示**：五要素直接映射 Maka 各包——runtime=上下文+工具、core 权限=约束、headless Self-check/eval=验证、runtime 恢复=纠正；"Feedback is not fact authority"正是 Verify 层的原则化表述。设计文档应把五要素写成各包验收清单。
- **可写设计文档**：《Maka Harness 五要素与包结构映射（含约束/验证/纠正的日志事件设计）》

### [KP-01-10] 范式演进：提示工程 → 上下文工程 → Harness 工程 → Loop 工程 → Graph 工程
- **一句话核心**：模型能力趋同时，竞争优势转移到模型之外的工程实践；五个阶段层层包含。
- **关键设计要点**：LangChain 在 Terminal Bench 2.0 上从 52.8%→66.5%，改变的不是模型而是 Harness；Graph 工程（2026）把循环/程序/人工审批组织成显式执行图，节点=能力、类型化边=路由、状态在关键边界持久化。
- **Maka 设计启示**：四信条几乎是 Loop 工程+Harness 工程合成；Task Event Log 即"关键边界处持久化"。
- **可写设计文档**：《Maka 的范式定位：从 Harness 工程到 Loop 工程再到可检查点持久化》

### [KP-01-11~13] Harness 核心原则 / 构建有效 Agent 原则 / 如何选择模型
- **KP-01-11 五要素原则**：见 KP-01-09；→《Maka 五要素核心原则与实现验收清单》
- **KP-01-12 简单/透明/ACI 防呆**：保持简单（每层抽象都是调试盲区）；保持透明（展示规划步骤/执行日志/决策轨迹，信任的前提）；ACI 从 Agent 视角设计接口、防呆（Poka-yoke），"模糊接口会被模型放大成系统性错误"。→《Maka 核心原则：简单、透明（日志投影 UI）与 ACI 工具接口规范》
- **KP-01-13 模型选择**：不只看排行榜要在自己任务上评估（第六章）；策略边界（能力≠产品允许调用）；绝大多数 Agent 需支持思考的模型；输出速度直接决定端到端延迟（20 轮×每轮慢 2 秒=多等 40 秒）；多模态是硬性要求时差异大。→《Maka 模型选型与多提供商适配（含策略边界与速率预算）》

### [KP-01-14] 编排模式：工作流 vs 自主 Agent vs 混合
- **一句话核心**：先单次调用→再工作流→最后才自主 Agent（延迟/成本换性能，谨慎权衡）；自主 Agent 必须设计明确停止条件。
- **关键设计要点**：工作流=预定义代码路径（严格流程控制+攻击面限制在单节点内，但缺乏变通）；自主 Agent=ReAct 循环（动态决策、风险更高）；混合（n8n 式）。"从简单到复杂"顺序降低意外风险。
- **Maka 设计启示**：TaskRun 即自主 Agent 实现，必须内置停止条件与预算；workflow 可作为确定性编排层与自主混合。
- **可写设计文档**：《Maka 编排模式：TaskRun 自主循环、Workflow 确定性流程与混合》

### [KP-01-15] 护栏与安全性：分层防御、护栏类型、人工干预
- **一句话核心**：护栏构成分层防线（输入/执行/输出侧），单个护栏不足、多个组合才有韧性；同时要防**误拒绝**；人工干预让 Agent 优雅移交控制权。
- **关键设计要点**：输入侧（相关性/安全分类器、内容审核、基于规则保护——越狱 vs 提示注入区别）；执行侧（工具风险评级：可逆性/权限/财务影响，高风险需额外审查或人工确认）；输出侧（PII 过滤器、输出验证）；Anthropic Constitutional Classifiers（规则驱动+上下文联合判断+两级筛查）；人工干预两触发（超失败阈值、高风险操作）。安全是架构问题，从第一行代码考虑。
- **Maka 设计启示**：支撑"Feedback is not fact authority"与 Self-check；headless 需要"失败阈值→人工升级"与"高风险操作→人工监督"；护栏评估既要测"该拒的拒了"也要测"该放的放了"（误拒绝）。
- **可写设计文档**：《Maka 护栏分层与人工干预设计（含自我检查证据与有界修复）》

## 本章金句 / 核心结论
- Agent = 大脑 + 眼睛 + 手脚；扩展眼睛和手脚是最主要的能力杠杆。
- 没有通过观察通道进入上下文的信息，对模型就像不存在；没有被动作接口允许的操作，模型只能停留在文字建议上。
- Harness 是竞争力所在；行业正从"能做事"向"可靠地做事"转变。
- 从工作流到自主 Agent（先提示词、再工作流、最后自主）；安全是架构问题。
- 实践在前、命名在后；没有评估就没有进步；好的设计原则穿越模型迭代周期。
- 方向认同、节奏务实：模型会持续吃掉 Harness，但"吃"远比直觉慢；模型此刻的能力边界就是 Harness 此刻的价值。
